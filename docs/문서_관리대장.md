### 기준 충돌 시 읽는 순서

1. **현재 상태**는 `현재 구현 상태`와 가장 최신의 범위가 맞는 실행 증거를 함께 읽는다. 실행 증거는 당시 결과이고 현재 자원이 남아 있다는 뜻이 아니다.
2. **현재 설계·계약**은 최상위 설계와 주제별 하위 기준 문서를 읽는다. 계획만으로 구현 완료를 판정하지 않는다.
3. **코드 사용 여부**는 기준 브랜치 `ikonly`의 실행·배포 참조와 코드 영역 분류를 확인한다. `checkpoint` 등 과거 브랜치는 현재 기준으로 삼지 않는다.
4. **과거·비활성 자료**는 삭제 대신 상태와 대체 문서를 표시해 보존한다. 최신 상태와 다른 문장은 당시 기록으로 읽는다.

## 점검 결과와 알려진 예외

- `docs/`에서 Markdown 118개를 확인했다. 비어 있는 Markdown 파일은 없다.
- 상대 경로 내부 Markdown 링크 1,038개를 검사했고 깨진 파일 경로는 발견하지 못했다. 외부 사이트의 접근 가능성이나 문서 내 앵커 존재 여부는 이 검사에 포함하지 않았다.
- 이미지 링크 6개 중 1개가 `docs/ik/pre/이벤트_기획안.md`의 원본 스냅샷에서 참조되지만 파일은 저장소에 없다. 원본 보존 원칙에 따라 스냅샷을 수정하지 않았으며, 같은 참조를 포함하던 팀 문서에는 누락 안내를 기록했다.
- 루트 과목 가이드와 IK `pre/` 스냅샷은 SHA-256이 동일하다. 복사본은 경로별 문서 경계를 보존하는 용도이므로 합치거나 삭제하지 않는다.
- 2026-10-09 정적 분석은 이후 변경으로 최신성이 달라졌다. `infra/compose.yml`은 현재 로컬 PostgreSQL 전용 구성이며, `infra/compose.release.yml`만 0 byte다. 과거의 “두 파일 모두 비어 있음”은 당시 기준으로만 읽도록 사후 상태 안내를 추가했다.
- `infra/compose.release.yml`을 배포 절차로 인용하던 Frontend·Backend 팀 문서에 과거 기준선 안내를 추가했다. 현재 CI/CD 작업을 추적할 때는 [현행 구현 상태](ik/현재_구현상태.md)의 최신 항목과 [CI/CD 검증 기록](ik/검증산출물/2026-10-13_현행코드_CICD_마무리.md)을 사용한다. 과거 절차 본문은 기록 보존을 위해 유지한다.
- `feature/checkpoint`와 `checkpoint`를 기준으로 한 2026-10-09 분석은 출처가 되는 과거 스냅샷으로 분류했다. 현재 작업·통합 브랜치로 관리하지 않으며, Compose·CI/CD의 과거 판정에는 기록 시점을 표시하고 현재 판단은 `ikonly` 문서·검증 자료로 연결했다.
- 초기 공통 문서의 내용은 이 대장만으로 최신성·대체 여부를 전부 확정하지 않는다. 해당 문서는 당시 이력으로 분류하고, 필요 시 주제별 IK 기준 문서와 연결을 추가한다.

## 갱신 규칙

1. 동작·설정·실행 절차를 바꾸면 해당 현행 기준 문서와 관련 검증 증거를 함께 갱신한다.
2. 실행 증거에는 실행일, 코드 식별자, 환경, 범위·모집단, 제외·제한을 적고 설계 계획과 구분한다.
3. 팀 작업 기록은 당시 맥락을 보존한다. 완료된 작업의 기준 상태는 현행 문서에 반영한 뒤 팀 기록은 이력으로 둔다.
4. 중복 문서·깨진 링크·사용 불명 파일은 먼저 담당·참조·보존 이유를 확인한다. 삭제·이동·병합은 영향이 확인된 뒤 수행한다.
5. 상태를 변경할 때는 이 표의 분류와 관련 색인도 함께 갱신한다. 미사용 코드 기준은 [코드 영역 분류](코드영역_분류.md)를 따른다.
