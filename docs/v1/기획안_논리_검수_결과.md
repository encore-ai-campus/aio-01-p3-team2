## RV-01. 동기식 Workflow와 MCP 장애 후 같은 작업 재개 방식이 충돌함

**근거**

- 시스템 기획안은 MVP가 Queue/Worker 없는 동기식 실행이라고 정의함 (`게임 라이브 이벤트 기획·검수 AutoHealing 시스템 기획안.md`, 1594행, 1612행).
- 같은 문서는 MCP 서버 중단 시 Retry 가능 상태를 유지하고, 운영자가 서버를 재시작한 뒤 다음 Retry에서 동일 Workflow를 재개한다고 정의함 (1242~1248행, 1823행).
- 개발 기획안도 Queue/Worker 기반 백그라운드 재개를 MVP에서 제외한다고 명시함 (`개발 기획안.md`, 2235행, 2255행).
- 그러나 개발 기획안의 TC-08은 운영자 재시작 후 다음 Retry가 실행되어 Workflow가 재개된다고 요구함 (2591행, 2756~2775행).

**문제**

동기식 요청 처리 중 서버 장애가 발생했을 때 Workflow가 어디에 멈춰 대기하는지, HTTP 요청이 계속 열려 있는지, 운영자 복구 후 무엇이 다음 Retry를 실행하는지 정의되어 있지 않음. 최대 재시도 횟수에 도달하면 Safe Stop/FAILED 처리한다는 정책과도 어떤 순서로 적용되는지 불명확함.

**영향**

TC-08을 현재 MVP 아키텍처만으로 구현하거나 재현하기 어려움. 장애 감지·재시도와 운영자 복구 후 이어하기의 성공 기준도 모호해짐.

**정리 필요 사항**

아래 두 방향 중 하나를 선택하고 관련 시나리오·API·상태 전이·테스트를 함께 맞출 것.

1. **동기식 MVP 유지:** MCP 장애 시 정해진 Retry 안에서 자동 복구되지 않으면 해당 Workflow를 `FAILED`로 종료. MCP 복구 후에는 새 Workflow로 재시도하며, 이를 “같은 Workflow 재개”로 표현하지 않음.
2. **같은 Workflow 재개 지원:** 대기 상태와 재개 트리거를 정의하고, 작업 상태 저장·재개 API 또는 Queue/Worker를 설계 범위에 포함. 이 경우 MVP의 Queue/Worker 제외 조건도 수정.

## RV-02. MVP에서 “보상 검수”가 어디까지인지 표현이 모호함

**근거**

- 시스템 기획안의 개요는 Agent들이 “미션·보상·게임 규칙을 검수”한다고 설명함 (11행).
- 같은 문서에서는 MVP가 실제 게임 데이터의 아이템 사용을 전제로 하고, 이벤트 재화 검증은 이후 확장이라고 설명함 (371행).
- Balance & Rule의 MVP 검증 범위는 레벨·기간·아이템·Mission Day 정합성으로 한정하고, 보상량·이벤트 재화 검증은 이후 확장으로 분류함 (398~408행).
- 개발 기획안은 보상량·이벤트 재화·상점 가격 검증과 관련 Error Type을 MVP에서 제외한다고 명시함 (`개발 기획안.md`, 868행, 1176행).

**문제**

개요만 읽으면 MVP에서 보상 밸런스까지 검수하는 것으로 오해할 수 있음. 실제 MVP 범위는 보상 아이템 ID의 존재 여부 확인에 가까우며, 수량·경제 밸런스·상점 가격 검증은 제외됨.

**영향**

요구사항·시연·테스트 기대치가 구현 범위보다 커질 수 있음. 특히 보상 검증 결과를 보여주는 시연에서 실제로 무엇을 보장하는지 불분명해짐.

**정리 필요 사항**

다음 중 MVP의 의도를 선택해 개요, Agent 역할, 검증 범위, 오류 사례, 테스트 케이스에 일관되게 반영할 것.

- MVP에서 아이템 ID 유효성만 확인한다면, 개요의 표현을 “보상 아이템 유효성 검수”처럼 구체화하고 수량·경제 밸런스 검증은 확장 범위라고 명시.
- 보상 수량·재화·가격까지 검수하는 것이 목표라면 필요한 게임 데이터, 계산 규칙, Error Type, 테스트를 MVP에 추가.

## RV-03. 가상 게임 규칙 데이터가 재현 가능한 검증 기준으로 부족함

**근거**

- 시스템 기획안은 Tiny Heroes를 모바일 판타지 RPG로 설정하고, 콘텐츠별 입장 레벨, 세 개 아이템 ID, 신규·복귀 유저의 날짜별 예상 레벨 일부를 제시함 (가상 게임 설정 절).
- 개발 기획안은 신규·복귀 유저의 기준점 사이 날짜에 직전 기준점 레벨을 적용하고 Day 7 이후에는 Day 7 값을 유지하는 계산 규칙을 정의함 (`개발 기획안.md`, 2008행).
- MVP의 Python Rule Engine은 유저 레벨, 콘텐츠 요구 레벨, 아이템 존재, Mission Day와 duration 범위를 판정함 (`개발 기획안.md`, 1960행 이후).

**문제**

일부 레벨 보간 규칙은 정의되어 있으나, 검증에 필요한 게임 데이터가 콘텐츠 ID와 게임 내 동작을 충분히 연결하지는 않음. 예를 들어 `content_id`별 허용 미션 유형, 콘텐츠 입장·선행 조건, 시도 한도와 행동 완료 조건은 명세되어 있지 않음. `new_user`·`returning_user`·`all_user`는 시스템 입력으로 구분하지만, 실제 유저 자격을 판정하는 가입·복귀 기준은 정의되어 있지 않음.

**영향**

현재 규칙으로는 일부 필드와 레벨 조건을 결정적으로 검사할 수 있지만, 미션이 게임에서 가능한 행동인지, `target_count`가 유저의 일일 한도 안에 있는지 등 더 넓은 달성 가능성은 판정하기 어려움. 다만 MVP가 이런 검증을 의도적으로 제외한다면 범위를 명시하는 것으로 해결 가능함.

**정리 필요 사항**

- 검증 대상 콘텐츠마다 ID, 필요 레벨, 해금 조건을 정의.
- 지원 미션 유형과 각 유형이 어떤 게임 기록·행동으로 완료되는지 정의.
- `target_count`의 단위, 일일/이벤트 전체 제한, 초기화 기준을 정의하거나 MVP 검증 대상에서 제외한다고 명시.
- 유저 그룹은 입력으로 선택만 받는지, 자격 조건까지 검증하는지 구분.
- 테스트용 규칙 데이터와 fallback snapshot의 버전·동일성 기준 유지.

## RV-04. 자연어 요청과 이벤트 기획안 명세 사이에 검증 공백이 있음

**근거**

- 사용자 입력은 `event_name`, `target_user`, `duration`, 자유 서술형 `objective`로 구성되고, 목적은 빈 문자열이 아닌지만 확인함 (`개발 기획안.md`, 1264~1274행, 2176~2182행).
- `EventPlanResult`는 `target_user`, `duration`, `missions`, `rewards`와 Mission(`day`, `content_id`, `mission_type`, `target_count`), Reward(`day`, `item_id`, `quantity`)를 구조화함 (`개발 기획안.md`, 840~880행).
- MVP의 결정적 검증은 레벨·아이템 존재·`1 <= mission.day <= duration`에 한정됨 (`개발 기획안.md`, 1960행 이후). Output Validation도 필수 필드와 형식 검사를 중심으로 설명함 (`개발 기획안.md`, 1291행 이후).

**문제**

입력이 자연어라는 점 자체는 문제가 아님. 현재 흐름은 자연어 입력을 구조화된 `EventPlanResult`로 바꾼 뒤 검증하므로 필드 형식과 일부 사실 조건은 검사할 수 있음. 그러나 입력의 `objective`는 자유 서술이고 성공 기준으로 변환되지 않으며, 출력 명세에는 `event_name`·목표와의 연결, 참여·완료 규칙, 적용 기간의 실제 날짜 또는 기간 산정 방식 등이 포함되지 않음. `mission_type`의 허용값과 의미, 날짜·대상 중복, 정수 범위·개수 제약 같은 필드별 제약도 충분히 고정되어 있지 않음.

따라서 현재 명세로는 “정해진 모양의 결과인지”, 일부 콘텐츠 레벨·아이템·날짜 조건은 검증할 수 있지만, “요청 목적을 달성하는 기획인지”, “미션과 보상이 이벤트 운영 규칙에 맞는지”를 완전하고 일관되게 검증하기 어려움. 이 부분을 Critic의 자연어 품질 판단에만 맡기면 판정 기준이 재현되지 않음.

**영향**

같은 자연어 요청에 대해 Planner가 서로 다른 구성의 기획안을 만들어도 무엇이 요구사항 위반인지 판정할 기준이 약함. Critic의 PASS/RETRY가 구조화된 수용 기준이 아니라 주관적인 품질 판단이 될 수 있고, 수정 후 문제가 해결됐는지 재검증하기 어렵게 됨.

**정리 필요 사항**

자연어는 사용자 편의를 위한 입력으로 유지하되, 실행 전 **정규화된 Event Brief**와 **고정된 EventPlanResult 스키마**를 두고 검증 계층을 분리할 것.

- Event Brief: 이벤트명, 목적, 대상, 기간, 필수/금지 조건, 성공 기준을 구조화하고 모호하거나 누락된 요구사항은 사용자에게 확인하거나 명시적 기본값을 적용.
- EventPlanResult: 이벤트 개요, 일정, 대상·참여 조건, 날짜별 미션, 보상, 완료·지급 규칙 등 MVP가 실제로 보장할 범위를 필드로 정의.
- 각 필드의 타입·허용값·수치 범위·중복 여부·필수 조건을 Pydantic/JSON Schema로 고정.
- 목적 적합성과 기획 품질은 측정 가능한 체크리스트로 바꾸고, Critic이 어떤 근거로 PASS/RETRY/FAIL하는지 명시.
- Python Rule Engine은 콘텐츠·기간·대상·아이템 등 정답이 명확한 사실을 검증하고, 스키마 검증과 Critic의 품질 검토는 각각 별도 결과로 기록.
- MVP에서 검증하지 않는 항목은 “검증 완료”로 보이지 않도록 결과 화면과 응답에서 검증 범위를 표시.

## RV-05. 구현 재현에 필요한 기술 스택 세부 선택이 미정

**현재 정해진 항목**

- Python 기반 Backend·Orchestrator·Rule Engine, FastAPI, Pydantic
- Streamlit UI, PostgreSQL 데이터베이스
- OpenAI Provider를 사용하는 LLM Agent, MCP Server와 Pytest
- Docker·Docker Compose, GitHub Actions, Docker Hub, AWS EC2

**미정 또는 구체성이 부족한 항목**

- Python 및 주요 라이브러리 버전과 의존성 잠금 방식
- OpenAI 모델명, API 방식/SDK 버전, Agent 호출·구조화 출력 구현 방식
- MCP Server의 구현 언어·공식 SDK·버전
- PostgreSQL 드라이버, ORM/쿼리 방식, 스키마 마이그레이션 도구
- 동기 API와 외부 호출을 위한 HTTP 클라이언트, 재시도·타임아웃 라이브러리
- 테스트·통합 테스트 도구의 구체적 구성 및 최소 실행 버전

**문제와 영향**

문서에는 상위 수준의 기술 선택은 있지만, 같은 설계를 각 담당자가 동일한 환경으로 구현하고 빌드할 수 있도록 기술 버전과 라이브러리가 고정되어 있지 않음. 특히 LLM Agent와 MCP의 구체적인 SDK/API 선택은 구현 구조, 장애 처리, 테스트 방식에 영향을 줌.

**정리 필요 사항**

저장소 생성 전에 언어 런타임과 주요 의존성을 결정하고 `requirements.txt` 또는 잠금 파일에 버전을 고정할 것. Agent/MCP 호출 방식, DB 접근·마이그레이션, API 타임아웃·재시도 라이브러리를 정해 서비스별 의존성 파일과 Docker 이미지 기준으로 문서화할 것. 선택 확장 기술은 MVP 스택과 분리해 표시할 것.

## RV-06. DB 논리 스키마는 있으나 물리 스키마·무결성 계약이 미정

**현재 정의된 수준**

`workflow_runs`, `traces`, `idempotency_records`, `test_runs`의 테이블 후보와 주요 컬럼이 나열되어 있고, 멱등성 Key의 UNIQUE 제약과 Docker 재시작 후 상태 보존 목표도 정의되어 있음 (`개발 기획안.md`, 2034~2152행).

**미정 또는 구체성이 부족한 항목**

- 각 컬럼의 SQL 타입, NULL 허용 여부, 기본값 및 구체적 PK/FK 관계
- `task_id`, `trace_id`, `test_id` 등의 생성·유일성 제약과 주요 조회 인덱스
- 상태 문자열의 허용값을 DB와 Pydantic 중 어디에서 강제할지
- 현재 결과·최종 결과 JSON의 저장 방식과 Schema 버전 관리
- Workflow 상태 변경, 승인, 멱등성 레코드 기록을 원자적으로 처리하는 트랜잭션 경계
- 동일 요청의 동시 도착 시 UNIQUE 충돌을 기존 결과 반환으로 변환하는 처리 규칙
- Trace/Test 데이터의 보존 기간, 삭제·마스킹 정책

**정리 필요 사항**

ERD와 SQL DDL 또는 동등한 마이그레이션 명세를 작성하고, FK·UNIQUE·CHECK·인덱스, 트랜잭션 및 동시성 처리, JSON Schema 버전, 데이터 보존 정책을 확정할 것. 특히 승인 상태 변경과 멱등성 기록이 중간 실패 시 부분 반영되지 않도록 원자성을 명시할 것.

## RV-07. API 흐름은 있으나 엔드포인트별 완전한 요청·응답 계약이 미정

**현재 정의된 수준**

일반 이벤트 생성, Test Mode 생성, 작업 상태·Trace 조회, 승인 처리, Health Check의 주요 경로와 일부 요청 예시·입력 제한·승인 상태 전이가 정의되어 있음 (`개발 기획안.md`, 2156~2375행).

**미정 또는 구체성이 부족한 항목**

- 엔드포인트별 완전한 JSON Request/Response Schema와 필드별 필수 여부·타입·범위
- HTTP 성공·오류 상태 코드와 공통 Error Response 형식
- 각 API의 정상·실패 응답 예시 및 `current_result`/`final_result` 상세 구조
- `GET /api/tasks/{task_id}/trace`의 정렬·페이지네이션·필터와 응답 크기 제한
- 동기 Workflow 중 타임아웃·클라이언트 연결 종료·부분 실패 시 반환 및 상태 조회 규칙
- 멱등성 Key 충돌·동시 요청·같은 Key에 다른 Payload가 들어온 경우의 처리
- Demo 권한을 API 호출에서 식별하는 방식과 Test API의 접근 통제 경계
- `GET /health/ready`가 DB/MCP 장애를 어떤 형식과 상태 코드로 표현하는지

**영향**

Frontend와 Backend 담당자가 각자 해석해 구현할 수 있어 요청 필드, 오류 표시, 재조회·중복 요청 처리가 달라질 수 있음. 현재 문서는 API 동작 개요로는 유용하지만 OpenAPI 명세 수준의 상호운용 계약은 아님.

**정리 필요 사항**

OpenAPI 문서 또는 동등한 계약 파일을 작성해 각 엔드포인트의 요청·응답·오류 스키마, 상태 코드, 멱등성 및 타임아웃 동작을 고정하고, Backend 자동 계약 테스트와 Frontend 연동 기준으로 사용할 것.

## RV-08. 기본 복구 성공 기준은 있으나 Recovery Contract 세부 조건이 부족함

이 항목을 복구 설계의 상위 계약으로 둡니다. RV-03의 게임 규칙·Fallback 데이터 조건과 RV-06의 DB 무결성·원자성 조건은 이 계약을 만족시키는 세부 설계와 연결됩니다. RV-01의 동기식 실행/수동 복구 충돌은 재개 메커니즘의 별도 아키텍처 결정입니다.

**현재 정의된 내용**

문서에는 기획 오류 수정 후 전체 재검증, Agent/Tool 오류의 재시도, Primary Tool 실패 시 Fallback, 최대 재시도 초과 시 Safe Stop 등 오류별 경로가 있음. 특히 개발 기획안 14절에는 복구 성공을 (1) 실패 단계 재호출/재연결 성공, (2) 결과 Validation 통과, (3) 다음 Workflow 단계로 정상 진행의 세 조건으로 정의함. 마지막 정상 상태와 Trace 보존, 검증되지 않은 결과를 최종 확정하지 않는 원칙도 명시되어 있음.

**문제**

기본 성공 기준은 있으나, 호출 성공과 업무상 정상 복귀를 구분하고 복구 시작점·운영 한도를 포함하는 Recovery Contract로는 충분히 구체적이지 않음. “다음 단계로 정상 진행”의 단계별 의미도 오류 유형별로 고정되어 있지 않음. 특히 다음 기준이 불명확함.

- 복구를 시작할 때 기준으로 삼는 마지막 정상 상태가 무엇인지, 그 상태의 입력·검증 결과·데이터 버전을 어떻게 식별하는지
- 재시도 시 실패 Agent/Tool만 재실행하는 조건과 전체 Workflow를 다시 검증하는 조건
- 장애 발생 중 생성된 부분 결과를 폐기·보존·재사용하는 기준
- Fallback 데이터의 Schema와 버전 신선도 확인 후 어디부터 재개하는지
- 상태 저장이나 승인 처리 도중 실패했을 때 중복 실행·중복 쓰기를 막고 일관된 상태로 돌아오는 기준
- 복구 성공으로 `RUNNING`에 복귀하거나 `WAITING_APPROVAL`에 도달했다고 판정할 구체 조건
- 자동 복구에 허용할 총 시간·LLM 호출/비용·대기 시간의 상한과 초과 시 종료 방식
- fallback snapshot의 허용 연령·버전 일치/호환 기준, 기준을 만족하지 못할 때의 처리
- 복구 중 다른 요청이 같은 Workflow를 수정하거나 승인할 때의 상태 충돌 처리

기존 문서의 “Agent/Tool 재호출 성공”은 호출 성공일 뿐 업무 결과가 복구됐음을 보장하지 않음. 반대로 이벤트 기획 오류는 전체 이벤트 재검증을 요구하므로, 복구 기준점과 재검증 범위가 오류 종류별로 연결되어야 함. 재시도 횟수만 제한되어 있고 시간·비용 상한이 없다면 동기 요청이 오래 점유되거나 예상보다 많은 호출 비용이 발생할 수 있음.

**영향**

같은 장애에서 실행 위치·결과 재사용 여부가 구현에 따라 달라질 수 있음. 오래된/불완전한 결과가 정상 상태로 취급되거나, 부작용이 중복 발생하거나, 오류가 해결되지 않았는데 Workflow가 정상 진행할 위험이 있음.

**정리 필요 사항**

오류별 Recovery Contract를 정의하고 다음 필드를 Trace와 Workflow State에 연결할 것.

- `checkpoint_id` 또는 동등한 식별자, 체크포인트 생성 시점·단계·상태 버전
- 체크포인트에 포함할 마지막 검증 입력/출력, `game_data_version`, 데이터 출처, 커밋 완료 여부
- 오류 유형별 재개 단계와 재실행 범위
- 복구 후 통과해야 할 재검증 목록 및 근거
- 중복 부작용 방지를 위한 멱등성 경계, 원자적 DB 커밋 조건 및 동시 요청 처리
- fallback 데이터의 최대 허용 연령·버전 호환성·검증 기준
- 기술 Retry 횟수뿐 아니라 최대 복구 시간·LLM 호출/비용·대기 시간 한도
- 복구 성공 / 안전 종료 판정식 및 수동 개입 경계

권장되는 최소 정상 복귀 조건은 다음과 같음.

1. 기준점의 입력과 마지막으로 검증된 상태·데이터 버전을 식별할 수 있음.
2. 기획 오류는 원래 Event Brief의 필수·금지 조건을 유지하며 수정되고, 전체 EventPlan이 규칙 검증 및 Critic 판정을 다시 통과함.
3. 기술 오류는 실패한 단계부터 재실행하고 Output Contract와 하위 검증을 통과함. Fallback 데이터는 명시된 신선도·버전 기준을 충족해야 함.
4. 복구 결과와 Workflow 상태 저장은 원자적이며, 동시 요청이나 Retry로 중복 승인·중복 쓰기·중복 지급이 발생하지 않음.
5. 위 조건이 재시도·시간·비용 예산 안에 충족되지 않거나 신뢰할 체크포인트가 없으면 Safe Stop함.

실패 단계의 재호출 성공만으로 복구 성공 처리하지 말고, 위 기준을 모두 만족한 경우에만 정상 진행 또는 `WAITING_APPROVAL`로 전환하도록 정의할 것.

## RV-09. 멱등성 Key가 동일 요청 내용인지 구분하지 않음

**근거**

- 이벤트 생성은 클라이언트가 `idempotency_key`를 보내며, 동일 Key 요청은 기존 task_id와 결과를 반환한다고 정의함 (`개발 기획안.md`, 2086~2108행, 2160~2190행).
- 승인 계열 Key는 `task_id + result_version + action`으로 생성하고, 동일 조합이면 기존 처리 결과를 반환한다고 정의함 (`개발 기획안.md`, 2310~2360행).
- `REQUEST_REVISION`에는 의미 있는 `comment`가 포함되지만 Key 구성에는 comment나 요청 Payload 지문이 없음.

**문제**

동일 Key로 다른 Payload가 들어온 경우를 정의하지 않음. 이벤트 생성에서 같은 Key에 다른 이벤트 목적·기간을 넣어도 기존 결과를 반환할 수 있음. 승인 계열에서도 같은 task/version/action에 서로 다른 수정 의견이 들어오면 어떤 요청이 유효한지 모호하며, 현재 키 구성은 첫 요청 결과를 재사용하게 함.

**영향**

클라이언트 버그나 동시 제출로 잘못된 결과가 정상 중복 응답처럼 반환될 수 있고, 사용자가 보낸 수정 의견이 조용히 무시될 수 있음.

**정리 필요 사항**

요청 Payload의 canonical hash를 저장해 Key와 함께 확인할 것. 동일 Key + 동일 Payload는 기존 응답을 반환하고, 동일 Key + 다른 Payload는 명시적 `409 Conflict` 등으로 거부하도록 정의. 서버 생성 승인 Key에도 action별 관련 Payload(특히 REQUEST_REVISION의 comment)를 포함하거나, 같은 task/version에서 수정 요청은 한 건만 허용하고 상이한 후속 요청은 충돌로 반환한다고 명시할 것.


## RV-10. 장애 복구 테스트는 구체적이나 이벤트 기획 품질 테스트 기준은 부족함

**현재 정의된 내용**

개발 기획안에는 정상 흐름, 미션 불가 조건, Agent 실패, MCP Timeout, DB 실패, Validation 오류, 최대 Retry 초과, MCP 컨테이너 중단, 영속성, Primary Tool 대체 등 기술·운영 테스트가 다수 정의되어 있음(TC-01~10). 신규·복귀·전체 대상 규칙(SEG-01~03), 승인(H-01~05), 멱등성(I-01~03), Guard(G-01~03) 테스트와 테스트 결과 기록 양식도 있음. 복구 성공 판정도 실패 단계 재호출/재연결, 결과 Validation 통과, 다음 Workflow 단계 진행으로 기술되어 있음.

**문제**

이 테스트들은 시스템 흐름과 정해진 규칙의 실행 여부를 확인하는 데 유용하지만, 이벤트 기획안이 입력된 목적과 대상에 맞는지, 각 이벤트 유형(복귀·신규·특별 등)에 적합한 구성인지, 미션과 보상의 의미적 완결성·다양성·운영 가능성이 있는지를 판정하는 품질 테스트는 구체화되어 있지 않음. 이는 RV-03의 게임 규칙 데이터와 RV-04의 Event Brief·출력 스키마·수용 기준 미정과 연결됨.

Critic의 PASS/RETRY/FAIL을 재현 가능하게 판정할 기준과, 자연어 요구가 모호하거나 서로 충돌할 때의 기대 결과도 테스트 자료로 고정되어 있지 않음. 따라서 테스트 케이스 수가 적다는 문제가 아니라, 의미 품질에 대한 정답 기준(oracle)이 부족한 문제임. 실제 구현 후 채울 시험 결과 기록란은 설계 누락으로 보지 않음.

**영향**

구조 검증과 기본 게임 규칙 검증을 통과해도 목적을 달성하지 못하는 기획안이 통과할 수 있음. 모델·프롬프트·규칙 변경 전후의 품질 저하를 감지하기 어렵고, Critic의 판정이 실행마다 달라져도 회귀 여부를 판단하기 어려움.

**정리 필요 사항**

RV-03과 RV-04에서 가상 게임 규칙, 이벤트 유형, Event Brief 및 기획안 수용 기준을 먼저 확정한 뒤, 다음을 별도의 이벤트 기획 품질 테스트 묶음으로 추가할 것.

- 대표 Event Brief와 기대되는 필수 조건·금지 조건·판정 결과를 담은 골든 케이스 세트
- 이벤트 목적 적합성, 대상 적합성, 게임 규칙 준수, 미션·보상 연결성, 완결성 등 Critic 평가표와 항목별 PASS/RETRY/FAIL 기준
- 정상·경계·불가능·누락·모호·상충 입력 사례와 기대되는 확인 질문 또는 안전한 거절 결과
- 신규·복귀·전체 대상 및 복귀/신규/특별 이벤트 유형별 시나리오 커버리지
- Planner/Prompt/모델/규칙 변경 시 골든 세트 회귀 실행, 항목별 점수와 판정 일관성 비교
- 품질 점수만으로 필수 규칙 위반을 통과시키지 않도록 결정적 규칙 검증과 의미 평가의 결합 판정 정의

기술 장애 주입·복구 테스트는 기존 TC와 Recovery Contract(RV-08)에 맞춰 유지하고, 이벤트 품질 테스트는 이와 별도 분류하되 같은 CI 및 릴리스 수용 기준에서 함께 확인하도록 정리할 것. MCP 장애 후 재개를 요구하는 TC-08은 RV-01의 아키텍처 결정과 일치시킬 것.


## RV-11. 코드 스타일·정적 품질 검사 기준과 도구가 미정

**현재 정의된 내용**

개발 기획안에는 Frontend/Backend/MCP의 독립 GitHub Actions CI/CD Workflow와 서비스별 테스트 실행이 정의되어 있음. Python Backend/MCP의 구체 구현 언어와 기술 스택 범주도 제시되어 있음.

**문제**

확인한 CI/CD 및 테스트 계획에는 Python 코드의 린트·포맷·타입 검사 도구(예: Ruff)의 선택, 설정 파일, 검사 범위, 실패 시 병합 차단 기준이 명시되어 있지 않음. 따라서 테스트 통과만으로는 일관된 스타일, 미사용 코드·일부 오류 탐지, 타입 품질을 보장하기 어려움. Frontend 도구 체계와 각 도구의 버전 고정 여부도 함께 정리되어 있지 않음.

**정리 필요 사항**

- Backend/MCP에 Ruff를 사용할지 결정하고, 사용한다면 lint와 format 검사 범위·규칙·버전을 `pyproject.toml`에 고정.
- 타입 검사가 필요한 범위와 도구를 정하고(예: mypy 또는 pyright), 테스트와 구분해 CI에서 실행.
- Frontend 린터·포매터와 버전을 명시하고 설정을 저장소에 포함.
- 로컬 개발과 CI에서 같은 명령을 사용하도록 표준 명령 또는 pre-commit 구성을 제공.
- CI에서 품질 검사 실패 시 해당 서비스 변경의 체크를 실패 처리하고, 예외 승인·기술 부채 허용 절차를 정의.
- 각 서비스의 CI Workflow에 설치, lint, format check, type check, test의 순서와 필수/선택 여부를 명시.

## RV-12. 팀 협업 도구·작업 관리·변경 통합 절차가 미정

**현재 정의된 내용**

문서에는 GitHub 저장소, 서비스별 디렉터리 및 독립 CI/CD Workflow, 에이전트 간 역할·handoff가 정의되어 있음. 다만 에이전트 협업 설계는 런타임 시스템 역할을 주로 설명하며, 개발팀 구성원이 실제로 작업을 나누고 통합하는 절차와는 구분할 필요가 있음.

**문제**

어떤 도구를 단일 기준으로 사용할지(예: GitHub Issues/Projects, PR, 문서 저장소), 작업을 어떻게 등록·담당·우선순위화·완료 처리할지, 브랜치·커밋·코드 리뷰·병합 규칙이 무엇인지 구체화되어 있지 않음. 서비스별 CI가 분리되어도 공통 계약이나 스키마 변경을 누가 조정하고 어떤 순서로 통합하는지 명확하지 않으면 병렬 작업 결과가 충돌하거나 완료 기준이 서로 달라질 수 있음.

**정리 필요 사항**

- 이슈/작업 보드, 문서, 코드, 의사결정 기록의 기준 도구와 위치를 지정.
- 작업 카드에 담당자, 산출물, 선행 작업, 완료 조건, 검증 방법을 기록하고 상태 흐름 및 우선순위 관리자를 정함.
- 브랜치 전략, PR 템플릿, 리뷰어 지정, 필수 CI 체크, 승인 수, 병합 방식과 긴급 수정 절차를 정의.
- API·공유 스키마·게임 데이터처럼 여러 서비스에 영향을 주는 변경은 계약 소유자, 변경 제안·검토·버전 관리 방식을 정함.
- 서비스 담당과 통합 담당의 책임, 정기 통합 시점, 충돌 해결·결정 기록 방식을 명시.
- 작업 완료 정의(코드/문서 갱신, 관련 검사 통과, 리뷰 및 병합, 데모·기록 갱신)를 합의.
## RV-13. LLM 모델·프롬프트 변경의 버전 추적과 평가 절차가 부족함

**현재 정의된 내용**

문서에는 Agent별 모델과 Tool을 설정 파일로 분리하는 방향이 있고, 이벤트 품질 골든 케이스 회귀 테스트를 권장안으로 추가함(RV-10).

**문제**

실행 결과에 사용된 모델 식별자·모델 제공자 설정·프롬프트 버전·생성 설정을 어떻게 기록할지, 변경을 누가 승인하는지, 변경 전후 품질을 어떤 기준으로 비교할지가 계약으로 정리되어 있지 않음. 프롬프트 또는 모델이 바뀌면 동일 입력에서도 결과가 달라질 수 있으므로, 단순히 코드 버전만 기록해서는 결과를 설명하거나 회귀를 추적하기 어려움.

**정리 필요 사항**

- 각 실행에 모델 제공자/모델 ID, 프롬프트·Agent 설정 버전, 주요 생성 파라미터, 코드 릴리스 버전을 기록.
- 프롬프트·모델 변경을 검토 가능한 변경 단위로 관리하고 변경 이력·담당자를 보존.
- RV-10의 골든 케이스로 변경 전후 필수 규칙 통과율, Critic 판정, 품질 항목별 점수와 변동을 비교.
- 회귀 기준 미달 시 배포 보류·원복 기준을 정하고, 모델 제공자 변경이나 API 호환성 변경도 평가 대상으로 포함.
- 로그에는 재현에 필요한 식별자를 남기되 민감한 원문 입력·불필요한 개인정보를 무기한 저장하지 않도록 RV-16과 맞춤.

## RV-14. LLM 토큰 사용량·비용의 계측과 상한·초과 정책이 미정

**문제**

Agent 재시도와 기획 수정은 LLM 호출을 추가로 발생시키며, 자동 복구 루프에서는 기술 Retry와 기획 Revision이 누적될 수 있음. RV-08은 복구 시간·LLM 호출/비용 한도를 Recovery Contract에 포함하라고 제안하지만, 정상 실행과 전체 Workflow의 비용 관리, 비용 추적 필드, 초과 시 동작은 별도 운영 기준으로 구체화되어 있지 않음. 토큰 비용은 반복 실행·시연·장애 상황에서 누적될 수 있어 우선순위 높게 확정할 필요가 있음.

**정리 필요 사항**

- 호출별 Agent/단계, 모델, 입력·출력 토큰 수, 호출 횟수, 재시도 여부, 추정 비용, 실행 ID를 계측·저장.
- 공급자 사용량과 내부 추정 비용이 다를 수 있으므로 추정 방식·가격표 버전·통화·가격 갱신 책임을 명시하고, 실제 청구액과 대조 가능한 방법을 정함.
- Workflow당 토큰·호출 수·비용 상한, 일일/월간 프로젝트 예산, 경고 임계치를 설정. 구체 수치는 모델·가격·시연 규모를 확인해 팀이 결정.
- 상한 도달 전 경고, 상한 도달 시 추가 LLM 호출 중단 또는 안전 종료, 사용자에게 표시할 상태와 수동 개입 방법을 정의.
- 이벤트 수정 재시도와 기술 장애 재시도를 별도로 계측해 비용 원인을 구분하고, 캐시 사용 시 신선도·버전 기준을 함께 적용.
- Test Mode/Fault Injection의 호출도 운영 사용량과 분리 집계하되, 비용 한도에서 제외할지 포함할지 명시.
- 비용 추적과 한도 초과·재시도 폭주를 검증하는 테스트 케이스를 RV-10 및 RV-08과 연결.

## RV-15. 정상 운영의 성능·동시성 목표와 과부하 동작이 미정

**현재 정의된 내용**

MVP의 동기식 실행 범위와 복구 관련 대기·시간 한도 문제는 RV-01 및 RV-08에 기록되어 있음. 개발 기획안은 최소 운영 지표를 두지만 정상 부하에서의 목표치는 별도 확정이 필요함.

**문제**

정상 요청의 처리시간 목표, 허용 동시 Workflow 수, API/DB/LLM별 Timeout 예산, 과부하 시 거절·대기·재시도 정책이 정해져 있지 않음. 동기식 요청에서는 느린 LLM 호출이나 동시 시연이 Backend 연결과 자원을 오래 점유할 수 있음.

**정리 필요 사항**

- 예상 사용자·동시 요청 규모와 시연 시나리오를 정하고 정상/최대 부하에서 목표 응답시간(예: p95)과 성공률을 설정.
- Workflow 전체 Deadline을 각 단계의 Timeout 예산으로 나누고, Retry가 전체 시간 예산을 넘지 않도록 정의.
- 동시 실행 상한, 초과 요청의 명시적 응답, DB 연결 풀·외부 호출 제한 및 대기 정책을 결정.
- 부하·동시성 시험의 입력 규모, 측정 지표, 합격 기준을 정하고 결과를 남김.
- 목표가 내부 데모 수준인지 실제 운영 수준인지 문서에서 분명히 구분하고, 목표 수치는 구현 환경에 맞게 결정.

## RV-16. 데이터 보존·삭제와 백업·복원 기준이 부족함

**현재 정의된 내용**

PostgreSQL Docker volume의 재시작 후 상태 보존 시험과 DB의 무결성·스키마 상세 부족은 문서에 다루어져 있음(RV-06 및 관련 개발 절).

**문제**

컨테이너 재시작 후 유지되는 것과 DB/호스트 손상에서 백업을 복구할 수 있는 것은 다른 보장임. Trace·입력·결과·테스트 데이터의 보존 기간, 삭제·마스킹 방식, 백업 주기·저장 위치·복원 검증·복구 목표가 명확하지 않음. LLM 요청/응답이나 실행 Trace에 업무상 민감한 정보가 포함될 때 보존 범위도 결정되어야 함.

**정리 필요 사항**

- 저장 데이터 종류별 목적, 민감도, 접근 주체, 보존 기간, 삭제·마스킹 정책을 정의.
- DB 백업 범위·주기·암호화·접근권한·보관 위치와 복구 책임자를 정함.
- 백업에서 복원하는 시험과 합격 기준을 추가하고, 복구 가능한 시점(RPO)·복구 시간(RTO)을 프로젝트 수준에 맞게 결정.
- 마이그레이션·롤백 시 데이터 호환성, 백업 보유·삭제 시점을 정의.
- 실제 개인정보를 MVP에 넣지 않는다면 테스트 데이터만 사용한다는 원칙과 검증 방법을 명시.

## RV-17. 시연 보안과 실제 운영 인증·권한 확장 경계가 미정

**현재 정의된 내용**

기획안은 Demo 로그인을 실제 사내 인증으로 취급하지 않고, Backend가 승인 가능한 Demo 담당자와 result_version을 별도 검증한다고 명시함. 실제 사내 인증은 MVP 범위에서 제외한다고 분명히 밝혀 둠.

**문제**

범위 제외 자체는 합리적이지만, 시연 환경에서 Backend가 어떤 네트워크 경계로 보호되는지, Demo actor 식별을 어떻게 위조할 수 없게 할지, Fault Injection/Test API를 누가 실행할 수 있는지 배포 설정과 검수 기준이 명확하지 않음. 또한 실제 운영 전환 시 필요한 인증·인가·역할 분리의 완료 조건이 구체적이지 않음.

**정리 필요 사항**

- 데모 환경의 공개/비공개 네트워크 경계, Backend 직접 접근 차단, 허용 Origin·호스트 및 Test API 접근 조건을 정의.
- 클라이언트가 보낸 actor_id를 신뢰하는 범위와 서버 측 검증 방법, Demo 자격증명 보관·회전 방식을 명시.
- 운영 전환 전 필수 항목으로 SSO 또는 동등한 인증, 역할 기반 인가, 승인 권한 관리, 감사 로그 보호·열람 권한을 지정.
- MVP에서 구현하지 않는 보안 통제를 배포 체크리스트에 표시하고, 실제 운영 용도로 오인되지 않도록 UI·문서에 범위를 표시.
- 보안 요구사항을 실제 배포 환경에서 확인하는 접근 통제 시험을 추가.

## RV-18. 운영 화면의 사용성·접근성 검증 기준이 미정

**현재 정의된 내용**

운영 화면 탭, 정상 실행·AutoHealing·Trace 확인 흐름은 정의되어 있음.

**문제**

화면 구성과 시나리오가 정해져 있어도 사용자가 오류 원인, 복구 진행 상태, 승인 필요 여부, 다음 조치를 오해 없이 파악할 수 있는지는 검증되지 않음. 색상만으로 상태를 구분하거나, 키보드 조작·좁은 화면에서 주요 업무가 불가능할 경우 운영자가 필요한 조치를 놓칠 수 있음.

**정리 필요 사항**

- 기획 담당자·승인자·운영자의 주요 작업을 기준으로 사용성 점검 시나리오와 완료 기준을 정의.
- 상태를 색상뿐 아니라 텍스트/아이콘으로 표현하고 오류에는 원인, 영향, 다음 조치를 표시.
- 키보드 포커스·레이블·대비·화면 확대 및 주요 화면 폭에서 핵심 기능 이용 여부를 점검.
- 장애/복구 상태에서 사용자가 인지해야 하는 정보와 경고 우선순위를 명시하고 간단한 사용자 검증을 수행.
- MVP에서 접근성 범위를 제한한다면 적용 기준과 미지원 항목을 기록.
## 권장안: 개발 과정 관리와 CI/CD 구체화

아래 내용은 현재 문서에 이미 확정된 요구사항이 아니라, RV-11·RV-12를 해결하기 위한 권장 운영안임. 팀 규모와 시연 범위에 맞춰 선택·조정한 뒤 개발 기획안에 확정할 것.

### 작업·협업 관리

- 모노레포 구조와 서비스별 담당자(Frontend / Backend / MCP)를 유지하고, API·공유 스키마·게임 데이터에는 변경 조율 책임자를 지정.
- GitHub Issues와 Projects를 작업 추적의 기준 도구로 사용. 각 작업에는 목적·범위, 담당자, 우선순위, 선행 작업, 영향 서비스, 완료 조건, 검증 방법을 기록.
- `main` 직접 push를 제한하고 작업 브랜치에서 PR로 통합. PR은 연결 이슈, 변경 요약, 실행한 검사, 필요한 화면·로그 증거를 포함.
- 최소 1명의 리뷰와 필수 CI 통과 후 병합. 공통 API·스키마 변경은 영향을 받는 서비스 담당자의 리뷰를 포함.
- 병합 방식과 긴급 수정 절차를 통일하고, 기술적 결정과 계약 변경 이력을 저장소에서 추적.
- 완료 정의에는 구현뿐 아니라 관련 문서·계약 갱신, 검사 통과, 리뷰·병합 및 시연/기록 갱신을 포함.

### CI 권장 단계

PR마다 서비스 변경 범위에 맞춰 다음 검사를 자동 실행하고, 필수 검사 실패 시 병합을 차단.

1. 의존성 설치 및 버전 확인
2. 린트·포맷 검사(Backend/MCP는 Ruff 권장, Frontend는 선택한 생태계 도구 명시)
3. 타입 검사와 단위 테스트
4. API·스키마 계약 테스트 및 필요한 통합 테스트
5. 서비스 빌드
6. Secret 및 기본 보안 검사

검사 명령·도구 버전·규칙은 저장소 설정 파일에 고정하고 로컬과 CI에서 동일하게 사용. 예외를 허용하는 경우 승인자와 기록 방식을 정함. 이벤트 품질 골든 케이스가 마련되면 모델·프롬프트·규칙 변경의 회귀 검사도 CI 또는 릴리스 게이트에 연결.

### CD 권장 단계

- PR 단계에서는 배포하지 않고 검사·빌드만 수행.
- `main` 병합 후 개발/시연 환경에 배포하고 기본 헬스체크를 실행.
- 스테이징 또는 최종 시연 확인 후 릴리스 승인을 거쳐 배포.
- 배포 실패 시 이전 이미지/버전으로 복구하는 절차와 실행 책임자를 명시.
- 현재 프로젝트가 내부 시연 범위라면 PR 검사와 개발 환경 배포를 우선 완성하고, 운영 배포 자동화는 실제 요구가 있을 때 확장.

### 문서화할 산출물

- `CONTRIBUTING.md`: 브랜치, 커밋, PR, 리뷰 및 긴급 수정 규칙
- 이슈·PR 템플릿 및 GitHub Projects 작업 보드
- `pyproject.toml` 등 린트·포맷·타입 검사 설정과 도구 버전
- 서비스별 GitHub Actions Workflow와 필수 상태 검사 목록
- 배포·롤백 절차 및 릴리스 체크리스트
- 작업별 담당자·선행 관계·완료 기준을 추적하는 보드 운영 규칙

이 권장안을 채택하면 RV-11은 품질 도구·실행 조건·병합 게이트가 정해진 상태, RV-12는 작업 추적·리뷰·통합 책임과 절차가 정해진 상태를 완료 기준으로 삼을 수 있음. 테스트 실행 시점과 범위는 RV-10의 기술 테스트·이벤트 품질 테스트와 연결해 중복되거나 누락되지 않게 맞출 것.

## 검수 문서 재점검: 정확성·범위·우선순위

두 기획안과 RV-01~RV-18을 다시 대조한 결과, 현재 검수 항목에서 확인한 핵심 사실은 대체로 원문과 부합함. 특히 테스트 계획, GitHub Actions, Docker 배포, 최소 운영 지표, 데모 인증 제외 및 내부 네트워크 원칙은 원문에 실제로 존재함. 따라서 해당 항목들은 기능 자체가 전혀 없다는 뜻이 아니라, 검증 가능한 완료 기준·수치·운영 절차가 충분히 명시되지 않았다는 의미로 해석해야 함.

### 표현 및 범위 해석

- RV-10은 장애 테스트가 없다는 지적이 아님. 기존 TC-01~10과 Guard/Approval/Idempotency 테스트는 기술 동작을 다루며, 입력 목적에 대한 의미 품질 평가와 회귀 기준이 상대적으로 부족하다는 지적임.
- RV-11은 CI/CD가 없다는 지적이 아님. 서비스별 GitHub Actions와 테스트·빌드·배포 흐름은 정의되어 있으나, 린트·포맷·타입 검사 도구와 PR 필수 체크 정책이 추가로 필요하다는 지적임.
- RV-12는 Agent 간 런타임 handoff가 없다는 지적이 아님. 개발팀의 이슈 관리, 브랜치/PR, 코드 리뷰, 병렬 작업 통합 절차가 별도로 필요하다는 지적임.
- RV-14의 Workflow 토큰/비용 상한은 RV-08의 장애 복구 예산과 겹침. RV-08은 복구 중 재시도·재개 한도, RV-14는 정상 요청까지 포함한 호출별 계측과 Workflow·프로젝트 예산 및 초과 처리의 상위 비용 정책을 다루도록 경계를 유지할 것.
- RV-15의 요청 처리시간·동시성은 RV-01의 동기식 재개 충돌과 RV-08의 복구 시간 한도와 관련되지만 다른 문제임. RV-01은 아키텍처상 실행 재개 가능성, RV-08은 복구 안전 한도, RV-15는 정상 부하의 서비스 목표를 다룸.
- RV-16의 컨테이너 재시작 후 데이터 유지 시험은 문서에 이미 있음. 이는 독립 백업에서 복원하는 재해 복구 능력을 증명하지 않으므로 백업·복원 기준과 구분함.
- RV-17은 MVP에서 실제 사내 인증을 제외한다는 결정을 문제 삼지 않음. 문서에 적힌 Backend/MCP 비공개 및 Demo 권한 경계를 배포 구성에서 검증하고, 향후 실제 운영 전환 조건을 정하자는 항목임.

### MVP 우선순위와 선후 관계 권장

모든 RV를 구현 전 필수 조건으로 취급하면 시연 MVP 범위를 불필요하게 키울 수 있음. 아래 순서로 설계 확정 항목과 운영 확장 항목을 구분하는 것을 권장함.

1. **기획·판정 기준 선행:** RV-03 게임 규칙/데이터와 RV-04 Event Brief·결과 스키마를 확정한 뒤, RV-10 의미 품질 테스트 및 RV-13 모델·프롬프트 회귀 평가를 구체화.
2. **실행·복구 계약:** RV-01 동기식 Workflow의 종료/재개 방식을 결정하고, RV-06 DB 저장 경계, RV-07 API 응답, RV-09 멱등성 정책을 맞춘 뒤 RV-08 오류별 복구 계약을 고정.
3. **비용·재현 가능성:** LLM 호출 경로를 정하면서 RV-14 토큰 계측·Workflow 한도·초과 시 동작을 MVP 운영 조건으로 결정. 가격·토큰량이 확정되지 않은 상태에서 임의의 숫자를 기획서에 넣지 말고, 계측 방법과 결정 책임자부터 고정.
4. **개발 통제:** RV-11 품질 검사와 RV-12 작업·리뷰 절차를 구현 초기에 정해 이후 병렬 개발의 공통 기준으로 사용.
5. **환경별 운영 수준:** RV-15 부하 목표, RV-16 백업/RPO/RTO, RV-17 실제 인증 확장, RV-18 접근성의 목표는 로컬 데모·발표용 MVP·실제 운영 환경별로 구분. MVP에서 제외할 항목도 담당자와 향후 전환 조건을 남김.

RV-14 토큰 비용은 프로젝트 운영 예산을 통제하기 위해 높은 우선순위로 유지하되, 다른 운영 수준 요구와 마찬가지로 실제 모델·요금·예상 사용량을 근거로 한도를 결정해야 함. 이 재점검은 원문 설계를 대체하거나 새로운 수치를 확정하는 것이 아니라, 검수 문서의 지적 범위와 의사결정 순서를 명확히 하는 보완임.
## 검수 메모

두 문서의 에이전트 역할 구분, `revision_count`와 `retry_count`의 분리, Critic 판정과 Supervisor 라우팅의 책임 분리, 사람 승인 흐름, 서비스별 CI/CD 구조는 검토 범위에서 큰 논리 충돌을 확인하지 못함.
