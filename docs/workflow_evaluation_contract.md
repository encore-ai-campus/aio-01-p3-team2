# Workflow 장애 복구 기록·평가 합의

상태: 2026-10-09 팀 합의. 이 문서는 백엔드 B·백엔드 A·MCP 담당자가 장애 주입 시험과 복구 평가에 함께 적용할 기준이다. 백엔드 B의 반복 평가 도구와 Mock·실제 LLM의 제한된 실행 결과는 [백엔드 B 평가 기록](team/backend-2/recovery_evaluation.md)에 있다. 더 넓은 입력·모델의 LLM 품질 평가는 별도 검증 대상이다.

## 공식 기록과 용도

| 기록 | 용도 | 현재 구현 상태 |
| --- | --- | --- |
| `GET /api/tasks/{task_id}/trace` | 실행 순서, 오류 감지, Supervisor 결정, Retry·Fallback·Safe Stop, 재검증, 최종 상태를 판정하는 공식 근거 | 백엔드 B가 이벤트를 생성하고 백엔드 A가 저장·조회한다. |
| `GET /api/tasks/{task_id}/tool-logs` | 개별 Tool 호출의 시간·오류·출처를 살피는 보조 진단 자료 | API와 Schema는 있지만, 현재 백엔드 B 복구 결과의 공식 판정 자료로 사용하지 않는다. |
| 장애 복구 평가 보고서 | 시험 입력·기대 결과와 API 응답·Trace의 실제 결과를 비교하고 복구율·시간을 집계 | 백엔드 B 평가 CLI가 JSON 보고서를 생성한다. 현재 별도 DB 테이블이나 API를 요구하지 않는다. |

**Tool logs가 비어 있거나 없어도** API 응답과 Trace만으로 복구 성공·안전 종료 여부를 판정할 수 있어야 한다. Tool logs의 호출 시간은 복구 시간과 다른 지표이며, 서로 대체하지 않는다.

## 시나리오 판정 기준

백엔드 B는 정상, 기획 오류, 기술 장애를 별도 사례로 정의한다. 각 사례에는 요청과 실행 모드, 장애 주입 여부·유형, 기대 Workflow 상태, 후보 존재 여부, 필수 Trace의 상대 순서, 재검증·Safe Stop 조건을 적는다. 평가 도구는 `POST /api/events/generate` 또는 Test Mode의 `POST /api/test/events/generate` 응답과 `GET /api/tasks/{task_id}/trace`를 함께 대조한다. 실제 오류가 발생했는지 확인하지 않은 요청은 장애 복구율의 분모에 넣지 않는다.

- **정상:** 확인된 기획 데이터를 조회한 뒤 Planner → 규칙 검증 → Critic → 승인 대기 순서로 진행한다. 오류·AutoHealing 이벤트를 임의로 만들어 넣지 않는다.
- **기획 오류:** `validate_plan` 실패와 Supervisor의 기획 수정 결정 뒤 Planner 수정안 생성, 전체 규칙 재검증, Critic 검토가 이어져야 한다. 수정 한도를 넘거나 재검증이 실패하면 검증되지 않은 후보를 승인 대기로 보내지 않는다.
- **기술 장애:** 오류 종류에 맞는 동일 작업 Retry 또는 허용된 Fallback 뒤 검증을 이어간다. 복구 경로·한도가 없으면 `SAFE_STOP`과 `FAILED`를 기록하고 승인 후보를 남기지 않는다.

Trace의 `sequence`와 시간대가 있는 `time`을 기준으로 순서를 확인한다. `phase`, `action`, `next_agent`, `tool_name`, `error_type`, `data_source`, `game_data_version`, `retry_count`, `revision_count`는 해당 사례에서 실제 확인된 값만 비교한다. Agent 재실행이나 Day별 Tool 조회 때문에 전체 행 수를 고정하지 않고 **필수 이벤트의 상대 순서**를 검사한다. 기존 API 필드의 정확한 형식은 [프론트엔드·백엔드 API 계약](frontend_backend_api_contract.md)과 [Trace 응답 계약 예시](team/backend-1/trace_contract_examples.md)를 따른다.

## 평가 지표

| 지표 | 합의된 정의 |
| --- | --- |
| 자동 복구율 | 실제 오류가 관찰된 시험 실행 중, 자동 조치 후 재검증을 통과해 `WAITING_APPROVAL`에 도달한 실행 수 ÷ 실제 오류가 관찰된 시험 실행 수. 장애 종류·모델·실행 모드별로도 나누어 기록한다. |
| 안전 종료 성공률 | 복구에 실패하거나 허용된 경로가 없을 때 `FAILED`·`SAFE_STOP`으로 끝나고 승인 후보가 없는 실행 수 ÷ 안전 종료가 기대된 실행 수. 복구율과 합치지 않는다. |
| 복구 시간 | 해당 실행의 첫 오류 감지 Trace 시각부터 재검증 성공 또는 Safe Stop Trace 시각까지의 경과 시간. 성공 복구와 안전 종료를 구분해 보고한다. 필수 시각이 없으면 측정 불가로 표시하고 추정값을 쓰지 않는다. |
| 실제 LLM 반복 평가 | 동일한 입력·모델·게임 데이터 버전·시나리오로 여러 번 실행해 `WAITING_APPROVAL`, 수정 횟수, `FAILED`, 규칙 검증, Critic 결과를 실행별로 남긴다. 단일 성공 사례를 품질 보장으로 표현하지 않는다. |

복구 시간은 Workflow 전체 응답 시간이나 개별 Tool 호출 시간이 아니다. Trace 시각만으로 정확한 소요 시간을 계산할 수 없는 환경에서는 평가 실행기가 시작·종료 시각을 별도로 기록하고, 그 측정 방식도 보고서에 명시한다. 반복 횟수와 품질 허용 기준은 평가를 시작할 때 모델 비용·시험 목적과 함께 정해 기록한다. 이 문서가 특정 횟수나 성공률 목표를 이미 달성했다고 뜻하지 않는다.

## 평가 보고서에 남길 항목

실행별로 시나리오 이름, 실행 모드, 모델 이름(실제 LLM 사용 시), 게임 데이터 출처·버전, 장애 주입 유형, `task_id`, 기대 상태·필수 Trace, 실제 상태·Trace 판정, 오류 유형, 복구 조치, 재검증 결과, 복구 시간 또는 측정 불가 사유를 남긴다. 집계에는 분모·분자와 실행 횟수를 함께 적는다. API 키, 비밀번호, DB URL, 전체 Prompt, 개인 식별 정보는 보고서와 Trace에 남기지 않는다. Test Mode 장애 주입 결과와 자연 발생 오류 결과를 구분한다.

평가 보고서는 우선 시험 산출물과 팀 문서의 결과 요약으로 관리한다. 공용 PostgreSQL 테이블이나 새 API를 선행 조건으로 만들지 않는다. 저장 형식·보존 기간이 필요해지면 백엔드 A와 별도 합의한다.

## 담당과 변경 절차

- **백엔드 B:** 시나리오별 기대 상태·필수 Trace 순서, 평가 도구와 실행별 결과·복구 지표를 담당한다. Agent·Supervisor·MCP 오류의 실제 실행 이벤트를 생성한다.
- **백엔드 A:** Trace의 저장·조회와 Task별 순서를 유지한다. 백엔드 B가 실제 누락 사례를 제시한 경우에만 API·저장 필드 변경을 협의한다. 여러 프로세스가 같은 Task에 동시에 기록하는 경우의 순서·중복 방지는 기존 Trace 계약의 별도 운영 과제다.
- **MCP:** Tool 오류, `source`, `game_data_version`을 기존 계약대로 반환한다. 실패한 조회의 출처·버전을 추측해 채우지 않는다. 호출 시간 측정이 필요하면 보조 진단 항목으로 백엔드 A·B와 협의한다.

현재 구현된 Trace 사례는 [백엔드 B 프론트엔드 Trace handoff](team/backend-2/frontend_trace_handoff.md)와 [백엔드 B handoff](team/backend-2/handoff.md)에 있다. 반복 평가의 실행 조건과 결과는 [백엔드 B 평가 기록](team/backend-2/recovery_evaluation.md)에 있다. 이 문서는 **평가의 합의 기준**이며 제한된 반복 실행을 운영 지표의 달성으로 해석하지 않는다.
