# 방치형 RPG 공개 자료와 설계 참고 패턴

## 목적과 사용 범위

이 문서는 가상 게임 설계를 쉽게 구체화하기 위해 공개된 게임 설명과 게임 설계 자료에서 반복되는 패턴을 추출한다. 특정 상용 게임의 캐릭터·아트·정확한 수치·내부 밸런스를 복제하거나 추정하지 않는다. 공개 스토어 설명은 제작사가 대외적으로 표방한 기능을 보여주는 자료이며, 내부 구현이나 실제 플레이 밸런스의 증거로 취급하지 않는다.

### 구현 자료에서 추출할 설계 점검 항목

이 자료들은 프로젝트의 최종 규칙을 대신 정하지 않는다. 다음 질문을 7개 하위 설계와 대조해, 빠진 계약만 보완하는 데 쓴다.

1. **카탈로그 스키마:** 스테이지·던전·층·적·보상·경험치·세그먼트의 안정 ID, 필수 필드, 참조 무결성, 데이터 버전이 정해져 있는가?
2. **행동 계약:** 각 플레이 명령의 입력, 사전조건, 서버 판정, 상태 변경, 결과 ActionRecord가 연결되어 있는가? 클라이언트가 성공 결과나 보상량을 정할 수 없게 되어 있는가?
3. **시간·난수:** 일일 초기화, 이벤트 기간, 전투 난수, 오프라인 보상 계산이 결정적이고 테스트 가능한 입력으로 정의되어 있는가?
4. **진행 상태와 저장:** 정적 카탈로그와 유저별 상태의 소유권이 나뉘는가? 저장 버전·마이그레이션·중복 요청·복구 경계가 정의되어 있는가?
5. **시뮬레이션과 연출:** 빠른 밸런스 검증과 플레이 화면이 같은 판정 규칙을 사용하는가? 화면 효과는 확정된 런타임 결과를 반영하는가?
6. **이벤트 연결:** 승인 설정이 참조하는 미션 행동·콘텐츠·보상이 카탈로그에 실제 존재하는가? 등록 이후 플레이 기록이 이벤트 진행도·보상 기록으로 이어지는가?

### 자료 확인 결과와 후속 적용

- 가장 직접적인 게임 도메인 참고는 AFK-RPG의 공개 규칙/설정 문서지만, 라이선스상 구현 재사용 대상으로 삼지 않는다.
- 서버와 UI를 분리하는 현재 설계에는 결정적 규칙 엔진, 버전이 있는 데이터, 입력된 시간/난수, 정적 카탈로그와 런타임 상태 분리 원칙이 잘 맞는다. 이는 개별 저장소의 구현 사실이 아니라 프로젝트 맥락에 대한 설계 적용 판단이다.
- 현재 하위 설계는 명령/시도/성공 행동의 분리, 버전 고정, deterministic MVP 판정, 멱등 요청, 미션 근거와 보상 원장/가상 인벤토리 갱신의 논리 계약을 정한다. 물리 DB 마이그레이션과 멱등 결과 보존기간은 구현/운영 결정으로 남는다. 권위 판정 난수는 MVP에서 사용하지 않으며 추가 시 별도 버전 계약이 필요하다. 오프라인 보상 포함 여부는 GD-09 결정 사항이다.
- 공개 프로젝트의 레벨 곡선, 드롭 확률, 오프라인 상한, 재화 수치는 게임별 전제에 종속되므로 우리 fixture에 복사하지 않는다. 시연 유저의 달성 가능성과 보상 영향은 우리 자체 규칙·검증 데이터로 정한다.

## 반복해서 보이는 설계 패턴

### 1. 비접속 중 진행과 복귀 보상

공개 사례는 플레이어가 접속하지 않을 때도 일정한 자원이나 경험치가 쌓이고, 돌아왔을 때 이를 확인·수령해 다음 성장에 쓰는 경험을 내세운다. 이는 방치형이라는 장르 약속을 관객이 바로 알아보게 하는 장치다. 보상 상한·계산 시각·중복 수령 방지는 게임별 구현 세부이므로 우리 규칙으로 별도 정의해야 한다.

### 2. 짧은 반복 루프와 누적 성장

플레이어는 현재 가능한 콘텐츠에 도전하고, 자원/경험치를 얻고, 성장한 뒤 더 높은 스테이지나 강한 보스에 다시 도전한다. 이를 탐험/선택 → 자동 또는 간소화된 전투 → 보상/성장 → 다음 콘텐츠 해금으로 표현하면 짧은 시연에서도 RPG 진행감을 줄 수 있다.

### 3. 보스와 단계 목표

단계 또는 스테이지 사이에 보스를 두면 진행의 중간 목표와 성공 순간이 생긴다. 이벤트 특별 던전의 층 진행과 최종 보스를 두는 현재 방향은 이 패턴에 잘 맞는다. 관객은 복잡한 규칙 설명 없이 “층을 올라 보스를 처치한다”는 목표를 이해할 수 있다.

### 4. 이벤트 퀘스트는 기본 게임 행동을 재맥락화

이벤트 미션은 게임에 없는 동작을 새로 만드는 대신, 이미 있는 스테이지 클리어·던전 도전·성장 행동에 기간과 특별 목표를 붙이는 편이 이해하기 쉽다. 이벤트 퀘스트 패널은 목표·현재 진행·남은 기간·보상을 보여주고, 해당 목표로 바로 이동할 수 있게 연결한다.

### 5. 성장은 숫자뿐 아니라 피드백으로 체감

레벨·스테이지 숫자만 증가하면 성장감이 약할 수 있다. 전투 결과, 해금된 콘텐츠, 유저 HUD, 이벤트 진행도에 같은 변화가 반영되어야 성장을 알아보기 쉽다. 시각 효과는 상태 변화의 원인이 아니라 서버 판정 결과를 표현해야 한다.

## 프로젝트 적용 권고

### 우선 권고: 아주 작은 방치 보상 루프를 포함

현재 게임 도메인 설계서는 방치 보상 수령을 MVP에서 제외하고 있다. 이는 개발 범위를 줄이지만, 오프라인 진행이 없는 게임은 관객에게 “모바일 방치형 RPG”라기보다 자동 전투 판타지 RPG로 읽힐 가능성이 있다. 따라서 다음 최소 기능을 검토할 것을 권한다.

- 서버가 마지막 접속/정산 기준 시각과 최대 적립 시간을 사용해 가상 자원·경험치 적립량을 계산한다.
- 접속 후 로비에 “돌아온 동안 쌓인 보상” 요약과 수령 동작을 보여준다.
- 수령은 서버에서 한 번만 반영하며, 기간 상한·기준 시각·수령 근거를 기록한다.
- 시연 fixture에는 일정 시간 비접속한 가상 유저를 준비해 보상 수령 → 레벨/성장 변화 → 이벤트 도전 자격 또는 미션 진행으로 이어지는 짧은 루프를 둔다.
- 오프라인 보상은 주 시연의 이벤트 적용 장면을 가리지 않는 보조 경험으로 둔다. 주 시연의 절정은 계속 “승인된 이벤트로 특별 던전이 열리고, 보스 처치가 미션/보상으로 반영되는 순간”이다.

이 기능을 추가하면 행동 카탈로그, 경제 모델, 버전/일일 정산 규칙, 미션 집계 범위를 바꿀 수 있다. 따라서 구현에 바로 넣지 말고 먼저 상위 게임 설계에서 **포함/제외를 결정**하고, 포함한다면 데이터·DB·Runtime/API·검증·화면 설계 5개 문서를 함께 갱신해야 한다. 제외한다면 장르 표현을 “idle progression을 일부 갖춘 가상 RPG”로 제한해 관객 기대를 맞추는 방안도 있다.
