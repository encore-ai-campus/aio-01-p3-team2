# 게임 데이터·스키마 설계서

## 문서 상태와 목적

- 상태: opong-data-1.5.0 카탈로그의 이벤트 특별 던전 독립 공간 계약 구현. 일반 던전은 무한 층 규칙을 유지한다. API 입력은 Pydantic, 저장 스키마는 SQL migration에서 관리하며 전용 JSON Schema 파일은 없음
- 목적: 먼저 완성할 가상 게임 Runtime의 정적 카탈로그·성장·아이템·경제 데이터 계약을 정의하고, 후속 WP-10에서 기획안 시스템과 연결할 경계를 표시한다.
- 상위 기준: [가상 게임 도메인 상세 설계서](../가상게임_도메인_상세설계서.md) §§4–6, 10
- 관련 설계: [게임 규칙·플레이 루프](01_게임규칙_플레이루프.md), [저장소·DB](03_게임저장소_DB.md), [검증·밸런스](07_게임검증_밸런스.md)
- 주의: 아래 필드 의미·허용값·상호 제약은 하위 설계 기준이다. JSON Schema/OpenAPI 기술 문법과 스키마 호환성 정책은 구현 인터페이스를 생성할 때 버전 고정한다.

### 구현 기준 업데이트 (2026-10-10)

1.2.0은 기존 단일 적 규칙의 보존 버전이다. 1.3.0부터 일반 던전에 `dungeon_enemy_roster`와 `dungeon_encounter_profile`을 추가해 별무리 폐광 전투 파티 3명, 5층 보스+호위 2명 구성을 생성한다. 스테이지와 이벤트 특별 던전은 1.2.0의 단일 적 계약을 유지한다. 각 파티원은 고유 ID·역할·시각 에셋 참조를 가진다.

영웅 기본 스탯은 HP 90 + 레벨당 12, 공격력 11 + 레벨당 2, 방어력 0이다. 무기 단련은 GOLD 비용 [20, 35, 55, 80, 110]으로 rank마다 공격력 4를 올리고, 갑옷 단련은 [18, 32, 50, 72, 100]으로 rank마다 최대 HP 18을 올린다. 1–5 rank 비용은 이 목록을 사용하고 이후 rank 비용은 progression 계수로 증가한다. 전투 시작 HP는 매 도전에서 최대치로 회복한다.

### 구현 기준 업데이트 (2026-10-11 선택 공간 계약)

신규 이벤트 기획 기준은 `domain_schema_version=1.4.0`, `event_schema_version=1.2.0`, `game_ruleset_version=opong-rules-1.5.0`, `game_data_snapshot_id=opong-data-1.5.0`, `capability_catalog_version=opong-capabilities-1.0.3`이다. 이벤트 특별 던전 템플릿은 `floors[]` 대신 독립 입장 가능한 `spaces[]`를 제공한다. 현재 공간 ID는 `rift_space_01`, `rift_space_02`, `rift_space_03`이며 1.4.0 이하 snapshot은 보존한다.

신규 기획 action은 `special_dungeon_space_clear`이고 Runtime progress type은 `space_cleared`다. 승인 적용 시 `venue.space_ids`에는 선택한 공간만 저장한다. 공간별 mission은 정확히 한 공간 ID를 참조하고, 그 공간의 성공 첫 완료만 연결 보상을 지급한다. 공간 순서는 표시 순서일 뿐 해금 선행 조건이 아니다. 구형 snapshot의 `special_dungeon_floor_clear`와 일반 폐광의 `dungeon_floor`는 이전 의미대로 유지한다. 상세 적용 동작은 [선택 공간 이벤트 계약](05_이벤트적용_계약.md#선택-공간-계약-구현-2026-10-11)을 기준으로 한다.

GameActionRequest는 `stage_mode`/`dungeon_mode`(`push|farm`)를 선택적으로 받는다. 클라이언트는 적 파티나 적 스탯을 제출하지 않고 서버가 버전 카탈로그로 생성한다. Attempt payload와 action 응답은 최종 HP, 승패, 전투 순서 로그를 보존한다. 파티 로그는 `actor_id`, `target_id`, `remaining_enemy_count`를 추가하고, Attempt에 영웅/파티원 스탯·이름·아트 참조·초기/최종 HP 및 규칙/카탈로그 버전을 스냅샷으로 저장한다. 유저 상태에는 highest_stage_order, current_hunt_stage_order, hunt_mode, weapon_upgrade_level, armor_upgrade_level이 저장된다. 보상/소비 변화는 item_id, delta, balance_before/after, source_type을 반환한다.

### 버전 이력과 이벤트 연동 후속

1.2.0과 1.3.0 snapshot은 과거 실행 재현을 위해 보존한다. 현재 카탈로그는 domain 1.3.0, ruleset `opong-rules-1.4.0`, snapshot `opong-data-1.4.0`이다. event schema 1.1.0은 finite/ongoing 이벤트 기간 및 이벤트 기간 중 층별 첫 클리어 mission/reward 연결을 담는다. 신규 적용은 선택된 snapshot을 고정하고 이전 snapshot도 별도 호환 경로로 읽는다. 게임 데이터 버전과 이벤트 포맷 버전은 서로 독립적으로 올린다.

### 스테이지·전투·성장 데이터 계약

스테이지 시각은 5개 슬롯을 반복 사용하고 몬스터 능력치는 스테이지 진행에 따라 성장한다. 데이터는 `stage_order`, `visual_cycle_slot`(1–5), `monster_id`/아키타입, 적용한 `progression_profile_id`, 최종 판정 스탯, 보상 프로필을 재현할 수 있어야 한다. 생성 ID는 `stage:{stage_order}`처럼 순번에서 결정하고 화면 이름과 분리한다. 폐광 층도 `dungeon:{dungeon_id}:floor:{floor_index}`로 안정 식별한다. 클라이언트에서 스탯을 임의 계산하지 않는다. 기준 스탯과 성장 곡선은 버전 카탈로그의 명시적 프로필로 관리하고 밸런스 검증에서 장기 진행 가능성을 평가한다. 16구역 이후 후보 곡선과 폐광 층 곡선은 [게임 규칙·플레이 루프](01_게임규칙_플레이루프.md)의 표를 기준으로 시뮬레이션하며, 승인된 `game_data_snapshot_id`에 anchor/계수/반올림 규칙을 고정한다.

전투 판정 입력에는 고정된 영웅 스탯 스냅샷과 적 스탯 스냅샷, 규칙 버전을 남긴다. 스테이지 입력은 단일 `monster`를 사용하고, 일반 던전은 순서가 있는 `enemies[]` 파티를 사용한다. 파티 원소는 `enemy_id`, `role`, `name`, `visual_asset_id`, `hp`, `attack`, `defense`, `position`을 포함한다. 결과 사실은 승패, 순서가 고정된 전투 로그, 각 적의 최종 HP/처치 상태, 피해/전투 종료 이유, 성장·보상 변화, 다음 사냥 위치와 모드를 포함한다. 자동 전투의 각 전투는 멱등 식별 가능한 행동 단위여야 한다. 전투 로그는 프론트엔드 애니메이션의 근거이며 클라이언트에서 판정 수치로 다시 계산하지 않는다.

왕국 로비의 강화 명령은 허용된 강화 ID만 받는다. Runtime이 비용을 확인하고 재화 차감, 영웅 스탯 갱신, 변경 원장을 원자적으로 저장한다. 현재 구현은 무기/갑옷 강화 각 5단계와 레벨 8 상한을 가진다. 목표 카탈로그는 이 상한을 두지 않고 `GrowthCostProfile`과 `HeroStatProfile` 함수로 모든 유효 rank/level을 계산한다. 향후 밸런스 변경은 새 카탈로그 snapshot으로 관리한다.

일반 던전은 기존 별무리 폐광 하나에서 무한 층을 제공한다. 별도 도전의 탑은 두지 않는다. 폐광은 자체 `DungeonProgressionProfile`과 독립된 최고 층/현재 층 상태를 사용하고, 재료 보상은 소비처와 함께 정의한다. 전투 파티는 기본 3명이며 5층마다 보스와 호위 2명으로 구성한다. 파티 구성과 스탯은 층·프로필 버전으로 결정적으로 생성한다. 이벤트 특별 던전은 승인된 설정이 선택하는 유한 템플릿이며, 일반 폐광의 적 파티 구성을 자동 상속하지 않는다. 해당 템플릿의 적 구성·보스 능력치는 승인 시점 스냅샷에 고정한다.

## 판정 입력과 행동 기록 논리 계약

최종 직렬화 형식은 API/DB 설계에서 고정하되, 스키마 설계는 명령(Command)과 사실(Record)을 구분한다.

| 계약 | 최소 필드 | 생성·검증 책임 |
|---|---|---|
| 플레이 명령 | `request_id`, `command_type`, `content_id`, 허용된 선택 파라미터, 선택적 `runtime_event_id` | 클라이언트가 요청 ID와 선택지만 제출. 사용자 권한은 인증 문맥에서 가져옴 |
| 행동 시도 | `attempt_id`, `request_id`, `user_id`, command/content 참조, `result`, `reason_code`, server `occurred_at`, 규칙/데이터 버전 | Runtime이 유효 도전의 성공/실패와 시각을 추가 전용으로 기록 |
| 성공 행동 사실 | `action_id`, `attempt_id`, `user_id`, `action_type`, 콘텐츠별 측정 필드, 규칙/데이터 버전, 선택적 이벤트 참조 | Runtime이 성공한 도전에서만 생성. 미션 집계는 이 기록만 사용 |
| 성장 변화 | 원본 `action_id`, 변경 전/후 레벨·경험치, 적용된 성장 규칙 참조 | Runtime이 행동 결과에 따라 파생. 클라이언트 수정 불가 |
| 보상 원장 사실 | `reward_record_id`, 유저, `grant_source_type`, source ID, item/currency ID, quantity, 근거, 생성 시각 | Runtime이 콘텐츠 성공 또는 이벤트 미션 완료 후 생성하며 VirtualInventory와 함께 갱신 |

모든 레코드는 자신이 판정된 `game_ruleset_version`과 `game_data_snapshot_id`를 참조한다. 이벤트 미션 집계는 행동 사실을 근거로 하며, 동일 행동 ID를 한 미션 집계에 두 번 반영하지 않는다. 성공 여부·레벨·경험치·보상 수량·발생 시각을 명령 필드로 받아 판정 근거로 사용하지 않는다.

현재 Runtime 카탈로그는 `backend/data/virtual_game_v1.json`에 있고 DB에는 digest와 원본 JSON을 `game_runtime_catalog_snapshots`로 보존한다. 게임 버전은 opong-data-1.1.0, opong-rules-1.1.0, 도메인 schema 1.1.0이다. 기획 Workflow의 검증 데이터 tinyheroes-1.0.0는 Runtime과 동일한 카탈로그로 간주하지 않는다. source version은 카탈로그의 `planner_source_game_data_versions` allowlist와 mission/content ID 매핑이 모두 존재할 때만 Opong Runtime 설정으로 변환한다.

### 플레이 명령/사실의 표준 논리 형태

다음은 의미와 필수 필드를 고정하는 예시다. 물리 직렬화 형식·UUID 표현 등은 API 구현 세부다.

```json
{
  "request_id": "<client-generated unique id>",
  "command_type": "special_dungeon_challenge",
  "content_id": "venue.floor.03",
  "difficulty_id": "difficulty.normal",
  "runtime_event_id": "<active event id>"
}
```

`command_type`은 `stage_challenge | dungeon_challenge | special_dungeon_challenge` 중 하나다. 일반 던전만 `difficulty_id`를 필수로 하고, 특별 던전은 `runtime_event_id`가 필수이며 `content_id`로 현재 도전할 floor를 지정한다. 스테이지/일반 던전은 해당 이벤트 미션에 행동을 연결할 때만 선택적으로 `runtime_event_id`를 보낸다. 이벤트 ID가 있으면 그 이벤트 하나만 자격·미션 대상으로 확인한다. 이벤트와 무관한 일반 플레이에서는 생략한다. `user_id`, 성공 여부, 결과 레벨, 보상 수량, 클라이언트 시각은 요청에서 받지 않는다.

매 유효 도전은 다음 `ActionAttempt`를 남긴다. 사용자가 인증되지 않았거나 요청 구조가 잘못된 경우처럼 도메인 도전에 진입하지 않은 요청은 게임 원장에 남기지 않고 보안/서비스 로그만 남긴다.

```json
{
  "attempt_id": "<id>",
  "request_id": "<same request id>",
  "user_id": "<authenticated user>",
  "command_type": "special_dungeon_challenge",
  "content_id": "venue.floor.03",
  "runtime_event_id": "<event id or null>",
  "result": "succeeded | failed",
  "reason_code": "cleared | level_below_clear_threshold",
  "occurred_at": "<server UTC timestamp>",
  "game_ruleset_version": "<fixed version>",
  "game_data_snapshot_id": "<fixed snapshot>"
}
```

성공일 때만 `ActionRecord`를 추가한다. `action_type`은 네 행동 카탈로그 값 중 하나이며, 관련 Attempt ID를 참조한다. 기록 ID는 `attempt_id + action_type + subtype`에서 안정적으로 결정한다. `special_dungeon_progressed`는 `venue_id`, `floor_id`, `floor_index`, `progress_type`을 포함한다. 보스 층 성공은 동일 Attempt에서 `floor_cleared`와 `boss_defeated` subtype을 각각 생성한다. 미션은 성공 행동만 입력으로 받으므로 실패 Attempt는 감사·운영 조회에는 보이나 진척에는 영향을 주지 않는다.

이벤트 미션의 논리 형태는 `mission_id + action_type + filters + goal(metric, aggregation, operator, target) + period`다. MVP `operator`는 `gte`, `aggregation`은 상위 도메인 문서가 정한 `count`/`max`만 허용한다. 필터·측정 필드·집계는 행동 타입별 허용표에 명시되어야 하며 자유 필드 경로 식이나 임의 표현식은 허용하지 않는다.

가상 보상 지급의 의미는 **유저 가상 인벤토리/재화 보유량을 증가시키고 불변 `RewardRecord`를 남기는 것**으로 정한다. 원장에는 `grant_source_type=content_clear|event_mission`과 해당 source ID를 기록한다. 두 변경은 하나의 처리 단위다. 단순 지급 영수증만 기록하고 게임 보유 상태는 바꾸지 않는 방식은 MVP 지급 완료로 간주하지 않는다.

WP-09의 원정대 보관함은 이 소유 상태를 읽는 게임 화면이다. 지갑 탭은 재화·재료의 권위 잔액을, 스킨 탭은 보유/미보유와 장착 상태를, 변경 기록 탭은 최근 원장 항목을 보여준다. 최근 항목 조회 범위는 잔액 계산 범위가 아니며, 화면은 일부 원장만 읽어도 서버 잔액을 전체 기준으로 표시한다. 장착 스킨은 소유한 스킨 중 하나만 선택할 수 있다.

스킨 카탈로그의 아트 참조는 현재 게임의 귀엽고 친근한 캐릭터 표현과 일관되어야 한다. 기존 캐릭터의 얼굴·실루엣·전투 가독성을 보존하는 색상/장식/테마 변형을 우선하며, 스킨 적용으로 전투 스탯이나 행동 규칙을 변경하지 않는다.

WP-09에는 고정 상품의 스킨 상점만 둔다. 상품은 카탈로그에 등록된 스킨 3종으로 제한하고 각 가격은 1 GEM이다. GEM은 첫 클리어 stage 5·10·15에서 각 1개 지급하여 게임 단독 흐름에서도 상품을 모두 살 수 있게 한다. 스테이지 보상은 해당 stage의 첫 클리어에서만 지급하며 반복 farm으로 중복 지급하지 않는다. 구매 시 서버가 offer 활성 여부, 스킨 미보유 여부, GEM 잔액을 확인하고 GEM 차감·스킨 소유·구매 영수증·원장 기록을 한 transaction으로 저장한다. 같은 request ID는 최초 결과를 반환하고 이미 보유한 스킨 구매는 거절한다. 랜덤 판매, 기간 한정, 현금 결제, 소모품/장비 판매, 환불은 WP-09 범위가 아니다.

현재 구현은 GOLD를 카탈로그 로비 강화에서 차감한다. 목표 경제에서는 MOON_SHARD도 rank 이정표 강화에서 소비하고, GEM은 무료 첫 클리어 보상과 스킨 구매에만 사용한다. 이벤트에서 GEM이나 스킨을 직접 지급하는 연동은 WP-10에서 다룬다. 모든 잔액 변경과 소비 효과는 원장과 멱등 응답에서 확인 가능해야 한다.

## 버전·시간·결정성 계약

- 승인 이벤트와 플레이 행동은 참조한 스키마·규칙·데이터 버전을 명시한다. 판정 도중 활성 버전 포인터가 바뀌어도 한 명령 내에서 버전을 섞지 않는다.
- 카탈로그 스냅샷은 식별자로 불변 참조한다. 수정은 기존 스냅샷 덮어쓰기가 아니라 새 스냅샷 생성이다.
- 시간은 UTC timestamp로 저장한다. 달력 기준 일일 초기화가 필요한 규칙은 명시적 IANA 시간대와 초기화 시각을 규칙 설정에 포함하며, 서버 호스트의 기본 시간대를 암묵적으로 사용하지 않는다.
- MVP 전투 판정에는 난수를 사용하지 않는 것을 권장한다. 이후 권위 판정에 난수를 도입하면 RNG 알고리즘/버전과 명령별 seed 또는 재현 가능한 난수 입력을 판정 근거에 추가해야 한다.
- 어떤 스키마 버전으로 저장된 이벤트/레코드인지 기록하고, 읽기 변환은 원본을 보존한 채 명시된 마이그레이션 단계로 수행한다. 과거 승인 결과의 의미를 현재 규칙으로 다시 해석하지 않는다.

## 스키마 제약 초안

- 식별자는 안정된 문자열 ID로 둔다. 표시명은 식별자로 쓰지 않는다.
- 기간은 ISO 8601 UTC 시각이며 종료 시각은 시작보다 뒤여야 한다.
- 게임 도메인과 이벤트 포맷의 버전은 상위 문서의 `domain_schema_version`, `event_schema_version`, `game_ruleset_version`, `game_data_snapshot_id`를 구분한다.
- 참조는 ID만 저장하되 검증 결과 및 승인 결과에 사용한 데이터 스냅샷을 고정한다.
- 숫자 수량은 음수가 될 수 없고, 레벨·층수·시도 한도는 양의 정수 범위를 갖는다.
- 미션은 상위 문서가 허용한 action/filters/metric/aggregation/operator 조합만 허용한다.
- 특별 던전 이외 유형에 `venue`가 있거나, 특별 던전 유형에 venue가 없으면 차단한다.
- 보상은 하나의 미션 완료 조건과 연결하며 중복 방지 기준을 명시한다.

### 기획안 시스템 연동 계약 (WP-10 후속)

아래 EventConfiguration과 stage/floor `content_scope`는 가상 게임 데이터 모델의 경계 정의다. WP-09에서 기획 Workflow를 수정하지 않는다. WP-10에서만 event schema 1.1.0을 도입하고, 게임 독립 수용을 통과한 카탈로그 ID·행동·아이템을 기존 기획안 시스템과 매핑한다.

### EventConfiguration 필수 구조 (WP-10 목표)

| 필드 | 필수성·논리 타입 | 제약 |
|---|---|---|
| `event_id` | 필수, 안정 문자열 ID | 한 카탈로그/승인 결과 안에서 유일 |
| `event_schema_version` | 필수, 버전 문자열 | 지원 버전이어야 함 |
| `event_type` | 필수 enum | `growth_progression`, `dungeon_challenge`, `special_dungeon` |
| `operation_mode` | WP-10 schema 1.1.0에서 필수 enum | `finite` 또는 `ongoing`; 게임 콘텐츠 진행 모드와 별도 |
| `schedule.start_at`, `schedule.end_at` | start 필수, end는 finite에서 필수·ongoing에서 null | UTC; finite는 `start_at < end_at`; ongoing은 평가 기간을 별도 지정하고 수동 종료 가능 |
| `evaluation_horizon_days` | ongoing에서 필수 양의 정수 | 무기한 이벤트의 보상 영향·난이도 계산 기준 기간; 기본 제안 30일 |
| `audience.segment_id` | 필수 카탈로그 참조 | 승인 버전에서 활성 세그먼트여야 함 |
| `venue` | 특별 던전에서 필수, 그 외 금지 | `template_id`, `layout_id`, `theme_id`, `difficulty_id`의 허용 조합 |
| `missions[]` | 필수 비어 있지 않은 목록 | 각 ID 유일, 허용 action/filters/goal 조합, 유형별 필수 action 포함 |
| `missions[].content_scope` | 선택, 타입별 구조 객체 | 무한 콘텐츠 목표에 한해 stage/floor 인덱스 범위를 지정하고 action type과 일치해야 함 |
| `missions[].reset_period` | WP-10 schema 1.1.0에서 필수 enum | `once`, `daily`, `weekly`; 주기마다 mission progress를 새 cycle로 계산 |
| `rewards[]` | 필수 목록(빈 목록이면 무보상 이벤트) | 각 reward ID 유일, mission 참조 유효, 지급 정책과 cycle/user 한도, 카탈로그 item/currency/skin 참조 유효. skin은 수량 1이며 중복 보상은 ItemDefinition 정책 사용 |
| `rewards[].grant_policy` | WP-10 schema 1.1.0에서 필수 enum | `once_per_user` 또는 `once_per_cycle`; ongoing의 반복 보상은 cycle 지급량과 유저별 상한을 명시 |
| `rewards[].max_grants_per_user` | 반복 지급에서 필수 양의 정수 | 평가 기간 내 유저당 총 지급 상한; 화폐·재료·스킨 모두 적용 |
| `content_cycle_policy` | ongoing `special_dungeon`에서 필수 | cycle마다 유한 템플릿 진행을 초기화하고 새 cycle ID 발급; 그 외에는 생략 |
| `references` | WP-10 schema 1.1.0에서 필수 | `domain_schema_version`, `game_ruleset_version`, `game_data_snapshot_id`, `balance_policy_version` 고정 |

미션 goal은 `metric`, `aggregation`, `operator`, `target`을 모두 갖는다. `target`은 양수이고 MVP operator는 `gte`다. `count`는 성공 사실의 수를 세며, `max`는 허용된 숫자 필드의 기간 내 최댓값을 비교한다. action별 허용 필드와 필터는 상위 도메인 §5.2 표에 한정한다. 스테이지/폐광 층 범위는 허용된 미션에 한해 `content_scope`의 타입 필드(`stage_order_min/max`, `dungeon_floor_min/max`)로 표현한다. 사용자가 제공한 필드 경로, 코드, 수식은 받지 않는다.

이벤트 유형별 조건: `growth_progression`은 `growth_milestone_reached` 또는 `stage_cleared`, `dungeon_challenge`는 `dungeon_cleared`, `special_dungeon`은 `special_dungeon_progressed` 미션을 최소 하나 포함한다. 스테이지 도달은 `stage_cleared`의 `max(stage_order)`와 양의 정수 `target`, 폐광 층 도달은 `dungeon_cleared`의 `max(floor_index)`로 표현한다. 특별 던전 미션은 `progress_type` 필터를 사용하며 venue 범위는 적용된 Runtime event context가 자동으로 제한한다. 기획안은 런타임 생성 전의 `venue_id`를 보내지 않는다. 각 reward는 같은 이벤트의 mission 하나를 참조하고 `grant_on=mission_completed`로 지급한다. reward 목록이 비어 있으면 이를 명시적으로 승인된 무보상 이벤트로 취급하며 자동 기본 보상을 만들지 않는다.

### 게임 규칙 카탈로그 필수 필드

- `GameRuleset`: 규칙 버전, 게임 일 시간대(IANA 이름), 일일 초기화 시각, 진행 규칙 버전, 명령/판정 의미 버전. MVP 기본값은 `Asia/Seoul`, `00:00:00`이며 데이터 버전으로 고정한다.
- `ProgressionProfile`: 시작 상태, 모든 레벨의 누적 경험치 임계치 함수, 성공 행동/콘텐츠별 경험치 함수.
- `HeroStatProfile` / `GrowthCostProfile`: 모든 유효 레벨·강화 rank의 능력치·비용 함수, 비용 재화와 증가 효과.
- `StageProgressionProfile` / `DungeonProgressionProfile`: 순번을 몬스터·전투 스탯·XP·재화·재료 보상으로 변환하는 결정적 함수와 5슬롯 외형 매핑. 함수 종류, anchor fixture, 계수, 반올림 규칙, 수치 표현 범위를 profile version에서 함께 고정한다.
- `EconomyProfile`: 각 재화의 생성원·소비처·보유 상한 정책·기준 획득량·검증 기간.
- `ContentDefinition`: 안정 ID·유형·순번/층 번호·해금 조건·entry/clear level·선택적 시도 제한·성공 보상 참조. 일반 폐광은 제한이 없고 이벤트 특별 던전은 승인 템플릿 한도를 가질 수 있다.
- `ActionDefinition`: 성공 사실 action type, 가능한 command type, 필수 콘텐츠 종류, 발생 필드, 미션 허용 필터/측정 필드. 동적 콘텐츠 사실은 `content_order`와 적용 progression profile version을 포함.
- `RewardDefinition`: 보상 ID·item/currency/skin ID·수량 범위·지급/반복 한도·활성 버전·보유 상한/영향 평가 참조.
- `UserSegmentProfile`: 자격 predicate의 허용 연산자와 참조 필드, 데모 시작 상태/기준 행동량, fixture 버전.

자격 predicate는 목록에 등록한 비교 연산자와 타입이 지정된 데이터 필드만 참조한다. 임의 코드 실행이나 자유식은 허용하지 않는다. 세부 필드명과 수치 예시는 데이터 fixture 단계에서 채우되, 필드 의미와 제약은 이 설계의 계약을 유지한다.

## 검증·호환성

검증 순서는 구조 → 참조 → 규칙 제약 → 버전 호환성이다. 실패는 필드 경로와 코드가 있는 `ValidationIssue`로 반환한다. 구버전 승인 이벤트는 원래 참조한 카탈로그·규칙 버전으로 읽을 수 있어야 한다. 마이그레이션이 필요하면 원본을 덮어쓰지 않고 새 버전 스냅샷을 만들며, 이전 승인 설정은 재현 가능하게 보존한다.

정확한 JSON Schema draft/version, schema registry 위치, 하위 호환성 수준은 아직 확정하지 않는다. WP-10에서 `balance_policy_version`을 검증 실행·결과·승인 스냅샷에 기록해 이벤트를 같은 경제/달성 가능성 정책으로 재현한다. event schema 1.0.0에는 이 참조가 없으므로 호환 어댑터는 값을 임의로 채우지 않고 `legacy_unversioned`로 표시한다. 과거 결과는 당시 검증 증거만 재현하며 새 밸런스 기준을 통과한 것으로 취급하지 않는다. 새 정책 검증/승인은 event schema 1.1.0 설정에서 수행한다.

WP-10에서 이벤트 검증기는 동일 progression/combat/reward 프로필로 목표 달성 가능성, 유저별 보상 규모, 기준 획득량 대비 비율, 집단 총 지급량, 보유 상한 위험을 계산한다. 계산에 필요한 프로필이 없으면 추측하지 않고 `insufficient_data`를 반환한다. 기존 `pre/개발_기획안.md`의 MVP 범위는 보상 아이템 존재 확인까지이므로, 이 검증 확장은 게임 독립 완성 이후 별도 연동 작업으로 구현한다.

## 미결 사항

| 항목 | 이유 | 결정 입력 |
|---|---|---|
| 신규/복귀 세그먼트의 실측 기준 | 자격·가능성 평가의 신뢰도에 영향 | 데모용 사용자 프로필 선정 |
| 경제 수치와 임계값 | 보상 영향 경고에 영향 | 검증·밸런스 fixture |
| JSON Schema 버전/호환 정책 | API 및 배포 계약에 영향 | 서비스 런타임·배포 설계 |
| 규칙/데이터 버전 배포 중 플레이 판정 고정 방법 | 진행 중 명령의 재현성에 영향 | Runtime/API 및 배포 설계 |

## 완료 기준

- 대표 유효/무효 이벤트 설정과 게임 카탈로그 fixture가 작성된다.
- 필수 참조·범위·버전 규칙을 자동 검증 가능한 형태로 표현한다.
- 승인 결과에서 게임 데이터·규칙의 정확한 버전을 재현할 수 있다.
