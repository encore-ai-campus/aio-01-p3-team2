# 이벤트 적용 계약 설계서

> 2026-10-11 원자성 보완: 현재 로컬 단일 PostgreSQL에서 승인 결정 및 이벤트 등록은 각각 Supervisor 상태·decision·Trace·멱등 결과와 같은 transaction으로 저장해야 한다. 현재 구현은 선행 업무 commit 뒤 상태를 따로 저장하므로 이 기준을 아직 충족하지 않는다. session 공유, ACK 유실 회수, 기존 불일치의 읽기·재조정 계약은 [Workflow 수정 계획 §3.2](../기획안설계/14_Workflow_검사결과_설계보완_수정계획.md#32-승인runtime-적용의-원자성)를 따른다.

## 목적·범위

- 상태: 승인 Plan adapter와 Runtime 적용 API가 구현되어 있다. `event_schema 1.1.0`에서 이벤트 던전 층별 첫 클리어 보상과 finite/ongoing 운영을 지원한다.
- 목적: 승인된 이벤트 기획 결과를 안전한 가상 게임 설정으로 바꾸고 등록하는 경계를 정의한다.
- 상위 기준: [가상 게임 도메인 상세 설계서](../가상게임_도메인_상세설계서.md) §§5.1, 5.3–5.5
- 연결: [데이터·스키마](02_게임데이터_스키마.md), [저장소·DB](03_게임저장소_DB.md), [Runtime·API](04_게임Runtime_API.md)
- 이 문서는 기획안에서 게임으로 가는 쓰기 계약만 다룬다. 승인 권한 정책 자체는 시스템 보안 설계에 둔다.

## 계약 불변 조건

1. 승인된 `task_id` + `result_version`만 적용 대상으로 받는다.
2. 승인 당시의 `event_schema_version`, `game_ruleset_version`, `game_data_snapshot_id`를 함께 검증한다.
3. 자유 실행 코드나 미등록 콘텐츠/행동/보상 규칙은 받지 않는다.
4. 같은 승인 버전의 재요청은 같은 Runtime 이벤트를 반환한다. 같은 멱등 식별자에 다른 내용이면 충돌한다.
5. 적용은 전체 유효 또는 전체 거절로 외부에 나타나야 한다.
6. 승인 결과 내용은 적용 과정에서 임의 수정하지 않는다. 변경은 새 기획 결과 버전을 요구한다.

적용 명령의 논리 입력은 `request_id`, `task_id`, `result_version`으로 한정한다. 이벤트 내용 본문을 클라이언트가 재구성해 보내지 않는다. 적용 서비스가 Workflow/승인 저장소에서 해당 버전의 승인 증거, 검증 결과, 원본 payload, schema/ruleset/data 버전과 content digest를 조회한다. 연결된 원본을 조회할 수 없거나 승인/검증 증거가 해당 digest와 일치하지 않으면 거절한다.

현재 source adapter는 승인된 canonical Plan을 우선 조회하고, 구형 Task 결과도 호환 경로로 처리한다. canonical Plan은 승인 상태와 result version을 확인하고 선택된 snapshot을 로드한다. Planner 검증 버전 `tinyheroes-1.0.0` 및 과거 Opong snapshot은 명시적 변환/호환 경로로만 허용한다. Runtime 이벤트에는 적용에 사용한 `event_schema_version`, `game_data_snapshot_id`, `game_ruleset_version`, source digest를 기록한다.

## 매핑 흐름

`승인 결과 조회 → 승인 행위·버전 확인 → 이벤트 schema 검사 → 게임 데이터/규칙 버전 확인 → ID 참조 및 템플릿 파라미터 검증 → 기간·세그먼트·미션·보상 교차 검증 → Runtime 설정 스냅샷 생성 → 등록 → 적용 영수증 반환`

| 기획 결과 | 게임 Runtime 표현 | 검증 |
|---|---|---|
| event type | 검증 프로필 | 지원 프로필인지, 필수 미션이 있는지 |
| period | effective period | UTC, 종료 > 시작, 해당 데이터 버전에서 유효 |
| segment | eligibility rule reference | 스냅샷 시점/프로필 버전 존재 |
| mission action/goal | action & aggregation reference | 허용 조합, 콘텐츠 필터, 기간 가능성 |
| reward | immutable reward definition refs | 활성 ID, 수량/한도, mission 연결 |
| venue | template/layout/theme/difficulty refs | special_dungeon 전용, 카탈로그 호환 |
| validation evidence | event schema, ruleset, data snapshot, profile, `balance_policy_version`, result digest | 승인 대상과 동일한 입력 버전인지, 달성·경제 계산 근거가 재현되는지 |

canonical Plan의 각 층 mission은 단일 floor ID를 가진 `special_dungeon_floor_clear`로 변환한다. Runtime은 이를 `special_dungeon_progressed/floor_cleared`에 연결하고, 이벤트가 active인 동안 day 값과 관계없이 검사한다. 완료된 mission row는 다시 지급되지 않으므로 보상은 이벤트·유저·층별 최초 성공 한 번이다. 이벤트 기간 밖 행동은 이벤트가 active가 아니어서 미션을 진행시키지 않는다. ongoing 이벤트는 `end_at=null`로 저장하고 시작 이후 종료 없이 active 상태를 유지한다.

event schema 1.0.0으로 승인된 과거 결과에는 balance policy 참조를 사후 삽입하지 않는다. 해당 결과는 원래 검증 증거로만 적용할 수 있고 새 경제/달성 가능성 검증을 통과한 것으로 표시하지 않는다. 새 balance policy 검증을 요구하는 이벤트는 schema 1.1.0으로 재검증·재승인하고 모든 버전 참조를 적용 영수증에 고정한다.

적용 서비스는 이벤트 인스턴스 ID를 발급한다. `special_dungeon`인 경우 동일 Runtime 이벤트에 속한 venue 인스턴스를 만들고, `runtime_event_id`로 venue를 역참조할 수 있게 한다. 기획 결과에는 카탈로그 템플릿 참조만 두며, 아직 존재하지 않는 `venue_id`를 입력하지 않는다. `special_dungeon_progressed` ActionRecord는 이 Runtime event context에서 venue/floor를 결정한다. 따라서 미션의 `progress_type`만 기획 설정에서 필터링하고 venue 범위는 해당 Runtime 이벤트로 자동 제한한다.

## 적용 상태·응답

Workflow 승인과 Runtime 적용은 별도 상태다. 적용 작업 상태는 `received → validating → applied | rejected | retryable_failure`다. `rejected`는 승인·스키마·참조·규칙 검증 실패의 확정 결과이며 자동 재시도하지 않는다. `retryable_failure`는 조회/저장소 등 일시 장애이고, 결과가 불확실하면 `reconciling` 상태를 거쳐 기존 Runtime 이벤트/영수증 존재를 확인한 뒤 `applied` 또는 `retryable_failure`로 정리한다. `failed`처럼 재시도 가능성과 최종 여부가 모호한 단일 상태는 사용하지 않는다.

이벤트 상태는 `scheduled`, `active`, `ended`다. finite 이벤트는 `start_at <= now < end_at`에서 active이고, ongoing 이벤트는 `start_at <= now`이면 계속 active다. 미래 시작 이벤트는 scheduled다. 기술 장애로 적용 결과가 불확실하면 적용 완료로 응답하지 않고 재조정 상태를 제공한다.

적용 영수증에는 `runtime_event_id`, source task/result version, 적용된 event/data/ruleset versions, 설정 해시, 적용 시각, 최종 상태를 담는다. 아래는 논리 응답 의미이며, 실제 JSON 필드 표기·DB 키는 Runtime/API 및 DB 설계에서 이 계약에 맞춰 매핑한다.

```json
{
  "request_id": "<unique id>",
  "task_id": "<approved task>",
  "result_version": "<approved version>"
}
```

성공 응답의 적용 영수증은 `status=applied`, `runtime_event_id`, `event_status=scheduled|active`, 원본 식별자, payload digest, 네 버전 참조, 적용 시각을 반환한다. 검증 거절은 `status=rejected`, 안정된 오류 코드, 필드 경로, 운영자용 설명을 반환한다. 재시도 가능한 오류는 `status=retryable_failure|reconciling`, 동일 request ID와 조회 경로를 반환한다. 동일 source/result와 동일 digest의 재요청은 기존 영수증, 동일 식별자에 digest가 다르면 `source_version_conflict`다.

## 거절 조건

미승인/버전 불일치, 잘못된 schema, 비활성 또는 누락 ID, 지원하지 않는 action/metric 조합, 특별 던전 venue 위반, 기간 오류, 필수 검증 근거 누락은 적용을 차단한다. 같은 승인 버전을 다시 보낸 경우는 거절이 아니라 기존 적용 영수증을 반환한다. 같은 source 식별자에 다른 내용이 오면 충돌로 기록한다.

## 원자성·재처리

저장소가 단일 트랜잭션을 지원하면 설정 스냅샷·Runtime 이벤트·적용 영수증을 함께 확정한다. 외부 승인 조회와 게임 DB가 별도 경계라면 먼저 승인 스냅샷을 고정한 뒤 로컬 transaction/outbox 등의 전달 패턴을 검토한다. 재처리는 원본 승인 버전을 재검증하고, 기존 적용 존재 여부를 확인하며, 서로 다른 내용의 덮어쓰기를 금한다. 최종 기술은 DB/API 상세 및 오류복구 설계와 함께 확정한다.

## 완료 기준·미결

- 승인된/미승인/버전 불일치/중복/내용 충돌의 결과가 정의된다.
- 모든 기획 필드가 Runtime 설정으로 매핑되거나 명시적으로 거절된다.
- 부분 등록과 불명확한 성공 응답이 불가능하도록 저장·재처리 설계가 확정된다.
- 승인 증거, 적용 영수증, Runtime 이벤트 간 추적이 가능하다.

## 구현 반영 (2026-10-11)

- 기획 UI는 지원 카탈로그에서 이벤트 던전 층과 보상 아이템을 보여주며 내부 ID 입력을 요구하지 않는다. 각 선택 층은 `special_dungeon_floor_clear` 미션 한 개와 명시적 보상 연결 한 개로 제출된다.
- 승인 Plan adapter는 층 단일 ID, 층 이름, source mission ID 및 reward mission link를 Runtime 구성으로 보존한다. Runtime은 각 층 mission을 이벤트 기간 전체에서 활성화한다.
- 보상 대상 완료는 층별 mission progress를 한 번만 완료시키고 같은 트랜잭션에서 reward ledger/잔액을 갱신한다. 이후 해당 층을 다시 클리어해도 이벤트 보상은 추가 지급하지 않는다.
- finite 이벤트는 1–7일 기간을 사용한다. ongoing 이벤트는 DB의 `end_at`을 null로 보존한다. migration `013_ongoing_event_and_first_clear_missions.sql`은 기존 행을 초기화하지 않고 nullable 변경을 적용한다.
- 신규 Runtime 카탈로그는 `opong-rules-1.4.0`, `opong-data-1.4.0`, `event_schema_version=1.1.0`이다. 기존 `opong-data-1.3.0` snapshot 파일은 보존된다.
- 코드 근거: `frontend-web/src/main.js`, `backend/app/game/event_source.py`, `backend/app/game/service.py`, `backend/app/game/rules.py`, `backend/sql/013_ongoing_event_and_first_clear_missions.sql`, `demo-game/src/main.js`.
- 테스트 근거와 미완료 UX 검토는 [현재 구현 상태](../현재_구현상태.md)를 따른다.

## 선택 공간 계약 구현 (2026-10-11)

- 신규 계약 버전은 `event_schema_version=1.2.0`, `opong-rules-1.5.0`, `opong-data-1.5.0`, `opong-capabilities-1.0.3`이다. snapshot은 이벤트 특별 던전의 세 항목을 독립적인 `spaces`로 제공한다. 기존 1.3.0/1.4.0 스냅샷은 보존하고 신규 기획은 1.5.0을 사용한다.
- 기획 UI는 공간 선택과 공간별 첫 클리어 보상을 받는다. 선택된 공간 집합만 `special_dungeon_space_clear` action/mission, `venue.space_ids`, reward link로 변환한다. 화면 결과에는 사람이 읽는 공간 이름을 표시한다.
- Runtime은 적용 시 공간 ID 중복·미등록·venue/template 불일치와 mission/reward 연결을 검증한다. 공간 입장 요청은 이벤트 `venue.space_ids`와 대조하며, 미선택 공간의 직접 API 요청은 `content_locked`로 거절한다. 공간은 순서와 무관하게 각각 입장할 수 있다.
- 성공 행동은 해당 공간 mission만 진행하고 mission 완료 트랜잭션에서 보상을 한 번 지급한다. 기존 floor action은 이전 snapshot 이벤트 호환을 위해 계속 읽는다. 일반 무한 던전은 층 기반으로 유지한다.
- 공간 기획 UI 단위 E2E, backend/MCP capability 단위 검사, PostgreSQL 적용 통합 시나리오가 통과했다. 전체 결과 및 제한은 [현재 구현 상태](../현재_구현상태.md#2026-10-11-선택-공간-이벤트-구현)를 따른다.
