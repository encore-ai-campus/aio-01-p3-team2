# 게임 저장소·DB 설계서

## 문서 상태와 목적

- 상태: 논리 엔티티·원자성·중복 방지 계약 정리 완료; 가상 게임 구현 계획에서 PostgreSQL 선택, 물리 DB/키·인덱스 미확정
- 목적: 읽기 중심 게임 카탈로그와 변경되는 Runtime 상태를 분리하고, 상태 보존·일관성 요구를 정한다.
- 상위 기준: [가상 게임 도메인 상세 설계서](../가상게임_도메인_상세설계서.md) §§2, 6, 10
- 관련 설계: [데이터·스키마](02_게임데이터_스키마.md), [Runtime·API](04_게임Runtime_API.md), [이벤트 적용 계약](05_이벤트적용_계약.md)

## 저장 책임 경계

| 저장 집합 | 권위 있는 책임자 | 변경 패턴 | 최소 보존 요구 |
|---|---|---|---|
| 게임 카탈로그·규칙 | 게임 데이터 공급자/카탈로그 어댑터 | 버전별 읽기·배포 | 검증에 쓰인 과거 버전 재현 |

| 보상 기록 | 가상 게임 Runtime | 추가 전용 지급 원장 | 중복 지급 방지와 감사 근거 |

## 논리 관계

`RuntimeEventInstance`는 승인된 이벤트 설정 버전을 참조한다. `EventParticipation`은 이벤트·유저별 한 건이며 자격 스냅샷을 보유한다. `ActionRecord`는 유저·규칙/데이터 버전의 성공 행동 사실이다. `MissionProgress`는 참여·미션별 집계 상태로 행동 근거를 참조한다. `RewardRecord`는 콘텐츠 성공 또는 미션 완료 grant source·아이템 정의·수량·근거와 연결된다. 설정 문서와 판정 원장을 덮어써서 과거 기록을 바꾸지 않는다.

논리 엔티티 연결은 다음을 기준으로 한다.

```text
RuntimeEventInstance 1 ── * EventParticipation * ── 1 VirtualUser
EventParticipation 1 ── * MissionProgress 1 ── * MissionEvidence * ── 1 ActionRecord
IdempotencyRecord 1 ── 0..1 ActionAttempt 1 ── 0..1 ActionRecord
MissionProgress 0..1 ── 0..* RewardRecord * ── 1 RewardDefinition
ActionAttempt 0..1 ── 0..* RewardRecord; RewardRecord * ── 1 ItemDefinition
RewardRecord 지급은 VirtualInventory의 해당 item/currency 잔액을 갱신
```

`ActionAttempt`는 실행 허용된 유효 도전의 성공/실패와, 던전의 경우 시도권 차감 근거를 보존한다. 성공 시 연결된 `ActionRecord`가 생성되고, 실패 시 ActionRecord와 미션 증거는 생성되지 않는다. `VirtualInventory`는 유저별 아이템/재화 잔액의 권위 저장 상태이며, `RewardRecord`는 잔액 변경의 불변 원장이다. 운영자는 원장과 잔액을 함께 조회할 수 있어야 한다.

논리 고유성 제약은 물리 스키마를 만들 때 다음 기준을 구현한다.

| 기록 | 중복 방지/참조 기준 |
|---|---|
| 명령 멱등 키 | 인증 사용자 + 작업 종류/엔드포인트 범위 + `request_id` 조합이 유일하다. 저장한 payload hash가 재요청과 같으면 저장된 결과를 반환하고 다르면 충돌한다. |
| 행동 기록 | 성공한 명령의 `request_id`당 권위 행동 결과는 하나다. 파생 성장 기록은 원 `action_id` + 임계치 ID가 유일하다. |
| 미션 집계 | 행동 ID는 해당 참여/미션에 최대 한 번 반영된다. 재계산 가능한 원장 근거와 집계 버전을 보유한다. |
| 보상 지급 | `grant_source_type + source_id + RewardDefinition`을 유일 키로 삼아 같은 콘텐츠 성공/미션 완료의 재처리에서 중복 지급을 막는다. 콘텐츠 source ID는 성공 Attempt ID, 이벤트 미션 source ID는 EventParticipation ID + mission ID 조합이다. 미션에 보상 정의가 여러 개면 정의별 RewardRecord를 만든다. MVP는 반복 수령 회차가 없다. |
| 가상 인벤토리 | 유저 + item/currency ID가 한 잔액을 식별한다. MVP는 소비/차감이 없으므로 초기 seed 잔액 + 해당 유저의 RewardRecord 합과 일치해야 한다. |
| 행동 시도 | 멱등 처리된 각 유효 도전 명령은 최대 하나의 Attempt를 가진다. Attempt의 소비 결과는 원자 처리되어 재시도에서 추가 차감되지 않는다. |
| 이벤트 적용 | source `task_id` + `result_version` 조합은 한 Runtime 이벤트에만 연결된다. 내용 digest가 달라지면 멱등 재전송이 아니라 충돌이다. |

멱등 응답을 보장하려면 최종 응답 본문/결과 참조와 처리 상태를 재요청 시 다시 읽을 수 있어야 한다. 임시로 진행 중인 명령과 최종 확정 결과를 구분하며, 보존 기간은 클라이언트 재시도 범위와 운영 보존 정책을 정한 뒤 확정한다.

## 원자성·중복 방지 요구

- 같은 행동 요청의 재전송은 행동·진행도·보상을 추가로 만들지 않는다.
- 행동 시도/시도권, 성공 행동/성장, 관련 미션 진행, 완료 시 보상 원장/인벤토리 잔액 증가는 하나의 논리 처리 단위다. 도메인상 도전 실패는 유효한 결과이므로 실패 Attempt와 시도권 차감만 함께 확정한다.
- 한 처리 단위에서 생성한 원 행동, 성장 변화, 미션 집계, 보상 기록과 멱등 결과는 함께 커밋하거나 모두 롤백한다. 이미 외부 경계를 넘은 통지는 outbox/재조정으로 전달하며, 재처리는 위 고유성 제약으로 안전하게 만든다.
- 승인 이벤트 적용은 이벤트 설정 전체가 유효할 때만 외부에 등록 완료로 보인다.
- 저장 경계를 넘어 단일 트랜잭션이 불가능하면 `pending/active` 등 명시적 상태와 재조정 작업을 설계하고, 부분 적용을 성공으로 응답하지 않는다.
- 보상 원장은 지급 취소/정정이 필요한 경우 기존 행을 삭제하지 않고 연결된 보정 기록으로 남긴다. MVP에 보상 취소 UI는 포함하지 않는다.

## 기술 선택 제안과 결정 유보

기존 Workflow 저장소와 게임 카탈로그가 PostgreSQL 경로를 사용하므로 [가상 게임 구현 계획서](../가상게임_구현계획서.md)는 Runtime 핵심 상태 저장소도 PostgreSQL로 선택했다. 이 선택은 아직 코드 구현 완료를 뜻하지 않는다. 남은 설계 작업은 물리 테이블/키/인덱스, transaction 경계, 마이그레이션·seed·reset 세부다. Runtime schema는 기존 Workflow payload table과 분리한다.

JSON 파일은 정적 초기 카탈로그/seed로 사용할 수 있으나 변경되는 진행·보상 상태의 유일한 운영 저장소로 쓰려면 동시성·백업·원자성 요구를 별도로 충족해야 한다. 브라우저 로컬 저장소는 운영자/게임 클라이언트의 권위 저장소가 될 수 없다.

## 초기화·환경

- 개발용 reset은 명시적 관리자 동작이며, 사용 대상 환경과 영향을 사전에 확인한다.
- reset은 카탈로그 버전을 바꾸지 않고 데모 Runtime 상태만 초기화하는 정책을 기본안으로 둔다.
- 사용자 시연 중 자동 초기화는 금지한다. reset 결과와 실행 주체를 기록한다.
- 테스트 seed에는 버전 ID와 생성 출처를 넣는다. 실제 계정 또는 비밀값을 포함하지 않는다.
- DB 구조 마이그레이션과 게임 카탈로그/규칙 버전 배포를 별개로 관리한다. 기존 행동·보상 원장의 규칙 의미를 덮어쓰지 않고, 새 카탈로그 스냅샷은 별도 버전으로 추가한다.
- reset은 명시적인 데모 유저/이벤트 범위만 대상으로 하며, 적용 영수증·판정 원장을 지울지 보존할지는 운영 시연 추적 요구를 확인해 별도 정책으로 정한다.
- 백업·보존기간·삭제 정책은 시스템 운영 설계에서 확정한다.

| 세그먼트 자격 스냅샷 저장 방식 | 논리 요구 확정, 물리 모델 미정 |

| 데모 reset 권한·API | 미정, 운영자 UX·보안과 함께 확정 |
