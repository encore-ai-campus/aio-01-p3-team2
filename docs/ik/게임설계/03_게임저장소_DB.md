# 게임 저장소·DB 설계서

## 논리 관계

`RuntimeEventInstance`는 승인된 이벤트 설정 버전을 참조한다. `EventParticipation`은 이벤트·유저별 한 건이며 자격 스냅샷을 보유한다. `ActionRecord`는 유저·규칙/데이터 버전의 성공 행동 사실이다. `MissionProgress`는 참여·미션별 집계 상태로 행동 근거를 참조한다. `RewardRecord`는 콘텐츠 성공 또는 미션 완료 grant source·아이템 정의·수량·근거와 연결된다. 설정 문서와 판정 원장을 덮어써서 과거 기록을 바꾸지 않는다.

논리 엔티티 연결은 다음을 기준으로 한다.

```text
RuntimeEventInstance 1 ── * EventParticipation * ── 1 VirtualUser
EventParticipation 1 ── * MissionProgress 1 ── * MissionEvidence * ── 1 ActionRecord
IdempotencyRecord 1 ── 0..1 ActionAttempt 1 ── 0..1 ActionRecord
MissionProgress 0..1 ── 0..* RewardRecord * ── 1 RewardDefinition
ActionAttempt 0..1 ── 0..* RewardRecord; RewardRecord * ── 1 ItemDefinition
RewardRecord 지급은 VirtualInventory의 해당 item/currency 잔액을 갱신
```

`ActionAttempt`는 실행 허용된 유효 도전의 성공/실패와, 제한 콘텐츠의 시도권 차감 근거를 보존한다. 성공 시 연결된 `ActionRecord`가 생성되고, 실패 시 ActionRecord와 미션 증거는 생성되지 않는다. `VirtualInventory`는 유저별 아이템/재화 잔액의 권위 저장 상태다. 목표 설계에서는 지급과 소비를 공통 불변 `InventoryLedgerEntry`(delta, before/after, source type/id, profile version)로 재구성하고, 운영자는 원장과 잔액을 함께 조회한다.

스테이지/성장 규칙을 확장할 때는 최고 클리어 스테이지와 다음 사냥 위치를 유저 Runtime 상태로 보존하고, 영웅 전투 능력치와 강화 단계도 서버 권위 상태로 저장한다. 로비 강화의 재화 차감, 능력치 갱신, 성장 변경 원장은 한 논리 처리 단위로 확정한다. 자동 사냥의 각 전투는 ActionAttempt/ActionRecord와 멱등 요청에 연결해 중복 처리를 막는다. 스테이지는 단일 몬스터, 일반 던전은 파티 encounter를 사용한다. 던전 파티 구성원과 전투 순서/최종 HP는 전투 시점의 버전 카탈로그 스냅샷과 함께 Attempt payload에 기록해 재현한다. 적별 진행 상태는 다음 층이나 재시도로 이월하지 않으므로 별도 mutable enemy 테이블은 두지 않는다.

논리 고유성 제약은 물리 스키마를 만들 때 다음 기준을 구현한다.

| 기록 | 중복 방지/참조 기준 |
|---|---|
| 명령 멱등 키 | 인증 사용자 + 작업 종류/엔드포인트 범위 + `request_id` 조합이 유일하다. 저장한 payload hash가 재요청과 같으면 저장된 결과를 반환하고 다르면 충돌한다. |
| 행동 기록 | 성공한 명령의 `request_id`당 권위 행동 결과는 하나다. 파생 성장 기록은 원 `action_id` + 임계치 ID가 유일하다. |
| 미션 집계 | 행동 ID는 해당 참여/미션에 최대 한 번 반영된다. 재계산 가능한 원장 근거와 집계 버전을 보유한다. |
| 보상 지급 | 현재 구현은 `grant_source_type + source_id + RewardDefinition`을 유일 키로 삼아 한 번 지급한다. WP-10 반복 미션은 event participation + mission + `cycle_id` + reward definition을 키로 사용하고, cycle/user 한도 검사를 같은 잔액 트랜잭션에 둔다. 콘텐츠 source ID는 성공 Attempt ID다. |
| 가상 인벤토리 | 유저 + item/currency ID가 한 잔액을 식별한다. 현재 구현은 RewardRecord와 GOLD 성장 차감 기록을 합쳐 잔액을 설명한다. 목표 구현은 모든 지급/소비의 ledger delta 합과 잔액이 일치해야 한다. |
| 행동 시도 | 멱등 처리된 각 유효 도전 명령은 최대 하나의 Attempt를 가진다. Attempt의 소비 결과는 원자 처리되어 재시도에서 추가 차감되지 않는다. |
| 이벤트 적용 | source `task_id` + `result_version` 조합은 한 Runtime 이벤트에만 연결된다. 내용 digest가 달라지면 멱등 재전송이 아니라 충돌이다. |

멱등 응답을 보장하려면 최종 응답 본문/결과 참조와 처리 상태를 재요청 시 다시 읽을 수 있어야 한다. 임시로 진행 중인 명령과 최종 확정 결과를 구분하며, 보존 기간은 클라이언트 재시도 범위와 운영 보존 정책을 정한 뒤 확정한다.

## 원자성·중복 방지 요구

- 같은 행동 요청의 재전송은 행동·진행도·보상을 추가로 만들지 않는다.
- 행동 시도/시도권, 성공 행동/성장, 관련 미션 진행, 완료 시 보상 원장/인벤토리 잔액 증가는 하나의 논리 처리 단위다. 도메인상 도전 실패는 유효한 결과이므로 실패 Attempt와 시도권 차감만 함께 확정한다.
- 로비 강화는 재화 차감·영웅 능력치 증가·강화 원장을 함께 커밋하거나 모두 롤백한다. 스테이지 전투 결과와 최고 클리어/다음 사냥 위치도 같은 전투 결과의 일부로 원자 반영한다.
- 한 처리 단위에서 생성한 원 행동, 성장 변화, 미션 집계, 보상 기록과 멱등 결과는 함께 커밋하거나 모두 롤백한다. 이미 외부 경계를 넘은 통지는 outbox/재조정으로 전달하며, 재처리는 위 고유성 제약으로 안전하게 만든다.
- 승인 이벤트 적용은 이벤트 설정 전체가 유효할 때만 외부에 등록 완료로 보인다.
- 저장 경계를 넘어 단일 트랜잭션이 불가능하면 `pending/active` 등 명시적 상태와 재조정 작업을 설계하고, 부분 적용을 성공으로 응답하지 않는다.
- 보상 원장은 지급 취소/정정이 필요한 경우 기존 행을 삭제하지 않고 연결된 보정 기록으로 남긴다. MVP에 보상 취소 UI는 포함하지 않는다.

## WP-08 DB 구현 갱신

003 migration은 기존 snapshot 및 이벤트/행동 원장을 보존하는 additive 변경이다. 게임 행동은 user row 잠금과 action 트랜잭션 안에서 Attempt, ActionRecord, XP, mission, inventory, reward, 사냥 상태 및 멱등 응답을 저장한다. 성장 요청은 user row 잠금, GOLD 차감, 업그레이드 레벨, game_growth_records 및 멱등 응답을 한 트랜잭션으로 저장한다.

## WP-09 DB 구현 계약

SQL 004 migration은 위 계약을 구현한다. 폐광 진행/성공 횟수와 장기 정수 컬럼을 추가하고, 보유 스킨·상점 영수증·재화 원장을 생성한다. 기존 보상/성장 기록에서 초기 원장을 backfill한다. 상점 구매와 재화 지급/소비는 잔액, 원장, 스킨 소유/영수증을 같은 transaction에 기록한다. 로컬 DB 적용과 기존 진행 보존은 seed 스크립트를 실행한 뒤 수용 단계에서 확인해야 한다.

## 기술 선택 제안과 결정 유보

기존 Workflow 저장소와 게임 카탈로그가 PostgreSQL 경로를 사용하므로 [가상 게임 구현 계획서](../가상게임_구현계획서.md)는 Runtime 핵심 상태 저장소도 PostgreSQL로 선택했다. 이 선택은 코드와 migration으로 구현되어 있다. 백업·보존기간·경합 부하 검증은 별도 수용 항목이다. Runtime schema는 기존 Workflow payload table과 분리한다.

JSON 파일은 정적 초기 카탈로그/seed로 사용할 수 있으나 변경되는 진행·보상 상태의 유일한 운영 저장소로 쓰려면 동시성·백업·원자성 요구를 별도로 충족해야 한다. 브라우저 로컬 저장소는 운영자/게임 클라이언트의 권위 저장소가 될 수 없다.

## 초기화·환경

- 개발용 reset은 명시적 관리자 동작이며, 사용 대상 환경과 영향을 사전에 확인한다.
- reset은 카탈로그 버전을 바꾸지 않고 데모 Runtime 상태만 초기화하는 정책을 기본안으로 둔다.
- 사용자 시연 중 자동 초기화는 금지한다. reset 결과와 실행 주체를 기록한다.
- 테스트 seed에는 버전 ID와 생성 출처를 넣는다. 실제 계정 또는 비밀값을 포함하지 않는다.
- DB 구조 마이그레이션과 게임 카탈로그/규칙 버전 배포를 별개로 관리한다. 기존 행동·보상 원장의 규칙 의미를 덮어쓰지 않고, 새 카탈로그 스냅샷은 별도 버전으로 추가한다.
- reset은 명시적인 데모 유저/이벤트 범위만 대상으로 하며, 적용 영수증·판정 원장을 지울지 보존할지는 운영 시연 추적 요구를 확인해 별도 정책으로 정한다.
- 백업·보존기간·삭제 정책은 시스템 운영 설계에서 확정한다.

## 미결·완료 기준

| 결정 | 현재 상태 |
|---|---|
| Runtime DB 기술/환경 | PostgreSQL Runtime 구현 및 로컬 전용 Compose DB |
| 세그먼트 자격 스냅샷 저장 방식 | RuntimeEvent의 eligibility_snapshot JSONB로 저장 |
| 행동 원장 보존기간 | 미정, 운영/개인정보 요구와 함께 확정 |
| 데모 reset 권한·API | 로컬 운영 스크립트로 구현; API reset은 없음 |
| 멱등 결과 보존 기간 | 미정, API 재시도/운영 보존 정책과 함께 확정 |

Runtime schema는 002_game_runtime.sql과 추가 migration 003_game_combat_growth.sql로 구성한다. 003은 유저 사냥/강화 컬럼과 game_growth_records 원장을 추가한다. seed는 두 migration을 순서대로 적용하고 snapshot을 적재한다. reset은 게임 진행/이벤트/원장/요청만 비우며 Workflow와 카탈로그 snapshot은 보존한다.

일반 던전 1:N 전투는 기존 `game_action_attempts.attempt_payload` JSONB에 encounter snapshot(`enemies[]` 순서/역할/ID/이름/시각 참조/시작·최종 HP/스탯), 영웅 스냅샷, 결정적 `combat_log`, 종료 사유, 규칙·카탈로그 버전을 함께 보존한다. 한 층은 단일 Attempt와 성공 ActionRecord로 기록한다. 파티원 개별 처치는 별도 원장/보상 행을 만들지 않는다. 따라서 이 설계만으로 신규 정규화 테이블이나 DB migration은 요구하지 않는다. 구현 시 현재 payload shape/version을 확인하고 호환 가능한 버전 필드가 필요하면 API·DB 설계를 함께 갱신한다.
