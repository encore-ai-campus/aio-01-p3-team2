# 상세 설계 작성 전략 (초안)

## 문서 상태

- 상태: 임시 제안, 팀 검토 전
- 목적: 가상 게임 도메인 상세 설계서를 기준으로 그 아래 7개 세부 설계서의 범위·순서·완료 기준을 정하고, 게임 구현 계획과 설계 완료 게이트를 연결한다.
- 적용 범위: `docs/ik/` 안의 설계 문서 작업
- 상위 기준: [최상위 시스템 설계서](최상위_시스템_설계서.md)
- 문서 탐색: [IK 문서 라우터](README.md)

이 문서는 **가상 게임 도메인 상세 설계서의 하위 설계 전략**이다. 계층은 `최상위 시스템 설계서 → 가상 게임 도메인 상세 설계서 → 게임 세부 설계서 7종`이다. 여기서 말하는 7종은 시스템 전체의 하위 설계서 개수가 아니다. 게임 도메인 세부 설계와 구현 계획은 분리한다. [가상 게임 구현 계획서](가상게임_구현계획서.md)는 작업 패키지·파일 경로·수용 기준을 정하고, 물리 구현 선택과 fixture 수치는 각 패키지에서 확정한다. 전체 설계의 미세한 미결 결정이 구현 시작을 일괄 차단하지 않는다.

## 작성 원칙

1. 최상위 설계서가 시스템 목적·경계·목표 구조의 기준이다. 하위 문서는 이를 반복하지 않고 세부 계약과 선택을 결정한다.
2. 현재 확인된 구현, 목표 상태, 미결 결정을 구분한다. 미구현 기능을 완료된 것처럼 쓰지 않는다.
3. `pre/` 문서는 보존 스냅샷이다. 필요한 구간만 참고하고 수정하지 않는다.
4. 새 결정은 결정 사항, 근거, 영향받는 문서, 미결 질문을 함께 기록한다.
5. 설계 단계 계획과 구현 계획을 구분한다. 먼저 세부 설계를 완성하고, 설계 산출물·수용 기준을 기반으로 구현 작업을 산출한다.
6. 기술 선택은 요구와 운영 책임에서 도출한다. 특정 기술을 먼저 확정하지 않는다.

## 가상 게임 도메인 하위 설계서 7종

상위 [가상 게임 도메인 상세 설계서](가상게임_도메인_상세설계서.md)가 게임의 목적·경계·핵심 규칙·논리 계약을 정한다. 아래 7개 하위 문서는 이 기준을 구현 가능한 수준으로 구체화한다.

| 순서 | 하위 설계서 | 구체화할 내용 | 완료 조건 |
|---|---|---|---|
| 1 | [게임 규칙·플레이 루프 설계서](게임설계/01_게임규칙_플레이루프.md) | 스테이지·일반/특별 던전·성장 규칙, 전투 결과, 행동 생성·집계 의미 | 대표 플레이 시나리오가 규칙만으로 판정 가능 |
| 2 | [게임 데이터·스키마 설계서](게임설계/02_게임데이터_스키마.md) | 콘텐츠·아이템·행동·미션·세그먼트·경제 기준 데이터의 논리 모델, 필드·제약·버전 | 유효·무효 예제를 같은 버전 스키마로 표현 가능 |

| 4 | [게임 Runtime·API 설계서](게임설계/04_게임Runtime_API.md) | 이벤트 등록, 게임 행동 처리, 진행도 집계, 보상 기록의 API·상태 전이·멱등성 | 정상·거절·중복 요청의 결과가 구체적으로 정의됨 |
| 5 | [이벤트 적용 계약 설계서](게임설계/05_이벤트적용_계약.md) | 승인된 기획안의 게임 설정 매핑, 특별 던전 개방·제한·미션 연결, 적용 버전·원자성 | 기획안 필드와 게임 Runtime 설정 간 매핑·거절 조건이 명확 |
| 6 | [게임 화면·시연 설계서](게임설계/06_게임화면_시연.md) | 로비·스테이지·던전·특별 던전·성장 화면, 사용자 흐름·상태·연출 | 화면 행동이 Runtime 요청·결과에 대응하고 시연 흐름이 닫힘 |
| 7 | [게임 검증·밸런스 설계서](게임설계/07_게임검증_밸런스.md) | 달성 가능성, 성장 속도, 던전 입장 가능성, 보상 영향, fixture·수용 시나리오 | 대표 세그먼트와 이벤트 유형별 통과·경고·차단 근거가 재현 가능 |

이 일곱 문서는 **가상 게임 도메인에 한정**한다. 멀티 에이전트 Workflow, 전 시스템 보안·권한, CI/CD와 공통 운영 관측 등은 최상위 설계서에서 별도 시스템 설계 대상으로 관리하며 이 7개 수에 포함하지 않는다.

게임 규칙은 데이터 모델보다 먼저 의미를 정한다. 데이터·저장소 설계 이후 Runtime/API와 이벤트 적용 계약을 확정하고, 화면은 계약 및 사용자 흐름을 함께 설계한다. 게임 검증·밸런스 설계로 예제를 닫은 다음 7개 문서를 교차 검토한다. 재시도·원자성은 Runtime/API와 이벤트 적용 계약에서 정한다.

## 설계 완료 게이트와 구현 착수 기준

아래 조건은 작업 패키지를 계획하고 수용 기준을 추적하기 위한 기준이다. 물리 테이블·모든 수치·최종 에셋까지 사전에 완성해야 구현을 시작할 수 있다는 뜻은 아니다. [가상 게임 구현 계획서](가상게임_구현계획서.md)가 파일 배치와 WP 순서를 정했으며, 상세 구현 선택은 해당 WP에서 확정한다.

- 각 영역의 책임자와 권위 있는 데이터 소유자가 정해져 있다.
- 게임 규칙·행동·미션·경제 입력에 논리 모델과 대표 유효/무효 예제가 있다.
- 스키마 식별자와 데이터 버전이 모호하지 않고 승인 이벤트가 검증 근거를 고정한다.
- API 계약에 정상·거절·중복 요청의 의미와 상태 변경 결과가 있다.
- 화면의 핵심 동작이 API·Runtime 상태에 매핑된다.
- 게임 시연은 승인 전/후의 시각 차이와 플레이 중 미션·보상 상태 변화를 실제 데이터 근거로 보이고, 화면·연출 작업과 시각 QA가 구현 계획에 별도 작업으로 포함된다.
- 핵심 검증(달성 가능성, 경제 영향, 권한, 중복 처리)의 입력·출력·차단/경고 조건이 정의되어 있다.
- 상위 성공 기준마다 검증 시나리오와 구현 완료 조건이 연결되어 있다.
- 미결 결정은 해소되었거나 영향을 받는 WP의 작업으로 지정되어 있다.
- 상태 변경을 시작하기 전에는 그 패키지에 필요한 도메인 조건, 실패 의미, 원자성·멱등성 조건만 확정한다.

따라서 계획서 작성 후 전체 게임 구현 착수를 막는 설계 게이트는 없다. 승인 source 검증, 상태 변경 transaction, 고정 버전 데이터, 로컬 전용 접근 경계는 각 구현 패키지에서 해당 기능보다 먼저 확정·검증한다.

## 각 설계서의 공통 골격

1. 문서 상태·목적·범위·제외 범위
2. 상위 설계에서 상속한 기준과 관련 절
3. 현재 구현 및 재사용 근거
4. 목표 책임·흐름·상태
5. 데이터·스키마·계약·정책
6. 실패·보안·운영 고려사항
7. 결정 사항과 미결 질문
8. 설계 완료 조건과 후속 구현 작업 후보
9. 관련 `ik/` 문서 링크

공통 목차는 문서 주제에 맞게 줄일 수 있지만, 상위 기준·현재와 목표의 구분·결정 상태는 유지한다.

## 결정 기록 형식

| ID | 결정 질문 | 선택·상태 | 근거 | 영향 문서 | 결정 주체/시점 |
|---|---|---|---|---|---|
| D-001 | 가상 게임의 정체성과 규칙 데이터 기준은 무엇인가? | 방향 합의: 기존 Opong Heroes 이름·세계관 컨셉을 잇는 모바일 방치형 RPG. 규칙·성장·경제 데이터는 별도 카탈로그로 설계 | 기존 자료 중 재사용할 자산과 새로 만들 기준 데이터를 구분 | 가상 게임 도메인, 게임 규칙, 게임 데이터·스키마 | 팀장 검토 후 수치·자산 기준 확정 |

결정이 바뀌면 영향을 받는 설계서와 최상위 설계서의 미결 항목을 함께 갱신한다.

## 현재 진행 위치와 다음 작업

1. [가상 게임 도메인 상세 설계서](가상게임_도메인_상세설계서.md)는 이 7개 문서의 상위 기준이다.
2. 현재 상위 문서에는 게임 루프·행동·미션·보상·세그먼트·특별 던전 적용·검증·버전의 논리 기준이 정리되어 있다.
3. 먼저 1번 게임 규칙·플레이 루프를 하위 설계로 구체화하고, 이어 데이터/스키마, 저장소/DB, Runtime/API, 이벤트 적용 계약, 화면/시연, 검증/밸런스를 작성한다.
4. 7개 하위 설계와 구현 계획 간 추적성·상호 모순을 검토한다. 세부 물리 선택은 게임 구현 계획의 WP 안에서 닫는다. 게임 구현 계획서와 별개인 전체 시스템 통합 구현 계획은 최상위 설계서 §17에 둔다.
