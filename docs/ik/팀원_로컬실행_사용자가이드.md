# 팀원 로컬 실행·사용자 가이드

작성: 2026-10-12. 대상: Windows, PowerShell 7, `main` 브랜치. 최초 설치·수동 사용자 확인을 위한 절차다. AWS 배포 없이 실행한다. 진행 중인 Linux CI 변경과 실제 AWS 배포 완료를 의미하지 않는다.

구현 근거: [현재 구현 상태](현재_구현상태.md), [통합 프론트 구조](기획안설계/21_기획안프론트_통합구현.md), [운영 이미지 검증](검증산출물/2026-10-12_운영이미지_로컬검증.md). 이 가이드는 기존 script·설정·화면과 대조했으며, 이번 문서 작성에서 새 PC의 전체 실행 시험을 수행하지는 않았다.

## 1. 실행 구조와 기본 모드

| 구성 | 로컬 주소/데이터 |
|---|---|
| 기획안 프론트 | `http://127.0.0.1:5177` — 일반·시험 API를 하나의 화면에서 사용 |
| 게임 프론트 | `http://127.0.0.1:5173` |
| 일반 Backend | `http://127.0.0.1:8004` |
| 일반 MCP | `http://127.0.0.1:8010/mcp` |
| 시험 Backend / MCP | `8013` / `8014` — 복구 시연을 사용할 때 시작 |
| PostgreSQL | `127.0.0.1:5434`, Compose project `ikonly-test` |
| 일반 사용자 데이터 | `eventquest_test` DB |
| 오류 시험 데이터 | `eventquest_fault_test` DB |
| 자동 검증 데이터 | `eventquest_auto_test` DB — 검증 wrapper가 준비 |

DB 서버는 하나지만 일반·오류 시험·자동 검증 DB를 구분한다. 위 DB 이름은 **로컬 실행용**이다. AWS의 DB/role 구성과 혼동하지 않는다. 사용자 진행 기록은 각 PC에 저장되며 팀장의 기존 DB·게임 진행 상태를 내려받지 않는다.

기본 모드는 **실제 PostgreSQL·실제 MCP·결정적 기획 생성**이다. LLM은 호출하지 않는다. 따라서 빠르게 생성되는 것이 실제 LLM 성공의 증거는 아니다. 실제 OpenAI 호출은 §6에서 별도로 설정한다. 가상 게임은 같은 일반 Backend의 API로 진행·보상을 DB에 저장한다.

## 2. 최초 설치

필요 도구: Git, Python 3.11, Node.js 22, pnpm 10.33.0, PowerShell 7(`pwsh`), 실행 중인 Docker Desktop(Linux containers), Edge 또는 Chrome.

새 디렉터리에 받는다. 이미 작업 중인 checkout이 있다면 변경을 보존하고 별도 디렉터리를 사용한다.

```powershell
git clone --branch main https://github.com/ik-e/multi-agent-autohealing.git team2-ikonly
Set-Location team2-ikonly
git status --short
py -3.11 -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt -r requirements-dev.txt
pnpm --dir frontend-web install --frozen-lockfile
pnpm --dir demo-game install --frozen-lockfile
```

pnpm이 없다면 `npm install --global pnpm@10.33.0`으로 설치한다. 각 native 명령의 종료 코드가 0인지 확인하고 실패한 단계에서 멈춘다. Windows 로컬 의존성 설치와 Linux 운영 이미지의 hash lock 설치는 별개다.

### 2.1 PostgreSQL과 개인 설정 파일

아래는 **처음 한 번** 실행한다. `backend/.env.team-local`이 이미 있으면 덮어쓰지 않는다. 5434를 사용하는 기존 서버가 있으면 중단하지 말고 별도 PC/환경에서 진행한다. 기존 `ikonly-test` Compose 환경은 동일 비밀번호와 설정을 재사용해야 한다.

```powershell
if (Test-Path backend/.env.team-local) { throw '기존 개인 설정 파일을 재사용하세요.' }
if (Get-NetTCPConnection -LocalPort 5434 -State Listen -ErrorAction SilentlyContinue) {
    throw '5434 포트가 사용 중입니다. 기존 DB를 보존하세요.'
}
$teamDbPassword = backend/.venv/Scripts/python.exe -c "import secrets; print(secrets.token_hex(24))"
$env:POSTGRES_DB = 'eventquest_test'
$env:POSTGRES_USER = 'eventquest_test'
$env:POSTGRES_PASSWORD = $teamDbPassword
$env:POSTGRES_PORT = '5434'
docker compose -p ikonly-test -f infra/compose.yml up -d --wait
if ($LASTEXITCODE -ne 0) { throw 'PostgreSQL 시작 실패: 설정 파일 생성 전에 해결하세요.' }
$teamRecordKey = backend/.venv/Scripts/python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
@"
DEPLOYMENT_MODE=local
DATABASE_URL=postgresql+psycopg://eventquest_test:${teamDbPassword}@127.0.0.1:5434/eventquest_test
MCP_DATABASE_URL=postgresql+psycopg://eventquest_test:${teamDbPassword}@127.0.0.1:5434/eventquest_test
MCP_HOST=127.0.0.1
MCP_PORT=8010
MCP_GAME_ID=tiny_heroes
MCP_URL=http://127.0.0.1:8010/mcp
WORKFLOW_ENGINE=agent_mcp
CANONICAL_PLANNING_MODE=deterministic
ENABLE_FAULT_INJECTION=false
OPERATOR_ACTOR_ID=liveops01
APPROVED_ACTOR_IDS=liveops01
APP_ALLOWED_ORIGINS=http://127.0.0.1:5177,http://localhost:5177,http://127.0.0.1:5173,http://localhost:5173
LLM_RECORD_ENCRYPTION_KEY=${teamRecordKey}
"@ | Set-Content backend/.env.team-local -Encoding utf8NoBOM
Remove-Item Env:POSTGRES_PASSWORD
Remove-Variable teamDbPassword, teamRecordKey
```

개인 설정 파일은 Git 제외 대상이다. 비밀번호와 암호화 키를 공유·커밋하거나 터미널 출력으로 제출하지 않는다. 저장된 암호화 원문을 읽으려면 동일한 암호화 키를 유지해야 한다. DB만 유지하고 키를 새로 만들지 않는다.

### 2.2 규칙 카탈로그·게임·정책 준비

저장소 루트에서 실행한다. `.env.team-local`을 명시적으로 읽고, 해당 URL의 DB에만 카탈로그와 게임 migration/초기 데이터를 적용한다. seed는 기존 플레이 진행을 리셋하지 않는다. 기존 카탈로그가 현재 초기값과 다르면 자동 덮어쓰기 대신 오류가 난다.

```powershell
backend/.venv/Scripts/python.exe -c "from dotenv import load_dotenv; load_dotenv('backend/.env.team-local', override=True); import os; from backend.scripts.apply_game_data_catalog import apply_catalog; from backend.scripts.seed_game_runtime import seed; apply_catalog(os.environ['DATABASE_URL']); seed(os.environ['DATABASE_URL']); from backend.app.services.recovery_policy import list_policies; list_policies(); print('로컬 DB/게임/정책 준비 완료')"
```

명령이 실패하면 다음 서버를 시작하기 전에 해결한다. `DEPLOYMENT_MODE=local`의 새 DB에 정책 최초 등록을 수행하며, 기존 활성 정책을 강제로 교체하지 않는다.

## 3. 서버 실행

모든 명령은 저장소 루트에서 시작한다. 일반 MCP와 API, 게임 프론트는 각각 별도 터미널에서 실행한다. 기획안 프론트와 시험 서버는 기존 관리 script로 시작한다. DB 외 서버는 Docker로 실행할 필요가 없다.

**터미널 A — 일반 MCP**

```powershell
backend/.venv/Scripts/python.exe -c "from dotenv import load_dotenv; load_dotenv('backend/.env.team-local', override=True); import runpy; runpy.run_module('mcp_server.server', run_name='__main__')"
```

**터미널 B — 일반 Backend**

```powershell
backend/.venv/Scripts/python.exe -c "from dotenv import load_dotenv; load_dotenv('backend/.env.team-local', override=True); import uvicorn; uvicorn.run('backend.app.main:app', host='127.0.0.1', port=8004, proxy_headers=False)"
```

**터미널 C — 시험 서버와 통합 기획안 프론트**

```powershell
pwsh -NoProfile -File infra/fault-lab-local.ps1
pwsh -NoProfile -File infra/planning-ui-local.ps1
```

시험 script는 `ikonly-test-postgres-1`의 소유권과 로컬 DB를 확인하고 8013/8014를 시작한다. 기획안 프론트는 5177 하나다. 오류 시험을 하지 않으면 시험 script를 생략할 수 있지만 `복구 시연` 화면은 연결 필요로 표시된다.

**터미널 D — 게임 프론트**

```powershell
$env:BACKEND_BASE_URL = 'http://127.0.0.1:8004'
pnpm --dir demo-game dev
```

브라우저에서 **기획안 `http://127.0.0.1:5177`**, **게임 `http://127.0.0.1:5173`**을 연다. 주소의 localhost/127.0.0.1을 임의로 섞지 않으면 출처 문제를 줄일 수 있다.

연결 확인:

```powershell
Invoke-RestMethod http://127.0.0.1:8004/health/ready
Invoke-RestMethod http://127.0.0.1:8004/api/game/state | Select-Object -ExpandProperty versions
Invoke-RestMethod http://127.0.0.1:8013/api/test/fault-status
```

일반 readiness가 `ready`, 게임 version 정보가 반환되고, 시험 상태가 `CLEAN`인지 확인한다. MCP의 `/health/ready`만 성공한다고 실제 도구 조회까지 검증된 것은 아니다. 기획 처리의 MCP 근거/Trace도 확인한다.

## 4. 게임 사용법

1. **로비:** 원정대와 현재 재화·레벨을 확인한다. 각 콘텐츠 버튼 또는 탭으로 이동한다.
2. **스테이지:** `다음 구역 돌파`를 선택하면 승리 후 자동 전진한다. 패배하면 진행 결과를 확인하고 성장 후 다시 도전한다. `최고 구역 자동 사냥`은 이미 도달한 구역을 반복해 재화를 모은다. `사냥 일시 정지`는 현재 전투 종료 후 멈춘다.
3. **성장:** 골드 등 화면에 표시된 비용을 지불해 공격력·최대 HP 등의 능력치를 강화한다. 강화 후 다음 비용과 스탯 변화를 확인한다. 레벨/경험치와 강화 단계는 별도다.
4. **일반 던전:** `다음 층 돌파` 또는 `최고 층 반복 도전`을 선택한다. 다수 몬스터/보스 전투와 서버 확정 결과를 확인한다.
5. **보관함·상점:** 재화와 소유 스킨을 확인한다. 상점에서 가격을 확인해 스킨을 교환하고, 보관함에서 장착·해제한다. 구매한 스킨은 상점에 보유 중으로 표시된다.
6. **월광 균열:** §5에서 승인·등록한 이벤트를 불러와 선택된 특별 공간에 입장한다. 선택하지 않은 공간이 열린 것으로 표시되면 이벤트 선택과 등록 결과를 확인한다.
7. **저장 확인:** 전투/성장 완료 후 새로고침해 재화·스탯·진행이 유지되는지 본다. 전투 연출 자체와 DB에 확정된 결과는 구분한다.

`로컬 특별 던전 열기`는 fixture 시연이다. 기획안이 실제로 연결되었는지 확인할 때는 이 버튼 대신 승인한 이벤트를 사용한다. 게임 초기화는 사용자 진행 데이터를 지우므로 기본 절차에 포함하지 않는다.

## 5. 기획안 생성→승인→게임 적용

1. **기획안 만들기:** 목표, 신규/복귀 대상, 기간 한정/상시 운영, 기간, 기대 지표를 입력한다.
2. 특별 공간 3개 중 사용할 공간을 체크하고 **선택한 공간마다 보상 아이템·수량**을 지정한다. 처음에는 공간 1개와 골드 10 등 작은 보상으로 확인한다. 콘텐츠 ID를 외워서 입력하지 않는다.
3. **기획안 검증 시작:** `진행 기록`에서 실제 처리 노드와 상태를 확인한다. 기본 모드는 결정적 생성이므로 짧게 끝날 수 있다. 필요한 세부정보·전체 Trace를 펼쳐 MCP 근거, 검증, Supervisor 전이·복구 결정을 본다.
4. 결과의 게임 규칙 검증, 보상/경제 영향 근거, 미지원 또는 개발 필요 요소를 확인한다. 근거 부족은 임의 성공 추정으로 해석하지 않는다. 안전 중단·검증 실패 결과는 승인 가능한 정상 결과가 아니다.
5. **승인 후 Runtime 등록 준비 → 가상 게임에 이벤트 등록:** 승인과 실제 게임 반영은 서로 다른 단계다. `Runtime 이벤트 등록 완료`를 확인한다. 이미 등록했다면 Task ID로 중복 등록할 필요가 없다.
6. 게임을 새로고침하거나 게임의 이벤트 목록/선택 UI로 해당 이벤트를 선택한다. 승인한 공간만 개방되는지 확인하고 특별 공간을 클리어한다.
7. 이벤트가 유효한 기간에 조건을 달성하면 미션 보상이 기록된다. **공간별 첫 클리어 보상은 한 번만** 지급되어야 한다. 재도전 보상과 일반 전투 보상이 존재하면 이벤트 최초 보상과 구분해 확인한다.
8. 기획안 `진행 기록`의 이벤트 진행 현황을 새로고침해 미션·지급 기록과 게임의 보관함/재화를 함께 비교한다. `운영 로그`에서 Workflow ID나 기획 목표로 기록을 찾는다.

이 브랜치는 개인별 단일 가상 유저를 사용하는 로컬 시연이다. 대상 세그먼트·입장 레벨·난이도가 현재 가상 유저와 다르면 달성 가능성이 달라진다. 이벤트가 등록됐다는 사실만으로 모든 공간에 즉시 입장하거나 승리할 수 있는 것은 아니다.

### 5.1 복구 정책·오류 시연

- **복구 정책:** 오류 코드별 대응·최대 시도를 확인한다. 수정은 `초안 저장 → 검증 → 변경 미리보기 → 검증 후 활성화` 순서다. 기획 실행 전 활성 정책의 계약 오류가 없는지 확인한다. 기존 버전과 감사 기록은 보존한다.
- **복구 시연:** 격리 환경 `연결됨/CLEAN`을 확인하고 고정 그래프에서 위치, 오류 원인, 패턴·정책 profile을 선택한 뒤 실행한다. 처음에는 Planner 출력 오류와 일회성 오류, 재시도 허용 profile로 확인할 수 있다.
- **판정:** `PASS`는 기대한 정책 대응과 실제 결과가 일치했다는 뜻이다. 기대가 안전 종료이면 PASS여도 복구 완료는 아니다. 예상/실제 대응, 재시도, 최종 상태, Trace를 함께 읽는다.
- **종료:** `COMPLETED` 뒤 격리 환경이 `CLEAN`으로 돌아오는지 확인한다. `FAIL/INCONCLUSIVE/BUSY/DIRTY`이면 원인과 로그를 먼저 확인하고 기록 삭제·DB 초기화로 숨기지 않는다. 일반 게임 DB와 시험 DB의 분리를 유지한다.

## 6. 실제 LLM을 사용할 때

일반 Backend만 Ctrl+C로 종료한다. 개인 `backend/.env.team-local`에 아래 필드를 설정한 뒤 §3 터미널 B 명령으로 재시작한다. 시험 서버는 결정적 모드를 유지한다.

```dotenv
WORKFLOW_ENGINE=agent_live
CANONICAL_PLANNING_MODE=live
OPENAI_API_KEY=<본인의 키>
OPENAI_MODEL=<사용 가능한 모델>
LLM_MAX_INPUT_TOKENS=<양의 정수 한도>
LLM_MAX_OUTPUT_TOKENS=<양의 정수 한도>
LLM_MAX_COST_USD=<실행 비용 한도>
LLM_INPUT_USD_PER_MILLION=<모델의 입력 토큰 단가>
LLM_OUTPUT_USD_PER_MILLION=<모델의 출력 토큰 단가>
LLM_PRICING_VERSION=<단가 확인 날짜와 모델을 식별하는 값>
LLM_COST_CURRENCY=USD
```

각 placeholder를 실제 값으로 바꾸고 모델의 현재 단가와 허용 출력량을 확인한다. 단가를 0이나 임의 숫자로 채워 비용 제한을 우회하지 않는다. 처음에는 기획안 하나만 실행하고 화면의 사용량·암호화 원문 저장·비용 기록을 확인한다. readiness 성공이 키 인증·실제 LLM 호출 성공을 보장하지 않는다. 비용이 발생하며 실제 호출 실패는 진행 기록에서 확인한다. 키를 문서·스크린샷·Git에 올리지 않는다.

## 7. 자동 검사와 종료·재실행

기본 core 검사는 DB·AWS·유료 LLM 없이 실행한다.

```powershell
pwsh -NoProfile -File infra/test-local.ps1 -Profile core
```

추가 PostgreSQL·브라우저 검사는 별도 자동 검증 DB `eventquest_auto_test`를 사용한다. `infra/test-local.ps1`, `infra/e2e-local.ps1`, `infra/verify-local.ps1`은 기존 격리 wrapper다. `verify-local.ps1`의 PostgreSQL 단계는 루트 `.venv`의 Ruff 실행기도 요구하므로 최초 설치에서는 `py -3.11 -m venv .venv`와 `.venv/Scripts/python.exe -m pip install -r requirements-dev.txt`를 추가해야 한다. 브라우저 E2E를 실행하려면 `pnpm --dir frontend-web exec playwright install chromium`도 필요하다. 기본 수동 사용에는 필요하지 않다. 외부 실호출 시험은 별도 허용 없이 실행하지 않는다.

서버 종료:

```powershell
pwsh -NoProfile -File infra/planning-ui-local.ps1 -Stop
pwsh -NoProfile -File infra/fault-lab-local.ps1 -Stop
```

일반 Backend/MCP/게임 프론트는 각각 실행한 터미널에서 Ctrl+C로 종료한다. 시험 서버 종료는 환경이 CLEAN이어야 한다. DB는 데이터를 유지한 채 `docker compose -p ikonly-test -f infra/compose.yml stop`으로 멈춘다. `down --volumes`는 기본 종료 절차로 사용하지 않는다.

DB 재시작은 `docker compose -p ikonly-test -f infra/compose.yml start --wait`를 사용한다. 이후 §3을 반복한다. 최초 설치의 임의 비밀번호 생성·설정 파일 생성은 반복하지 않는다. 다른 PowerShell 세션에서 `up`을 다시 사용하려면 기존 설정 파일의 비밀번호와 동일한 Compose 환경을 먼저 구성해야 한다.

| 증상 | 먼저 확인할 항목 |
|---|---|
| 포트 사용 중 / state file 존재 | 기존 서버를 보존하고 해당 script의 `-Stop`으로 본인이 시작한 서버만 종료 |
| 기획이 즉시 완료 | deterministic 모드 여부. DB/MCP 연결과 LLM 호출 여부는 별도로 확인 |
| 입력값 확인 / 안전 중단 | 필드별 오류와 전체 Trace, 활성 정책, MCP 연결, live 설정·예산 확인 |
| 복구 시연 연결 필요 | 8013/8014 서버와 `eventquest_fault_test`, 5177의 시험 proxy 확인 |
| 게임 데이터/이벤트가 안 보임 | 게임 proxy가 8004인지, 등록 완료·선택 이벤트·기간·입장 조건 확인 |
| 새 PC에서 DB 접속 거부 | Docker Desktop, 5434 매핑, 개인 설정 URL과 기존 DB 비밀번호 확인 |

팀에 공유할 때는 `git rev-parse HEAD` 결과, 실행 모드, 재현 절차, 예상/실제 결과, 비밀값을 제외한 오류 코드·Workflow ID를 함께 전달한다.
