## 1. 결정과 목적

- 고정 상황 주입 시험의 137 PASS와 정상화 51/51은 그대로 보존한다. 실제 LLM 시험을 섞어 기존 지표를 재계산하지 않는다.
- 추가 시험은 실제 Planner/Critic 응답을 검증하고, 일시 오류 뒤 실제 재호출·수정·재검증을 거쳐 최종 기획안이 전달되는지 증명한다.
- 모든 오류를 성공으로 만들지 않는다. 보안/권한 위반, 복구 금지 조건, 지속 장애 및 한도 초과는 기존 정책대로 종료한다. 복구율을 높이려고 정책/원래 요청을 완화하지 않는다.
- Supervisor가 상태·전이·ID·정책 결정을 소유한다. LLM은 기존 역할의 설명·판정 계약을 지키며 게임 설정이나 고정 요청을 임의 변경하지 않는다.
- 문서 작업은 `docs/ik`만 사용하며 `pre`와 사전 명세는 보존한다. 결정 → 시험 계약 → 실행 ID → 증빙 → 현재 구현 상태를 연결한다.

## 2. 이번 시험 결과에 따른 보완

| 항목 | 처리 / 검사 |
|---|---|
| 알려진 Trace 메타데이터 | 오류 코드 없는 `llm.usage_recorded`, `candidate_saved`를 `observations`/TRACE_METADATA로 구분. 원본 Trace 유지, 그래프 단계로 억지 매핑하지 않음 |
| 실제 누락 감지 | 알 수 없는 이벤트는 계속 UNMAPPED_EVENT, 알려진 메타데이터라도 error_code가 있으면 오류 경고 유지. 중요 오류를 숨기지 않음 |
| UI 설명 | 보조 관측 정보 별도 펼침. FAILED를 작업 실패 종료로 설명하고 시험 PASS/FAIL과 별도라고 명시 |
| 과거 결과 | 기존 137개/준비 FAIL/warnings/화면 증빙은 재작성하지 않음. 후속 새 실행 ID로 보완 효과를 기록 |

수정 범위는 runner 판정의 비핵심 관측 분류와 UI 설명이다. 오류 대응 정책·재시도 한도·Supervisor 상태 전이를 변경하지 않는다.

## 3. 시험 실행 경계

기존 `/api/test/fault-runs`와 시험실은 결정적 adapter 전용이다. 이 보호 조건을 해제해 일반 요청이나 전체 137개를 실호출로 전환하지 않는다. **명시적으로 실행하는 별도 로컬 검증 경로**에서 실제 canonical Planner/Critic, 기존 서비스, 전용 시험 DB와 실제 MCP를 연결한다.

실행 경로는 다음 조건을 갖춰야 한다.

1. 로컬 전용 시험 DB/소유권, 환경 CLEAN, 원래 정책과 게임 snapshot 확인. 사용자 DB 초기화 및 게임 승인/적용 금지.
2. 실제 LLM 사용이 명시된 실행 옵션, 사례 whitelist, 순차 worker 1. 요청 본문으로 키/모델/DB URL/운영자 identity 선택 금지.
3. 실제 model, prompt/schema version/digest, policy version/hash, fixture 및 주입 위치/횟수와 코드 digest 기록.
4. 기존 workflow별 호출/입력·출력 token/cost/deadline 제한과 별도 시험 전체 비용 상한. 실제 usage 없는 비용은 계산 불가로 처리하고 무한 재실행 금지.
5. 키/암호화 설정 존재 확인 후 실제 유효성 확인. 프롬프트·응답 원문은 기존 암호화 DB 저장, 공개 보고서에는 시크릿/원문 복사 금지.
6. 주입 전 실제 provider 응답과 주입 후 변형·검출 증거를 구분. 정책이 실제 LLM을 다시 호출했다는 invocation/usage/Trace 증거 필요.
7. 완료·실패 시 원래 정책/CLEAN 복원. 복원 실패는 DIRTY 및 다음 사례 중지. 종료된 Workflow의 임의 재개 금지.

`backend/.env`의 키·모델·토큰/비용/가격 version·암호화 설정은 2026-10-11 존재를 확인했다. **존재 확인은 API 키 유효성·가격 설정 정확성·실호출 통과 증거가 아니다.** 비밀값은 기록하지 않는다.

## 4. 순서와 사례

| 단계 | 사례 | 독립 완료 기준 |
|---|---|---|
| L1 실제 정상 기획 | 단일 공간/재화, 복수 공간/보상 연결, 미지원 요구의 개발 필요 결과. 각 3회 | 지원 요구는 승인 대기·근거/형식/게임 규칙 통과. 미지원은 개발 필요 표시·Runtime 차단. 원래 목적/대상/기간/공간/연결 보존 |
| L2 실제 LLM 복구 | 첫 응답 형식 오류, 수정 가능한 설명 불일치, 첫 호출 timeout 상황. 성공/수정 한도 경계 대표 | 실제 호출 후 주입 또는 호출 경계 예외 → 실제 검출 → 고정 정책 결정 → 실제 재호출/수정 → 재검증 → 유효한 최종 결과 |
| L3 실제 통신 장애 | 격리 MCP 통신의 연결 거절·지연, 제한 안에서 정상 통신으로 복귀. 지속 실패 대조 포함 | 실제 transport 실패 감지와 분류, 한도 안의 정상 통신 및 다음 단계 진행. 지속 실패는 종료, 서비스 복구 후 새 정상 요청 |
| L4 Edge E2E | L1/L2 결과와 진행·정책·로그·최종 기획안. 정상화 및 종료 대표 | 실제 실행/보고서/DB와 UI의 단계·오류·횟수·근거·결과 일치. 저장 결과 조회·새로고침은 실호출 재실행 없음 |

L1의 실제 지원 여부와 수치는 current capability/게임 규칙에서 정한다. 과거 Task fixture를 canonical 실제 LLM 검증으로 대신하지 않는다. L2의 상황 주입은 실제 provider 장애 유발과 구분한다. L3는 일시 시험 프로세스/통신 경계를 사용하고 기존 사용자 MCP/공유 PostgreSQL 컨테이너를 중단하지 않는다. 추가 서버는 시험 동안만 소유·종료 관리하며 프런트를 상시 중복 실행하지 않는다.

## 5. 평가·기록과 동기화

- 합격 기준: 실제 생성 여부, 역할 계약, 원래 요청 보존, 게임 규칙·계산 가능한 경제 근거, 정상화 후 최종 결과, 금지 부작용 0, 정책 원복.
- 기획 수정/retry/fallback/ACK 재조정을 별도 집계. 실제 LLM 호출·token·비용·latency·수정 횟수와 수동 개입을 기록한다.
- 정상화율의 모집단과 안전 종료/입력 차단/finding 제외 기준을 사전 확정. 작은 실호출 표본을 보편 성공률로 표현하지 않는다.
- 결과는 `docs/ik/검증산출물/`에 별도 실호출 결과보고서로 추가하고 본 계획, 결과 라우터, `현재_구현상태.md`와 연결한다. 기존 137개 보고서는 당시 결과를 유지한다.
- 필요한 실행 경로/검사 코드가 아직 없는 부분은 준비 예정으로 기록하며 완료로 표시하지 않는다. 설정·계약·실행 방법이 바뀌면 관련 문서도 같은 작업에서 갱신한다.
