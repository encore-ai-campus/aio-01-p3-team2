# 이벤트 던전 층별 미션·보상 계약 변경 작업

## 목적과 상태

- 문서 종류: 계약 변경 및 구현 추적 기록
- 상태: 사용자 합의 규칙을 코드와 설계 문서에 반영함. 구현 사실·검증 상태는 아래 구현 반영 및 현재 구현 상태 문서를 참조
- 적용 범위: 기획안 입력 계약, 승인 Plan의 Runtime 변환, 가상 게임 이벤트 진행·보상
- 기준: [기획안·게임 기능 계약](01_기획안_게임기능_계약_설계.md), [Runtime Capability·MCP 계약](10_RuntimeCapability_MCP_계약.md), [게임 이벤트 적용 계약](../게임설계/05_이벤트적용_계약.md), [가상 게임 구현 계획](../가상게임_구현계획서.md)
- 현재 구현 사실: [현재 구현 상태](../현재_구현상태.md)

아래의 초기 변경 기준과 수용 기준은 결정 근거로 보존한다. 구현 반영 내역은 [게임 이벤트 적용 계약](../게임설계/05_이벤트적용_계약.md#구현-반영-2026-10-11)과 [현재 구현 상태](../현재_구현상태.md#2026-10-11-이벤트-던전-층별-기획보상-연결)에서 확인한다. 보존 자료인 `pre/`는 수정하지 않았다.

## 합의된 제품 규칙

1. 사용자 기획 대상은 데모 게임의 이벤트 던전이다. 지원 장소가 하나인 동안 사용자가 임의의 장소나 콘텐츠 ID를 입력하지 않는다.
2. 이벤트 던전 안에서 발생하는 층 클리어 행동만 이벤트 미션으로 사용한다.
3. 각 보상 대상 층은 별도 미션으로 표현하고, 해당 층 미션에 그 층 보상을 연결한다.
4. 모든 층 미션은 이벤트 유효 기간 전체에서 활성화한다. `Day 1`, `Day 2`와 같이 미션을 날짜별로 순차 활성화하지 않는다.
5. 한 사용자가 이벤트 기간에 특정 층을 처음 클리어하면 그 층의 미션을 완료하고 보상을 한 번 지급한다. 이벤트 시작 전의 과거 클리어는 이 이벤트의 보상을 받은 것으로 간주하지 않는다.
6. 같은 이벤트에서 같은 층을 다시 클리어해도 해당 층 보상을 다시 지급하지 않는다. 이벤트 종료 후의 행동도 진행도와 보상에 반영하지 않는다.
7. 콘텐츠 ID, action ID, mission ID, reward ID, 이벤트 던전 템플릿 및 게임 데이터 버전은 시스템이 카탈로그에서 생성·연결한다. 사용자는 이름과 조건으로 기획한다.

예시:

| 사용자에게 보이는 미션 | 이벤트 기간 중 첫 클리어 보상 |
|---|---|
| 월광 균열 1층 클리어 | 왕국 골드 100개 |
| 월광 균열 2층 클리어 | 회복 포션 2개 |
| 월광 균열 3층 클리어 | 월광 파편 5개 |

층 이름과 층 목록은 고정 문자열로 복제하지 않고 선택된 이벤트 던전의 버전 고정 카탈로그에서 제공한다. 지원되지 않는 층·행동·보상 조합은 조용히 보정하지 않고 개발 필요 또는 데이터 필요로 반환한다.

## 현재 구현과 차이

| 영역 | 현재 확인된 동작 | 변경 필요 |
|---|---|---|
| 기획 UI | 미션 행동 1개, 콘텐츠 ID 텍스트 입력 1개, 보상 1개를 제출한다. 기본 콘텐츠 ID는 `stage_01`이다. | 이벤트 던전·층 이름 선택, 층별 미션/보상 행 추가·삭제, 임의 ID 입력 제거 |
| Brief 계약 | `actions[]`, `rewards[]`, `mission_reward_links[]`를 지원한다. | 특별 던전 사용자 입력 규칙과 여러 층 행의 생성·참조 규칙을 명문화한다. |
| 특별 던전 동작 매핑 | `special_dungeon_floor_clear`를 `special_dungeon_progressed/floor_cleared`로 연결한다. 개별 특별 던전 층 ID를 Runtime 미션 대상에 넣을 수 있다. | 이 동작만 이벤트 미션으로 노출하고 venue/template 및 floor 카탈로그와의 관계를 검증한다. |
| Plan → Runtime adapter | 각 Plan mission을 배열 순서대로 Day 1부터 배정한다. 각 mission의 `content_scope`에서 첫 content ID만 Runtime에 전달한다. | 날짜별 배정을 제거하고 층 범위/복수 콘텐츠를 손실 없이 전달하거나, 층별 단일 ID로 계약을 제한한다. |
| Runtime 진행 | 현재 이벤트 날짜와 mission day가 같은 경우에만 진행도를 올린다. 층 ID, 행동 유형, floor-cleared 신호를 확인한다. | 이벤트 활성 기간 전체에서 모든 층 미션을 평가한다. 동일 이벤트·유저·층의 최초 성공만 미션 완료/보상 지급으로 확정한다. |
| 보상 연결 | 미션 완료와 연결된 보상 지급 경로가 있으며 Runtime은 grant 원장·멱등 요청을 저장한다. | 같은 트랜잭션에서 층 미션 완료, 단일 지급, 보상 원장, 진행 응답을 확정하고 재시도·동시 행동에서도 중복 지급을 막는다. |
| 장소 전달 | 현재 승인 Plan의 Runtime 변환은 venue 선택을 이벤트 payload에 보존하지 않는다. 특별 던전 미션 행동으로 이벤트 타입을 판별한다. | 단일 이벤트 던전을 제품 기본값으로 고정할지, 선택된 template을 적용 payload에 보존할지 결정한다. 사용자에게 장소와 콘텐츠를 중복 입력시키지 않는다. |

현재 코드 경로의 핵심 근거는 [기획 입력 UI](../../../frontend-web/src/main.js), [Brief 스키마](../../../backend/app/schemas/planning.py), [특별 던전 행동 매핑](../../../backend/app/game/catalog.py), [Plan→Runtime 변환](../../../backend/app/game/event_source.py), [Runtime 이벤트·진행 처리](../../../backend/app/game/service.py)다. 실제 파일 위치·동작은 구현 착수 시 다시 확인한다.

## 설계 변경 작업

### A. 사용자 입력 계약과 화면

- 이벤트 던전을 제품의 유일한 이벤트 공간으로 고정한다. 카탈로그에 던전 템플릿이 하나라면 폼에 불필요한 자유 장소 입력을 두지 않는다.
- 사용자에게 이벤트 목표, 대상 유저, finite/ongoing 운영 방식 및 유효 기간, 층별 클리어 조건, 층별 보상, 기대 지표를 받는다.
- 층 선택은 이름·순서·필요 레벨 등 의미 있는 정보를 표시하는 카탈로그 선택기로 제공한다. ID 문자열 필드는 노출하지 않는다.
- 층별 행마다 `층 → 최초 클리어 조건 → 연결 보상`이 분명히 보이도록 한다. 보상 아이템·수량은 아이템 카탈로그 선택으로 입력한다.
- 한 층에 보상이 여러 개 필요한 경우 해당 층 mission에 복수 reward link를 연결한다. 행의 추가·삭제·중복 층·보상 미연결을 제출 전 검증한다.
- 제출 전 사용자 문장으로 요약한다. 예: “이벤트 기간에 월광 균열 2층을 처음 클리어하면 회복 포션 2개를 지급합니다.”
- 동작 중인 UI가 기존 다른 이벤트 유형도 노출한다면, 제품 범위 결정에 맞게 숨기거나 별도 모드로 분명히 구분한다.

### B. 사용자 입력→내부 Plan 변환

- 사용자 폼 계약과 내부 `EventBriefInput` 계약을 분리하고 서버에서 신뢰 가능한 카탈로그 참조로 변환한다.
- 각 층 행은 하나의 `special_dungeon_floor_clear` action/mission 및 해당 층의 단일 내부 floor ID로 변환한다. 여러 층 구간을 허용하려면 각 floor ID의 의미가 보존되도록 명시적으로 확장한다.
- 각 보상은 정확한 mission에 링크하고 Plan의 `mission_reward_links`와 `rewards[].mission_id`가 동일한 관계를 갖게 한다.
- 선택된 던전 template, 층 catalog/data snapshot, ruleset, event schema, capability version을 Plan·검증 근거·적용 이벤트에 보존한다.
- 층/템플릿이 존재하지 않거나 snapshot이 다르거나 capability 조합이 맞지 않으면 적용 가능 상태로 승격하지 않는다.

### C. 기간 내 진행과 첫 클리어 보상

- Runtime 이벤트의 유효 기간은 기존 UTC `[start_at, end_at)` 기준을 따른다.
- 이벤트가 `active`인 동안 모든 층 mission을 평가하며 mission day에 의한 gate를 제거한다. 저장 데이터의 기존 `day` 필드를 제거·재해석하는 방식은 schema migration/version 계획과 함께 결정한다.
- mission 완료 키는 Runtime event ID + 인증된 user ID + floor ID를 기준으로 유일하게 보장한다. 이벤트 전 일반 플레이 이력은 이 키에 포함되지 않는다.
- 층 클리어 ActionRecord가 같은 Runtime event에 속하고, 해당 층에 대해 성공한 경우에만 mission을 완료한다. 실패, 이벤트 밖 행동, 다른 층, 다른 이벤트 행동은 대상이 아니다.
- 첫 성공을 확정하는 DB transaction에서 mission 완료, reward grant, inventory/skin ownership 변경, ledger, idempotency response를 원자적으로 저장한다.
- 같은 층 재클리어와 동일 요청 재전송은 기존 완료/지급을 반환하고 중복 지급하지 않는다. 서로 다른 동시 요청도 유일 제약 또는 잠금으로 하나의 지급만 확정한다.
- `once_per_user` 용어를 이벤트 전체 한 번인지 층별 한 번인지 명확히 한다. 이 제품 규칙의 의미는 **이벤트별·사용자별·층별 최초 1회**다.
- 상시 이벤트는 종료 시각이 없는 유효 기간 표현을 사용하되, 첫 클리어 보상은 그 이벤트 인스턴스에서 한 층당 한 번으로 제한한다. 주기 반복 지급은 이번 계약에 포함하지 않는다.

### D. 화면 결과와 운영 기록

- 기획 결과에 층 이름, 층별 달성 조건, 연결 보상, 최초 1회 지급 정책, 검증 근거를 표시한다.
- 데모 게임 이벤트 패널은 각 층의 `미진행 → 진행/완료`와 보상 지급 상태를 표시한다. 완료 이후 재도전은 게임 플레이를 허용할 수 있지만 이벤트 보상은 다시 주지 않는다.
- 운영 로그/Trace에는 해당 층 행동과 이벤트 mission/reward 결과를 연결하는 식별자와 안전한 요약을 남긴다.
- 실패/기한 만료/중복 요청은 지급 완료처럼 화면에 표시하지 않는다.

## 구현 계획에 반영할 작업 패키지

1. **계약/카탈로그:** 사용자 입력 DTO, template/floor 선택 데이터, 층 미션·보상 linkage, 버전 고정, finite/ongoing 기간 규칙을 정의한다.
2. **검증/계획:** 지원 층·행동·대상 접근성·보상 한도·중복/누락 링크 검증을 반영한다. 의미가 없는 free-form ID 검증은 UI 서버 경계에서 제거한다.
3. **Runtime adapter:** 기존 Day 기반 변환을 층별 mission으로 변환하고, 전체 이벤트 기간 활성 규칙을 보존한다.
4. **Runtime 원자성:** first-clear 완료와 보상 지급을 동시·재시도 상황에서 exactly-once 효과로 저장한다.
5. **기획 UI:** 여러 층 행과 층별 보상 연결, 사람이 읽을 수 있는 요약·오류 표시를 구현한다.
6. **게임 UI:** 적용 이벤트, 층별 mission 진행, 보상 지급 결과를 실제 Runtime 조회로 표시한다.
7. **데이터 호환:** 이전 Day 기반 이벤트 인스턴스와 신규 기간 전체 미션의 event schema 버전을 분리하고, 기존 test DB 이벤트를 파괴적으로 초기화하지 않는다.
8. **검증:** 함수/서비스/API/E2E 각각에서 기간 경계·층 분리·다중 보상·이벤트 외 과거 클리어·반복 클리어·동시 클리어·idempotent 재요청을 검증한다.

## 수용 기준

- 사용자는 콘텐츠 ID를 외우거나 입력하지 않고 층 이름으로 이벤트를 설계한다.
- 하나의 이벤트에 층별 mission과 각각의 reward link를 2개 이상 생성할 수 있다.
- 모든 층 mission은 이벤트 유효 기간 전체에서 활성화되며 서로 다른 날짜로 강제 분리되지 않는다.
- 이벤트 기간 전에 같은 층을 클리어한 유저도 이벤트 기간 중 그 층을 성공적으로 클리어하면 해당 이벤트 보상을 받는다.
- 이벤트 기간 내 첫 클리어는 해당 층 보상을 한 번 지급하며, 동일 층 반복·요청 재전송·동시 요청으로 중복 지급하지 않는다.
- 보상은 실패 전투, 다른 층, 다른 이벤트, 이벤트 유효 기간 밖의 행동에서 나오지 않는다.
- 층 미션 완료, 보상 보유량, 보상 원장, UI 표시가 DB 재조회 및 브라우저 새로고침 후 일치한다.
- 미지원 층/행동/아이템 또는 버전 불일치는 잘못된 Runtime 등록 없이 사람에게 데이터 필요/개발 필요로 설명된다.
- 이전 schema 이벤트는 명시적 호환 경로로 읽거나 안전하게 거절하며, 테스트 DB를 초기화하지 않는다.

## 미결 사항

- 사용 가능한 이벤트 던전 template이 하나뿐인 동안 이를 사용자 화면에서 숨기고 내부 기본값으로 고정할지, 이름만 읽기 전용으로 보여줄지.
- 미션 목표를 항상 “층 1회 클리어”로 고정할지, “해당 층 N회 클리어”도 선택하게 할지. N회가 가능해도 보상은 최초 완료 때 한 번 지급하는 것이 기본 원칙이다.
- 유효 기간 입력 UI가 현재 duration 기반인 경우 절대 시작/종료 시각을 지원할지, 기존 기간 방식으로 유지할지.
- 유한 층 목록을 초과하는 무한 이벤트 던전이 추후 도입되면 동적 층별 보상을 별도 계약으로 다룰지. 현재 카탈로그 밖의 층/보상을 추정 생성하지 않는다.

## 2026-10-11 후속 방향 결정: 층에서 독립 이벤트 공간으로

위 층별 계약은 그 시점의 구현·결정 이력으로 보존한다. 후속 설계에서는 이벤트 특별 던전을 순차 층으로 다루지 않고, 카탈로그의 세 공간 중 사용자가 선택한 공간만 이벤트에 연다. 선택 공간은 각각 독립 입장·클리어가 가능하고, 선택되지 않은 공간은 화면과 서버 양쪽에서 닫는다. 각 공간의 첫 클리어 미션·보상은 유지하되 층 순서·다음 층 해금은 적용하지 않는다. 구현 계획과 신규 계약은 [선택 공간과 Runtime 개방 공간 동기화 계획](12_기획안_선택공간_Runtime_개방동기화_변경계획.md)을 기준으로 한다. 이 결정은 현재 코드가 이미 바뀌었다는 뜻이 아니다.
