# 검증·평가·피드백 설계

## 2026-10-13 미지원 결과와 Critic 검토의 구분

Critic 출력은 기존 `status/reason/review_note/repairability`에 `findings`를 추가한다. 각 항목은 `{kind: SEMANTIC | SCOPE, field_path: string(1~200), reason: string(1~1000)}`이며 최대 16개다. live provider는 배열을 필수로 요구하고, 기존 저장 응답의 누락은 빈 배열로 읽는다. Agent는 업무 ID·최종 상태를 발급하지 않는다.

이미 결정적 검증에서 기록한 `NEEDS_DEVELOPMENT/NEEDS_DATA`와 `runtime_eligible=false`는 기획 결과의 정상적인 지원 범위 제한이다. Critic은 별도의 의미 모순이 없으면 PASS를 반환한다. REVIEW를 반환한 경우에도 Supervisor는 다음 조건을 모두 만족할 때만 실효 평가를 PASS로 조정한다.

- Plan 상태가 `VALIDATED_WITH_DEVELOPMENT_ITEMS` 또는 `NEEDS_DATA`이며 런타임 실행이 차단되어 있다.
- 모든 결정적 blocking finding이 SCOPE이고 `NEEDS_DEVELOPMENT/NEEDS_DATA`다.
- Critic의 비어 있지 않은 findings가 모두 SCOPE이며 기존 blocking finding의 필드 경로 또는 하위 경로와 일치한다.

원래 REVIEW·사유·findings는 유지하고 `reported_status=REVIEW`, `review_resolution=EXISTING_SCOPE_FINDINGS`, 서버가 확인한 `matched_scope_codes`를 기록한다. 암호화된 LLM 원문은 수정하지 않는다. 새로운 의미 모순, 보안 차단, 알 수 없는 경로, 빈 findings, 실행 가능한 Plan의 REVIEW는 이 조정을 적용하지 않는다. 이후 상태·전이는 기존 Supervisor 흐름에서 결정하며, 지원 범위 제한만 있으면 개발/데이터 필요 결과를 포함한 COMPLETED, 독립적인 사람 검토 사유가 있으면 WAITING_REVIEW다.

검증 증거는 [보완 후 실제 LLM 재시험](../검증산출물/2026-10-13_실제LLM_보완후_재시험결과.md)을 따른다.

## 2026-10-11 설명 수정 계약

Critic 출력에 `repairability: HUMAN_REVIEW | PLANNER_EXPLANATION`을 사용한다. 기존 응답의 누락 값은 HUMAN_REVIEW로 처리하고 live provider JSON schema는 필수 enum으로 요구한다. REVIEW + PLANNER_EXPLANATION + 결정적 runtime_eligible인 경우에만 Supervisor가 정책을 적용한다. Planner 입력에 `repair_feedback: {reason, modifiable_fields, fixed_brief: true}`를 전달하며 변경 필드는 summary/action_rationales/reward_rationales다. reason은 1~1000자 보안 검증을 거친다. 수정 후 전체 규칙·경제·지원 검사와 Critic을 반복한다. 행동/보상 수치·연결·ID·사용자 요구는 Brief에서 Supervisor가 다시 결합한다. [정책 적용 범위 §6](15_오류대응정책_Workflow_연결_재검사.md#6-정책-연결-보완-구현)을 따른다.

## 1. 목적과 기준

이 문서는 기획안이 요청·게임 계약을 만족하는지 확인하는 validator와 Agent 평가·피드백 계약을 정한다. LLM critic은 보조 판단자이며 결정적 Schema·권한·게임 규칙 validator를 대체하지 않는다.

현재 `validation_error`, `mission_unreachable`, `item_not_found`, `event_brief_mismatch` 등은 코드상 복구 경로가 있지만, 요청 형식·Agent 출력·도구 응답·도메인 규칙 문제를 일관된 finding schema로 통합한 것은 목표 설계다.

## 2. 검증 단계와 순서

| 단계 | 검사 주체 | 검사 항목 | 실패 시 기본 처리 |
|---|---|---|---|
| 1. Request schema | API/Schema validator | 필수값, 타입, 크기, enum, 날짜·수량 범위 | 필드 오류 반환, 재시도 안 함 |
| 2. Input semantics | Semantic Guard | 목적·대상·기간·장소·행동·보상·영향 간 모순, 허용되지 않는 지시 | 모호하면 사용자 보완, 보안 위반은 block |
| 3. Capability | Scope Checker | venue/action/reward/template 지원 상태와 버전 | 개발 필요/데이터 필요 finding 기록 |
| 4. Agent output schema | Contract validator | 필드·타입·참조·계약 버전·필수 연결 | 생성 오류면 제한된 Agent retry 후 중단 |
| 5. Game rule validation | 결정적 Rule Validator | 해금, 판정 가능성, 목표량, 기간/시도, reward availability/limits | 수정 가능 finding으로 revise |
| 6. Impact validation | Balance evaluator | 기대 지표, 대상 달성 가능성, 보상 경제 영향의 근거와 범위 | 결정적으로 계산 가능한 항목은 계산; 근거 부족은 `unknown`; finding severity/terminal result 기준 적용 |
| 7. Critic evaluation | Critic Agent + deterministic checks | 요청 부합성, 근거, 누락, 모순, 설명 가능성 | 구조화 finding을 Planner에 전달하거나 human/block |
| 8. Final consistency | 서버 측 validator | 모든 finding 해소, capability status, result/data versions, runtime eligibility | 최종 상태 계산; LLM output 값을 신뢰하지 않음 |

검증 순서는 보안 Guard의 결과에 따라 조기 종료할 수 있다. 상태 변경 후에는 영향을 받는 하위 검증뿐 아니라 최종 consistency를 다시 실행한다.

## 3. Finding 계약

```yaml
finding_id: string
finding_type: INPUT | CONTRACT | DOMAIN | SCOPE | SECURITY | DATA | IMPACT
code: stable_code
severity: INFO | WARNING | ERROR | BLOCKER
location: { field_path: string, component: string, phase: string }
message_safe: string
evidence_refs: []
related_capability_id: string | null
repairability: AUTO_REVISION | USER_INPUT | NEEDS_DEVELOPMENT | NEEDS_DATA | HUMAN_REVIEW | NOT_REPAIRABLE
suggested_action: string | null
blocks_runtime: boolean
```

`message_safe`는 사용자 표시용이며 내부 exception이나 민감 prompt를 넣지 않는다. finding의 근거는 game data/rule version 또는 validator ID를 참조한다.

## 4. 평가 결과

| 상태 | 조건 | Workflow 효과 |
|---|---|---|
| `PASS` | 필수 형식·의미·규칙 검사 통과, 보안 finding 없음 | 지원 범위 내이면 final approval 대기 |
| `REVISE` | 해결 가능한 비보안 ERROR가 있고 revision budget 남음 | Planner에 finding 전달 후 전체 영향 검증 |
| `NEEDS_DEVELOPMENT` | 의미 있는 초안은 있으나 capability 구현이 필요 | 개발 필요 finding 포함 결과 반환, `runtime_eligible=false` |
| `NEEDS_DATA` | 게임 카탈로그/근거가 없어 사실 검증 불가 | 의미 있는 평가 결과와 필요 데이터가 있으면 `PLAN_READY_WITH_DATA_GAPS`로 종료; 필수 사용자 입력이 누락된 경우에만 `AWAITING_USER_INPUT` |
| `HUMAN_REVIEW` | 상충·모호성으로 안전한 자동 결정 불가 | `AWAITING_HUMAN_REVIEW`; 해결되면 새 실행 또는 재검증 상태로 복귀, 권한 정책은 그대로 유지 |
| `BLOCK` | 보안·권한 위반, 금지된 게임/제품 정책 | 후보 폐기/격리, 안전 종료 |

가장 높은 차단 우선순위는 `BLOCK`이고, 그 다음 데이터·사람 검토, 개발 필요, 수정, PASS 순이다. `WARNING`은 평가 결과 enum이 아니라 finding의 `severity`로 표현한다. 개발 필요 태그는 검증을 통과했다는 뜻이 아니다. 모든 확정 가능한 규칙은 계속 검사하고 미검증 부분을 분리해서 표시한다. 평가 결과와 저장 Plan 상태 및 Workflow 상태의 정식 매핑은 [기획안·게임 기능 계약](01_기획안_게임기능_계약_설계.md)의 표를 단일 기준으로 사용한다.

## 5. Feedback loop

1. Validator는 사람이 수정 가능한 finding만 `AUTO_REVISION`으로 표시한다.
2. Supervisor는 해당 finding과 관련 필드·증거를 Planner 입력에 연결한다.
3. Planner는 Brief의 고정 제약을 유지하며 결과를 수정한다.
4. Workflow는 새 result version을 만들고 관련 계약·도메인 검증과 최종 일관성 검사를 다시 실행한다.
5. 수정 횟수는 오류 정책의 별도 revision budget을 따른다. 한도 초과 시 자동 통과시키지 않는다.

사용자 고정 조건은 자동으로 완화하지 않는다. 이를 만족하는 해가 없으면 `HUMAN_REVIEW` 또는 명시적 불가능 결과를 반환한다. 보안 finding은 일반 수정 루프로 전달하지 않는다.

## 6. 평가 근거와 영향 분석

- 결정적 수치 판정은 versioned game rules/data와 재현 가능한 계산기를 사용한다. 필요한 근거와 계산기가 있는데도 이를 추정치로 대체하지 않는다.
- LLM Critic은 누락·일관성·서술 품질을 보조 검토할 수 있지만 근거 참조를 생성해야 하고, 수치 검증을 대체하지 않는다.
- 영향 결과는 `measured`, `calculated`, `estimated`, `unknown`을 구분한다. `calculated`는 버전 고정된 규칙·게임 데이터·결정적 계산식으로 재현 가능한 결과다. `estimated`는 근거 자료가 있으나 표본·가정·확률 모델로 인해 정확한 결정값이 아닌 결과에만 쓴다. 근거가 없으면 `unknown`이다.
- 게임 규칙과 버전 지정 데이터가 있고 결정적 계산이 가능한 미션 달성 가능성·보상 경제 영향은 계산해 `calculated`로 기록한다. 계산 근거가 없으면 임의 추정하지 않고 `unknown`/`NEEDS_DATA`에 연결한다. 미지원 행동이나 보상의 영향은 추정값으로 채우지 않고 `NEEDS_DEVELOPMENT` 또는 `NEEDS_DATA` finding에 연결한다.
- 결과에는 사용한 brief, rules/data, validator, 평가 기준 버전을 저장한다.

## 7. 완료 기준

- 각 단계의 schema, domain, security 검증 담당과 실패 처리가 구분됨
- finding이 수정·개발·데이터 필요·사람 검토·보안 차단을 혼동하지 않음
- 수정 후 전체 영향 재검증 및 `runtime_eligible` 재계산을 강제
- 평가 근거와 게임 데이터 버전이 결과와 함께 추적됨
- positive, revise, unsupported, missing data, prompt attack 시나리오별 기대 결과가 있음
