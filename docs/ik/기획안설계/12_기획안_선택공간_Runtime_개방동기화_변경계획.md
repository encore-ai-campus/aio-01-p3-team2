# 기획안 선택 공간과 Runtime 개방 공간 동기화 변경 계획

## 목적과 상태

- 문서 종류: 구현 변경 계획
- 상태: 구현 완료, 자동 검증 완료. 사용자 Edge 수용 테스트는 별도 진행 가능.
- 목적: 승인된 기획안이 선택한 이벤트 공간만 가상 게임의 해당 이벤트에서 열리도록 한다.
- 기준: [이벤트 던전 변경 작업과 결정 이력](11_이벤트던전_층별_미션보상_변경작업.md), [게임 이벤트 적용 계약](../게임설계/05_이벤트적용_계약.md), [게임 Runtime API](../게임설계/04_게임Runtime_API.md), [현재 구현 상태](../현재_구현상태.md)

## 현재 상태와 문제

월광 균열 템플릿은 현재 세 개 항목을 `floors`로 정의한다. 기획안은 선택 항목을 미션·보상으로 저장하지만, Runtime은 선택된 미션 범위를 입장 가능 범위로 사용하지 않고 템플릿 전체 `floors`를 노출한다. Plan의 선택과 실제 이벤트 공간이 연결되지 않는 결함이다.

기획과 Runtime을 간단히 맞추기 위해 이 세 항목을 순차 층이 아니라 **독립적으로 선택·입장하는 이벤트 공간 세 개**로 정의한다. 각 공간은 기존 전투·보상 규칙을 재사용한다. 층 순서 해금, 다음 층 계산, 층 완료에 따른 연쇄 개방은 이 이벤트 공간 흐름에서 제거한다.

## 목표 규칙

1. 이벤트 던전에는 카탈로그가 제공하는 세 개의 공간이 있다. 각 공간은 고유 이름, 안정 ID, 입장 조건, 전투 설정을 가진다.
2. 사용자는 기획안에서 공간을 선택하고, 선택한 공간마다 “이벤트 기간 중 첫 클리어” 조건과 보상을 구성한다. 선택한 공간은 각각 독립적으로 입장할 수 있다.
3. 이벤트에 적용되는 공간 집합은 승인 Plan의 선택 공간 집합과 정확히 같다. 미선택 공간은 이벤트 화면에서 열리지 않고 서버도 입장을 거부한다.
4. 공간별 첫 성공 행동은 같은 공간의 미션 하나만 완료하고 연결된 보상을 1회 지급한다. 한 공간의 행동이 다른 공간의 미션을 완료하지 않는다.
5. Plan→Runtime 변환은 선택 공간 ID를 `venue.space_ids`에 저장하고, 공간별 mission도 같은 ID를 참조하게 한다. 층 기반 내부 식별자는 새 계약부터 공간 ID로 교체한다.
6. Runtime은 `venue.space_ids`를 해당 템플릿의 공간과 대조하고 비어 있음·중복·미등록 공간·Plan mission/reward 불일치를 등록 전에 거절한다.
7. Runtime API 응답, 게임 화면, 이벤트 진행 기록은 같은 저장된 공간 ID 집합을 사용한다. 클라이언트 필터만으로 입장을 제한하지 않는다.
8. 일반 무한 던전의 층 진행은 그대로 유지한다. 이 변경의 공간 개념은 이벤트 특별 던전에만 적용한다.

## 구현 변경 단계

| 단계 | 대상 | 작업 | 완료 증거 |
|---|---|---|---|
| 1. 게임 카탈로그·규칙 | `backend/data/virtual_game_v1_5_0.json`, game catalog/rules, MCP capability | 완료: 기존 1.3.0/1.4.0 스냅샷을 보존하고 신규 1.5.0에 세 공간, 공간 완료 행동 및 capability를 추가했다. 일반 던전의 층 모델은 유지했다. | 세 공간이 catalog/capability에서 같은 ID·버전으로 조회됨 |
| 2. 기획 입력·Plan 계약 | `frontend-web/src/main.js`, Brief/Plan schema 및 canonical planning | 완료: 공간 선택/공간별 첫 클리어 보상 입력으로 변경했다. 선택된 각 공간만 mission 및 보상 링크를 생성하고 Plan 결과에 공간별 구성을 표시한다. | 1개 또는 여러 공간 선택 시 Plan 공간·mission·reward 집합이 일치 |
| 3. 적용 변환·검증 | `backend/app/game/event_source.py`, `backend/app/game/service.py` | 완료: 승인 Plan에서 `venue.space_ids`와 공간별 mission 대상을 생성하고 버전 고정 카탈로그 참조 및 교차 일관성을 검증한다. | 승인 Plan의 공간 집합이 적용 payload에 손실·추가 없이 저장됨 |
| 4. 입장·완료 처리 | Runtime special dungeon action 처리 | 완료: 선택 공간은 각각 바로 입장 가능하다. 새 공간 이벤트에서 순차 해금을 제거하고 요청 공간을 이벤트 허용 목록과 대조한다. 성공한 공간의 action만 해당 mission을 진행시킨다. | 선택 공간 성공, 비선택 공간 거부, 교차 진행·중복 보상 없음 |
| 5. 게임 화면·조회 API | `backend/app/api/game.py`, `backend/app/game/service.py`, `demo-game/src/main.js` | 완료: 활성 이벤트에서 선택한 공간만 이벤트 던전 화면에 표시하며 서버도 같은 허용 집합으로 입장을 검증한다. | 화면에 보이는 공간 ID 집합과 서버 허용 집합이 일치 |
| 6. 호환·검증·문서 | event schema/저장 호환, backend·MCP·E2E tests, `docs/ik/` | 완료: 기존 저장 이벤트를 변경하거나 초기화하지 않는다. 1.3.0/1.4.0 스냅샷과 구형 floor action 호환 경로를 보존하고, 신규 공간 이벤트는 `event_schema_version=1.2.0`, `opong-data-1.5.0`, `opong-capabilities-1.0.3` 계약으로 저장한다. 구현 상태를 문서화했다. | 신규 공간 흐름의 통합·브라우저 검증 통과 |

## 데이터 호환 원칙

- 새 이벤트 공간 계약은 `space_id`와 `venue.space_ids`를 사용한다. 의미가 바뀌므로 event schema 및 capability 계약 버전을 올리고 해당 버전의 schema와 변환 경로를 함께 제공한다.
- 이미 승인·등록된 이벤트 payload와 과거 trace는 수정하지 않는다. 구버전 층 이벤트는 구버전 Runtime 경로로 보존하고, 새 공간 이벤트에만 독립 공간 규칙을 적용한다.
- JSON/DB payload 형식에 실제 DDL 변경이 필요한지 구현 전 확인한다. 필요가 확인된 경우에만 additive migration을 작성하고 기존 이벤트·게임 상태를 변환 또는 초기화하지 않는다.
- 현재 전용 테스트 DB와 사용자 테스트 DB를 초기화하지 않는다. 검증은 별도 테스트 이벤트와 전용 자동 검증 DB를 사용한다.

## 검증 및 완료 기준

1. 세 공간 중 하나만 선택한 Plan은 Runtime과 게임에 그 공간 하나만 열고 나머지 두 공간의 직접 API 입장을 거부한다.
2. 세 공간 중 둘 이상을 선택하면 선택한 공간만 모두 표시되고 서로 독립적으로 입장할 수 있다. 순차 해금을 요구하지 않는다.
3. 선택 공간의 첫 성공만 그 공간의 mission/reward에 반영된다. 다른 공간의 action, 실패 전투, 반복 요청은 보상을 주지 않는다.
4. 비어 있는 공간 집합, 중복/미등록 ID, 공간 mission 또는 보상 링크 불일치는 적용을 거부한다.
5. 새로고침·API 재기동 후 UI, API, DB의 허용 공간 목록과 진행/보상 상태가 같다.
6. 기존 층 기반 이벤트와 일반 던전의 층 진행이 기존 동작을 유지한다.
7. 단위·API·PostgreSQL 통합·E2E 검증 결과와 미검증 경계를 현재 구현 상태 문서에 기록한다.

구현 결과와 확인한 검증 범위는 [현재 구현 상태](../현재_구현상태.md#2026-10-11-선택-공간-이벤트-구현) 및 [이벤트 적용 계약](../게임설계/05_이벤트적용_계약.md#선택-공간-계약-구현-2026-10-11)을 참조한다.

## 실행 순서

공간 계약 및 버전 결정 → 카탈로그/capability → 입력·Plan 계약 → Plan→Runtime 변환 → 서버 허용 목록 및 행동 처리 → API·화면 → 구버전 호환 → 테스트·현재 구현 상태 갱신.

기획·Runtime·화면이 모두 같은 공간 ID 집합을 쓰는 것이 완료 게이트다. 기존 사용자의 게임 데이터는 보존한다.
