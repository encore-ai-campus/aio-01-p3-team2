# 오류 주입·정책·오토힐링 및 복구 시연 시험표

작성일: 2026-10-11 · 상태: **실행 전 시험 명세**

## 1. 목적·입력 기준

[정밀 테스트 계획](17_오토힐링_정밀테스트_계획.md)에 따라 「배포 및 장애 복구 보고서」의 장애 시험을 수행하기 위한 실행 목록이다. **오류 대응 실제 동작과 복구 시연 UI의 일치**를 함께 확인한다. 이 문서를 작성한 것은 137개 시험의 통과나 실행을 뜻하지 않는다.

- 카탈로그: 실제 시험 API 8013의 오류 28개/시나리오 28개. 게임 근거는 canonical `opong-data-1.5.0`, 기존 Task 3개는 `tinyheroes-1.0.0`.
- 현재 정책: 시험 DB의 활성 version 1. MCP 003은 과거 002 상속을 적용한 유효 규칙을 기준으로 한다. 사용자 서버의 정책 버전과 동일하다고 가정하지 않는다.
- [시험 명세 JSON](18_오류주입_시험명세.json): 각 case의 요청, 기대 코드/정책/action/최종 상태/시도/부작용과 상태 PLANNED를 포함한다. 기대값은 분류기/runner oracle 실행 결과를 가져온 것이 아니라 카탈로그·고정 정책·설명된 업무 예외 계약을 대조해 작성했다. 실행 전 명세 자체도 검토한다.
- JSON의 `request`만 실제 POST payload로 사용한다. 기대값과 UI 체크는 보고서/검사 데이터이며 API 입력 필드가 아니다.
- 코드/설정 digest와 정책·카탈로그·snapshot이 바뀌면 동일성 확인 후 명세 버전을 확정한다. 정책을 시험 결과에 맞춰 사후 변경해 PASS를 만들지 않는다.

## 4. 전용 예외 계약과 추가 확인

- **입력 오류:** REQUEST_BLOCKED/HTTP 422가 정상이다. 오류 정책을 통한 재시도 실행을 기대하지 않는다. 단순히 아무 422가 나왔다고 원인 분류가 맞다고 판정하지 않는다.
- **업무 finding:** COMPLETED와 NEEDS_DATA/NEEDS_DEVELOPMENT + blocks_runtime=true가 기대 결과다. 자동 오류 복구와 별도 집계한다.
- **ACK 유실:** 정책상 재시도 금지여도 commit 확인 후 WAITING_APPROVAL을 반환한다. 이것을 정책 무시 또는 새 쓰기 재시도로 해석하지 않는다.
- **CAS 충돌:** 충돌 요청은 거절되고 기존 정상 Workflow의 승인 대기는 유지된다. 기존 작업 정상화와 충돌 거절을 구분한다.
- **LIMIT:** 선택 코드 ERR-CTRL-LIMIT-001과 실제 원인 ERR-CONTRACT-PLANNER-001을 각각 기록한다. 강제로 LIMIT 예외를 만든 시험이 아니다.
- **게임 규칙 MCP 003:** primary 실패 뒤 검증된 fallback 1회. fixture의 다음 콘텐츠 primary 조회와 실패 작업 retry를 구분한다.
- **기획 수정:** 현재 정책 max_attempts=3은 최초 결과와 최대 수정 2회를 의미한다. Agent retry 3회와 혼동하지 않는다.

다음 API 거절은 별도 보조 검사로 실행한다: 없는 scenario, 금지 profile, 미지원 pattern, first_n=0/5, 임의 추가 필드, 같은 멱등 key/다른 본문, 외부 Origin. 각각 현재 API 계약의 HTTP 상태와 응답을 대조한다. 본문의 137개 유효 실행 조합에 포함하지 않는다.

## 5. 기존 구현/검사의 공백과 보완 우선순위

아래는 **코드에서 확인한 검사·표시 범위의 한계**다. 모든 항목이 실제 실행 실패로 재현됐다는 뜻은 아니다.

| 우선 | 공백 | 다음 보완/확인 |
|---|---|---|
| 먼저 | 입력 오류 oracle는 실제 응답이 422인지로 검출 증거를 인정 | 입력 형식/보안 원인별 응답 내용을 독립 기대값으로 비교. 실제 응답 계약 확인 후 기대 필드 확정 |
| 먼저 | UI actionLabels에 RUN_AGENT/TOOL_FALLBACK의 한국어 설명 없음 | 기획 수정/대체 게임 규칙 조회로 표시되는지 검증하고 필요한 표시 수정 |
| 먼저 | terminalLabels에 REQUEST_BLOCKED/COMPLETED가 없고 finding을 결과 설명에서 풀어주지 않음 | 입력 거절, 자료/개발 필요, 실행 범위 제한을 분명히 표시. UI 표현을 먼저 보완 |
| 먼저 | LIMIT 선택 코드와 실제 원인 코드의 관계를 UI 결과가 충분히 설명하지 않음 | 선택 시나리오/관측 원인을 함께 표시하고 검출 실패로 혼동하지 않게 확인 |
| 먼저 | 명세에서 정한 정책 rule/한도와 actual Trace의 rule ID/정책 참조/전이 순서를 함께 비교할 필요 | 기존 checks에 더해 고정 정책·matched rule·상태 버전·후속 금지 호출의 독립 비교 범위 확인/추가 |
| 병행 | 기존 Edge는 일부 대표 흐름만 검사 | 28개 대표 결과와 입력/finding/CAS/ACK/LIMIT/revision/fallback 및 FAIL/INCONCLUSIVE를 구분해 보강. 저장 결과 조회를 활용 |
| 별도 | DB 반복 장애는 UI once만 제공 | 기존 저장 복구 단위 검사를 재사용하고 필요한 통합 fixture만 보강. UI 지원 범위로 꾸미지 않음 |

현재 JSON 기대값은 실행 전 기준이다. 위 전용 예외의 기대값과 실제 pinned policy 참조를 대조한 후 결과 판정에 사용한다. 기존 oracle 결과만 복사해 새로운 독립 검증을 했다고 기록하지 않는다.

## 6. 실행 순서·중단 조건·결과 기록

1. 공통 명세/정책 동일성 확인 및 위 '먼저' 항목 보완.
2. 무주입 정상 요청 1개로 DB/MCP/협업/저장 기준 확보.
3. 오류 28개의 current_active 기본 case를 작은 묶음으로 순차 실행. LIMIT은 always.
4. 자동 복구 프로필의 once 및 safe_stop으로 대응 분기 확인.
5. first_n=2/3/4, always로 한도 직전/도달/이후 검사. 의미가 같은 조합의 실행 생략은 이유를 명세에 기록하고 미실행을 PASS로 세지 않음.
6. 저장된 결과를 조회해 U1~U8와 대표 판정의 Edge 증빙 확보. UI 요청 선택 자체는 실제 POST 실행으로 최소 대표 검증.
7. 실패 원인 분석/수정/관련 회귀 후 보고서에 실행 ID·기대/실제·시간·수동 개입·원래 정책 복원·증빙 기록.

상위 단계 실패가 같은 원인으로 후속 case를 모두 막으면 전체 반복 실행을 멈추고 해당 분기를 먼저 수정한다. 정책 복원 실패/DIRTY/금지 부작용/불확실 DB 결과도 중단 조건이다. suite 최대 100개 이하, 공유 정책을 사용하므로 실행 worker 1. 사용자 서버를 추가로 중복 실행하거나 사용자 DB를 초기화하지 않는다.

**이번 작업 결과:** 시험표/137개 요청·기대값 명세와 기존 공백을 작성했다. 이번 단계에서 137개 시스템 시험, 추가 UI 시험, 실제 서비스 장애 시험을 실행하거나 공백 항목의 코드를 수정하지 않았다. 기존 검사 결과는 [16 구현·검증 기록](16_오류시험실_구현과_검증.md)에서 구분해 확인한다.

## 7. 2026-10-11 실행 준비 보완

§5의 '먼저' 항목을 보완했다. 입력 원인 응답 검사, 정책 version/hash·실제 결정 rule·canonical 전이/최종 상태, 종료 publication 이후 실제 호출 관측을 추가했다. UI에는 재작성/fallback/입력 거절/finding/CAS/ACK/LIMIT과 횟수 구분을 반영했다. 늦게 덧붙는 과거 복구 설명을 종료 후 실행으로 오인한 준비 검사 실패를 수정했고 실패 이력은 보존했다.

현재 카탈로그의 137개 요청/코드/위치/프로필별 정책 rule 및 기준 정책/게임 버전을 읽기 전용 preflight로 대조한다. 저장된 결과는 명세와 따로 비교하며 기존 PASS라도 불일치가 있으면 보고서 FAIL이다. 실제 복구시간은 catch 또는 실제 Supervisor failure input 시점부터 Workflow 처리 완료까지 측정한다.

**준비 검증:** 영향 단위 99 passed, 대표 smoke 10/10 PASS, 시간 계측 영향 2/2 PASS, Edge 2 passed, production build 통과. 이는 기본 28개와 전체 137개 본 시험의 완료가 아니다. 상세 준비/실패/수정/증빙은 [장애 시험 결과보고서](../검증산출물/장애시험_결과보고서.md)를 따른다. 최초 정책(version 1)과 CLEAN 복원을 확인하고 본 시험 실행 직전에 새 preflight를 기록한다.
