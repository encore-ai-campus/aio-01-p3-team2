# 기획안·게임 기능 계약 설계

## 1. 목적과 범위

이 문서는 사용자 요청(Event Brief), 게임 기능 지원 범위(capability), 생성 결과(Event Plan), 검증 finding 사이의 논리 계약을 정한다. 기획안이 게임이 실제로 판정·실행할 수 있는 구조인지 판단하는 기준이다. 이 문서의 필드명·타입·null 규칙을 논리 계약의 기준으로 삼고, API 직렬화 및 DB 저장 매핑은 [API·저장·Trace 설계](06_API_저장_Trace_설계.md)를 따른다. Runtime capability의 세부 조회 계약은 [Runtime Capability·MCP 데이터 계약](10_RuntimeCapability_MCP_계약.md)을 따른다.

대상 범위는 기획 Workflow의 요청부터 결과 반환까지다. Runtime 등록·전투·보상 처리 계약은 [전체 시스템 최상위 설계](../최상위_시스템_설계서.md)와 게임 도메인 설계를 따른다.

## 2. 현행 구현 기준

- 현 Workflow에는 `mission_unreachable`, `item_not_found`, `event_brief_mismatch` 등의 도메인 오류가 있고 일부는 Planner 재기획으로 라우팅된다.
- 게임 Runtime은 승인된 Task 결과와 게임 데이터 버전을 확인해 이벤트를 등록한다.
- 현행 MCP/Planner 경로는 canonical Runtime capability 계약과 완전히 일치하지 않는다. 새 기획에 적용할 목표 계약과 현행 지원 여부를 구분한다.
- 현재 Runtime의 승인 결과 연결은 존재하지만 `NEEDS_DEVELOPMENT` 태그 및 `runtime_eligible` 기획 결과는 목표 설계이며 현재 구현 완료로 간주하지 않는다.

## 3. 계약 엔터티

### 3.1 Event Brief (요청)

| 필드 | 의미 | 규칙 |
|---|---|---|
| `brief_id`, `brief_version` | 요청 식별자·계약 버전 | 요청 재실행과 수정 버전을 구분 |
| `objective` | 이벤트 목적 | 검증 가능한 목표 문장 또는 목적 코드 포함 |
| `target_segments[]` | 대상 유저군 | 게임 데이터에 정의된 세그먼트 ID 참조 |
| `event_type`, `operation_mode` | 이벤트 유형·기간 운영 형태 | 지원 capability와 연결. `finite`/`ongoing`은 게임 콘텐츠 push/farm과 구분 |
| `schedule` | 시작·종료·시간대 | 종료가 시작보다 뒤여야 함. 모호한 시간대 금지 |
| `venue` | 장소·콘텐츠 ID | capability/data catalog ID를 참조 |
| `actions[]` | 유저가 할 행동 | 게임 `action_type`, 허용 `filters/content_scope`, 측정 가능한 `goal` 참조 |
| `rewards[]` | 보상 ID·수량·조건 | 게임 item/currency/skin catalog, 지급 정책과 한도를 참조하거나 미지원 finding으로 전환 |
| `mission_reward_links[]` | 행동·완료조건과 보상의 연결 | 유효한 mission/action 및 reward ID를 연결 |
| `impact_targets[]` | 기대 영향·성공 지표 | 대상·측정 시점·단위·근거를 정의 |
| `constraints[]` | 반드시 지킬 조건 | 생성기가 임의 완화하지 않음 |
| `preferences[]` | 조정 가능한 선호 | 대안이 필요할 때 우선순위로 사용 |
| `source_game_version` | 기준 게임 규칙·데이터 버전 | 결과 및 검증에 전파 |

정형 입력의 기준은 다음과 같다. `required`는 반드시 제공하고, `optional`은 생략 가능하며, 명시적 `null`은 표에 허용된 경우에만 쓴다. 생략 필드에 의미를 바꾸는 암묵적 기본값을 적용하지 않는다.

| 필드 | 필수/nullable | 타입·제약 |
|---|---|---|
| `objective` | 필수, non-null | 1–500자 문자열. 의미 검증에서 측정 가능한 목적 또는 명시적 목적 코드로 확인 |
| `target_segments` | 필수, non-null | 1개 이상 ID 배열. MVP는 실제 적용 시 1개만 허용; 다중 대상은 분할 가능 여부를 별도 판정 |
| `event_type` | 필수, non-null | capability catalog의 enum |
| `operation_mode` | 필수, non-null | MVP `finite`만 지원. 그 외는 capability finding |
| `schedule` | 필수, non-null | 절대 시각 또는 `duration_days` 중 한 표현. 두 표현을 동시에 주지 않음 |
| `schedule.timezone` | schedule 필수, non-null | 유효한 IANA timezone. 수신 후 UTC 정규화, 원래 timezone 보존 |
| `venue` | 조건부 | special dungeon이면 capability ID 참조 필수, 그 외 생략 가능. 임의 ID 금지 |
| `actions` | 필수, non-null | 1개 이상. action·metric·조건은 catalog enum/ID 참조 |
| `rewards` | 필수, non-null | 보상 없는 이벤트는 빈 배열로 명시 가능. 지급할 때는 유효 item ID와 양의 정수 수량 필요 |
| `mission_reward_links` | 조건부 | 보상 지급 조건을 미션과 연결. 대상 mission/reward ID가 모두 존재해야 함 |
| `impact_targets` | 필수, non-null | 1개 이상 지표·단위·측정시점. 수치 산정 근거가 없으면 값은 null이며 상태 `unknown` |
| `constraints`, `preferences` | 필수, non-null | 배열. 비어 있으면 `[]`; hard constraint와 조정 선호를 혼합하지 않음 |

목표·대상·기간·행동·보상 연결이 의미적으로 불명확하면 임의 추정하지 않고 `AWAITING_USER_INPUT` 또는 근거 판단이 필요한 경우 `AWAITING_HUMAN_REVIEW`로 반환한다. `venue`는 특별 던전 이벤트에만 요구되며 일반 진행 이벤트에 억지로 부여하지 않는다. Brief의 시간은 IANA timezone 기준 입력으로 해석해 UTC로 정규화하고, 원래 시간대는 표시·감사 목적으로 보존한다. 버전별 기계 검증 가능한 JSON Schema 파일은 계약 버전을 바꿀 때 구현 계획에서 이 표와 함께 추가한다.

### 3.2 Capability Catalog (지원 범위)

| 속성 | 의미 |
|---|---|
| `capability_id`, `capability_version` | 안정적인 기능 식별자와 버전 |
| `capability_type` | venue, action, mission_rule, reward, event_template 등 |
| `supported_status` | `SUPPORTED`, `NEEDS_DEVELOPMENT`, `NEEDS_DATA`, `UNSUPPORTED_BY_POLICY` |
| `contract_ref` | 입력·출력·판정 계약 버전 |
| `required_game_data[]` | 기능이 필요로 하는 게임 카탈로그·규칙 |
| `validation_rules[]` | 기능별 형식·의미·범위 검증 규칙 |
| `runtime_adapter_ref` | 실제 Runtime에서 적용 가능한 구현 참조 또는 null |
| `evidence_ref` | 지원 여부의 근거·데이터 출처 |

상태 의미:

- `SUPPORTED`: 현재 버전의 계약·게임 데이터·Runtime adapter로 생성·판정 가능.
- `NEEDS_DEVELOPMENT`: 기능 또는 Runtime 계약 구현이 필요함. 개발 항목을 결과에 기록한다.
- `NEEDS_DATA`: 기능 자체 지원 여부를 판단할 데이터·근거가 부족함. 미지원으로 단정하지 않고 확인 필요를 기록한다.
- `UNSUPPORTED_BY_POLICY`: 보안·제품 경계·게임 정책상 제공하지 않는 기능. 개발 필요로 포장할 수 없으며 차단한다.

Capability catalog의 버전·소유·갱신 절차는 기획 및 게임 데이터 담당 영역의 API·저장 상세 설계에서 정한다. 미지원 여부를 LLM의 추측만으로 선언하지 않는다.

### 3.3 Event Plan (생성 결과)

논리 결과 계약은 다음 필드를 가진다.

```yaml
plan_id: string
result_version: string
brief_ref: { brief_id: string, brief_version: string }
source_ref: { workflow_id: string, task_id: string }
game_context:
  source: string
  domain_schema_version: string
  event_schema_version: string
  game_data_snapshot_id: string
  game_ruleset_version: string
  capability_catalog_version: string
  balance_policy_version: string
plan_status: DRAFT | VALIDATED | VALIDATED_WITH_DEVELOPMENT_ITEMS | NEEDS_DATA | BLOCKED
runtime_eligible: boolean
objective: string
event_type: growth_progression | dungeon_challenge | special_dungeon
operation_mode: finite | ongoing
audience: { segment_id: string }
schedule: { start_at: datetime_utc, end_at: datetime_utc | null, timezone: IANA_TZ, evaluation_horizon_days: integer | null }
venue: { template_id: string, layout_id: string, theme_id: string, difficulty_id: string, support_status: string } | null
missions:
  - mission_id: string
    action_type: string
    filters: object
    content_scope: object | null
    goal: { metric: string, aggregation: count | max, operator: gte, target: number }
    reset_period: once | daily | weekly
    support_status: string
rewards:
  - reward_id: string
    mission_id: string
    item_id: string
    quantity: integer
    grant_policy: once_per_user | once_per_cycle
    max_grants_per_user: integer | null
    support_status: string
mission_reward_links: [{ mission_id: string, reward_id: string }]
impact_assessment: [{ metric: string, display_label: string | null, status: measured | calculated | estimated | unknown, value: number | null, unit: string, method_ref: string | null, evidence_refs: [] }]
development_requirements: []
validation_summary: { status: string, findings: [] }
evidence_refs: []
```

이 예시는 논리 계약이다. `plan_status`는 저장되는 Plan의 결과 분류이고 Workflow 실행 상태나 사람 승인 상태와 별개다. `result_version`은 Plan 내 양의 정수 버전, 모든 ID는 불투명 문자열이며, 수량·target은 부동소수점이 아닌 정수 또는 명시된 decimal 계약을 사용한다. 시간은 RFC 3339 UTC instant로 직렬화하고 입력 timezone을 별도 보존한다. 상태 매핑은 아래 표를 따른다.

필드 규칙: required 필드는 항상 존재한다. `venue`, `end_at`, `evaluation_horizon_days`, `display_label`, `method_ref`, `value`, `runtime_adapter_ref`처럼 조건부 값만 nullable이다. 목록형 필드는 데이터가 없으면 null 대신 빈 배열을 쓴다. `impact_assessment.value`는 결정적 계산 또는 근거 있는 추정이 있을 때만 숫자이며 `unknown`이면 null이어야 한다. `calculated` 결과는 재현 가능한 `method_ref`와 snapshot/evidence 참조를 모두 포함한다. 사용자 KPI의 실제 성과는 population/행동 근거가 없으면 `unknown`이다. 별도로 Runtime이 grant policy를 보장하는 경우에는 item별 `per_user_reward_ceiling`을 수량×최대 지급 횟수로 결정적으로 계산할 수 있다. 이 값은 아이템 단위의 지급 상한이며, 참여율·실제 수령량·다른 재화로 환산한 가치를 뜻하지 않는다. 미션 콘텐츠의 시작 시점 접근 가능성은 같은 snapshot의 `start_level`/segment 최소 레벨과 `entry_level`로 계산하고, segment 상한보다 높은 콘텐츠는 BLOCKED finding으로 Runtime 적용을 막는다. 이벤트 기간의 접근 가능성은 성장 곡선 자료가 없으면 `unknown`으로 남긴다. 결정적 전투 규칙·적 스탯·영웅 기본 스탯이 snapshot에 모두 있으면 `mission_combat_feasibility`로 콘텐츠 입장 레벨 또는 segment 최소 레벨, 그리고 segment 최고 레벨에서 기본 성장 상태(장비 강화 0)의 1회 전투 결과를 계산할 수 있다. 이 결과는 명시된 레벨·기본 스탯의 규칙상 승패이지 실유저 승률이나 기간 내 완료 확률이 아니다. 장비 강화 분포·유저 성장률·반복 참여 데이터가 없는 결과는 `unknown`으로 남기며 추정 숫자를 만들지 않는다. 각 `mission_id`, `reward_id`, `capability_id`, `item_id` 참조는 같은 Plan 및 고정된 `game_context`에서 해석되어야 한다. 상세 capability 조합과 지원 상태는 문서 [10](10_RuntimeCapability_MCP_계약.md)을 단일 기준으로 한다.

이벤트 적용 시 이 계약은 [게임 이벤트 적용 계약](../게임설계/05_이벤트적용_계약.md)의 event schema에 매핑된다. `action_type`/`filters`/`goal`/`content_scope`, 세그먼트, venue, 보상 지급 정책은 게임 카탈로그가 허용한 조합만 쓴다. `mission_reward_links[]`와 `rewards[].mission_id`는 서로 같은 연결을 표현하며 서로 불일치하면 거절한다. 이벤트 runtime에 없는 venue ID를 Plan에서 만들지 않고 template 참조만 전달한다.

게임 이벤트 schema는 현재 한 `segment_id`를 받는다. Brief에서 여러 대상 segment를 요청하면 별도 이벤트로 분리 가능한지 검증하고, 게임 계약이 이를 표현하지 못하면 임의로 하나를 선택하지 않고 `NEEDS_DEVELOPMENT` 또는 명시적 대안 확인으로 반환한다. Event Plan의 `source_ref.task_id`는 기존 Task 기반 기획 결과와 게임 적용 adapter를 연결한다. `plan_id`는 도메인 식별자이며 기존 적용 계약의 `task_id + result_version`을 대체하지 않는다.

| 평가 결과 | `plan_status` | Workflow 상태 | `runtime_eligible` |
|---|---|---|---|
| `PASS` | `VALIDATED` | `AWAITING_FINAL_APPROVAL` | 모든 필수 검증이 통과하고 현재 capability가 지원될 때만 `true` |
| `NEEDS_DEVELOPMENT` | `VALIDATED_WITH_DEVELOPMENT_ITEMS` | terminal `PLAN_READY_WITH_DEVELOPMENT_ITEMS` | 항상 `false` |
| `NEEDS_DATA` | `NEEDS_DATA` | terminal `PLAN_READY_WITH_DATA_GAPS` | 항상 `false` |
| `HUMAN_REVIEW` | `DRAFT` 또는 미확정 candidate | `AWAITING_HUMAN_REVIEW` | 항상 `false` |
| `REVISE` | candidate는 `DRAFT` 유지 | `REVISING` 후 전체 재검증 | 항상 `false` |
| `BLOCK` | `BLOCKED` | terminal `BLOCKED` 또는 `SAFE_STOP` | 항상 `false` |

필수 사용자 입력 자체가 누락된 경우 Plan을 만들지 않고 `AWAITING_USER_INPUT`으로 전환한다. 게임 데이터/근거가 없어 의미 있는 평가가 불가능한 `NEEDS_DATA` 결과는 데이터 gap과 필요한 출처를 기록해 종료한다. 사용자가 누락 데이터를 제공하거나 데이터 카탈로그가 갱신되면 새 Brief/Workflow version으로 다시 실행한다. `runtime_eligible`은 서버가 검증 결과로 계산하며 모델 출력이나 클라이언트 입력을 신뢰하지 않는다.

## 4. 개발 필요 항목 계약

`development_requirements[]`의 각 항목은 다음을 포함한다.

| 필드 | 의미 |
|---|---|
| `requirement_id` | 결과 안에서 안정적인 finding 식별자 |
| `capability_id`, `support_status` | 미지원 capability와 상태 |
| `requested_behavior` | 사용자가 원한 동작을 구체적으로 설명 |
| `required_work[]` | 필요한 게임 로직·데이터·화면·API·검증 작업 |
| `dependencies[]` | 필요한 콘텐츠·규칙·시스템 계약 |
| `impact` | 영향받는 미션·보상·밸런스·Runtime 경계 |
| `evidence_refs[]` | 지원 여부와 판단 근거 |
| `unknowns[]` | 지금은 계산·검증할 수 없는 항목 |
| `acceptance_criteria[]` | 해당 기능이 지원 가능으로 바뀌는 확인 조건 |

여러 미지원 요소가 한 기능을 함께 요구하면 하나의 capability requirement로 묶되, 개별 미션·보상과의 연결을 보존한다. 요약에는 중요도와 Runtime 적용 불가 이유를 표시한다.

## 5. 계약 불변조건

1. 모든 미션은 허용된 `action_type`/필터와 판정 가능한 `goal(metric, aggregation, operator, target)`을 가져야 한다.
2. 보상은 유효한 미션 완료 조건 또는 명시된 지급 조건에 연결되어야 한다.
3. 장소·행동·보상·이벤트 template은 capability ID와 버전을 참조한다.
4. 개발 필요 finding이 하나라도 남아 있으면 `runtime_eligible=false`다.
5. `UNSUPPORTED_BY_POLICY`는 `NEEDS_DEVELOPMENT`로 바꿀 수 없다.
6. `NEEDS_DATA`는 검증 통과로 간주하지 않으며 불확실성·필요 데이터·재실행 조건을 결과에 명시하고 `runtime_eligible=false`로 둔다.
7. Runtime 적용은 별도 사람 승인과 source result version 검증을 요구한다.
8. LLM이 만든 설명은 근거가 아니며, evidence reference와 검증 결과를 함께 저장한다.

## 6. 완료 기준과 후속 결정

- 요청의 8개 핵심 요소(목적, 대상, 시간, 장소, 행동, 보상, 영향, 행동-보상 연결)가 계약에서 빠짐없이 연결된다.
- 지원·개발 필요·데이터 필요·정책 차단 상태의 의미와 Runtime 자격이 명확하다.
- 시나리오 예시: 전부 지원, 일부 개발 필요, 데이터 부족, 정책 차단, 행동-보상 링크 누락.
- 기획안·게임 데이터·Runtime 계약의 `domain_schema_version`, `event_schema_version`, `game_ruleset_version`, `game_data_snapshot_id`, `capability_catalog_version`, `balance_policy_version` 연결 및 evidence 기준이 합의된다.

실제 게임 경제 한도와 세그먼트 정의는 Runtime catalog를 권위로 삼는다. 게임 규칙·데이터 및 버전이 확인되어 결정적 계산기로 재현 가능한 영향은 `calculated`로 기록한다. 그 값을 근거 없이 `estimated`로 낮춰 표현하지 않는다. `estimated`는 근거가 있지만 모델·표본·가정 때문에 결정적 수치가 아닌 경우에만 사용하며, 근거 자체가 없으면 `unknown`으로 둔다.

## 구현 반영: 이벤트 던전 입력 계약 (2026-10-11)

현재 UI는 이벤트 던전을 고정 장소로 제시하고, `opong-data-1.5.0` 카탈로그의 공간 중 열 공간을 선택하게 한다. 선택된 공간은 `special_dungeon_space_clear`, 목표 1회의 action/mission으로 변환되며 공간별 보상 링크를 갖는다. 선택하지 않은 공간은 Runtime 등록과 게임 입장에서 제외된다. 선택 공간 계약은 [변경 계획·구현 기록](12_기획안_선택공간_Runtime_개방동기화_변경계획.md), 과거 floor 계약 결정은 [층별 미션·보상 변경 기록](11_이벤트던전_층별_미션보상_변경작업.md), 확인된 현재 동작은 [현재 구현 상태](../현재_구현상태.md)를 기준으로 한다.
