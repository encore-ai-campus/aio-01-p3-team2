# 오류 분류·복구 정책 설계

## 1. 목적·범위·현행 기준

이 문서는 기획 Workflow 요청부터 승인 대기까지 발생하는 오류를 안정된 원인·장소 코드로 기록하고, 오류 원인과 복구 action을 분리하는 정책을 정한다. 승인 후 게임 Runtime 등록·진행·보상 오류는 Runtime 상세 설계의 별도 정책을 따른다.

현재 `routing.py`는 planning error 3종을 Planner revision, Agent/validation/LLM timeout 오류를 retry, 일부 MCP 오류를 retry/fallback, DB connection error를 retry, 기타를 safe stop에 보낸다. `retry.py` 기본값은 최초 호출 후 기술 retry 3회(최대 4회 호출), plan revision 최대 2회다. 이는 현재 동작과 목표 기본값이 일치하는 항목이다. 180초 Workflow deadline, 호출별 30초 timeout, backoff/jitter, Workflow당 LLM 최대 8회 호출, 누적 token·비용 budget, policy version registry/operator policy UI는 목표 설계이며 현재 기본 라우터에는 구현되어 있지 않다.

## 2. 오류 ID와 발생 이벤트 계약

고정 오류 유형은 `ERR-<CAUSE>-<LOCATION>-<ID>`로 표기한다. 예: `ERR-DOMAIN-PLANNER-001`. 첫 segment는 아래 Registry의 대문자 cause code, 두 번째는 대문자 component/location code, 마지막은 해당 cause-location namespace 안에서 영구 배정되는 3자리 순번이다. 이 문서에 표기된 `SEC`, `STORE`, `DEP`, `CTRL`, `OBS`는 정식 코드이며 별칭이 아니다. 기존 시스템의 error type은 Registry에 legacy alias로 연결한다. 코드 이름에 severity, retry count, task UUID, 메시지를 넣지 않는다.

초기 정식 vocabulary는 `INPUT`, `SEC`, `SCOPE`, `DATA`, `CONTRACT`, `DOMAIN`, `DEP`, `STORE`, `CTRL`, `OBS`, `INTERNAL`이다. 장소 코드는 `API`, `SCOPE`, `PLANNER`, `HANDOFF`, `RULE`, `REWARD`, `TOOL`, `LLM`, `MCP`, `DB`, `TRACE`, `WORKFLOW`를 사용한다. 신규 조합은 registry 검토와 문서 변경으로만 추가하며 기존 코드를 다른 의미로 재사용하지 않는다. `SCOPE`는 통상 결과 finding이지 장애 exception이 아니므로, 아래 `ERR-SCOPE-CHECK-001`은 기계적으로 처리해야 하는 지원 범위 판정 event code로만 사용한다.

각 발생 이벤트는 최소 다음을 기록한다.

```yaml
error_code: ERR-...
error_occurrence_id: string
category: INPUT | CONTRACT | DOMAIN | SCOPE | SECURITY | DATA | DEPENDENCY | STORAGE | CONTROL | INTERNAL
phase: request | scope | planning | tool | validation | critic | approval
component: string
operation: string
task_id: string
workflow_id: string
trace_id: string
attempt: integer
revision_count: integer
retry_class: NEVER | OPERATION | AGENT | PLAN | HUMAN
severity: INFO | WARNING | ERROR | CRITICAL
safe_details: object
occurred_at: datetime
```

이벤트 발생 사실과 복구 정책 결정은 서로 다른 레코드다. 정책 기록은 `recovery_policy_id`, `recovery_policy_version`, `matched_rule_id`, `action`, `decision_reason_code`, `deadline`, `attempt`, `result`를 참조한다. 사용자 메시지는 안전한 template ID로 만들며 exception 원문을 직접 노출하지 않는다.

## 3. 초기 오류 카탈로그

| 코드 | 원인·장소 | 기본 분류 | 허용 대응 |
|---|---|---|---|
| `ERR-INPUT-API-001` | 요청 필수값·타입·범위 오류 | INPUT | `FAIL_FAST`; 필드 보완 안내 |
| `ERR-SEC-INPUT-001` | 악의적 지시·secret 요청·정책 우회 의도 | SECURITY | `SAFE_STOP` 또는 안전 부분 분리 불가 시 block |
| `ERR-SCOPE-CHECK-001` | 미지원 capability | SCOPE finding, 시스템 장애 오류 아님 | 기획 결과에 `NEEDS_DEVELOPMENT`; Runtime 차단 |
| `ERR-DATA-CONTEXT-001` | 게임 데이터 미존재·버전 불일치 | DATA | 다른 버전을 섞지 않고 `NEEDS_DATA`/`PLAN_READY_WITH_DATA_GAPS` 또는 safe stop |
| `ERR-CONTRACT-PLANNER-001` | Planner 출력 schema 불일치 | CONTRACT | 제한된 `RETRY_AGENT`; 반복 실패 stop |
| `ERR-CONTRACT-HANDOFF-001` | task 수신자·입력·버전 계약 불일치 | CONTRACT | 잘못된 handoff 거부, 원인 수정; 무한 retry 금지 |
| `ERR-DOMAIN-PLANNER-001` | 목적·Brief mismatch | DOMAIN | Planner 수정, 전체 재검증 |
| `ERR-DOMAIN-RULE-001` | 미션 달성 불가·게임 규칙 위반 | DOMAIN | 변경 가능한 조건만 수정, hard constraint면 human/stop |
| `ERR-DOMAIN-REWARD-001` | 미존재/불가 보상·수량 한도 초과 | DOMAIN | 대안 조건 내 수정, 고정 요구면 finding 반환 |
| `ERR-SEC-TOOL-001` | Agent/Tool 권한 또는 argument policy 위반 | SECURITY | 즉시 차단, no retry/fallback/revision |
| `ERR-DEP-LLM-001` | LLM 일시 timeout/throttle/5xx | DEPENDENCY | `RETRY_AGENT` bounded |
| `ERR-DEP-LLM-002` | LLM 인증·설정 등 영구 오류 | DEPENDENCY | fail fast, operator action |
| `ERR-DEP-MCP-001` | MCP timeout/연결 오류 | DEPENDENCY | 허용 read operation만 bounded retry |
| `ERR-DEP-MCP-002` | Tool 오류 또는 응답 contract 위반 | DEPENDENCY/CONTRACT | tool별 retry/fallback 허용표; invalid data는 fallback 금지 |
| `ERR-STORE-DB-001` | DB 일시 연결·읽기 실패 | STORAGE | retry budget 내 재호출 |
| `ERR-STORE-DB-002` | DB write 결과 불명확/충돌 | STORAGE | 결과 조회·멱등성 확인 후 결정; blind retry 금지 |
| `ERR-OBS-TRACE-001` | 필수 Trace 기록 실패 | STORAGE | 정책상 감사 필수 시 task success 불가 |
| `ERR-CTRL-LIMIT-001` | retry/revision/deadline budget 소진 | CONTROL | `SAFE_STOP`, 마지막 상태 보존 |
| `ERR-UNKNOWN-WORKFLOW-001` | 미분류 exception/policy missing | INTERNAL | fail-closed `SAFE_STOP` |

`mission_unreachable`, `item_not_found`, `event_brief_mismatch` 등 기존 error type은 전환 기간 동안 legacy alias로 유지하고 새 code로 매핑한다. fault-injection input은 runtime error code와 구별한다.

## 4. Recovery Policy 모델

```yaml
recovery_policy_id: planning.retry.agent.transient
recovery_policy_version: 1
status: DRAFT | ACTIVE | DISABLED
match:
  error_codes: [ERR-DEP-LLM-001]
  phases: [planning, critic]
  components: [event_planner_agent, critic_agent]
action: RETRY_AGENT
max_retries: 3
max_total_attempts: 4
workflow_deadline_seconds: 180
call_timeout_seconds: 30
backoff: { strategy: exponential_jitter, initial_ms: 250, max_ms: 4000 }
max_llm_calls_per_workflow: 8
  max_input_tokens_per_workflow: positive_integer_from_model_config
  max_output_tokens_per_workflow: positive_integer_from_model_config
  max_cost_per_workflow: { amount: positive_decimal_from_runtime_config, currency: configured_iso_4217 }
fallback_target: null
required_revalidation: [output_schema, domain_rules, final_consistency]
user_message_template: retrying_transient_dependency
operator_signal: dependency_retry_exhausted
```

기술 retry는 최초 호출 뒤 최대 3회(총 최대 4회), 자동 plan revision은 최대 2회다. Workflow 전체 deadline은 180초, 개별 LLM/MCP 호출 timeout은 30초로 시작한다. transient 오류 재시도 간격은 exponential jitter, 250ms 시작·4초 상한을 사용한다. Workflow당 LLM 호출은 최대 8회다. Controller는 이 한도와 별개로 누적 input token, output token 및 비용을 함께 계수한다. Token 상한은 provider/model config의 양의 정수이고, 비용 상한은 실행 설정의 양수 decimal 및 ISO 4217 통화로 전달한다. 단가가 없는 모델은 비용을 `unknown`으로 기록하고 비용 한도를 통과한 것으로 간주하지 않는다. 운영 시작 시 가격표 누락은 SAFE_STOP으로 처리한다. 코드 hard cap은 모델 설정으로 상향할 수 없다. 호출 수·시간·token·비용 중 하나라도 소진되면 추가 호출 없이 `SAFE_STOP`하고 실제 사용량/계측 불가 사유를 Trace에 기록한다. 보안·권한 오류, 계약 위반, 결과 불명 DB write는 이 예산이 남아 있어도 retry하지 않는다.

## 5. 허용 action과 strict rules

| Action | 사용 | 금지 조건 |
|---|---|---|
| `FAIL_FAST` | 입력/영구 오류 | 오류 감춤 또는 사용자 입력을 자동 변경 |
| `RETRY_OPERATION` | transient safe read | 권한·보안·invalid response, write 결과 불확실 |
| `RETRY_AGENT` | 일시 model/agent 오류 | schema/permission violation 반복, budget 초과 |
| `REVISE_PLAN` | 수정 가능한 도메인 finding | security finding, 고정 사용자 조건 완화 |
| `USE_FALLBACK` | 사전 allowlist된 동등 데이터 소스 | 다른 schema/version/stale/unauthorized source |
| `REQUIRE_HUMAN` | 모호한 근거·상충 조건 | 단순 지원 범위 초과는 finding으로 표기 |
| `SAFE_STOP` | unclassified, security, budget exhaustion, safe recovery unavailable | stop 후에도 검증되지 않은 plan을 approval에 노출 금지 |

불변조건:

1. security/permission error는 policy config로 retry/fallback/revision할 수 없다.
2. unknown error, missing/invalid policy는 항상 `SAFE_STOP`이다.
3. user policy cannot increase code-level retry/revision ceilings or disable validators.
4. fallback은 source/version/schema equivalence를 결정적으로 확인한 경우에만 허용한다.
5. Recovery success는 output/domain/final validation을 모두 통과해야 한다.
6. persistent write retry는 idempotency key와 outcome lookup 없이 허용하지 않는다.
7. policy matching은 결정적 우선순위이며 ambiguous multiple matches는 reject한다.

## 6. 정책 문서 관리 lifecycle

1. 단일 권한 사용자가 허용된 YAML/JSON field로 policy draft 작성
2. schema/type/range/action/phase/tool/rule overlap 검사
3. hard security invariant와 retry budget 검사
4. representative error corpus replay 및 변경 영향 preview
5. 통과 시 immutable version 저장, 사용자가 activation 결정
6. Workflow 시작 시 active policy version을 고정하고, 실행 중 활성 버전이 바뀌어도 해당 Workflow는 시작 시점의 버전을 끝까지 사용
7. 모든 실행에 `recovery_policy_id/recovery_policy_version` Trace 기록
8. 오류율/복구 성공률 확인, 이상 시 이전 version rollback

정책 파일은 Python/shell/임의 expression을 실행하지 않는다. 작성자·승인자 분리는 후속 RBAC로 가능하지만, 초기에도 자동 검증과 감사는 생략하지 않는다.

## 7. 기본 정책 매핑

| Error class | Policy action | 재검증/종료 |
|---|---|---|
| 사용자 입력 불량 | fail fast | 수정 필드 반환 |
| transient LLM/MCP | bounded retry | 성공 후 Schema+rules+final validation |
| Planner의 수정 가능 finding | revision | 전체 영향 검증; 최대 2회 현행값 |
| 미지원 기능 | no healing; result annotation | `runtime_eligible=false`, terminal proposal |
| 권한·보안 위반 | immediate safe stop | 감지 finding/trace, no retry |
| ambiguous evidence | human review 또는 needs-data result | 추정하지 않음 |
| DB write 결과 불명 | outcome lookup | idempotent replay only |
| retry/revision/deadline 소진 | safe stop | 마지막 검증 상태 기록 |
| unknown/policy unavailable | safe stop | 운영자 조사 |

## 8. 운영 지표와 완료 기준

오류별 발생량, recovery action, 성공률, attempt 수, revision 수, terminal state, policy version, Runtime eligibility, human review 건수를 측정한다. 오류 label은 집계 가능한 고정 코드며 자유형 exception message를 metric label로 쓰지 않는다.

완료 기준:

- 모든 현행 error type은 카탈로그에 alias와 위치가 있음
- 같은 event가 같은 policy version에서 결정론적으로 같은 route를 선택
- 공격·권한 오류와 일반 복구 오류가 분리됨
- 누락 정책·중복 매칭·예산 소진을 fail-closed 처리
- policy draft 검증, preview, activation, rollback과 trace 연결이 정의됨
- capability finding은 시스템 장애 retry와 분리
