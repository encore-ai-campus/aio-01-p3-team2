# 오토힐링 정밀 테스트 계획

작성일: 2026-10-11 · 상태: **계획 / 이번 문서 작성에서 시험을 실행하지 않음**

## 1. 목적과 기준

**목적은 가이드의 「배포 및 장애 복구 보고서」에 들어갈 장애 시험을 수행하고 증빙을 확보하는 것이다.** 실제 실행 지점에 오류 상황을 주입해 검출·분류·오류 대응 정책 적용·오토힐링·안전 중단이 제대로 작동하는지 검증한다. 정상화 결과뿐 아니라 정책 준수, 복구시간, 수동 개입, 실패 원인도 기록한다. 아키텍처 설계서나 CI/CD 보고서 전체를 만드는 작업으로 범위를 확대하지 않는다.

참조 순서:

1. [현재 시험실 구현 및 증빙](16_오류시험실_구현과_검증.md): 현재 지원 범위와 기존 결과. 최근 수정은 §9, UI는 §10.
2. [오류 정책 설계](05_오류분류_복구정책_설계.md): 오류 코드·정책·한도·복구 금지 조건.
3. [Workflow 설계](02_멀티에이전트_Workflow_설계.md), [보안 설계](04_보안_권한_설계.md), [API·저장 설계](06_API_저장_Trace_설계.md).
4. [보존 가이드](../pre/멀티_에이전트_협업_및_서비스_운영_가이드.md): 3절 7단계, 4절 장애 대응 결과 지표, 제출 체크리스트. 예시 전략 전부를 구현해야 한다는 뜻은 아니다.

CI/CD·배포 차단·알림 파이프라인 검증은 이번 장애 주입 시험의 범위 밖이다. 이 시험이 보고서 전체의 배포/알림 항목까지 검증했다는 뜻은 아니다.

### 1.1 장애 시험에서 반드시 답할 질문

| 검증 항목 | 확인할 질문 | 증거 |
|---|---|---|
| 주입 | 선택한 함수/경계에 의도한 상황이 발생했는가? | 위치·패턴·횟수·변형값·주입 journal |
| 검출·분류 | 실제 코드가 검출하고 올바른 오류 코드로 분류했는가? | catch/검증 결과·검출 journal·Trace |
| 정책 적용 | 고정된 정책의 규칙·한도·금지 조건대로 판단했는가? | 정책 version/hash·적용 규칙·기대/실제 action |
| 복구 실행 | 재시도·대체 경로·기획 수정 등이 실제로 실행됐는가? | 호출/수정/대체 횟수·상태 전이·실행 Trace |
| 결과 안전성 | 정상화 또는 안전 중단하고 중복/금지 부작용을 막았는가? | 최종 상태·결과/DB 비교·멱등성·추가 호출 금지 |
| 측정·분석 | 복구시간·수동 개입·실패 원인과 개선을 설명할 수 있는가? | 실제 측정·판정·수정 전후 실행 ID |

### 1.2 산출물과 범위

작성할 결과는 `docs/ik/검증산출물/장애시험_결과보고서.md`로 계획한다. 아직 작성/완료되지 않았으며, 향후 「배포 및 장애 복구 보고서」의 장애 시험 절에 사용할 근거다. 입력·기대·실제·증빙·복구시간·수동 개입과 장애 유형별 집계를 포함한다. 별도 아키텍처/파이프라인 보고서 골격을 먼저 만들 필요는 없다.

등록 오류 28개와 허용된 정책/주입 패턴의 분기를 검증한다. 동일 의미의 조합은 묶을 수 있지만 서로 다른 정책 결정·복구 한도·부작용 분기는 생략하지 않는다. 모든 사례의 PASS뿐 아니라 정책 위반·복구 실패·판정 불가의 원인을 식별할 수 있는 것이 중요하다. 안전 중단 PASS는 자동 정상화 성공으로 집계하지 않는다.

## 2. 현재 가능한 시험과 추가 준비

| 범위 | 현재 상태 | 이 계획에서 할 일 |
|---|---|---|
| 등록 오류 28개 / 시나리오 28개 | 격리 DB/MCP와 실제 Workflow로 실행 가능 | 허용된 정책·패턴 조합을 명세하고 다시 실행 |
| 고정 데이터 변형·예외·예산/시간/버전 조건 주입 | 구현됨 | 값 변형·경계값·일시/지속 오류를 확대 |
| 실제 검출·정책·상태·DB 효과 검사 | runner의 checks 및 Trace 존재 | 독립적인 기대값과 누락/오판정 검사 보강 |
| DB 반복 쓰기 실패 | 저장 복구 단위 검사 존재, UI는 once만 허용 | 기존 단위 검사를 활용하고 시스템 전용 fixture 필요성 판단 |
| 실제 MCP/DB 중단, worker 종료 | 관련 통합 검사 파일 존재 | 현재 환경에서 적용 가능한 범위 확인 후 별도 실행·증빙. 파일 존재를 통과 증거로 쓰지 않음 |
| 실제 LLM 응답·품질·사용량 | 현재 시험실은 고정 adapter | 일반 기획 경로의 별도 실호출 시험 사용. 시험실을 실호출 지원처럼 표현하지 않음 |
| 실행 중 정책 변경·취소·DIRTY 복구 | 시험실 전용 시나리오/UI 미지원 | 전용 fixture/절차를 먼저 보완하고 통과 전까지 미검증 표시 |
| 승인 후 게임 등록·미션·보상 장애 | 시험실 runner 미지원 | 기획 오토힐링 완료와 분리한 후속 Runtime 시험 |

기존 Task의 미션/아이템/요청 불일치 3개는 canonical 경로의 의미 검사 전체를 대신하지 않는다. 현재 canonical 경로의 경제 계산·게임 지원 범위·근거 연결을 별도 계약 시험으로 확인한다.

## 3. 공통 실행 계약

- 환경: 시험 UI 5183, API 8013, MCP 8014, 전용 DB `eventquest_fault_test`. 현재 launcher 설정을 실행 직전에 대조한다. 사용자 DB와 일반 서버는 중단/변형 대상으로 삼지 않는다.
- 준비: 환경 상태 CLEAN, 기준 게임 snapshot과 digest, 활성 정책과 원래 hash/effective hash, 오류 카탈로그 version을 확보한다. 정책 복원이 실패하면 다음 시험을 멈춘다.
- Git HEAD만으로 코드 버전을 증명하지 않는다. 현재 작업 트리 변경이 있으므로 HEAD + 관련 코드/설정의 digest + dirty 여부를 기록한다. 비밀 환경값은 수집하지 않는다.
- 시험 목록은 실행 전에 확정한다. `patterns/profiles`는 카탈로그와 API 검증을 따른다. UI가 허용하지 않는 조합은 요청을 억지로 보내지 않고, 전용 단위/통합 fixture로 구분한다.
- 결과의 오류 코드·결정·종료 상태를 사람이 정한 기대값과 비교한다. 테스트 대상의 분류 함수로 기대 오류 코드까지 계산하면 동일 결함을 놓칠 수 있으므로 별도 명세를 사용한다.
- 이전 FAIL/INCONCLUSIVE 보고서는 보존한다. 수정 전 결과 → 변경 근거 → 수정 후 결과를 실행 ID로 연결한다.
- 시험실의 정책 활성화가 서로 충돌하지 않도록 시스템 시험은 순차 실행한다. 병렬화는 공유 DB/정책에 영향 없는 단위 검사에만 적용한다.

## 5. 실행 단계

### A. 무주입 정상 기준 확보 — 최우선

정상 요청 3종: 단일 특별 던전 공간/재화 보상, 복수 공간/각 행동의 보상 연결, 스킨 보상. 각 요청은 현재 capability로 지원 여부를 먼저 확인한다. 미지원 스킨/구성은 개발 필요 결과를 기대하고 정상 Runtime 적용으로 간주하지 않는다.

확인: 원래 목적·대상·기간·선택 공간 유지, 측정 가능한 행동과 보상 연결, 계산 가능한 경제 영향의 계산 근거, Planner/Critic 인계, 사람용 결과와 Runtime 전달 결과의 일관성, 승인 전 게임 변경 0, 실제 DB 결과 조회. 지원되는 요청은 승인 대기까지 도달해야 한다. 무주입 기준이 실패하면 오류 주입 전체 실행보다 원인 해결을 우선한다.

### B. 등록 오류와 정책 분기 — 최우선

카탈로그의 28개에 대해 `current_active` 및 허용된 `safe_stop/retry_allowed`를 각각 확인한다. 프로필 이름만으로 결과를 결정하지 않는다. 업무 finding, 입력 차단, CAS, ACK 유실 조정 등은 전용 기대값을 따른다.

복구가 허용되는 오류는 once, first_n, always를 확인한다. first_n의 N=1은 once와 같은 의미이면 중복 실행을 생략하고 이유를 명세한다. 허용 범위 안에서 **복구 한도 직전 성공 / 한도 도달 중단 / 한도 이후 추가 실행 금지**를 확인한다. N=1..4를 정책 한도와 대조하며 지원하지 않는 값/조합은 API 거절 시험으로 분리한다. 기획 수정 한도와 재시도 한도는 따로 검사한다.

모든 case의 공통 합격 조건:

1. 선택한 위치에 주입된 증거와 실제 검출 증거가 별도로 존재한다.
2. 실제 분류 코드가 명세와 일치한다. 별도 원인 코드를 유지하는 한도 시나리오는 카탈로그의 관측 코드 계약으로 확인한다.
3. pinned 정책, 적용 규칙, 결정 이유, 시도/수정/대체 횟수가 일치한다.
4. 상태 버전과 전이 순서가 유효하며 terminal 이후 Agent/Tool/쓰기가 추가 실행되지 않는다.
5. 원래 요청과 마지막 유효 결과가 보존된다. 원래 요청을 임의로 바꿔 복구 성공을 만들지 않는다.
6. 금지된 Runtime 호출 0, 기준 게임 데이터 불변, run 소유 결과만 저장, 중복 row/부작용 0.
7. 필요한 Trace와 검출 근거가 빠지면 PASS가 아닌 INCONCLUSIVE다.
8. 원래 정책과 환경 CLEAN 복원이 확인된다.

### C. 데이터 변형과 의미 검사 — 최우선

| 묶음 | 추가 입력 변형 | 기대 결과 |
|---|---|---|
| 형식 | 필수 필드 누락/null/잘못된 타입, 빈 목록, 알 수 없는 필드 | 해당 계약에서 거절, 허용하지 않은 다음 작업 금지 |
| 참조 | 콘텐츠/아이템 없는 ID, 다른 게임 버전, 공간/템플릿 불일치 | 실제 snapshot 기준 검출, 잘못된 Runtime 구성 금지 |
| 행동·보상 | 연결 누락/중복, 음수·0·한도 초과 보상, 중복 첫 클리어 지급 설정 | 각 규칙에서 허용/거절을 먼저 명세하고 비교 |
| 기간·난이도 | 유한/무한 허용 값, 기간 경계, 달성 불가 조건 | 저장된 게임 규칙으로 계산; 근거 없는 추정 금지 |
| 경제·근거 | 재화 영향 계산, 스킨의 비재화 효과, 근거 없는 숫자/오래된 snapshot | 계산 가능한 값은 정확히 계산, 없는 근거는 unknown/자료 필요 등 계약 결과 |
| 기획 의미 | 요청 대상·공간·기간·목적 불일치, 사람용 설명과 Runtime 설정 불일치 | 수정 가능한 설명은 제한 수정, 고정 계약 변경은 차단/재검증 |

각 묶음은 정상 1개 + 규칙 경계 아래/정확히 경계/위 + 대표 부정 입력을 사용한다. 값은 현재 schema/게임 규칙에서 가져오고 임의의 경제 한도를 새로 정하지 않는다. 필수 값과 선택 값의 null 규칙을 구분한다. 고정 seed로 입력을 생성하고 결과 보고서에 seed와 실제 입력을 남긴다. 무제한 fuzzing은 하지 않는다.

### D. 정책·권한·상태·저장 불변조건 — 최우선

- 정책: 미등록 코드, 잘못된 action/한도, NEVER 복구 시도, 검증되지 않은 활성화, rollback, 과거 003 상속과 새 draft의 003 필수성.
- 정책 pin: 실행 중 새 버전 활성화 후 기존 실행의 판단은 원래 버전, 새 실행은 새 버전. 전용 fixture 준비 후 실행하며 현재 시험실 UI 지원으로 표현하지 않는다.
- 보안: 사용자 입력·MCP 자료·컨텍스트·Agent 출력의 지시 무시/시크릿 요청/쓰기 요청을 각각 검사. 금지 문구뿐 아니라 실제 읽기 전용 권한과 필드 whitelist, 허용된 정상 문장의 오차단도 검사한다. 유한 사례를 통과해도 모든 프롬프트 공격 방어를 보증하지 않는다.
- 저장: commit 전 실패, commit 후 ACK 유실, 재조정 읽기 실패, 소유권/version 변경, 제약조건 오류. 조회 불명/소유권 상실은 무조건 쓰기 재시도하지 않는다.
- 멱등성: 같은 key/같은 본문은 같은 실행, 같은 key/다른 본문은 거절. 같은 최종 처리의 중복 결과/보상 0.
- 격리: 주입 중 일반 무주입 요청이 영향받지 않음, 추가 시험 요청의 lease 충돌, 일반 API의 fault 필드/시험 경로 거부, finally 후 주입 컨텍스트 해제.
- crash: runner/worker 종료 후 성공으로 처리하지 않음, DIRTY/불확실 결과 보존, 자동 재실행 금지, 정책·DB 확인 후 명시적 복원. 기존 프로세스 검사와 시험실 전용 crash 절차의 차이를 기록한다.

### E. 실제 서비스 장애 — 후속 로컬 완료 게이트

순서: 격리 MCP의 연결 거절 → 지연/timeout → 응답 계약 오류 → 서비스 재시작 후 새 정상 요청. 해당 통신 계층에 맞는 실제 시험 fixture를 준비한다. HTTP status 429/5xx는 HTTP transport가 지원되는 경로에서만 시험하며 다른 transport의 예외와 혼동하지 않는다.

실제 DB 중단은 사용자 DB와 같은 컨테이너를 공유하므로 **현재 컨테이너를 중단하지 않는다**. 전용 PostgreSQL 프로세스/컨테이너 또는 연결 실패만 발생시키는 시험용 경로를 마련한 후 수행한다. 단순 synthetic OperationalError는 DB 프로세스 중단 통과로 기록하지 않는다.

장애가 복구되어도 기존 안전 중단 Workflow를 이어서 실행했다고 가정하지 않는다. 현재 계약에 따라 새 요청으로 정상화 여부를 확인한다. 시험 전후 MCP/DB 연결·정책·데이터 복원 증거를 남긴다.

### F. 실제 LLM 품질·비용 — 별도 평가

실제 LLM 일반 경로에서 대표 요청 3종을 각 3회 실행하는 작은 평가로 시작한다. 지원되는 특별 던전 기획, 다중 공간/보상 연결, 미지원 요구의 개발 필요 결과를 포함한다. 실험값으로 기획 규칙을 임의 변경하지 않는다.

모델·prompt/schema version·입출력 token·호출 수·latency·근거·수정 횟수·최종 결과를 기록한다. 비용은 확인된 실행 가격 설정과 실제 usage가 있을 때 계산하며 없는 값은 확인 불가다. 기존 token/call/deadline/cost budget을 먼저 확인하고 총 실호출 상한을 설정한다. 실패 반복을 무제한 재실행하지 않는다. 비밀값과 원문 응답은 공개 보고서에 복사하지 않는다.

정확한 prose 문자열 대신 목표/대상/기간/공간/행동/보상/근거 및 게임 규칙 준수로 평가한다. 9회 결과는 작은 표본으로 표시하며 보편적인 성공률로 표현하지 않는다. provider 연결 불가·키/가격/usage 정보 부재는 미실행/확인 불가로 기록한다.

### G. Edge 사용자 흐름과 결과 보고 — 최우선

무주입 정상 요청, 자동 복구, 예상 안전 중단, 실제 FAIL 또는 보존된 FAIL 조회, INCONCLUSIVE의 설명을 확인한다. 실패 화면 검사를 위해 정상 복구 코드를 고장내지 않고 화면 fixture/보존 보고서를 구분한다.

확인: 고정 그래프 좌표, 선택한 위치/원인, 실행 중 확인되지 않은 단계의 표시 금지, 완료 후 강조 초기화, 명시적 경로 보기/숨기기, 결과 선택/기록 조회 시 새 POST 없음, 정책 편집→검증→미리보기→활성화, 새 오류 코드 반영, JSON 증빙, 모바일/키보드 접근.

## 6. 결과 레코드와 지표

계획 목록에는 `case_id, scenario_id, route, target, variant, pattern/N, profile, expected_code/actions/terminal/counters, required_evidence, readiness`를 포함한다. 결과에는 run ID, 코드/설정 digest, snapshot/digest, pinned 정책 참조, 입력/seed, 실제 대응/DB 효과, 검출/완료 시간, 수동 개입 여부, verdict, 증빙, 원인/재검증 ID를 연결한다. 현재 API에 없는 메타데이터는 별도 명세/평가 보고서에 보완하고 지원하지 않는 요청 필드로 보내지 않는다.

- **코드 커버리지:** 필요한 28개 중 실제 검출·대응 증빙을 확보한 코드 수. alias/특수 관측 코드는 매핑을 명시한다.
- **분기 커버리지:** 사전 확정한 적용 가능한 정책/패턴/한도/저장 분기 중 실제 검증한 수. 28개 실행과 동일하지 않다.
- **시험 통과율:** PASS / (PASS + FAIL). NOT_EXECUTED/INCONCLUSIVE와 계획 대비 미실행 수를 바로 옆에 공개한다.
- **장애 자동 정상화율:** 자동 정상화 수 / 사전 확정한 기술·기획 장애 사례 수. 안전 중단은 정상화 성공이 아니다. 입력 거절·업무 자료/개발 필요·CAS 등 제외 목록과 이유를 공개한다. 안전 중단 전용 사례를 제외한 '복구 허용 사례 성공률'을 추가하면 별도 지표로 이름 붙인다. 정책에 맞춰 분모를 사후 축소하지 않는다.
- **복구시간:** 검출 → 정상화 완료의 실제 측정. 자동 정상화 성공 건만 평균을 계산하고 표본 수/측정 누락을 공개한다. 단조 시계 검출 증거가 없으면 null; 전체 처리 시간을 대체값으로 사용하지 않는다. 반복 실행 시 중앙값/최대도 함께 기록한다.
- 정책 준수율·안전 중단 성공률·금지 부작용 수·수동 개입 건수는 별도 표시한다.

한도 성공/중단 대표 case는 3회 반복해 흔들림을 확인한다. 전체 조합 반복을 기본으로 하지 않는다. latency SLO는 아직 확정하지 않았으며 현재 deadline/budget 준수부터 확인한다.

## 7. 완료 기준과 실행 순서

### 장애 주입 시험 완료

- 28개 등록 오류와 적용 가능한 정책·복구/중단 분기를 명세하고 실행 증거를 확보한다. 기존 Task와 canonical의 범위는 구분한다.
- 선택 위치의 주입 → 실제 검출/분류 → pinned 정책 결정 → 실제 복구/중단 → 최종 상태/DB 효과를 case별로 연결한다.
- 일시 실패 후 정상화, 반복 실패 후 한도 종료, 복구 금지 오류의 즉시 차단, 원래 요청 보존, 상태/권한/멱등성/저장 안전성을 확인한다.
- 계획 목록에 있는 FAIL·INCONCLUSIVE·NOT_EXECUTED를 분석하고 필요한 수정/재검증을 수행한다. 미지원 fixture는 미검증으로 남겨 전체 검증 완료라고 하지 않는다.
- 금지 쓰기·중복 결과·시크릿 노출 등 완료를 막는 결함을 해결한다. 과거 실패 기록은 보존하고 수정 후 실행 ID를 연결한다.
- 입력/기대/실제/증빙/측정 시간/개입 여부 및 복구율·평균 복구시간의 모집단과 계산 기준을 결과보고서에 기록한다.
- 시험 종료 후 원래 정책과 환경 CLEAN 복원을 확인한다.

### 보조·확장 시험의 구분

A의 무주입 정상 요청은 장애 주입 결과를 비교할 기준이다. C/D는 오류 검출·대응의 정확성과 안전성을 위한 검사다. G는 시험 선택/판정/증빙 UI의 정확성을 확인한다. E의 실제 서비스 장애와 F의 실제 LLM 품질·비용은 상황 주입 시험과 구분한 확장 평가다. 확장 시험 미실행을 고정 상황 주입의 실패로 섞거나, 고정 상황 주입 PASS를 실제 장애·실제 LLM 품질 보증으로 확대하지 않는다.

실행 순서: **오류별 주입/정책 분기 목록·기대값 확정 → 정상 기준 → 함수/계약 검사 → 실제 Workflow 오류 주입 → 실패 분석·수정·영향 재검증 → UI/증빙 확인 → 장애 시험 결과·지표 보고서 작성**.

## 8. 의미·디자인 체크리스트

- 처음 보는 사람이 어디에서 어떤 오류를 넣는지 알 수 있다.
- 주입 성공과 실제 검출 성공을 구분할 수 있다.
- 정책의 버전·결정·근거와 최종 상태를 연결할 수 있다.
- PASS가 복구 성공만 뜻하지 않으며 안전 중단/자료 필요/개발 필요를 구분한다.
- 원래 요청·결과·게임 적용 가능 범위와 경제 계산 근거를 확인할 수 있다.
- 자세한 Trace를 열지 않아도 결과를 이해하고, 필요하면 원문과 기대/실제 차이를 확인한다.
- 이전 기록이 현재 선택/실행으로 보이지 않는다. 새로고침이나 기록 조회가 재실행하지 않는다.
- 긴 오류 설명, 모바일, 키보드, 색상 없이도 위치와 판정을 확인할 수 있다.

각 항목에 충족/미충족/미확인과 화면·실행 ID를 남긴다. 자동 E2E의 통과와 별도로 사람이 읽을 수 있는 의미 검토 기록을 남긴다.

## 9. 자원·시간 관리

- 코드 변경 시 영향받는 함수/계약 → 관련 통합 → 필요한 Edge 순서로 실행한다. 문서만 바뀌면 서버/전체 시험을 재실행하지 않는다.
- DB/정책을 공유하는 시험은 worker 1로 순차 실행하고 별도 서버를 중복으로 띄우지 않는다.
- 같은 의미의 조합은 명세에서 묶고 대표 실행 근거를 남긴다. 서로 다른 정책/한도/부작용 분기는 묶어 생략하지 않는다.
- 기대 결과와 다른 case를 발견하면 해당 분기의 명세·oracle·실제 코드를 구분해 원인을 찾는다. 원인 해결 후 그 분기와 연결 회귀부터 재검증한다.
- 실험 완료 후 환경/정책 복원과 소유 프로세스를 확인한다. DIRTY이면 자동 정리하지 않고 증거 보존 후 명시적 복원한다.
