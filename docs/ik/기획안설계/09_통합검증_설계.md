# 통합 검증 설계

## 1. 목적과 범위

상세 설계 간 계약이 모순 없이 연결되는지 확인할 종단 시나리오와 증거를 정한다. 이 문서는 검증 설계 기준이며, 구현 완료나 실행된 테스트 결과를 주장하지 않는다. 구현 단계별 명령·담당·일정은 별도 구현 계획서에서 작성한다.

## 2. 현재 검증 기준

현재 증거는 [현재 구현 상태](../현재_구현상태.md)와 각 게임 설계의 최신 확인 기록에 한정한다. 게임 Runtime/API 및 UI 일부의 실제 DB·브라우저 검증은 수행됐지만, 본 문서의 기획 workflow capability 처리, 정책 UI/activation, 통합 Trace, 전체 오류 복구 시나리오가 모두 검증됐다는 뜻은 아니다. 이 문서의 E2E 항목은 향후 수용 기준이다.

## 3. 검증 계층

1. **함수/단위(Unit):** 순수 계산과 개별 규칙. 예: route decision, error mapping, budget 산정, 입력 정규화, Schema validator, 계산식, canonical request hash.
2. **컴포넌트(Component):** 한 컴포넌트의 경계 계약. 예: Handoff validator, Policy evaluator, MCP Tool response parser, repository, fault adapter. 외부 의존성만 명시적 fake/stub으로 대체한다.
3. **통합(Integration):** 내부 실제 API·서비스와 PostgreSQL/MCP의 연결. migration, transaction, unique constraint, 멱등성, 버전 조회와 오류 전파를 검증한다.
4. **시스템(System):** Backend Workflow 전체를 실제 PostgreSQL 및 내부 API로 실행해 상태 전이, Agent/도구 handoff, 복구·종료 결과를 검증한다. LLM은 고정된 결정적 adapter로 대체 가능하나 DB·내부 API를 mock으로 대체하지 않는다.
5. **브라우저 E2E:** 실제 UI→API→Workflow→PostgreSQL을 연결해 사용자 핵심 경로와 장애 시연 화면을 검증한다.
6. **운영·보안:** 비밀 마스킹, 권한 거부, 오류 복구, 정책 version/rollback, DB·cache·dependency 장애를 검증한다. CI/CD 배포 차단은 로컬 검증이 안정화된 뒤 별도 단계에서 검증한다.

LLM/외부 API가 없는 검증에서는 deterministic fake adapter를 경계에 주입할 수 있지만, DB와 내부 API를 대체 mock으로 흉내 내지 않는다. 외부 dependency를 생략한 결과는 그 한계를 증거에 표시한다.

### 3.1 테스트 파일과 자동화 관리

테스트는 함수 개수에 맞춰 잘게 쪼개기보다 계약·행동·장애 시나리오 단위로 관리한다. 저장소의 기존 테스트 framework와 실행 구조를 확인한 뒤 아래 분류를 적용하고, 이미 존재하는 flat test 파일은 단계적으로 옮기거나 명명 규칙으로 구분한다.

```text
backend/tests/
  unit/          # 순수 함수·정책·schema·라우팅 규칙
  component/     # Agent/Tool/Repository 컴포넌트 경계
  integration/   # PostgreSQL, MCP, 내부 API 연동
  system/        # Browser 없이 전체 Workflow 및 장애 분기
  e2e/           # 브라우저에서 실제 UI부터 DB까지
  fixtures/      # 버전 고정 catalog, Brief, Plan, 오류 시나리오
```

각 테스트는 `UT`, `CT`, `IT`, `ST`, `E2E`와 scenario ID 또는 기능명을 이용해 찾아갈 수 있게 한다. 단위 테스트는 빠르고 격리된 DB 없는 실행이어야 한다. DB 통합·시스템·E2E 테스트는 별도 테스트 DB를 사용하고 테스트 전용 schema/DB만 초기화한다. fixture는 버전과 출처가 고정되며 production 데이터·secret은 사용하지 않는다. 테스트 순서나 이전 실행 상태에 의존하지 않게 만든다.

로컬 개발 중에는 아래 gate를 같은 실행 명령/스크립트로 반복할 수 있게 자동화한다.

```text
형식·lint·Schema/정적 검사
  → Unit + Component
  → PostgreSQL/MCP Integration
  → Backend System Workflow
  → Browser E2E 핵심 경로
  → 로컬 release build
```

테스트 실패 또는 실행 누락은 성공으로 간주하지 않는다. flaky test를 성공 처리하기 위한 무조건 재시도는 두지 않는다. 외부 LLM 실제 provider 호출은 별도 credential이 필요한 smoke suite로 분리하고, 기본 로컬 suite에서는 고정 adapter로 결정적 검증을 한다. provider smoke가 생략되면 해당 실행 기록에 미검증 범위를 표시한다. 최종 사용자 테스트는 반복 기능 검증을 대신하지 않고, 자동 E2E로 검증할 수 없는 이해도·시각적 명확성 등 UX 수용 확인에 한정한다.

### 3.2 CI/CD 후속 단계

CI/CD는 로컬 기능·통합 테스트가 안정화된 뒤 착수한다. 따라서 GitHub Actions, artifact/image publish, 배포와 rollback은 로컬 시스템 기능 완료의 선행 조건이 아니다. 후속 CI/CD 단계에서는 로컬에서 반복 통과한 동일 테스트 명령을 Pipeline에 연결하고, 테스트 실패 시 publish/deploy 차단, 배포 후 health 확인, 실패 시 rollback을 별도 수용 기준으로 검증한다. Pipeline 적용 전까지는 로컬 test/build 실행 결과와 commit을 기록한다.

## 4. 필수 종단 시나리오

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| E2E-01 | 완전 지원되는 Brief 제출 | versioned Plan과 evidence, workflow trace 생성; eligibility true가 되는 조건 충족 |
| E2E-02 | 게임 기능 미지원 Brief | 개발 필요 요소·영향·수용 조건이 Plan에 기록되고 `runtime_eligible=false`; 등록 불가 |
| E2E-03 | 필요한 게임 데이터 누락/버전 불일치 | `NEEDS_DATA`/`PLAN_READY_WITH_DATA_GAPS`와 명확한 근거; 다른 버전 데이터 혼합 금지 |
| E2E-04 | mission-reward link 누락/불일치 | 검증 finding 또는 제한된 revision 후 재검증; 무근거 통과 금지 |
| E2E-05 | 사용자 승인 후 Runtime 등록 | 승인한 plan version 및 게임 규칙 버전만 등록; 실제 상태 기록 조회 가능 |
| E2E-06 | 같은 등록 요청 재전송 | 같은 idempotency key 결과 재사용, 중복 이벤트/보상 없음 |
| E2E-07 | 동일 key에 다른 payload | conflict, 기존 요청 결과 불변 |
| E2E-08 | transient LLM/MCP 실패 | 정해진 budget 안에서 재시도, 성공 후 전체 검증; 소진 시 안전 중단 |
| E2E-09 | prompt injection 또는 권한 위반 | 즉시 차단, 재시도/fallback/revision 금지, 안전 로그 기록 |
| E2E-10 | 정책 변경·활성화·rollback | schema/guard/replay 검사, immutable version 및 실행 참조 기록 |
| E2E-11 | Redis 미설정(초기 MVP) 또는 선택적 캐시 장애 | 로컬 MVP는 Redis 없이 DB 권위 경로로 실행되며 멱등성·보상 정합성을 유지한다. Redis 도입 뒤에는 동일 시나리오에서 cache outage fallback/제한을 별도 실행한다. |
| E2E-12 | DB 결과 불명/Trace 쓰기 실패 | outcome lookup 또는 업무 성공 불가 처리, 결과 상태를 숨기지 않음 |
| E2E-13 | UI 진행 표시 | 표시한 단계·시도·대기·결과가 실제 workflow event와 일치; 전체 수 사전 고정 금지 |
| E2E-14 | LLM 호출·token·비용 budget 소진 | 호출 8회 또는 누적 설정 budget에 도달하면 다음 호출 전에 `SAFE_STOP`; 실제 usage와 소진 원인을 Trace에 기록 |
| E2E-15 | Prompt/LLM 원문 열람·보존 | 제한된 단일 운영자만 raw record를 조회; 일반 Trace는 참조·요약만 보임; 30일 후 원문 삭제 |
| E2E-16 | MCP write 시도 | 초기 Tool catalog에 write가 없어 거부; 허용된 업무 변경은 내부 API/Controller 경계만 통과 |
| E2E-17 | 원격 접속·위조 actor_id | loopback 밖 접근을 거부하고 request body의 actor ID를 권한 증거로 수용하지 않음 |
| E2E-18 | 장애 시연 화면에서 사전 정의 시나리오 실행 | demo mode에서만 허용된 fault profile 주입; 실제 Controller/Router/정책/Trace 경로 사용; retry 복구·budget 소진 SAFE_STOP·revision 재검증 결과가 UI와 DB/Trace에서 일치하고 Runtime 상태는 변하지 않음 |

## 5. 구현 완료 수용 기준

전체 구현은 아래 게이트를 모두 통과할 때 완료로 판정한다. 문서·화면 목업·mock 내부 API만으로는 통과할 수 없다. 각 항목은 실행 기록, commit/build 식별자, Workflow/Trace ID, API 응답 및 필요한 DB 관찰 결과를 증거로 남긴다.

| Gate | 완료 조건 | 통과 증거 |
|---|---|---|
| G1. 정상 업무 흐름 | 사용자가 Brief를 제출하고, 규칙·근거 검증을 거친 Plan을 확인·승인한다. 같은 Plan 버전만 게임 Runtime에 적용되고, 가상 유저의 미션 진행·보상 기록이 화면과 PostgreSQL에서 확인된다. 브라우저 새로고침과 Backend 재시작 후에도 같은 상태가 복원된다. | E2E-01·05의 실제 API/UI/DB 결과, 동일한 `plan_id/result_version`, `runtime_event_id`, Trace ID |
| G2. 안전한 분기 결과 | 미지원 기능은 개발 필요 항목과 `runtime_eligible=false`로, 근거 부족은 `NEEDS_DATA`로 반환한다. 보안 위반은 차단하며 어느 경우도 승인·Runtime 적용 경로에 진입하지 않는다. | E2E-02·03·09, 결과 상태와 승인/등록 거부 응답 |
| G3. Workflow·Agent 계약 | Supervisor/Router가 LLM 호출 없이 동일한 입력·상태·정책 버전에 대해 같은 route와 `reason_code`를 반환한다. Handoff의 contract/version/권한 검사에 실패하면 수신 작업이 실행되지 않는다. Planner 수정 뒤에는 규칙 검증과 최종 검증이 다시 실행된다. | route 결정 로그, 유효·무효 Handoff 결과, E2E-04의 재검증 Trace |
| G4. 자동 복구·안전 종료 | `DEMO-HEAL-01`은 첫 MCP read timeout 뒤 재시도하여 회복하고, 전체 검증을 마친다. `DEMO-HEAL-02`는 최초 호출 포함 최대 4회에서 종료하고 `SAFE_STOP`하며 승인 가능한 Plan을 만들지 않는다. `DEMO-HEAL-03`은 수정 가능한 finding을 Planner에 전달하고 수정 뒤 전체 검증을 통과한다. 보안 오류는 자동 retry/fallback/revision하지 않는다. | scenario ID별 attempt/revision, policy version, terminal result와 Trace. 각 시나리오 3회 연속 재현 결과 |
| G5. 정책 관리 | 정책 draft의 형식·불변조건 검사, 대표 오류 replay preview, 활성화와 rollback이 가능하다. 활성화된 새 버전은 이후 실행에만 적용되고 기존 Workflow는 시작 시 고정한 버전을 유지한다. | E2E-10 및 변경 전/후 policy version·감사 Trace |
| G6. 상태 정합성·멱등성 | 동일 scope/key/hash의 재요청은 최초 결과를 재사용하고 서로 다른 payload는 conflict다. 이벤트·진행·미션·보상 쓰기는 PostgreSQL transaction/business key로 중복 반영되지 않는다. Redis 부재/장애가 권위 상태나 멱등성을 깨뜨리지 않는다. | E2E-06·07·11·12의 API 결과, DB row/잔액/원장 전후 대조 |
| G7. UI·Trace·장애 시연 | 사용자 화면의 현재 상태·시도·복구·중단 결과가 실제 Workflow event와 일치하며 전체 단계를 미리 확정해 표시하지 않는다. 장애 시연은 demo mode에서만 보이고 게임 Runtime 상태를 바꾸지 않는다. 내부 원문·secret은 일반 UI에 노출하지 않는다. 의미·시각 검토 UX-01~07에서 위험한 상태 오표시/CTA가 없어야 하며, 첫 사용자가 핵심 상태와 다음 행동을 이해할 수 있어야 한다. | Edge 브라우저 종단 시연, UI/API/Trace 상관 ID, Runtime 상태 전후 비교, UX-01~07 체크리스트와 화면 캡처/viewport 기록 |
| G8. 보안·경계 | 원격 접속과 위조 actor ID를 거부하고, exact Origin/CSRF 경계를 지킨다. MCP는 읽기 전용이다. 실제 상용 게임 계정·서버·경제에 write하지 않는다. prompt 원문은 제한 접근·30일 보존 정책을 따르고 일반 Trace에는 참조·안전 요약만 노출한다. | E2E-15·16·17, 접근 거부 응답 및 감사 로그 |
| G9. 로컬 실행 재현성 | 저장소 문서대로 로컬 환경을 시작하고 자동 테스트 suite를 실행할 수 있다. 테스트 실패·미실행을 성공으로 표시하지 않는다. | 깨끗한 로컬 환경 실행 기록, test/build 결과, commit 식별자 |
| G10. CI/CD 후속 수용 | 로컬 테스트 안정화 후 동일 검증을 GitHub Actions에 연결한다. format/lint/schema/필수 테스트/build 실패 시 artifact publish와 deploy를 차단한다. 배포 범위가 확정되면 image 식별, health 확인, rollback까지 검증한다. | CI/CD 단계의 성공·실패 Pipeline run ID, 실패 gate의 publish/deploy 차단 증거, 배포 health/rollback 기록 |

최종 사용자 수용 시연은 G1의 정상 흐름을 Edge에서 처음부터 수행하고, G2의 개발 필요 결과, G4의 자동 복구·안전 중단을 장애 시연 화면에서 이어서 보여준다. 각 시연은 설정된 LLM/MCP provider와 같은 외부 환경을 기록한다. 외부 의존성을 대체 adapter로 수행한 경우 실제 provider 연동 증거와 혼동하지 않고 별도 표기한다.

UI의 정적 계약은 자동 테스트로 확인하되, 상태 의미·정보 위계·화면 일관성·게임 연출은 [UI·UX 설계 §8.1의 UX-01~07 체크리스트](07_UI_UX_운영자콘솔_설계.md#81-의미디자인-검증-체크리스트)에 따라 Edge에서 검토한다. 이 검토는 기능 회귀를 수동으로 반복하는 절차가 아니라, UI 변경 후 위험 상태 표현 및 UX 수용을 확인하는 별도 증거다.

### 오토힐링 지표 판정

- **시나리오 복구 통과율:** 사전 정의된 자동 복구 가능 fault 시나리오 중 기대 terminal result와 재검증을 모두 만족한 실행 수 ÷ 해당 fault 시나리오 전체 실행 수. MVP 수용 시 deterministic fault 시나리오는 각 3회 실행하고 100% 일치해야 한다.
- **자동 복구율(운영 지표):** 안전하게 자동 복구 가능하다고 사전에 분류된 실제 일시 장애 중 사람 개입 없이 정상 업무 결과와 최종 검증까지 회복한 건수 ÷ 해당 일시 장애 전체 건수. 보안 차단·정책 차단·근거 부족·의도된 `SAFE_STOP`은 분모에서 제외하고 별도 건수로 보고한다.
- **평균 자동 복구 시간:** 자동 복구 성공 건에서 첫 장애 감지 시각부터 재검증을 통과한 시각까지의 평균. `SAFE_STOP`까지 걸린 시간은 복구 시간에 넣지 않고 안전 종료 시간으로 별도 보고한다. 실패·제외 건수와 기간도 함께 표시한다.
- 이 지표는 결과 목표값을 꾸며내기 위한 숫자가 아니다. 수용 시험의 정해진 주입 결과는 100% 재현성을 요구하고, 실제 운영 표본의 복구율·시간은 측정값으로 보고한다.

## 6. 불변조건 검증

- 개발 필요 항목이 존재하거나 정책상 차단이면 승인/Runtime API에서 거부된다.
- 실행은 자신이 사용한 Brief, Plan, 게임 데이터, 규칙, capability, recovery policy 버전을 기록한다.
- 재시도와 revision은 제한 예산·전체 deadline을 넘지 않고 성공 후 요구된 검증을 다시 수행한다.
- 미션 완료와 보상 지급은 원자적이며 중복 실행에 안전하다.
- `SAFE_STOP` 후 불완전 Plan은 성공/승인 가능 결과로 노출되지 않는다.
- 장애 시연 fault profile은 격리된 Workflow 범위에서만 활성화되고 Runtime 등록·보상 지급 상태를 변경하지 않는다.
- 사용자 UI·운영 로그·상세 Trace의 노출 정보는 권한과 민감도 규칙을 지킨다.

## 7. 증거와 설계 완료 게이트

각 시나리오는 입력 fixture, 실행 환경, 실제 DB/API 경계, 사용한 adapter, 결과 상태, 관련 trace ID, 관찰된 DB row/게임 상태, 판정 기준을 기록한다. 테스트 이름만으로 성공을 선언하지 않고 실제 assertion과 결과를 남긴다.

설계 완료 게이트:
- 계약·Workflow·보안·오류·데이터·UI·운영 문서의 용어와 version 참조가 일치
- 모든 상태 전이에 정상·복구·차단 또는 종료 경로가 존재
- 각 불변조건에 이를 검증할 시나리오 또는 정적 검사 연결
- 필요한 외부 dependency와 대체 adapter의 검증 한계를 밝힘
- 미결 항목과 구현 전에 필요한 결정을 분리하고 추적 가능
