# UI·UX·운영자 콘솔 설계

## 1. 목적과 범위

처음 보는 사용자가 이벤트를 요청하고 결과를 이해하며 진행 상태·근거·오류를 확인할 수 있게 화면 흐름과 정보 계층을 정한다. 운영자는 같은 화면에서 복구 정책의 초안·검증·영향 미리보기·활성 버전을 관리한다. 화면은 백엔드 상태를 표현하며 실행 단계를 미리 만들어내지 않는다.

## 2. 현재 구현 기준

현재 운영 콘솔은 기획안 입력, Workflow·Trace, 복구 정책, 격리 장애 시연, 운영 로그를 제공하고 승인된 Plan의 가상 Runtime 등록을 연결한다. 승인과 등록 이후 Trace는 PostgreSQL lifecycle event를 다시 조회한다. Runtime 등록 후에는 권위 Game API에서 미션 진행·보상 원장을 읽어 결과 화면에 표시하고 사용자가 갱신할 수 있다. 2026-10-10 Edge에서 UX-01/03/04/06 일부와 정책·Runtime 진행 화면을 확인했고, 긴 정책 이력 및 네이티브 입력 디자인을 개선했다. UX-01~07 전체 수용은 미완료이며, 최신 확인 및 잔여 항목은 [현재 구현 상태](../현재_구현상태.md#최신-edge-ux-수용-확인)를 기준으로 한다.

## 3. 사용자와 정보 계층

초기 사용자는 한 명이며 기획·검토·승인·정책관리 권한을 가진다. 보안 불변조건과 정책 상한은 사용자 권한으로도 완화할 수 없다. 화면 정보는 다음 계층을 따른다.

1. **요약:** 지금 무슨 일이 일어나는지, 결과/대기/차단 여부, 다음 행동.
2. **근거:** 주요 판단, 게임 데이터·규칙 버전, 지원 여부, 개발 필요 항목.
3. **세부 정보:** Agent/task/handoff, 검증 finding, 오류 코드, 복구 시도와 Trace.

사용자에게 내부 component 이름이나 stack trace를 기본 노출하지 않는다. 확장 영역에 안전한 요약과 trace ID를 제공한다.

## 4. 화면과 핵심 흐름

| 화면 | 주요 내용 | 주요 동작 |
|---|---|---|
| 기획 시작 | 목적·대상·기간·장소·행동·보상·영향·제약 입력 | 초안 검증, 실행 시작 |
| 진행 상황 | 실제 workflow 상태, 현재 단계 설명, 완료/대기/재시도 표시 | 상세 펼치기, 진행 이력 보기 |
| 결과 검토 | 이벤트 plan, 미션-보상 연결, 근거, 밸런스 영향 | 수정 요청, 승인 또는 거절 |
| 개발 필요 결과 | 미지원 기능과 `required_work`, 영향, 수용 조건 | 결과 확인 후 종료; Runtime 적용 CTA 없음 |
| 데이터 부족 결과 | 확인되지 않은 데이터·필요 출처·검증 영향·재실행 조건 | 데이터 보완 또는 카탈로그 갱신 후 새 실행; 승인 CTA 없음 |
| 사용자 확인 대기 | 모호하거나 상충하는 요청, 확인 질문과 관련 근거 | 답변 제출로 새 Brief version/execution 생성; 직접 승인으로 우회하지 않음 |
| Runtime 이벤트 | 승인된 등록 상태, 게임 내 활성 이벤트, 진행/보상 기록 | 등록 결과 확인, 실행 로그 보기 |
| 로그·Trace | 시간순 workflow/task/error/policy/decision | correlation 검색, 안전한 상세 열기 |
| 복구 정책 | 버전 목록, 매칭 조건, action, hard cap | draft 편집, schema 검사, replay preview, activate, rollback |
| 장애 시연 | 사전 정의된 장애 시나리오와 격리 상태 표시 | 데모 Workflow에서 장애 주입 실행, 복구·안전 중단 과정 확인 |

`runtime_eligible=false`인 결과는 승인 버튼을 노출하지 않는다. 기능 개발 필요 결과는 그 필요 사항을 명확히 보여주고 사용자 요청을 종결한다. 실제 지원되는 결과에만 승인 및 Runtime 등록 경로가 나타난다.

## 5. 진행 상태 표현

상태 라벨은 `접수됨`, `기획 중`, `검증 중`, `수정 중`, `사용자 확인 필요`, `기획 결과 작성 완료`, `승인 완료`, `게임 등록 완료`, `이벤트 진행 중/종료`, `개발 필요 항목 포함`, `데이터 확인 필요`, `중단됨`처럼 서로 다른 업무 경계를 구분해 표현하고 내부 enum은 상세에서 확인하게 한다. 기획 완료와 Runtime 등록 완료를 같은 `완료` 라벨로 합치지 않는다. 진행 단계는 이벤트 기반으로 나타내며 예상 전체 단계 수를 선표시하지 않는다. 대기 원인, 재시도 중인 작업, 실패 후 재개 여부를 분리해 표현한다.

각 진행 항목에는 시각, 간단한 설명, 상태, 근거/결과 링크가 있다. 재시도는 새 실행처럼 숨기지 않고 같은 작업의 시도 번호로 표시한다. 중단 시 마지막 성공 지점과 다음 조치를 표시한다.

## 6. 오류 정책 편집 UX

정책 편집은 Draft→형식/범위 검사→보안 불변조건 검사→대표 오류 replay preview→활성화 확인→새 immutable version 생성 순서다. 미리보기에는 변경 전후 route, 영향을 받는 오류 표본, 재시도 상한, 막히는 경로를 보여준다. 비활성화·rollback도 새 감사 이벤트를 남긴다.

UI는 허용되지 않는 action 조합이나 hard cap 초과를 저장 전에 막되, 서버가 같은 검증을 다시 수행한다. 보안 오류에 retry/fallback을 지정하거나 validator를 끄는 설정은 편집할 수 없다. 활성 version과 각 workflow가 사용한 version을 확인할 수 있다.

## 7. 장애 시연 화면

장애 시연은 실제 장애를 발생시키거나 운영 의존성을 끊지 않고 AutoHealing을 보여주는 전용 데모 기능이다. 일반 기획 Workflow와 화면에서 명확히 구분하고, 서버의 명시적 demo mode가 켜진 로컬 환경에서만 노출한다.

화면 흐름은 `시나리오 선택 → 영향 범위/기대 동작 확인 → 격리된 시연 Workflow 시작 → 발생·감지·라우팅·재시도/수정·검증 이벤트 실시간 표시 → 복구 또는 SAFE_STOP 결과와 Trace 확인`으로 한다. 각 시나리오는 고정된 scenario ID와 허용된 fault profile을 사용하며, 사용자가 임의 오류 코드·횟수·내부 payload를 입력해 주입하지 못하게 한다. 본 시연은 테스트용 Workflow/task와 fixture를 사용하고 승인·실제 게임 등록·보상 지급 같은 외부 상태 변경을 금지한다.

초기 시연 카탈로그는 다음 세 가지로 제한한다.

| Scenario ID | 주입 위치·상황 | 기대 화면 결과 |
|---|---|---|
| `DEMO-HEAL-01` | 허용된 MCP read 호출 1회 transient timeout | 실패 감지와 retry 1회를 표시하고, 동일 version 재조회 및 후속 검증 성공을 보여줌 |
| `DEMO-HEAL-02` | MCP read 호출이 retry budget까지 계속 timeout | 시도 횟수·budget 소진·마지막 성공 지점을 표시하고 `SAFE_STOP`으로 종료 |
| `DEMO-HEAL-03` | Planner candidate에 수정 가능한 규칙 finding 삽입 | finding을 Planner에 전달하고 revision 후 규칙·최종 검증을 다시 수행한 결과를 표시 |

화면은 “장애 주입”, “복구 중”, “복구 성공”, “안전 중단”을 텍스트로 구분하고 해당 시나리오가 실제 서비스 장애나 production incident가 아님을 항상 표시한다. 시연 중에도 실제 Controller·복구 Router·정책 평가·Trace 저장 경로를 사용하며, fault adapter는 지정된 dependency 경계에서 정해진 횟수만 실패를 반환한다. 종료 시 scenario ID, policy version, attempts, terminal result, trace ID를 요약한다.

## 8. 접근성·오류 상태·완료 기준

주요 상태는 색상만으로 구분하지 않고 텍스트·아이콘을 함께 사용한다. 빈 상태, 로딩, 연결 실패, 권한 오류, 데이터 부족, 정책 차단, 개발 필요를 별도 메시지로 표현한다. 상세 정보는 접고 펼칠 수 있으며 작은 화면에서도 핵심 행동과 결과를 확인할 수 있다.

### 8.1 의미·디자인 검증 체크리스트

UI 검증은 API/DB 일치 자동 테스트와 분리해 **화면 의미 검토**와 **시각 디자인 검토**를 수행한다. 상태 fixture로 같은 화면의 성공·대기·실패·개발 필요 변형을 재현한다. 각 항목은 `통과 / 실패 / 해당 없음`으로 기록하고 실패 항목에 화면·상태·근거를 남긴다. 안전·상태 오표시는 차단 결함이며 모두 수정되기 전 수용할 수 없다.

**의미·사용 흐름 검토**

- 화면을 처음 본 사람이 현재 화면의 목적과 지금 상태를 짧게 설명할 수 있다.
- 사용자가 해야 할 다음 행동이 하나의 명확한 주 동작으로 드러나고, 진행 중에는 중복 제출·중복 승인을 유도하지 않는다.
- `기획 완료`, `승인 완료`, `게임 등록 완료`, `이벤트 진행 중/종료`가 서로 구분된다.
- `runtime_eligible=false`, `NEEDS_DATA`, 보안 차단, SAFE_STOP 상태에서 승인·적용 가능하다는 인상을 주지 않으며 허용되지 않은 CTA가 없다.
- 개발 필요 결과는 개발할 항목·영향·수용 조건을, 데이터 부족은 부족한 근거·재실행 방법을 보여준다.
- 진행 단계·attempt·revision·대기 원인·복구 결과가 실제 workflow event/Trace와 일치하고 미래 단계를 만들어 표시하지 않는다.
- 근거와 게임/정책 버전은 확인 가능하지만 내부 component명·원문 prompt·secret·stack trace가 요약 화면에 노출되지 않는다.
- 장애 데모는 실제 서비스 장애가 아닌 로컬 격리 시연임을 알리고, 게임 Runtime을 변경하지 않는다는 범위가 이해된다.
- 운영 콘솔의 등록 이력과 게임 안의 이벤트 장면이 같은 Runtime event/source version을 가리킨다.

**시각·상호작용 검토**

- 제목·상태·주요 결과·다음 행동 순서로 시선이 자연스럽게 이동하며 중요도에 맞는 크기·간격·대비를 가진다.
- 기획 결과, 경고, 차단, 성공, 진행 상태가 색상만으로 구분되지 않고 텍스트/아이콘도 일관되게 사용된다.
- 카드·표·배지·버튼·여백·폰트 사용이 화면 사이에서 일관되며 같은 뜻의 정보는 같은 표현을 쓴다.
- 한 화면에 내부 정보를 과도하게 펼치지 않고 근거·Trace·정책 상세는 사용자가 요청할 때 확인할 수 있다.
- 로딩·빈 목록·검증 오류·API 단절·재시도·SAFE_STOP·완료 상태에서 레이아웃이 깨지거나 이전 상태가 성공처럼 남지 않는다.
- 주요 상호작용은 명확한 hover/focus/disabled/pending/confirmed 피드백을 제공하고 키보드로도 접근할 수 있다.
- Edge에서 합의한 기준 viewport와 작은 viewport에서 잘림·가로 넘침·겹침 없이 핵심 정보와 주 동작을 사용할 수 있다. 검토 기록에 viewport 크기를 남긴다.
- 게임 장면은 운영 콘솔의 표·관리자 스타일을 복제하지 않고, 기존 가상 게임의 귀여운 세계관·시각 자산과 장면별 연출을 유지한다.

**검토 시나리오와 증거**

| 검토 ID | 화면 상태 | 중점 확인 | 남길 증거 |
|---|---|---|---|
| UX-01 | 입력 전/필수값 오류 | 요구 정보와 제출 가능 여부, 필드 오류 이해 | Edge screenshot, viewport, 체크 결과 |
| UX-02 | 진행 중/재시도/대기 | 실제 상태 반영, 다음 행동, 단계 수 오해 여부 | 실제 또는 고정 workflow trace와 화면 캡처 |
| UX-03 | 지원 가능 결과/승인 전 | Plan·근거·미션-보상·영향, 승인 행동 명확성 | Plan version·근거와 화면 캡처 |
| UX-04 | 개발 필요/데이터 부족/보안 차단 | 상태별 의미, 승인 CTA 부재, 재실행 방법 | finding fixture·화면 캡처 |
| UX-05 | 정책 replay/활성화/rollback | 변경 전후 차이, hard cap, 확인 행동·감사 정보 | policy version·preview 결과와 캡처 |
| UX-06 | 장애 시연 복구/SAFE_STOP/revision | 시연임을 이해, 복구 과정·최종 결과, 게임 상태 불변 | scenario/Trace ID·전후 Runtime 확인·캡처 |
| UX-07 | 게임 이벤트 적용/진행 | 실제 게임 장면·미션·보상 인식과 운영 화면의 출처 버전 일치 | Runtime event ID·진행/보상 상태·게임 캡처 |

체크리스트는 기획자/개발자가 구현 때 실행하고, 첫 사용자의 이해도 평가는 대표 시나리오에서 별도로 한 차례 수용 확인한다. 자동 테스트는 API·버전·CTA 조건·접근성 속성 및 상태 fixture를 확인하되, 시각적 위계와 의미 이해를 자동 점수만으로 통과 처리하지 않는다.

완료 기준:
- 첫 사용자가 입력→진행→결과/개발 필요→승인된 Runtime 등록 흐름을 구분 가능
- 화면 진행 이력이 실제 backend trace/state와 일치하고 전체 단계를 미리 가정하지 않음
- 지원 불가 결과가 Runtime 등록·승인으로 오인되지 않음
- 정책 변경의 검증·영향 preview·활성 버전·rollback이 감사 이력에 연결됨
- 오류·대기·복구 상황에서 원인 요약과 사용자의 다음 행동을 알 수 있음
- 장애 시연은 격리된 demo mode에서만 실행되고 운영 데이터나 게임 상태를 변경하지 않음
- 시연 화면의 단계·시도·복구 결과가 실제 Workflow event와 Trace에 일치함
- UX-01~07의 의미·시각 검토를 기록하고, 상태 오표시·위험 CTA·Runtime 출처 불일치 같은 차단 결함이 없음
