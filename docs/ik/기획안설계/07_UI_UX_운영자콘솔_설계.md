# UI·UX·운영자 콘솔 설계

## 2026-10-11 Planner 진행 표시 보완

Planner의 성공 기록만으로 주 흐름 노드를 만들지 않는다. 실제 호출 직전에 저장되는 `planner.started / STARTED`를 기획 시작으로 표시해 검증 전 실패도 숨기지 않는다. 이전 실행은 `llm_usage.records`에 canonical Planner의 실제 호출 참조가 있을 때만 저장된 호출 결과를 주 흐름에 표시한다. handoff 요청은 실행 증거로 사용하지 않는다. 성공·실패 상태는 Trace/결과를 따르며 옛 실패 기록을 수정하지 않는다. [원인·검증 기록 15 §7](15_오류대응정책_Workflow_연결_재검사.md#7-실제-planner-실패와-provider-계약-동기화)을 따른다.

> 2026-10-11 검사 후 보완: 아래 내용은 설계 기준이며 구현 완료 선언이 아니다. 최신 보완 계약은 [Workflow 수정 계획 §3.6](14_Workflow_검사결과_설계보완_수정계획.md), 현재 사실은 [현재 구현 상태](../현재_구현상태.md)를 따른다.

## 검사 후 추가 적용 기준

완료 후 Trace 표시와 실시간 진행을 구분한다. 접수 202/Workflow ID 이후 확정 DB 상태를 polling하고 재연결·새로고침 복원을 지원한다. 정식 이벤트 supervisor.state_transition_decided와 이전 alias를 함께 읽는다. HTTP 오류를 곧바로 Workflow 실패로 표시하지 않는다.

구체 변경 위치·의존 순서·검증 증거는 [수정 작업 §4 및 검증 §5](14_Workflow_검사결과_설계보완_수정계획.md#4-구현-순서와-변경-범위)에 연결한다. 기존 계약과 중복되면 이번 보완의 더 엄격한 저장·접근·검증 조건을 적용한다.

## 1. 목적과 범위

처음 보는 사용자가 이벤트를 요청하고 결과를 이해하며 진행 상태·근거·오류를 확인할 수 있게 화면 흐름과 정보 계층을 정한다. 운영자는 같은 화면에서 복구 정책의 초안·검증·영향 미리보기·활성 버전을 관리한다. 화면은 백엔드 상태를 표현하며 실행 단계를 미리 만들어내지 않는다.

## 2. 현재 구현 기준

현재 운영 콘솔은 기획안 입력, Workflow·Trace, 복구 정책, 격리 장애 시연, 운영 로그를 제공하고 승인된 Plan의 가상 Runtime 등록을 연결한다. 승인과 등록 이후 Trace는 PostgreSQL lifecycle event를 다시 조회한다. Runtime 적용은 완료됐지만 lifecycle Trace 저장만 실패한 경우 Workflow 조회에서 `APPLIED`와 `MISSING` 상태를 표시하고, 결과 패널에 Runtime event ID 및 Trace 복구 재시도 버튼을 제공한다. Runtime 등록 후에는 권위 Game API에서 미션 진행·보상 원장을 읽어 결과 화면에 표시하고 사용자가 갱신할 수 있다. 기본 Playwright E2E는 Chromium을 사용한다. 별도 `playwright.edge.config.js`와 `infra/e2e-local.ps1 -Browser edge`로 같은 UX 시나리오를 Microsoft Edge에서도 실행한다. 최신 Edge 캡처는 1910×912 및 390×844 viewport 증거다. UX-02 승인/거절 버튼 위계와 UX-05 오류 코드 줄바꿈·모바일 글자 크기, UX-06 복구 결과 요약·모바일 Trace 표기를 보완했다. 2026-10-11 Microsoft Edge 자동 suite는 14 passed/2 opt-in skipped와 API 재기동 복원 1 passed, opt-in MCP HTTP 503 종단 1 passed를 기록했다. 별도 Edge 게임 캡처에서 Phaser 장면과 적용 이벤트를 확인했다. UX-02는 390×844에서 세로 버튼 배치와 가로 넘침 없음을, UX-06은 재시도·수정 횟수 및 terminal 결과의 Trace 일치와 모바일 표기를 확인했다. 영향 근거 요약은 안정 세그먼트 ID 대신 한국어 세그먼트명을, 콘텐츠 ID 대신 동일한 버전 고정 Runtime snapshot의 콘텐츠명을 표시하며 원 ID는 접힌 상세에서 보존한다. canonical unit 29개, Edge 핵심 E2E 4개, 해당 변경을 포함한 T5 3회 연속(Backend 255/11 skipped, E2E 14/2 opt-in skipped, 재기동 복원 1) 통과를 확인했다. 전체 의미·시각 체크리스트와 첫 사용자 이해도 수용은 미완료다. 캡처와 실행 근거는 [현재 구현 상태](../현재_구현상태.md#2026-10-11-운영-ui-후속-확인)를 따른다. 진행 요약과 운영 로그 표에서는 상태·Trace 이벤트를 한국어로 표시하고 execution profile, 원본 enum·event 코드는 접힌 상세에 둔다. `NEEDS_DEVELOPMENT`와 `VALIDATED_WITH_DEVELOPMENT_ITEMS`는 각각 “개발 필요”와 “개발 항목 포함”으로 표시하고 주의색 marker를 함께 쓴다. 새 기획 입력 화면에는 이전 실행 결과를 남기지 않으며, Plan 상태 enum도 사용자용 라벨로 바꾼다. 경제 영향 `unknown`은 `근거 부족 · 미산출`로 표시하며 수치 추정으로 대체하지 않는다. Runtime이 보장하는 1회 지급 보상은 아이템별 `per_user_reward_ceiling`을 규칙 기반 계산으로 표시하고, 사용자 KPI와 추정 불가 값은 unknown 상태를 유지한다. 계산 근거와 method는 세부 정보에서 확인한다. Playwright에서 정책 초안·preview·activate·rollback UI 흐름과 390px 내비게이션을 검증했다. UX-01~07 전체 수용은 미완료이며, 최신 확인 및 잔여 항목은 [현재 구현 상태](../현재_구현상태.md#최신-edge-ux-수용-확인)를 기준으로 한다.
2026-10-11 후속 UI 확인: UX-01 필수값 오류는 browser tooltip 대신 입력 필드 옆 `role=alert`로 표시한다. UX-04 finding code는 결과 요약에서 의미가 통하는 한국어 문구로 보이고 원 코드는 접힌 Trace 상세에서 확인한다. 동일 finding이 반복하는 조치 문구는 화면에서 한 번만 표시한다. UX-03의 승인/거절 위계도 캡처 갱신에서 확인했다. UX-05 복구 정책 화면은 API가 제공하는 오류 카탈로그 안전 메시지와 원 코드·분류 위치를 함께 보여주고 action은 한국어로 표시한다. 390×844에서는 원인 설명을 위에 두고 대응·횟수 입력을 아래에 배치해 가로 넘침 없이 사용한다. 정책 lifecycle, 데이터 부족 화면, API 카탈로그를 대상으로 한 targeted 검사는 Backend 1 passed와 Playwright 3 passed였다. 이후 UX 표시명 수정까지 포함한 전체 T5는 Backend 255 passed/11 skipped, Edge E2E 14 passed/2 opt-in skipped, API 재기동 복원 1 passed로 3회 연속 통과했다. 근거 요약에는 버전 snapshot의 콘텐츠명과 한국어 세그먼트명이 나오며 내부 ID는 접힌 상세에 남는다. 증거와 실행 세부는 [현재 구현 상태](../현재_구현상태.md#2026-10-11-운영-ui-후속-확인)를 참조한다. 전체 의미·시각 체크리스트의 첫 사용자 이해도 확인은 여전히 완료 전이다.

추가 반응형 검토(2026-10-11): UX-01/03/04/05/06/07의 390×844 화면을 새로 캡처하고, 화면별 필수 오류·승인 선택·finding 설명·정책 편집·복구 결과·Runtime 미션/보상 상태의 가시성과 가로 넘침을 확인했다. UX-04 개발 필요 finding은 스킨 내부 ID 대신 상품명을 보여주고, 옛 Plan에 지표 display label이 없으면 알려진 metric을 한국어 이름으로 대체한다. 화면 증거는 [`ux-evidence/`](../ux-evidence/)에 보존한다. 검토 중 모바일 복구 제목의 음절 분리와 등록 직후 toast가 전체 페이지 캡처를 가리는 문제가 확인되어 CSS/E2E를 수정하고 재촬영했다. 자동화된 의미·레이아웃 검토는 통과했지만, UX-01~07의 전체 상태 fixture 검토와 첫 사용자의 실제 이해도 평가는 별도 수용으로 남는다.

2026-10-11 UX-05 정책 목록 탐색: 오류 정책 화면에 실시간 검색 필드를 추가해 안전 설명, 오류 코드, category/location, 현재 설정된 대응 이름으로 목록을 좁힌다. 검색 결과 개수와 결과 없음 상태를 보여주며 입력을 지우면 전체 목록을 복원한다. 정책 데이터나 lifecycle API는 검색으로 변경하지 않는다. Edge E2E는 코드·MCP 분류 위치·대응 이름 검색, 결과 없음, 전체 복원을 확인하고 390×844에서 전체 목록과 검색 필드가 가로로 넘치지 않는 것을 검사한다. 이 변경 이후 전체 T5 3회 연속(매회 Backend 255 passed/11 skipped, E2E 14 passed/2 opt-in skipped, API 재기동 복원 1 passed)이 통과했다. Edge 캡처는 [현재 구현 상태](../현재_구현상태.md#ux-0107-캡처-기반-구현자-점검)를 참조한다. 검색의 실제 탐색 편의와 정책 preview/rollback 이해도는 첫 사용자 수용 때 확인한다.

기본 성장 기준의 1회 전투 가능 여부는 segment의 낮은 레벨/입장 레벨과 높은 레벨에서 각각 표시하고, 전투 성공률로 오해되지 않도록 기본 스탯 계산임을 함께 쓴다.

## 3. 사용자와 정보 계층

초기 사용자는 한 명이며 기획·검토·승인·정책관리 권한을 가진다. 보안 불변조건과 정책 상한은 사용자 권한으로도 완화할 수 없다. 화면 정보는 다음 계층을 따른다.

1. **요약:** 지금 무슨 일이 일어나는지, 결과/대기/차단 여부, 다음 행동.
2. **근거:** 주요 판단, 게임 데이터·규칙 버전, 지원 여부, 개발 필요 항목.
3. **세부 정보:** Agent/task/handoff, 검증 finding, 오류 코드, 복구 시도와 Trace.

사용자에게 내부 component 이름이나 stack trace를 기본 노출하지 않는다. 확장 영역에 안전한 요약과 trace ID를 제공한다.

## 4. 화면과 핵심 흐름

| 화면 | 주요 내용 | 주요 동작 |
|---|---|---|
| 기획 시작 | 목적·대상·기간·장소·행동·보상·영향·제약 입력 | 초안 검증, 실행 시작 |
| 진행 상황 | 실제 workflow 상태, 현재 단계 설명, 완료/대기/재시도 표시 | 상세 펼치기, 진행 이력 보기 |
| 결과 검토 | 이벤트 plan, 미션-보상 연결, 근거, 밸런스 영향 | 수정 요청, 승인 또는 거절 |
| 개발 필요 결과 | 미지원 기능과 `required_work`, 영향, 수용 조건 | 결과 확인 후 종료; Runtime 적용 CTA 없음 |
| 데이터 부족 결과 | 확인되지 않은 데이터·필요 출처·검증 영향·재실행 조건 | 데이터 보완 또는 카탈로그 갱신 후 새 실행; 승인 CTA 없음 |
| 사용자 확인 대기 | 모호하거나 상충하는 요청, 확인 질문과 관련 근거 | 답변 제출로 새 Brief version/execution 생성; 직접 승인으로 우회하지 않음 |
| Runtime 이벤트 | 승인된 등록 상태, 게임 내 활성 이벤트, 진행/보상 기록 | 등록 결과 확인, 실행 로그 보기 |
| 로그·Trace | 최근 50개 Workflow, 시간순 workflow/task/error/policy/decision | Workflow ID·Task ID·기획 목표 검색, 안전한 상세 열기 |
| 복구 정책 | 버전 목록, 매칭 조건, action, hard cap | draft 편집, schema 검사, replay preview, activate, rollback |
| 장애 시연 | 사전 정의된 장애 시나리오와 격리 상태 표시 | 데모 Workflow에서 장애 주입 실행, 복구·안전 중단 과정 확인 |

`runtime_eligible=false`인 결과는 승인 버튼을 노출하지 않는다. 기능 개발 필요 결과는 그 필요 사항을 명확히 보여주고 사용자 요청을 종결한다. 실제 지원되는 결과에만 승인 및 Runtime 등록 경로가 나타난다.

## 5. 진행 상태 표현

상태 라벨은 `접수됨`, `기획 중`, `검증 중`, `수정 중`, `사용자 확인 필요`, `기획 결과 작성 완료`, `승인 완료`, `게임 등록 완료`, `이벤트 진행 중/종료`, `개발 필요 항목 포함`, `데이터 확인 필요`, `중단됨`처럼 서로 다른 업무 경계를 구분해 표현하고 내부 enum은 상세에서 확인하게 한다. 기획 완료와 Runtime 등록 완료를 같은 `완료` 라벨로 합치지 않는다. 진행 단계는 이벤트 기반으로 나타내며 예상 전체 단계 수를 선표시하지 않는다. 대기 원인, 재시도 중인 작업, 실패 후 재개 여부를 분리해 표현한다.

각 진행 항목에는 시각, 간단한 설명, 상태, 근거/결과 링크가 있다. 재시도는 새 실행처럼 숨기지 않고 같은 작업의 시도 번호로 표시한다. 중단 시 마지막 성공 지점과 다음 조치를 표시한다.

## 6. 오류 정책 편집 UX

정책 편집은 Draft→형식/범위 검사→보안 불변조건 검사→대표 오류 replay preview→활성화 확인→새 immutable version 생성 순서다. 미리보기에는 변경 전후 route, 영향을 받는 오류 표본, 재시도 상한, 막히는 경로를 보여준다. 비활성화·rollback도 새 감사 이벤트를 남긴다.

UI는 허용되지 않는 action 조합이나 hard cap 초과를 저장 전에 막되, 서버가 같은 검증을 다시 수행한다. 보안 오류에 retry/fallback을 지정하거나 validator를 끄는 설정은 편집할 수 없다. 활성 version과 각 workflow가 사용한 version을 확인할 수 있다.

## 7. 장애 시연 화면

장애 시연은 실제 장애를 발생시키거나 운영 의존성을 끊지 않고 AutoHealing을 보여주는 전용 데모 기능이다. 일반 기획 Workflow와 화면에서 명확히 구분하고, 서버의 명시적 demo mode가 켜진 로컬 환경에서만 노출한다.

화면 흐름은 `시나리오 선택 → 영향 범위/기대 동작 확인 → 격리된 시연 Workflow 시작 → 발생·감지·라우팅·재시도/수정·검증 이벤트 실시간 표시 → 복구 또는 SAFE_STOP 결과와 Trace 확인`으로 한다. 각 시나리오는 고정된 scenario ID와 허용된 fault profile을 사용하며, 사용자가 임의 오류 코드·횟수·내부 payload를 입력해 주입하지 못하게 한다. 본 시연은 테스트용 Workflow/task와 fixture를 사용하고 승인·실제 게임 등록·보상 지급 같은 외부 상태 변경을 금지한다.

초기 시연 카탈로그는 다음 세 가지로 제한한다.

| Scenario ID | 주입 위치·상황 | 기대 화면 결과 |
|---|---|---|
| `DEMO-HEAL-01` | 허용된 MCP read 호출 1회 transient timeout | 실패 감지와 retry 1회를 표시하고, 동일 version 재조회 및 후속 검증 성공을 보여줌 |
| `DEMO-HEAL-02` | MCP read 호출이 retry budget까지 계속 timeout | 시도 횟수·budget 소진·마지막 성공 지점을 표시하고 `SAFE_STOP`으로 종료 |
| `DEMO-HEAL-03` | Planner candidate에 수정 가능한 규칙 finding 삽입 | finding을 Planner에 전달하고 revision 후 규칙·최종 검증을 다시 수행한 결과를 표시 |

화면은 “장애 주입”, “복구 중”, “복구 성공”, “안전 중단”을 텍스트로 구분하고 해당 시나리오가 실제 서비스 장애나 production incident가 아님을 항상 표시한다. 시연 중에도 실제 Controller·복구 Router·정책 평가·Trace 저장 경로를 사용하며, fault adapter는 지정된 dependency 경계에서 정해진 횟수만 실패를 반환한다. 종료 시 scenario ID, policy version, attempts, terminal result, trace ID를 요약한다.

## 8. 접근성·오류 상태·완료 기준

주요 상태는 색상만으로 구분하지 않고 텍스트·아이콘을 함께 사용한다. 빈 상태, 로딩, 연결 실패, 권한 오류, 데이터 부족, 정책 차단, 개발 필요를 별도 메시지로 표현한다. 상세 정보는 접고 펼칠 수 있으며 작은 화면에서도 핵심 행동과 결과를 확인할 수 있다.

### 8.1 의미·디자인 검증 체크리스트

UI 검증은 API/DB 일치 자동 테스트와 분리해 **화면 의미 검토**와 **시각 디자인 검토**를 수행한다. 상태 fixture로 같은 화면의 성공·대기·실패·개발 필요 변형을 재현한다. 각 항목은 `통과 / 실패 / 해당 없음`으로 기록하고 실패 항목에 화면·상태·근거를 남긴다. 안전·상태 오표시는 차단 결함이며 모두 수정되기 전 수용할 수 없다.

**의미·사용 흐름 검토**

- 화면을 처음 본 사람이 현재 화면의 목적과 지금 상태를 짧게 설명할 수 있다.
- 사용자가 해야 할 다음 행동이 하나의 명확한 주 동작으로 드러나고, 진행 중에는 중복 제출·중복 승인을 유도하지 않는다.
- `기획 완료`, `승인 완료`, `게임 등록 완료`, `이벤트 진행 중/종료`가 서로 구분된다.
- `runtime_eligible=false`, `NEEDS_DATA`, 보안 차단, SAFE_STOP 상태에서 승인·적용 가능하다는 인상을 주지 않으며 허용되지 않은 CTA가 없다.
- 개발 필요 결과는 개발할 항목·영향·수용 조건을, 데이터 부족은 부족한 근거·재실행 방법을 보여준다.
- 콘텐츠 접근성 표시는 시작 레벨 기준의 결정값, 세그먼트 최고 레벨 초과 차단, 성장 곡선 부재로 인한 `unknown`을 구분하고 승률·달성 확률처럼 오해될 숫자를 만들지 않는다.
- 진행 단계·attempt·revision·대기 원인·복구 결과가 실제 workflow event/Trace와 일치하고 미래 단계를 만들어 표시하지 않는다.
- 근거와 게임/정책 버전은 확인 가능하지만 내부 component명·원문 prompt·secret·stack trace가 요약 화면에 노출되지 않는다.
- 장애 데모는 실제 서비스 장애가 아닌 로컬 격리 시연임을 알리고, 게임 Runtime을 변경하지 않는다는 범위가 이해된다.
- 운영 콘솔의 등록 이력과 게임 안의 이벤트 장면이 같은 Runtime event/source version을 가리킨다.

**시각·상호작용 검토**

- 제목·상태·주요 결과·다음 행동 순서로 시선이 자연스럽게 이동하며 중요도에 맞는 크기·간격·대비를 가진다.
- 기획 결과, 경고, 차단, 성공, 진행 상태가 색상만으로 구분되지 않고 텍스트/아이콘도 일관되게 사용된다.
- 카드·표·배지·버튼·여백·폰트 사용이 화면 사이에서 일관되며 같은 뜻의 정보는 같은 표현을 쓴다.
- 한 화면에 내부 정보를 과도하게 펼치지 않고 근거·Trace·정책 상세는 사용자가 요청할 때 확인할 수 있다.
- 로딩·빈 목록·검증 오류·API 단절·재시도·SAFE_STOP·완료 상태에서 레이아웃이 깨지거나 이전 상태가 성공처럼 남지 않는다.
- 주요 상호작용은 명확한 hover/focus/disabled/pending/confirmed 피드백을 제공하고 키보드로도 접근할 수 있다.
- Edge에서 합의한 기준 viewport와 작은 viewport에서 잘림·가로 넘침·겹침 없이 핵심 정보와 주 동작을 사용할 수 있다. 검토 기록에 viewport 크기를 남긴다.
- 모바일(390px)에서 사용자가 읽고 조작하는 본문·설명·입력 글자는 12px 이상으로 유지한다. 오류 코드·버전 같은 보조 식별자는 10px 이상으로 표시하고 전체 값을 확인할 수 있게 줄바꿈한다.
- 게임 장면은 운영 콘솔의 표·관리자 스타일을 복제하지 않고, 기존 가상 게임의 귀여운 세계관·시각 자산과 장면별 연출을 유지한다.

**검토 시나리오와 증거**

| 검토 ID | 화면 상태 | 중점 확인 | 남길 증거 |
|---|---|---|---|
| UX-01 | 입력 전/필수값 오류 | 요구 정보와 제출 가능 여부, 필드 오류 이해 | Edge screenshot, viewport, 체크 결과 |
| UX-02 | 진행 중/재시도/대기 | 실제 상태 반영, 다음 행동, 단계 수 오해 여부 | 실제 또는 고정 workflow trace와 화면 캡처 |
| UX-03 | 지원 가능 결과/승인 전 | Plan·근거·미션-보상·영향, 승인 행동 명확성 | Plan version·근거와 화면 캡처 |
| UX-04 | 개발 필요/데이터 부족/보안 차단 | 상태별 의미, 승인 CTA 부재, 재실행 방법 | finding fixture·화면 캡처 |
| UX-05 | 정책 replay/활성화/rollback | 변경 전후 차이, hard cap, 확인 행동·감사 정보 | policy version·preview 결과와 캡처 |
| UX-06 | 장애 시연 복구/SAFE_STOP/revision | 시연임을 이해, 복구 과정·최종 결과, 게임 상태 불변 | scenario/Trace ID·전후 Runtime 확인·캡처 |
| UX-07 | 게임 이벤트 적용/진행 | 실제 게임 장면·미션·보상 인식과 운영 화면의 출처 버전 일치 | Runtime event ID·진행/보상 상태·게임 캡처 |

체크리스트는 기획자/개발자가 구현 때 실행하고, 첫 사용자의 이해도 평가는 대표 시나리오에서 별도로 한 차례 수용 확인한다. 자동 테스트는 API·버전·CTA 조건·접근성 속성 및 상태 fixture를 확인하되, 시각적 위계와 의미 이해를 자동 점수만으로 통과 처리하지 않는다.

완료 기준:
- 첫 사용자가 입력→진행→결과/개발 필요→승인된 Runtime 등록 흐름을 구분 가능
- 화면 진행 이력이 실제 backend trace/state와 일치하고 전체 단계를 미리 가정하지 않음
- 지원 불가 결과가 Runtime 등록·승인으로 오인되지 않음
- 정책 변경의 검증·영향 preview·활성 버전·rollback이 감사 이력에 연결됨
- 오류·대기·복구 상황에서 원인 요약과 사용자의 다음 행동을 알 수 있음
- 장애 시연은 격리된 demo mode에서만 실행되고 운영 데이터나 게임 상태를 변경하지 않음
- 시연 화면의 단계·시도·복구 결과가 실제 Workflow event와 Trace에 일치함
- UX-01~07의 의미·시각 검토를 기록하고, 상태 오표시·위험 CTA·Runtime 출처 불일치 같은 차단 결함이 없음

## Workflow 수정 후 화면 동작 (2026-10-11)

[수정 계획 14 §7](14_Workflow_검사결과_설계보완_수정계획.md#7-2026-10-11-구현검증-기록)의 실행 증거를 기준으로 한다. UI는 202 접수 즉시 진행 화면을 열고 700ms 간격으로 마지막 확정 상태를 조회한다. 조회 실패는 3초 뒤 재연결하며 작업 실패로 바꾸지 않는다. 새로고침 후 DB 조회로 polling을 복원한다. 데이터 조회/기획 설명/규칙 검증/검토 등의 상태와 handoff 이름을 한국어로 표시하고 상세 Trace는 펼쳐 본다.

- 진행 취소: 현재 version으로만 취소한다. 늦게 도착한 결과를 반영하지 않는다.
- 기록 재조정: 불일치 표시가 있을 때 운영자가 실제 승인·등록 근거로 연결한다. 게임 등록을 반복하지 않는다.
- 정책 누락: active 계약 오류가 있으면 새 draft 검증/preview/활성화 절차를 표시한다. 제안 route는 편집 초안에만 합치며 active 실행 정책을 자동 수정하지 않는다.
- 요청 실패 후에도 공간·보상·목표 입력을 보존해 같은 요청과 멱등 키로 다시 시도할 수 있게 한다.
- 최근 기록 복원이 사용자가 이미 시작한 새 기획 입력 화면을 덮어쓰지 않도록 한다.
- 그래프의 business observation과 handoff는 실제 발생 순서대로 저장한다. 총 단계 숫자나 임의 완료 비율을 생성하지 않는다.
