## 1. 환경·기준·지원 범위

- 단일 오류/동일 오류 반복 주입. 복합 오류는 미지원.
- 시험 UI 5183 / API 8013 / MCP 8014, PostgreSQL 시험 DB `eventquest_fault_test`. 실제 DB/MCP, 결정적 LLM adapter. 사용자 DB와 일반 서버는 시험 대상으로 변경하지 않는다.
- 카탈로그 28개, 계획 요청 137개. 시험 DB 활성 정책 version 1, 과거 MCP 003의 002 상속을 반영한다. 정책은 각 case에서 고정하고 profile 시험 후 원래 정책을 복원한다.
- canonical snapshot `opong-data-1.5.0`, 기존 Task 3개는 `tinyheroes-1.0.0`. 코드 HEAD와 dirty 여부/소스 digest, 명세 digest, 정책 digest, 게임 버전/상태 digest를 preflight JSON에 기록한다. 환경 비밀값은 기록하지 않는다.
- 실행 직전에 preflight를 다시 기록한다. source digest는 파일 기준이며 운영 배포나 모든 실행 중 프로세스의 이미지 버전을 증명하는 값은 아니다. 시험 runner는 각 case의 새 프로세스에서 현재 코드를 로드한다.

## 2. 준비 단계에서 보완한 사항

| 항목 | 보완 내용 |
|---|---|
| 입력 오류 | HTTP 422만으로 인정하지 않고 `INPUT_VALIDATION_ERROR` + timezone/duration 오류 필드 또는 `ERR-SEC-INPUT-001` 응답을 비교 |
| 정책·상태 | 고정 정책 version/hash, 실제 적용 rule ID, canonical 상태 version/from/to/event/최종 상태, 종료 후 추가 작업 확인 |
| 늦게 기록된 설명 | 과거 복구 설명의 Trace 추가를 재실행으로 오인하지 않음. 저장 완료된 상태 publication 시각과 실제 Agent/MCP 호출 journal을 비교 |
| 측정 | 실제 catch 또는 실제 오류가 Supervisor에 전달된 시점부터 Workflow 처리 완료까지 측정. 뒤따르는 snapshot/멱등성/정책 복원 검사 시간은 복구시간에 포함하지 않음 |
| UI | 기획 재작성·대체 조회, 입력 거절·자료/개발 필요·상태 충돌·ACK 재조정, LIMIT 선택 코드와 실제 원인 코드를 구분 |
| 횟수 | 별도 콘텐츠 Primary 조회와 retry, 기획 수정 후 재검증과 기술 retry를 구분 |
| 명세 대조 | 결과를 실행 전 명세와 별도로 비교. 저장된 PASS라도 명세와 다르면 보고서 FAIL. 원본 기록은 변경하지 않음 |

canonical 상태의 전이 체인은 전체 검사한다. 기존 Task의 일부 Trace에는 from/to가 없으므로 version 순서·정책 참조를 확인하되 같은 수준의 전체 전이 검증을 주장하지 않는다. 시험용 관측 hook은 허용된 격리 주입 context 밖에서 상태를 바꾸거나 기록하지 않는다.

## 5. 집계 기준

- 시험 통과와 자동 정상화를 구분한다. 기대한 안전 중단은 PASS일 수 있지만 정상화 성공은 아니다.
- 자동 정상화율의 제외 항목: 입력 거절, 자료/개발 필요 finding, 상태 CAS. 제외 목록을 보고서에 공개한다. ACK 재조정은 실제 저장 결과를 확보하면 정상화에 포함한다.
- 사전 선택한 오류 사례 중 정상화 수/오류 사례 수를 집계한다. 실패·판정 불가·미실행 수는 별도로 공개하고 사후 제외해 수치를 높이지 않는다.
- 평균 복구시간은 자동 정상화 성공 중 실제 측정이 있는 사례만 계산하며 표본 수·측정 누락도 공개한다. 전체 실행/검사 시간을 대체값으로 넣지 않는다.
- 서로 다른 소스/정책/측정 프로토콜의 과거·수정 후 기록은 같은 최종 모집단으로 섞지 않는다. 개선 이력으로 연결한다.

## 6. 실행 전 확인·증빙 명령

저장소 루트에서 실행한다. 두 명령은 GET 조회와 로컬 증빙 저장만 수행하며 오류 시험 POST/정책 변경/DB 초기화를 하지 않는다.

```powershell
backend/.venv/Scripts/python.exe -m backend.scripts.prepare_fault_precision
backend/.venv/Scripts/python.exe -m backend.scripts.prepare_fault_precision --run-id <완료된-실행-UUID>
```

두 번째 명령은 여러 `--run-id`를 지원한다. 동일 run ID 중복은 거절한다. 다른 실행의 반복 case는 반복 표본이므로 각 실행을 구분한다. 정책·카탈로그·snapshot 변경 또는 BUSY/DIRTY이면 준비를 거절하고 자동 정리하지 않는다.

## 7. 본 시험 완료와 확장 범위

기본 28개 → 안전 종료 27개 → 복구 허용 46개 → 현재 정책 반복 36개를 실행해 **137 PASS / FAIL·INCONCLUSIVE·NOT_EXECUTED 0**을 확인했다. 정상화를 기대한 51개는 모두 정상화했고 평균 검출→처리 완료 시간은 1.085초(51개 계측, 누락 0)였다. 안전 종료를 포함한 사전 오류 모집단의 정상화 비율은 51/127이며 정책 대응 통과율 137/137과 구분한다. 세부 환경/정책 복원 및 Edge 증빙은 [실행 결과](2026-10-11_단일오류_본시험결과.md)에 기록한다. 복합 오류, 실제 DB 프로세스 중지, 실제 provider 장애·품질·비용은 이번 단일 상황 주입의 완료 범위와 구분한다.
