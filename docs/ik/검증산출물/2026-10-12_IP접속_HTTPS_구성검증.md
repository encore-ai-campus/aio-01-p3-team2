# IP 접속·HTTPS 구성 검증

2026-10-12, `ikonly`. 기준: [구현 계획 24 §17](../기획안설계/24_AWS_배포_CICD_구현계획.md#17-ip-접속https-계약-2026-10-12). 이번 결과는 로컬 준비와 AWS 조회 검증이며 실제 배포 성공이 아니다.

## 확정 사항과 변경

- 도메인/DNS 없이 기획안·게임 웹의 서로 다른 EIP로 접속한다.
- 웹별 내부 CA로 HTTPS를 제공한다. 실제 사용자 PC에 두 공개 루트 인증서를 신뢰 등록해야 한다.
- 웹 80/443 접근은 `OperatorCidr`로 제한한다. 현재 컴퓨터 공인 IPv4 /32를 Git 제외 config에 반영했다.
- 인프라 계획은 EIP 할당 전에 가능하다. 완료된 application stack에서 EIP 소유·host 연결을 조회한 뒤 웹/Backend Origin 설정을 산출한다.
- GitHub 보호/OIDC가 미확인인 동안 자동 배포는 비활성으로 유지한다. 최초 인프라 생성은 로컬 인증과 검토한 change set으로 진행할 수 있다.
- 수동 정리 방식을 유지한다. 실제 자원은 아직 생성하지 않았다.

## 중간 실패와 수정

1. PostgreSQL profile은 명시적인 격리 DB URL을 요구해 실행을 거부했다. 신규 웹 시험은 DB를 사용하지 않아 기본 profile로 해당 함수만 실행했다. DB guard를 완화하지 않았다.
2. 최초 실제 이미지에서 IP 접속 시 SNI가 없어 TLS 인증서 선택에 실패했다. Caddy `default_sni`를 웹 IP로 지정하고 재빌드했다. 재시험에서 미신뢰/다른 IP 인증서 실패와 올바른 IP 신뢰 성공을 모두 확인했다.
3. Linux 직접 `pytest` 실행에서 import 경로가 없어 conftest 로딩에 실패했다. `/workspace`에서 `PYTHONPATH=/workspace python -m pytest`로 재실행해 core 전체를 통과했다.

## 실제 배포 수용에서 남은 작업

1. change set 검토·적용, EC2/SSM/private RDS와 host 권한 수용.
2. A6 release helper·ECR 동일 artifact·설정 주입·배포/rollback 연결. `web_endpoints.py`는 설정 산출까지 구현했으며 host 배포 연결은 후속이다.
3. 두 웹의 지속 `/data`·`/config` 설정, 실제 CA 공개 root의 지문 대조·PC 신뢰 등록과 Edge 실제 EIP 접속 확인.
4. 실제 API/MCP/DB/LLM·알림·복원·정리 수용 및 GitHub 보호/OIDC 활성화.

실제 root는 SSM으로 확인한 공개 인증서만 가져온다. 신뢰할 파일의 SHA-256을 host와 대조한 후 `Import-Certificate -FilePath <확인한-root.crt> -CertStoreLocation Cert:\CurrentUser\Root`로 설치하고 반환된 thumbprint를 로컬 증빙에 기록한다. 두 웹 각각 수행하며 정리 시 해당 thumbprint만 제거한다. 시험 fixture 인증서를 사용자 PC에 등록하지 않는다. CA 개인 키는 가져오지 않는다.

기술 근거: [Caddy 내부 HTTPS](https://caddyserver.com/docs/automatic-https), [TLS internal 설정](https://caddyserver.com/docs/caddyfile/directives/tls), [SNI 없는 클라이언트의 기본 인증서 선택](https://caddyserver.com/docs/caddyfile/options#default-sni). 이 경로는 내부 CA를 신뢰한 시험 컴퓨터용이며 공인 CA 인증서 발급 완료를 뜻하지 않는다.
