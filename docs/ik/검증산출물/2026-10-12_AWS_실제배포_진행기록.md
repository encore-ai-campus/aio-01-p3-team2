# AWS 실제 배포 진행 기록

2026-10-12 최신 운영 상태: 사용자 요청으로 AWS 실행 환경을 데이터 보존 방식으로 정리 완료했다. 5개 stack 삭제와 실행·네트워크·DB·권한 잔존 없음 확인을 마쳤다. 기존 EIP 주소는 해제되어 접속할 수 없다. 스냅샷·이미지·증거·복원 키는 보존하여 저장 비용이 일부 남는다. Windows 루트 인증서 두 개 제거는 사용자 요청으로 보류했다. [정리 결과](2026-10-12_AWS_정리결과.md)를 먼저 확인한다. 아래 배포 기록은 정리 전 상태의 이력이다.

사용자 요청으로 2026-10-12 실제 인프라 생성과 서비스 배포를 시작했다. 기준은 [구현 계획 24](../기획안설계/24_AWS_배포_CICD_구현계획.md#17-ip-접속https-계약-2026-10-12)다. 도메인 없이 웹별 EIP·내부 CA HTTPS·현재 PC 공인 IP /32·수동 종료를 사용한다. 비밀값·개인 config·실제 리소스 manifest는 Git 제외 결과 디렉터리에 보관한다.

## 시작 시 확인

- AWS 인증 유효, 서울 리전과 선택 계정 일치.
- `ikonly`는 origin보다 로컬 커밋 3개 앞서 있었으며 원격에만 있는 커밋은 없었다.
- 네트워크 변경안 50개 모두 Add, IAM/ECR/SSM 변경안 19개 모두 Add를 검토했다. 기존 프로젝트 자원 수정은 포함하지 않는다.
- 네트워크·access change set을 검토한 hash로 실행 요청했다. 실행 요청을 완료/수용으로 기록하지 않는다.
- CloudFormation 최초 CREATE change set의 placeholder stack은 태그가 비어 있어 기존 review guard가 거부했다. 정확한 계정/stack/template/parameter 대조 후, REVIEW_IN_PROGRESS·빈 stack 태그·모든 변경 Add인 경우에만 change set 소유 태그로 검증하도록 수정했다. 태그 누락·Modify 거부 회귀 검사를 보충했다.

## 배포 게이트

동일 GitHub CI artifact를 게시·배포한다. `ikonly`에 배포 준비 변경을 반영해 원격 CI를 실행하고 성공한 artifact만 선택한다. 다른 브랜치 배포 workflow는 사용하지 않는다. GitHub OIDC 자동 배포 역할은 보호 기능 확인 전 비활성이다. 초기 AWS 적용·ECR 게시·SSM 배포는 현재 로컬 인증으로 수행한다.

## 정리 전 배포 상태

실제 인프라 5개 stack과 서비스 6개 배포 완료. 아래 최종 수용 결과를 따른다. 초기 DB는 별도 main/fault database와 6개 DB 역할을 생성해 동일 private RDS 서버에서 격리한다.

## 첫 원격 CI와 보완

`bb5d862`의 원격 실행 38198238276에서 core/PostgreSQL/UI/build/실제 image 검사는 모두 통과했지만 release-gate는 `ui.json` 누락으로 거부했다. UI 보고서와 브라우저 trace를 서로 다른 루트에서 하나의 artifact로 업로드해 압축 내 `test-results/` 경로가 유지된 것이 원인이다. 보고서 artifact와 브라우저 trace artifact를 분리해 동일 디렉터리로 보고서를 내려받도록 수정한다. 실패한 candidate는 ECR 게시·배포하지 않는다.

`host_release.py`는 root 전용 hash/계정/역할/이미지 revision 검증·자기 역할 Parameter 조회·digest pull·Compose 적용·health 수용을 구현한다. `ssm_operations.py`는 소유 태그/실행 상태 확인 후 초기 로컬 운영 명령을 전송하고 결과에서 stdout/stderr를 제외한다. host health는 전체 서비스 수용과 구분한다. 전역 release/maintenance/rollback 수용 결과는 실제 확인 후 추가한다.

두 번째 원격 실행 38198677402에서도 기능 검사는 통과했으나 같은 구조의 image-checks artifact가 `verify-images.json`을 중첩 경로에 넣어 gate가 거부했다. image 보고서와 trace도 분리한다. 두 실패 실행 모두 승격하지 않았다.

5개 stack 생성 완료. EC2 6대 SSM Online과 두 EIP 연결을 확인했다. 최초 Ubuntu 24.04 bootstrap은 `apt awscli` 패키지 부재로 중단됐다. [AWS 공식 snap 설치](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)를 적용하고 기존 호스트도 SSM으로 같은 bootstrap을 재실행한다. 공식 snap은 자동 갱신되며 엄격한 CLI minor version 고정은 현재 적용하지 않는다.

실제 manifest export에서 S3 Bucket와 BucketPolicy의 PhysicalResourceId가 같은 것을 확인했다. 고유성 검사를 `(kind,id)`로 변경해 둘 다 기록하고 같은 종류/ID 중복은 계속 거부한다. 기존 manifest 자료 구조·실제 AWS ID는 변경하지 않으며 정리 시 종류에 따라 처리해야 한다. 관련 영향 단위 검사 51 PASS.

`host_database.py`는 bootstrap/migration 임시 profile을 확인한 뒤 해당 운영 Parameter만 읽고, owner 전용 일회성 container로 provisioning·migration·초기화·maintenance를 수행한다. 운영 env 파일은 root 0600이며 실행 후 제거한다. 서비스 컨테이너에는 owner/master 자격을 전달하지 않는다.

## 실제 환경에서 확인한 보완

1. Windows Git archive CRLF와 Linux CI의 소스 fingerprint 차이를 LF archive로 해소했다. Docker Desktop의 OCI manifest ID와 Linux의 config ID는 원본 tar의 config/blob/manifest를 검증해 동일 이미지임을 확인한다. 다른 이미지나 소스의 후보는 거부한다.
2. IAM simulator의 다중 resource 응답은 `ResourceSpecificResults`에 실제 allow/deny를 담는다. 이를 먼저 해석하고 기존 단일 응답을 호환하며 회귀 검사했다.
3. Compose inline tmpfs 옵션의 쉼표가 두 항목으로 해석되어 최초 웹 실행이 실패했다. 옵션 전체를 인용한 뒤 웹 2대만 재실행했고 단위 검사에 포함했다.
4. Windows text stdin의 CRLF 변환 때문에 최초 로그인 암호 hash가 입력 암호와 달랐다. byte stdin으로 LF를 고정해 같은 암호의 hash만 두 SecureString Parameter에 갱신하고 웹 2대를 재적용했다. 최종 공개 로그인·Edge 검사가 통과했다.
5. IAM profile 교체 시 association ID가 바뀐다. 복귀 시 현재 associated ID를 다시 조회해 runtime profile을 복원했다.

AWS 자원은 계속 실행 중이며 자동 종료하지 않는다. 사용자 수동 정리 요청 시 생성 manifest와 snapshot·CA thumbprint를 기준으로 진행한다. GitHub OIDC 자동 배포는 보호 설정 확인 전 비활성 상태이며, 이번 배포는 검증된 CI artifact를 로컬 AWS 인증으로 게시·배포했다. 전체 자동 CD·전역 rollback·snapshot 복원·실제 역순 정리 시험을 완료했다고 표현하지 않는다. SNS 이메일 구독 승인도 별도 확인 사항이다.
