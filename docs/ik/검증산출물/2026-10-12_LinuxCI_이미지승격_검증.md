## 실제 확인한 흐름

1. 두 운영 이미지를 source SHA label과 함께 한 번 빌드하고 tar로 저장했다.
2. 다른 Docker daemon에서 그 tar를 load하고 hash·image ID·revision label을 확인했다. 검증 단계에서 rebuild하지 않았다.
3. 자체 CA/TLS의 임시 실제 PostgreSQL과 main/fault API·MCP, plan/game Caddy를 실행했다.
4. HTTPS 인증·라우팅·직접 API 차단·MCP Host/Origin·DB 조회·maintenance·오류 runner·restart·fallback 금지를 확인했다.
5. Chromium에서 실제 catalog 입력 폼, 정책 화면, 격리 Planner 오류의 복구 시연, Phaser 게임 및 DB 상태 표시를 확인했다. 일반 정책이 시험으로 바뀌지 않았음을 비교했다.
6. 실제 보고서·receipt·tar를 사용하고 로컬에서 완료한 단계의 성공 결과를 입력해 release-gate를 재현했다. 원격 Actions job 상태를 조회한 것은 아니다.

일반 API는 유료 provider를 호출하지 않는 시험용 key/model 설정을 사용했다. 기존 E2E는 결정적 에이전트와 실제 DB를 사용하고, 디자인/상태 표현 사례에는 명시적인 UI fixture가 포함된다. 운영 이미지 화면의 catalog·게임 상태·정책·복구 시연은 실제 API/DB/MCP를 거쳤다. 실제 OpenAI 정상 호출은 아직 검증하지 않았다.

Chromium은 임시 자체 인증서 때문에 `ignoreHTTPSErrors`를 사용한다. Python HTTPS 검사는 자체 CA·hostname/SNI를 검증하며, 실제 AWS의 public ACME 인증서 검증은 별도 수용 단계다.

## 중간 실패·해결

| 발견 | 해결 |
|---|---|
| Windows `docker cp`가 Python 파일에 실행 권한을 부여해 Ruff EXE002 발생 | 소유한 Linux snapshot의 파일 mode를 644로 조정. Git 추적 Python 파일은 100644 |
| JUnit 클래스 이름 때문에 함수/parameter 증빙을 누락으로 판단 | 클래스 namespace와 수집된 parameter ID를 정확히 대응 |
| profile hook의 False 반환이 pytest 기본 `--ignore`를 막아 이미지 시험 2개가 DB job에서 skip | 포함 파일에는 None 반환. 별도 회귀 검사 추가. DB job 재실행 52 PASS/skip 없음 |
| MCP503 UI 시험이 비동기 요청에 예전 201 응답을 기대 | 현재 `Prefer: respond-async`의 202 접수와 완료 조회를 검증. 재시도 3회·안전 종료·저장 Trace 검증 유지 |
| Node APIRequestContext가 `plan.localhost`/`game.localhost`를 해석하지 못함 | Chromium의 실제 인증된 화면 안에서 same-origin fetch로 DB 상태/정책 비교 |

실패한 필수 검사를 제외하거나 성공으로 바꾸지 않았다. 수정 후 최종 전체 선택 그룹이 통과했다.

## 재현·정리·다음 단계

Linux job은 고정 `requirements.ci.lock`, pnpm10.33.0/frozen lock, Chromium을 준비한 뒤 아래 경로를 사용한다. `GITHUB_SHA`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`는 실제 CI 제공 값을 쓴다.

```sh
bash infra/ci/run-python.sh core
# PostgreSQL/UI/image job마다 별도 CI_JOB_ROLE을 설정한다.
source infra/ci/database.sh
bash infra/ci/run-python.sh postgres
bash infra/ci/run-ui.sh
# image 후보를 내려받은 독립 job에서 실행
bash infra/ci/verify-images.sh
python -m infra.ci.gate approve --output test-results/ci-verified.json
```

실제 MCP 준비 및 Node proxy·tar 생성·job별 실행 순서는 workflow와 [계획 §15](../기획안설계/24_AWS_배포_CICD_구현계획.md#15-linux-ci동일-이미지-승격-검사-구현-2026-10-12)를 따른다. `approve`는 GitHub `needs` JSON과 같은 실행의 artifact 전체를 요구한다.

Windows에서는 `infra/ci/Dockerfile.runner`와 소유권 label이 있는 임시 Docker daemon/volume을 사용해 Linux 환경을 재현했다. privileged daemon은 로컬 시험용이며 production 서비스에는 적용하지 않는다. 외부 host Docker socket을 전달하지 않았다. nested DB·fleet·network와 임시 환경 파일은 fixture/trap에서 정리하고, 원본 확보 후 소유 label을 확인해 runner/daemon 및 workspace/tmp/socket volume을 제거했다. 기존 `ikonly-test-postgres-1`은 유지했으며 사용자 DB/서버를 변경하지 않았다. 로컬 image/build cache는 남고 실행 중 시험 자원은 없다.

다음은 원격 push 후 Actions의 실제 성공 run 증빙과 A5 AWS 인증·IaC·IAM/OIDC·Parameter Store·보호된 배포 환경 구성이다. A6에서 신뢰할 CI workflow/branch/run을 확인하고 검증 tar만 ECR로 게시하며, 게시 digest를 실제 release manifest에 연결한다. CI hash는 전자 서명이나 AWS 배포 권한을 대신하지 않는다.

참고: [GitHub artifact 전달/검증](https://docs.github.com/en/actions/tutorials/store-and-share-data), [job 실패·skip과 조건](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax). Actions 자체 digest 경고에만 의존하지 않고 내부 tar/report hash 불일치를 실패로 처리한다.
