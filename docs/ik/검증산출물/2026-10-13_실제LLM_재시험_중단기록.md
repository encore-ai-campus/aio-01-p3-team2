## 1. 목적·실행 경계

고정 adapter 통과와 실제 모델 응답 통과를 구분하기 위해 이전 실호출 방식으로 현재 통합 코드를 시험했다. 실제 Planner/Critic, DB/MCP, 규칙 검증, Supervisor 상태 전이와 암호화 원문 저장을 연결했다.

- 코드 `ikonly`, `a0a40f4`; 이번 작업에서 앱 코드를 변경하지 않았다.
- 모델 `gpt-4.1-mini`, 실제 OpenAI 응답. API 키 인증과 실제 generation을 확인했다.
- 전용 PostgreSQL `eventquest_fault_test`, MCP 8014, 공유 UI 5177, 기존 시험 API 8013. 사용자 DB/게임 데이터 초기화·승인·게임 반영을 하지 않았다.
- 시험 정책 version 1 고정·원복. 실호출은 기존 CLI를 사용하고 시험 API의 결정적 adapter 제한은 유지했다.
- 캠페인 `00e0b553-2b5c-4445-b3d5-05016cc86348`, 상한 90회/$3. Workflow 기존 호출·토큰·비용·기한 제한을 유지한다.
- 사전 점검 통과 후 정상 3종 각 3회→일시 LLM 복구→지속 오류 종료→MCP 통신 오류→새 정상 요청 순서로 계획했다. FAIL/판정 불가이면 후속 호출을 중지한다.

## 3. 발견 1: 미지원 업무 판정과 Critic 의미 검수의 불일치

요청의 `venue.future_boss_room`은 등록되지 않은 capability다. 결정적 검증은 개발 필요 항목과 `runtime_eligible=false`를 만들었다. 실제 Critic은 그 미지원 사유를 실행 불가능한 모순으로 보고 `REVIEW / HUMAN_REVIEW`를 반환했다. 별도의 요청/산출물 의미 모순을 제시하기보다 기존 capability 미지원 판정을 사람 검토 사유로 다시 사용했다.

그 결과:

1. 개발 필요 항목 생성·Runtime 차단.
2. Critic `REVIEW` 반환.
3. `canonical_planning.py`가 `CRITIC_REQUIRES_HUMAN_REVIEW` finding을 추가하고 Plan을 `BLOCKED`로 변경.
4. `agents/supervisor.py`의 `plan_reviewed` 전이가 `WAITING_REVIEW` 선택.
5. 결과와 Trace 저장. 무한 실행이나 잘못된 게임 적용은 없었다.

Supervisor가 상태 전이 계약을 어기거나 LLM이 상태를 직접 저장한 문제는 아니다. **미지원 요구는 개발 필요 결과로 끝낸다는 업무 계약과 실제 Critic의 판단을 어떻게 결합할지 부족한 부분**이다. 고정 Critic은 참조 일치를 확인하고 capability 최종 판정을 규칙 검증에 맡겨 PASS를 반환하기 때문에 고정 시험에서는 드러나지 않았다.

현재 Critic 프롬프트에도 capability·안전·경제 최종 판정은 결정적 검증이 담당한다고 적혀 있지만, 실제 응답이 그 경계를 지킨다고 보장하지 못했다. 모든 REVIEW를 PASS로 강제하거나 실제 상태를 이유 없이 COMPLETED로 덮어쓰는 방식은 적절하지 않다.

권장 보완: 이미 확정된 NEEDS_DEVELOPMENT/NEEDS_DATA와 **추가 의미 모순**을 구조적으로 구분한다. Critic은 검수한 필드·구체적 모순·근거를 반환하고, 규칙 기반 Supervisor/검증이 미지원 사유만으로 업무 결과를 사람 검토로 변경하지 않게 판단한다. 별도의 실제 의미/보안 문제가 있으면 기존 사람 검토·차단을 유지한다. 구현 변경은 이번 시험에서 하지 않았다.

## 4. 발견 2: 복구 시연 UI 최종 상태 매핑 누락

실제 실패 결과를 조회하는 opt-in Edge 검사가 FAIL이었다. Backend는 `WAITING_REVIEW`를 저장했지만 `frontend-web/src/fault-lab-topology.js`의 `terminalLabels`에 이 상태가 없어 화면의 최종 상태가 **확인 불가**로 표시됐다.

- 정상 실호출 6개 결과의 UI 조회 검사: **1 PASS**, 사용량/암호화 검사 결과·새로고침과 POST 0 확인.
- 실제 실패 결과의 UI 의미 검사: **1 FAIL**, WAITING_REVIEW 표시 기대와 불일치.
- 두 UI 검사에는 추가 provider 호출이 없었다. 실패 판정과 원본 JSON은 유지됐다.
- 별도 read-only 화면 수집으로 FAIL/확인 불가 표시를 보존했다. 이것을 UI 합격으로 재분류하지 않는다.

권장 보완: `WAITING_REVIEW`의 한국어 이름·결과 안내 및 관련 경로 표시를 실제 상태 계약에 맞춰 추가하고, 이번 저장 결과로 재조회 회귀 검사를 수행한다.
