# 에러 분류와 복구 정책 구성 제안

## 목적

체크포인트의 기존 Error Type, Fault Injection, Routing, Retry/Fallback/Safe Stop을 최대한 유지하며 정책을 점진적으로 정리하기 위한 제안이다. 먼저 현행 동작을 기준선으로 만들고, 원인 코드와 처리 정책을 분리한 뒤 기존 경로를 정책 계층에 연결한다. 전면 재작성은 전제하지 않는다.

## 0. 오류 정책보다 먼저 확정할 시스템 경계

오류 분류와 복구 정책을 정하기 전에 **무엇이 이 시스템 안에 있고, 어느 구성요소가 어떤 작업을 책임지며, 어디서 시스템 밖으로 나가는지**를 먼저 합의한다. 경계가 정해져야 오류의 소유 계층, 안전한 재시도 범위, 사람에게 넘길 조건을 구분할 수 있다.

### 제품 경계

현재 제품 목표는 게임 이벤트를 생성·검수하고 운영자 승인 대기 상태까지 제공하는 내부 기획 도구다. 실제 게임 서버에 이벤트·미션·보상을 등록하는 쓰기 동작은 현재 제품 경계 밖에 둔다. Clash 공개 API는 읽기 표본을 얻는 외부 의존성이고, demo-game은 승인 결과를 시연하는 별도 프레젠테이션 계층이다. 둘을 실제 게임 운영과 혼동하지 않는다.

실제 게임 쓰기 연동을 추후 포함한다면 별도의 범위 변경으로 승인하고, 읽기 조회와 쓰기 실행을 별도 권한·API·오류 경계로 설계한다.

### 실행 구성요소와 책임 경계

| 구성요소 | 맡는 책임 | 경계를 넘는 요청/결과 |
|---|---|---|
| Frontend | 사용자 입력, 작업 결과·Trace 표시, 승인 요청 | Backend API에 요청하고 반환된 상태·에러를 사용자에게 안전하게 표현 |
| Backend API/Task Service | 요청 검증, 권한·멱등성·Task 상태·저장, API 오류 응답 | HTTP 오류와 Workflow의 FAILED 결과를 구분 |
| Workflow/Supervisor/Agents | Agent 실행, Handoff, 정책 판단, retry/revision/fallback/Safe Stop 선택 | MCP/LLM 결과를 검증된 상태로 변환하고 정책 결정 Trace 생성 |
| MCP Server/외부 API | 게임 데이터·공개 표본 조회 | Tool 요청·응답 계약, 원천·버전·시간·통신 실패 정보를 Backend에 전달 |
| PostgreSQL/JSON/Cache | 상태 또는 게임 데이터 제공 | 데이터 최신성·스키마·버전·쓰기 결과의 일관성 책임 지정 |
| 운영자 | 승인·수정·거절 및 시스템 장애 수동 복구 | 권한 있는 결정만 수행하고 누가 언제 조치했는지 감사 기록 |
| GitHub Actions/Docker/AWS | 코드 검증과 이미지 배포, 배포 Health/Rollback | 배포 실패는 런타임 Workflow 오류가 아니라 전달 파이프라인 실패로 분류 |

### 신뢰 경계

먼저 입력·Agent 생성 결과·MCP/외부 API 응답·정책 설정·DB 상태 중 무엇을 신뢰하지 않을지 정한다. 특히 LLM이나 Tool이 반환한 값은 권한이 아니며, 실제 Tool 실행 권한은 Backend 코드와 승인 경계에서 검사한다. 정책 편집 권한과 이벤트 승인 권한, 시스템 운영 권한도 서로 같은 역할이라고 가정하지 않는다.

### 경계 확정 시 답할 질문

1. Workflow가 책임지는 마지막 단계는 승인 후보인가, 승인 완료인가, 실제 게임 반영인가?
2. LLM, MCP, DB, 외부 게임 API 중 각 의존성의 연결·Timeout·데이터 정확성을 어느 계층이 책임지는가?
3. 같은 오류를 MCP Client, Agent, Workflow 중 어느 한 곳이 재시도하고 다른 계층은 어떻게 그 시도 이력을 아는가?
4. DB 쓰기 결과가 불명확할 때 재실행 전에 누가 멱등성/저장 상태를 확인하는가?
5. 사용자 입력 오류, 정책 차단, 서비스 장애, 잘못된 게임 데이터 중 누가 수정해야 하는가?
6. 운영자 수동 개입과 자동 복구의 책임 전환 시점을 무엇으로 기록하는가?
7. CI/CD 실패, 배포 실패, 실행 중 Workflow 실패를 서로 다른 운영 절차로 다룰 것인가?

위 질문을 합의한 뒤에야 아래 오류 분류와 복구 정책을 확정한다.

## 1. 실무 표준에서 가져올 원칙

모든 제품에 통용되는 하나의 Error taxonomy가 있는 것은 아니다. 표준과 운영 지침은 각 층에서 다르므로 역할별로 적용한다.

- HTTP API 오류는 IETF [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)처럼 기계가 식별할 문제 유형과 HTTP 상태, 사람이 읽을 설명을 구분한다.
- 운영 Trace/Metric은 [OpenTelemetry 오류 기록 관례](https://opentelemetry.io/docs/specs/semconv/general/recording-errors/)처럼 집계 가능한 고정 `error.type`을 사용하고, 복구된 내부 오류와 최종 작업 실패를 구별한다. 예외 메시지에는 민감정보가 포함될 수 있어 노출을 제한한다.
- 복구 정책은 서비스별로 정하되, [AWS retry 가이드](https://docs.aws.amazon.com/sdkref/latest/guide/feature-retry-behavior.html)와 [Google SRE](https://sre.google/sre-book/handling-overload/)의 공통 원칙인 일시 오류와 throttling 구분, 제한된 retry, 지수 backoff+jitter, retry budget을 참고한다.
- 지속 장애에는 [AWS Circuit Breaker 지침](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/circuit-breaker.html)처럼 반복 호출을 잠시 차단하는 방법을 검토한다.
- Agent 보안 오류는 일반 생성 오류와 분리한다. [OWASP Prompt Injection 지침](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)은 필터만 믿지 말고 Tool 경계에서 권한·인자·승인을 강제하고 최소 권한을 사용하도록 안내한다.

이 자료는 프로젝트 코드 목록을 대신하지 않는다. 표준화할 것은 오류를 기록하고 HTTP로 전달하는 형식과 재시도 안정성 원칙이며, 도메인 오류와 복구 정책은 팀이 정한다.

## 2. 현재 구현에서 재사용할 기반

- 기존 Error Type에는 도메인/기획 오류(`mission_unreachable`, `item_not_found`, `event_brief_mismatch`), 실행 오류(`agent_failure`, `llm_timeout`), MCP·DB 오류, `validation_error` 등이 있다.
- Fault Injection `fault_type`은 시험에서 오류를 만드는 입력이고, 실행 결과의 `error_type`과는 별도다. 이 구분은 유지한다.
- `routing.py`는 도메인 오류를 Planner revision, Agent 오류를 재실행, 규칙 Tool 오류를 fallback, MCP/DB 오류를 제한 retry, 복구 불가를 Safe Stop으로 보낸다.
- retry 최대 3회와 자동 기획 수정 최대 2회를 서로 다른 카운터로 관리한다.
- Trace에는 `error_type`, `reason_code`, `policy_decision`, phase, Agent/Tool, retry/revision count, fallback, 데이터 출처·버전이 있다.
- Supervisor의 LLM은 일부 정상 전환·복구 경로를 심사하지만, 코드 정책이 허용 경로와 한도를 제한한다. LLM 판단 실패는 Safe Stop한다.

확인 위치: `backend/app/orchestration/routing.py`, `retry.py`, `engine.py`, `backend/app/agents/supervisor.py`, `backend/app/fault_injection/fault_types.py`, `backend/app/schemas/workflow_state.py`.

## 3. 핵심 설계: 오류 원인과 복구 정책 분리

하나의 `error_type`에 원인, 심각도, retry 여부, 복구 행동, 사용자 메시지를 전부 담지 않는다.

1. **Error Code:** 무슨 일이 발생했는가. API·로그·시험에서 유지되는 안정적인 코드.
2. **Category/Phase:** 어떤 성격의 문제이며 어느 단계에서 발생했는가. 예: 도메인, 계약/검증, Agent/LLM, 외부 의존성, 저장소, 보안/권한, 내부 결함; input/planning/tool/approval 등.
3. **Retry Class:** 같은 작업 retry, Agent 재호출, 기획 수정, fallback, 사람 조치, retry 금지 중 무엇이 안전한가.
4. **Severity/Impact:** 사용자·데이터·보안 영향의 크기. 심각도는 retry 여부와 별개다.
5. **Policy Action:** 현재 호출 대상과 상태에 적용할 제한된 행동 및 상한.
6. **Presentation:** 사용자/API에는 안전한 안내를, 내부 로그에는 권한이 제한된 진단 근거를 준다.

이 분리는 `mcp_timeout` 하나라도 기획 데이터 조회와 Primary 규칙 Tool에서 허용 가능한 fallback이 다르다는 점을 표현한다.

## 4. 권장 Schema

### Error Event (발생 사실)

| 필드 | 의미 |
|---|---|
| `error_code` | 기존 `error_type`과 호환되는 안정 코드 |
| `category`, `phase` | 문제 성격과 Workflow 위치 |
| `component`, `operation` | Agent/Tool/저장소 및 실행 작업 |
| `task_id`, `trace_id` | 실행·로그 상관관계 |
| `retry_class`, `attempt` | retry 안전성 분류와 실제 시도 번호 |
| `safe_details` | 민감정보 제거된 오류 근거 |
| `occurred_at` | 시간대가 포함된 발생 시각 |

### Recovery Policy (처리 규칙)

| 필드 | 의미 |
|---|---|
| `policy_id`, `policy_version` | 적용한 정책과 재현 가능한 버전 |
| `match` | error code/category, phase, component/tool의 제한된 조건 |
| `action` | `FAIL_FAST`, `RETRY_OPERATION`, `RETRY_AGENT`, `REVISE_PLAN`, `USE_FALLBACK`, `SAFE_STOP`, `REQUIRE_HUMAN` 등 제한된 선택지 |
| `max_attempts`, `deadline` | 시도 수와 전체 작업 시간 상한 |
| `backoff` | 적용 시 대기·jitter·상한·`Retry-After` 반영 |
| `fallback_target` | 코드에서 사전 허용한 대체 Tool/원천 ID |
| `revalidation` | 복구 후 필수 Schema/Rule/Critic 검사 |
| `user_action`, `operator_alert` | 사용자 안내와 운영자 조치/알림 |
| `enabled`, `effective_at` | 활성화와 적용 시점 |

정책 파일은 임의 Python/표현식을 실행하지 않는 Schema 기반 설정이어야 한다. 보안 Guard, Tool 권한, 가능한 fallback, 최대 retry hard cap, 필수 재검증은 코드의 불변 조건으로 두어 일반 사용자가 약화시킬 수 없게 한다.

## 5. 기존 오류의 초기 분류 방향

아래는 기존 코드의 의미를 나누기 위한 초안이며, 최종 정책 확정표가 아니다.

| 현재 Error Type 또는 상황 | 분류 | 현재 경로 | 논의할 점 |
|---|---|---|---|
| `mission_unreachable`, `item_not_found`, `event_brief_mismatch` | 기획/도메인 품질 오류 | Planner revision 후 전체 재검증 | 수정 가능한 필드, revision 완료 기준, 한도 |
| `validation_error` | 계약·출력·데이터 검증 | 일부 Agent 오류는 retry | 사용자 입력, LLM 출력 형식, MCP Tool 응답, Rule 위반을 발생 위치별 하위 코드로 점진 구분. 입력 오류는 retry하지 않음 |
| `agent_failure`, `llm_timeout` | Agent/Model 실행 오류 | 현재 같은 Agent retry | timeout, rate limit/throttling, 5xx, 영구 인증/설정 오류를 구분할 수 있는지 검토. 현재 예외가 generic `LLMExecutionError`로 뭉칠 수 있음 |
| `mcp_timeout` | 외부 의존성 통신 오류 | Tool별 bounded retry | 읽기 작업의 재시도 안전성, retry 소유 계층, timeout 예산 |
| `mcp_tool_error` | Tool 실행 또는 응답 계약 오류 | 규칙 Tool은 fallback, 일부는 retry, 미지원 경로는 Safe Stop | fallback 데이터 동등성·버전·신선도, Tool별 구분 |
| `db_connection_error` | 저장소 오류 | 제한 retry | 읽기와 쓰기를 구분하고 쓰기 결과 불명확 시 중복 실행 방지·기존 저장 상태 확인 |
| Schema/Guard/actor 권한 차단 | 입력·보안·권한 오류 | Fail Fast 경로 | Agent 오류로 retry하지 않고 차단·감사·안전한 사용자 안내 |
| 미분류 예외·누락 정책 | 내부 오류 | Safe Stop 또는 일반 실패 | 기본값은 자동 retry/fallback 금지, 원인 수집과 운영 확인 |

도메인 오류는 반드시 시스템 장애는 아니다. `mission_unreachable`을 고쳐 새 기획안을 내는 revision과, `mcp_timeout` 뒤 같은 조회를 다시 하는 retry는 다른 카운터·성공 기준을 가져야 한다.

## 6. 실무형 복구 원칙 제안

- **일시 오류만 retry:** 입력·권한·보안·확정적 Rule 오류를 같은 조건으로 반복해도 해결되지 않으므로 fail-fast, revision 또는 사람 검토로 보낸다.
- **멱등성 확인:** 읽기 요청과 LLM 재생성, 실제 게임 이벤트 등록을 동일하게 재시도하지 않는다. 쓰기 작업은 idempotency key 또는 결과 확인 후 재시도한다.
- **한 계층이 retry 소유:** SDK·MCP Client·Agent·Workflow가 중복 재시도하지 않도록 계층을 정하고 상위 호출이 시도 예산을 공유한다. 중첩 retry는 트래픽과 비용을 증폭할 수 있다. ([Google SRE](https://sre.google/sre-book/handling-overload/))
- **횟수와 총 시간/비용 제한:** 기존 count cap을 유지하되 외부 서비스에는 deadline, 적절한 backoff/jitter, 전체 요청 retry budget을 검토한다. 현재 `retry.py`는 카운터 한도만 계산하며 backoff·jitter·circuit breaker 구현은 확인되지 않았다.
- **fallback은 호환 데이터만:** 데이터 Schema·버전·신선도를 검증한다. 다른 버전의 규칙을 섞거나 최신 여부를 알 수 없으면 승인 후보를 만들지 않고 Safe Stop한다.
- **복구 성공은 재검증 후:** 호출 재성공만으로 복구 완료로 보지 않고 해당 Output/Tool Schema, Rule Engine, Critic 검사를 통과시킨다.
- **보안 경계는 LLM 밖에서 강제:** 모델의 판단이나 설명은 권한을 만들지 않는다. Tool/API가 실행 사용자, 허용 인자와 승인된 작업을 검사한다.
- **미분류 오류는 안전 종료:** 새로운 유형에 임의 fallback을 적용하지 않는다. 내부 reason code와 안전한 사용자 안내, 운영 확인을 남긴다.

현재 저부하 시연 단계라면 Circuit Breaker는 바로 넣지 않아도 된다. 지속적인 MCP/LLM/게임 API 장애나 동시 요청이 관찰되면 threshold와 관측 지표를 정해 도입한다.

## 7. 전면 변경 없이 도입하는 순서

### 단계 0 — 시스템 경계와 책임 확정

제품의 시작/종료 지점, Backend·Agent·MCP·저장소·운영자 책임, 신뢰 경계, 게임 API 읽기/쓰기 범위, CI/CD와 런타임 운영 절차를 합의한다. 이 단계에서 Error Type이나 재시도 횟수를 먼저 결정하지 않는다.

### 단계 1 — 현행 정책 기준선

기존 error code별 발생 지점, fault injection, 현재 Routing, 허용 retry/revision, fallback, 최종 상태, Trace action, 시험 근거를 표로 만든다. 이 단계에서는 코드 동작을 바꾸지 않는다.

### 단계 2 — Registry와 호환 resolver

Error Catalog와 Recovery Policy Schema를 만든다. 기존 `decide_recovery()`의 행동을 정책 Registry로 옮기되 같은 입력에서 같은 `RecoveryRoute`가 나오도록 기존 인터페이스 뒤에 resolver를 추가한다. 누락·오류 정책은 fail-closed Safe Stop한다.

### 단계 3 — 분류와 관측 보강

기존 `error_type` 문자열을 API 호환 코드로 보존하고 내부에 `category/phase/retry_class`를 매핑한다. Trace에 `policy_id/version`, attempt, 상관관계 ID를 추가한다. 민감한 stacktrace와 사용자 노출 설명을 분리한다. 필요 시 RFC 9457 형식은 기존 API 계약을 깨지 않는 별도 전환으로 검토한다.

### 단계 4 — 제한적 안정성 개선

실제 외부 요청에서만 필요한 backoff+jitter/deadline을 넣고, retry가 한 계층에서만 실행되게 정리한다. 영구 오류는 빠르게 중단하고, rate limit은 제공자가 준 대기 지시를 반영한다. DB write의 멱등성과 결과 확인을 먼저 보장한다.

### 단계 5 — 운영 UI

먼저 활성 정책 조회와 예시 입력의 시뮬레이션 UI를 만든다. 실제 수정은 RBAC, 필드 검증, 작성/승인, 감사 로그, 버전, 적용 시점, rollback이 준비된 뒤 허용한다. 보안·권한·Hard cap은 일반 운영자가 편집할 수 없게 둔다.

## 8. 정책 UI와 외부 게임 API의 안전 조건

- 사용자가 수정할 수 있는 한도와 시스템 관리자/보안 담당자만 수정할 조건을 분리한다.
- 정책 저장 전에 Schema·상호 모순·존재하지 않는 Tool/Agent 참조를 검증한다.
- 샘플 장애 시나리오로 기존 정책과 신규 정책의 결과를 미리 비교한다.
- 정책 변경자·승인자·이유·시작 시각·적용 Task를 기록하고 이전 버전으로 되돌릴 수 있게 한다.
- 실제 게임 API에 이벤트를 쓰는 경우 read/write 권한을 분리하고 Sandbox, 사람 승인, idempotency key, 중복 발급 확인, 취소/보상 처리, 감사 기록을 요구한다.
- 게임 연동 Tool을 추가해도 정책 편집이 해당 Tool의 권한 범위를 넓힐 수 없게 코드에서 제한한다.

## 9. 팀 논의에서 정할 항목

구체 Error Type을 한꺼번에 확정하지 않고 아래 질문 순서로 정책 워크숍을 진행한다.

1. Workflow의 제품 경계와 외부 연동의 읽기/쓰기 범위는 어디인가?
2. API, Agent/Workflow, MCP, DB, 운영자, CI/CD가 각각 책임지는 실패와 인계 시점은 무엇인가?
3. 기획 오류와 실행 장애, 입력/보안 차단을 어떤 결과 상태로 구분할 것인가?
4. Supervisor LLM은 경로를 제안/심사하는가, 결정적 정책의 최종 결과를 거부할 수 있는가?
5. 어떤 호출이 멱등하며 retry를 담당하는 유일한 계층은 어디인가?
6. 오류별 retry 횟수뿐 아니라 전체 시간·비용 예산을 어떻게 정할 것인가?
7. 어떤 fallback이 업무 의미·데이터 버전 면에서 안전하며, 안전하지 않을 때 어떤 Safe Stop을 할 것인가?
8. 운영자가 편집할 수 있는 정책과 승인/관리자 권한이 필요한 정책은 무엇인가?
9. 복구 성공·Safe Stop·수동 개입·false recovery를 어떤 시험과 지표로 입증할 것인가?

워크숍 산출물은 ① Error Catalog ② Recovery Policy Schema/표 ③ 권한·승인표 ④ 시나리오별 평가·회귀시험 ⑤ 정책 버전·감사·Rollback 절차로 한다.

## 결론

추천 순서는 **시스템 경계와 책임 확정 → 현재 Error Type/Routing 기준선 → 오류 원인 Catalog와 별도 Recovery Policy 도입 → 같은 동작 재현 → 검증된 차이의 단계 반영**이다. 경계와 현행 동작을 합의하기 전에는 사용자가 바꿀 오류 정책을 정하지 않는다.

가장 먼저 손볼 것은 오류 코드 이름이 아니라 `validation_error`처럼 서로 다른 원인을 뭉뚱그린 경계, 재시도 계층과 전체 예산, LLM/MCP의 transient·throttling·permanent 오류 구분, 정책 버전 Trace다. 사용자 정책 편집 UI와 Circuit Breaker는 그 이후에 권한·감사·지표가 준비될 때 추가한다.
