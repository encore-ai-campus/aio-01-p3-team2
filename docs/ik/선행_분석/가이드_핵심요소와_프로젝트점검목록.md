# 프로젝트 진행 가이드 핵심요소와 점검목록

## 목적

팀장 관점에서 교과목 가이드가 요구하는 핵심을 먼저 고정하고, 이후 기획·구현·시험·발표가 같은 기준을 따르는지 점검하기 위한 문서다. 가이드의 예시 아키텍처·도구·수치는 필수 구현으로 복사하지 않는다. 프로젝트 주제에 맞게 개념을 적용하고 실제 코드와 시험 결과로 증명한다.

## 1. 가이드 요약

가이드의 핵심 과제는 **멀티 에이전트의 역할과 협업 흐름을 설계하고, 장애를 감지·판단·복구하는 AutoHealing을 구현한 뒤, 서비스 배포와 장애 시험으로 복구 결과를 검증하는 것**이다.

권장 순서는 다음과 같다.

1. 해결할 문제, 사용자, 정상·실패 시나리오를 정의한다.
2. 에이전트별 책임과 금지 범위, 최종 판단 주체를 정한다.
3. Handoff 데이터와 공유 상태·메모리 전달 방식을 설계한다.
4. 정상 협업 경로와 Critic의 PASS/RETRY/FAIL 분기를 구현한다.
5. 장애 유형별 감지 기준, 복구 정책, 한도와 안전 종료 조건을 만든다.
6. 컨테이너·배포 환경·CI/CD·알림 흐름을 구성하고 테스트 실패 시 배포를 차단한다.
7. 장애를 주입해 기대·실제 결과와 복구 시간을 기록하고 복구율·평균 복구시간을 산출한다.

필수 산출물은 다음 세 가지다.

1. **멀티 에이전트 아키텍처 설계서** — 역할, Handoff, 상태 전달, 정상·재시도·실패·종료 흐름
2. **배포 및 장애 복구 보고서** — 실제 배포 구성, 장애 감지·복구 전략, 장애 시험 증빙, 지표, 수동 개입 조건
3. **파이프라인 구현 결과 보고서** — 커밋부터 배포까지 자동화, 단계별 성공·실패 정책, 실제 실행 결과와 로그

가이드는 예시와 실제 요구를 명시적으로 구분한다. Supervisor/Planner/Executor/Critic/Memory Keeper, Kubernetes, Ingress, 대체 모델·API는 가능한 예시다. 프로젝트에 필요한 구조를 선택하되 **문서에는 실제 구현 구조와 시험 결과만 완료로 기록**한다.

## 2. 프로젝트에 반영해야 할 개념 전체 목록

### A. 문제와 사용자 시나리오

- [ ] 해결할 문제와 대표 사용자를 구체적으로 정의한다.
- [ ] 사용자 요청부터 최종 결과까지의 end-to-end 흐름을 한 문장과 흐름도로 표현한다.
- [ ] 멀티 에이전트로 역할을 나누는 이유와 단일 에이전트 대비 이점을 설명한다.
- [ ] 정상 요청뿐 아니라 실패, 지연, 결과 불일치, 복구 불가 시나리오를 정의한다.
- [ ] 프로젝트 범위와 제외 범위를 명시해 데모 기능과 실제 운영 기능을 구분한다.

### B. 에이전트 아키텍처와 책임

- [ ] 협업 구조(예: Supervisor 중심 조정형)와 선택 이유를 기록한다.
- [ ] 각 역할에 대해 책임, 입력, 출력, 금지 행동을 정한다.
- [ ] 역할이 겹치는 부분과 담당자가 없는 책임을 점검한다.
- [ ] 최종 성공·실패·재시도·중단 판단 주체를 정한다.
- [ ] Critic 또는 동등한 검증 단계의 PASS/RETRY/FAIL 의미와 분기를 정의한다.
- [ ] Supervisor 같은 중앙 조정자가 실패할 때의 영향과 운영 복구 방법을 설명한다.

### C. Handoff·상태·메모리

- [ ] 에이전트 간 전달에 `task_id`, 목적, 입력, 제약, 기대 출력, 시도 횟수를 포함한다.
- [ ] 전달 주체·수신 주체, 결과 작성자, 검증 상태를 추적한다.
- [ ] 공유 상태·중간 결과·실패 원인·재시도 횟수가 다음 단계에 누락 없이 전달된다.
- [ ] 참조값으로 상태를 전달하는 경우 실제 접근 경로와 수명 정책을 정한다.
- [ ] 민감정보와 시크릿을 프롬프트, Handoff, 로그, 장기 메모리에 넣지 않는다.
- [ ] 재시도 때 이전 실패 원인과 수정 지시를 전달하고 반복 상한을 둔다.

### D. Workflow·검증·종료

- [ ] 최소 협업 경로를 각 Agent의 개별 확인 후 연결한다.
- [ ] 결과가 다음 단계로 넘어가기 전에 계약·형식·정책 검증을 받는다.
- [ ] PASS·RETRY·FAIL에 따라 경로가 실제로 달라진다.
- [ ] 최대 반복 횟수, 시간 제한, 재시도 초기화 조건을 정해 무한 실행을 막는다.
- [ ] 정상 완료, 사용자 수정, 기술 재시도, 복구 성공, Safe Stop/최종 실패를 구분한다.
- [ ] 검증되지 않은 부분 결과를 성공 결과로 확정하지 않는다.
- [ ] 사용자에게 최종 상태와 후속 조치 또는 수동 개입 필요 여부를 설명한다.

### E. 장애 감지와 AutoHealing

- [ ] 장애 유형을 네트워크, DB, 외부 API/Tool, LLM/Agent, Validation, 보안/프롬프트 공격 등 프로젝트 위험에 맞춰 분류한다.
- [ ] 장애별 감지 조건과 확인 지표를 정의한다.
- [ ] 재시도, 재연결, fallback, 대체 서비스/모델, 캐시 등 적용 가능한 조치를 장애별로 선택한다.
- [ ] 어떤 오류는 자동 재시도하고 어떤 오류는 즉시 중단하는지 구분한다.
- [ ] 복구 상한, 최종 실패 조건, Safe Stop 시 보존할 상태와 결과를 정한다.
- [ ] 복구 불가 시 사용자 메시지, 운영자 알림, 담당자와 수동 조치를 정한다.
- [ ] 장애 발생부터 복구·중단까지 Trace/운영 로그에서 원인과 조치를 추적할 수 있다.
- [ ] AutoHealing이 무조건 성공을 만들지 않고, 확인할 수 없는 경우 안전하게 멈춘다.

### F. 배포·운영 구성

- [ ] 실제 구성요소, 컨테이너, 통신 경로, 외부 노출 범위, 상태 확인 방법을 기록한다.
- [ ] 설정과 시크릿의 전달·저장 위치를 정하고 저장소/로그에 비밀값이 노출되지 않게 한다.
- [ ] 코드 커밋 → 빌드 → 단위 시험 → 통합 시험 → 이미지/배포 → 상태 확인의 파이프라인을 설명한다.
- [ ] 테스트 실패 시 배포 중단 정책이 실제 동작한다.
- [ ] 배포 실패 시 이전 버전 유지/롤백 정책을 정한다.
- [ ] 성공·실패·지연 알림 대상과 에스컬레이션 경로를 정한다.
- [ ] 배포 환경과 보고서·시연 환경이 일치하는지 확인한다.

### G. 장애 시험·측정·증빙

- [ ] 정상 요청, Agent 실패, API/Tool timeout, DB 연결 오류 등 핵심 시나리오를 실행한다.
- [ ] 각 시험의 Scenario ID, 입력, 주입 장애, 기대 결과, 실제 결과를 기록한다.
- [ ] 복구 시간과 수동 개입 여부, 판정, 증빙 링크를 남긴다.
- [ ] 자동 복구율을 명시된 분모·분자 기준으로 산출한다.
- [ ] 평균 복구시간을 성공 건 기준으로 산출하고 제외 건을 설명한다.
- [ ] 장애 유형별 성공·실패 수와 실패 원인을 공개한다.
- [ ] 실패 이력과 개선 전후 결과를 보존한다.
- [ ] 시험 수치와 Pipeline ID/커밋/시각은 실제 수행한 결과만 기입한다.

### H. 필수 산출물·발표 준비

- [ ] 아키텍처 설계서에 역할, 책임, Handoff, 상태, 정상·실패·종료 흐름을 넣는다.
- [ ] 배포·장애 복구 보고서에 실제 환경, 감지 지표, 대응 전략, 시험 증빙, 복구 지표를 넣는다.
- [ ] 파이프라인 결과 보고서에 단계별 성공 조건·실패 처리·실행 로그를 넣는다.
- [ ] 구현·설계·시험 결과가 서로 일치하는지 교차 점검한다.
- [ ] 정상 Workflow, Critic 분기, 대표 장애 복구, 실패 시 배포 차단, 지표를 시연할 수 있다.
- [ ] 실행 URL, 저장소, 로그/모니터링, Pipeline, 환경과 시험 계정 정보를 준비한다.
- [ ] 발표 자료와 시연은 실제 동작을 보여주고 미구현 부분은 계획 또는 한계로 표시한다.

## 3. 이 프로젝트에 맞춰 점검할 핵심 해석

현재 프로젝트는 게임 라이브 이벤트 기획·검수 AutoHealing을 주제로 한다. 따라서 가이드의 예시 로그 분석 Planner/Executor 구조를 그대로 채택할 필요는 없다. 현재 제품 흐름에 맞춰 아래 대응이 설득력 있게 설명되는지 점검한다.

| 가이드 개념 | 프로젝트에서 확인할 대응 |
|---|---|
| 사용자 문제와 최종 응답 | 운영 담당자의 이벤트 요청부터 검수된 승인 후보/안전 종료까지 |
| Agent 역할 | Event Planner, Balance & Rule, Critic, Supervisor 및 결정적 Rule Engine의 책임 경계 |
| 도구 실행 | MCP 기획 맥락·게임 규칙·아이템 조회와 외부 공개 표본 조회의 입력·출력·실패 경계 |
| 공유 상태/Handoff | Event Brief, 제한 Context, 계획·규칙 검증·Critic 결과, 시도 횟수와 게임 데이터 버전 |
| 결과 검증 | Agent Output 계약, MCP Tool 결과 검사, Python Rule Engine, Critic의 목적·품질 검토 |
| AutoHealing | 기획 오류 수정과 전체 재검증, 기술 장애 재시도, Primary/Fallback, Safe Stop 구분 |
| Memory·운영 기록 | Task와 Trace의 저장 방식, 재시작 후 보존, 실패 원인과 수동 개입 추적 |
| 서비스 배포 | Frontend·Backend·MCP·DB의 실제 배포 범위, 내부 통신·Secret·Health 확인 |
| 평가와 증빙 | 장애 시나리오 시험 결과, 실제 복구 시간, 수동 개입, 자동 복구율 및 반복 LLM 품질 평가 |

실제 게임 이벤트 등록은 현재 프로젝트의 기존 범위로 가정하지 않는다. 이를 목표로 추가하려면 게임 운영 API, 권한, 중복 방지, 취소/보상 정책, 감사 기록을 별도 요구사항으로 승인·설계해야 한다.

## 4. 팀장 점검 방식

각 체크 항목은 다음 중 하나로 판정한다.

- **구현 확인:** 코드 경로와 실행 증빙이 있다.
- **문서만 존재:** 계획·계약은 있으나 구현 또는 실행 증빙이 없다.
- **부분/환경 의존:** 설정·외부 서비스·시험 데이터가 있을 때만 동작한다.
- **미구현:** 코드와 실행 증빙이 없다.
- **범위 제외:** 프로젝트에서 하지 않기로 결정했고 그 근거가 기록되어 있다.

완료 판정에는 가급적 세 가지 증거를 연결한다: **요구사항/설계 → 코드·설정 → 재현 가능한 시험 결과**. 문서에 체크박스가 있거나 API/화면이 존재한다는 사실만으로 운영 동작 완료를 판정하지 않는다.

## 5. 다음 단계

1. 이 체크리스트의 각 항목을 현재 코드·설정·시험 기록과 대조한다.
2. 불일치 항목을 담당 팀과 결정 필요 항목으로 분류한다.
3. 제품 범위에서 제외할 개념은 제외 사유를 기록하고, 필수 산출물에는 그 범위를 정확히 설명한다.
4. 구현 작업은 우선순위, 담당자, 완료 조건, 증빙 계획을 정한 뒤 팀 지침에 맞는 작업 브랜치로 진행한다.
