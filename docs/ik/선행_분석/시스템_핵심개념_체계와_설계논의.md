# 시스템 핵심 개념 체계와 설계 논의

## 목적

멀티 에이전트 기반 게임 이벤트 기획·검수 시스템을 구현하고 운영하기 위해 필요한 개념을 하나의 구조로 정리한다. 이 문서는 제품 방향과 아키텍처 논의의 출발점이다.

오류 분류와 오류별 복구 정책은 검증·보안·Guard·권한과 함께 정해야 하므로 이 문서에서 구체적인 분류표나 대응 규칙을 확정하지 않는다. 해당 내용은 별도 정책 논의에서 정한다.

## 1. 시스템을 한 문장으로 정의

**운영자의 게임 이벤트 기획 요청을 여러 역할의 Agent와 게임 데이터·규칙으로 처리하고, 결과를 검증·복구해 승인 후보로 제시하며, 실행 근거·운영 상태·배포 이력을 추적할 수 있는 시스템.**

시스템은 네 층으로 나눠 생각한다.

1. **제품 작업:** 게임 이벤트 기획안 생성, 규칙 검수, 사람의 승인.
2. **협업·복구 실행:** Agent 역할, Workflow, Handoff, 검증, AutoHealing.
3. **운영 제어·관측:** 정책 설정, 권한, Trace·로그·지표, 피드백.
4. **개발·서비스 기반:** 데이터·외부 연동, 테스트, CI/CD, 배포, 저장·복구.

발표 연출은 이 네 층이 실제로 동작한다는 것을 보여주는 표현 계층으로 둔다. 시각 효과가 시스템 상태나 복구 결과를 대신해서는 안 된다.

| H. 유지보수와 확장 | API·Schema 버전, DB migration/backup, 정책 버전, 확장 어댑터, 용량·비용 | 변경 영향과 복구 방법을 알고 게임·Agent·환경을 추가할 수 있는가? |

|---|---|---|
| 1. 주제 작업 | A 제품 작업 | 게임 이벤트 기획·검수라는 실제 사용자 작업과 성공 결과를 먼저 정의한다. |
| 2. 작업 AutoHealing | D 복구 실행 | 복구는 결과를 억지로 성공시키는 것이 아니라 재검증 가능한 정상 상태로 회복하거나 안전 종료하는 동작이다. |

| 4. 멀티 에이전트 실행 | B 협업 | 여러 Agent가 존재하는 것뿐 아니라 역할에 따른 분업, 통제, 결과 결합이 확인되어야 한다. |
| 5. 입출력 Schema·Workflow 패턴 | B 협업 | Agent·Tool 간 계약, 상태 전이, 분기, 종료 조건을 문서와 코드로 연결한다. |
| 6. 오류 분류·대응 Schema와 정책 | D 복구 + C 신뢰 제어 | 지금은 설계 논의 대상으로 둔다. 오류 taxonomy, 심각도, 재시도 가능성, 복구 권한, 검증 요구를 통합해서 결정한다. |
| 7. GitHub Actions·AWS·Docker CI/CD | G 개발·서비스 기반 | 빌드·Lint·단위·통합·보안 확인, 이미지 생성, 승인/환경 분리, 배포 후 Health, 실패 배포 차단과 Rollback을 포함한다. |
| 8. Role, Task, Handoff, Trace, 보안, 권한, MCP, Schema, Evaluate, Feedback | B/C/E/F 협업·안전·데이터·개선 | 시스템 구성요소와 운영 루프를 함께 이루는 개념이다. 아래 4~6절에서 세부화한다. |
| 9. 게임 데이터 연결 | E 데이터 | 게임 데이터 원천, ID, 버전, 갱신 주기, 품질 검증, 출처 표시를 정한다. |

| 11. 가상 게임 시연 | I 발표·제품 데모 | 기획 결과를 이해하기 쉽게 체험시키되 데모 상태를 실제 계정/보상/서버 상태로 오인시키지 않는다. |
| 12. Workflow·복구 그래프 | F 관측 + I UX | 실제 Trace 이벤트를 바탕으로 정상 경로·분기·복구·Safe Stop을 그린다. 애니메이션은 사실 기록을 왜곡하지 않아야 한다. |

| 16. 발표 연출 | I 발표·UX | 문제, 정상 흐름, 오류 감지, 복구 결정, 재검증, 승인/안전 종료를 짧은 이야기로 보여준다. 실제 실행과 시각 효과를 구분한다. |
| 17. 시스템 유지 기반 | G/H 운영·유지보수 | 설정, Secret, DB migration·backup, Health, 로그·지표, 알림, 배포·Rollback, 문서·소유권·장애 대응을 포함한다. |

## 4. 더해 고려할 중요 개념

제안 목록에 이미 포함된 개념을 실행 가능한 시스템으로 만들려면 다음 기반도 함께 정의해야 한다.

### 제품 범위와 책임

- 사용자 역할과 권한 경계: 기획자, 검수자, 승인자, 운영자, 시스템 관리자.
- 최종 승인 지점과 실제 게임 반영 지점의 구분.
- 정상·오류·지연·중복 요청·취소·부분 실패 시 사용자 경험.
- MVP, 선택 확장, 명시적 제외 범위와 완료 조건(Definition of Done).

### 작업·데이터 무결성

- Task 식별자, 멱등성, 중복 제출, 상태 전이, 타임아웃, 취소와 재개 여부.
- Agent/Tool 호출 버전, 모델·프롬프트 설정 버전, 게임 데이터 버전, 정책 버전의 실행별 연결.
- 결과 출처·근거와 승인된 결과의 불변 기록.
- 데이터 신선도, 품질 검사, 버전 일치, 개인정보·보존·삭제 정책.

### 보안·정책 통제

- 역할 기반 권한(RBAC), 최소 권한, 시스템·Agent·Tool·사용자 권한 분리.
- 사용자 입력·외부 게임 데이터·Tool 응답·LLM 응답을 신뢰하지 않는 입력으로 처리.
- Secret 저장소·회전·전송 암호화·로그/Trace 마스킹.
- 정책 변경의 작성자, 검토/승인자, 유효 시점, 변경 이유, 이전 버전 복구.
- 실제 게임 API의 쓰기 권한은 읽기 권한과 분리하고 사람 승인 후에만 실행.

### 신뢰성과 운영

- DB/API/LLM/MCP별 Timeout, Rate Limit, Circuit Breaker 또는 대체 경로 적용 기준.
- Queue/Worker 필요성, 장시간 작업, 재시작 뒤 Task 복구, 중복 실행 방지.
- DB 백업·복구, Schema migration, 장애 복구 Runbook, 환경 간 설정 차이 관리.
- 지표 정의: 완료율, 실패율, 자동 복구율, 복구 시간, 수동 개입, LLM 비용·지연, Tool 오류율.
- 로그/Trace/Metric/Alert 간 상관관계와 저장 기간·검색·접근 통제.
- 용량·동시 사용자·처리시간·외부 API 한도·예산/비용 관리.

### 평가와 피드백 루프

- 고정 Evaluation Set, 기대 결과, 평가자와 합격 기준.
- LLM의 품질·결정성 변화, 회귀 테스트, 모델/프롬프트 변경 비교.
- 운영자 승인·수정·거절 사유의 구조화된 피드백 수집.
- 피드백을 데이터·정책·Prompt 개선에 반영하기 전 검토·승인·검증.
- Evaluation 결과가 배포를 허용/차단하는 CI 품질 게이트.

### 발표·데모 안전성

- 데모 전용 데이터·계정·API key와 실제 운영 자격 증명 분리.
- 발표 중 외부 서비스 장애, 느린 LLM, 네트워크 불안정에 대비한 재현 가능한 시연 시나리오.
- 사전 녹화 또는 정적 결과를 사용하는 경우 실제 라이브 실행과 구분해 표시.
- 시각화의 각 노드·전환·복구가 실제 Trace의 어떤 필드에서 왔는지 설명 가능.

## 6. 정책 관리 UI를 위한 안전 요구

사용자가 복구 정책을 쉽게 바꿀 수 있게 하려면 정책은 단순 환경변수나 프롬프트 문장이 아니라 버전 관리되는 설정 자산이어야 한다.

1. **정책 편집 범위:** 사용자가 조절해도 되는 항목과 개발자/보안 담당자만 바꿀 항목을 분리한다.
2. **Schema와 검증:** 잘못된 정책, 모순된 Retry 조건, 존재하지 않는 Tool/Agent 참조를 저장 전에 거부한다.
3. **미리보기/시뮬레이션:** 샘플 오류 시나리오에서 새 정책이 어떤 경로를 택할지 실행해 본다.
4. **권한·승인:** 정책 작성자와 적용 승인자를 분리할지, 적용 범위에 따라 승인 수준을 나눈다.
5. **버전·감사:** 누가, 언제, 왜 바꿨고 어떤 Task부터 적용됐는지 기록한다.
6. **배포·Rollback:** 정책을 즉시 적용할지 단계 적용할지 정하고, 오류 시 이전 버전으로 되돌린다.
7. **실행 재현성:** Task가 실행 당시 사용한 정책 버전을 보존한다.

오류 분류와 복구 정책의 구체 Schema, 항목, 권한표, 우선순위는 별도 논의에서 결정한다.

## 7. 게임 데이터·실제 API·캐시 경계

### 읽기 경로와 쓰기 경로

- **읽기:** 콘텐츠/레벨/아이템/밸런스/공개 표본 등 기획과 검증의 근거를 가져온다. 원천·수집 시각·게임 버전을 기록한다.
- **쓰기:** 승인된 이벤트를 실제 게임 운영 API에 등록·수정·취소한다. 읽기 Tool과 다른 권한, 사람 승인, 멱등성, 감사, Sandbox 시험이 필요하다.
- 실제 게임 API 연동은 향후 확장을 위한 adapter 경계만 먼저 고려할 수 있으며, 작동하지 않는 연동을 UI에서 완료 기능처럼 보여주지 않는다.

### Redis 적용 판단

Redis는 다음 조건을 확인한 뒤 선택한다.

- 같은 게임 데이터/외부 API를 반복 호출해 실제 병목 또는 비용이 있는가?
- 어느 데이터가 캐시 가능하고 TTL과 무효화 주체는 누구인가?
- 기획과 검증에서 서로 다른 게임 데이터 버전을 섞지 않게 하는가?
- Cache miss, stale data, Redis 장애에서 안전하게 원천 조회 또는 Safe Stop을 하는가?
- 민감 데이터나 승인 상태를 캐시해 일관성·권한 문제가 생기지 않는가?

캐시는 성능 최적화 수단이다. 게임 데이터 버전·출처·만료 규칙을 증명할 수 없으면 캐시가 결과 신뢰성을 낮출 수 있다.

## 8. CI/CD와 품질 게이트 개념

GitHub Actions, Docker, AWS를 사용할 때 파이프라인은 단순 배포 스크립트가 아니라 변경이 안전하다는 근거를 만드는 흐름이다.

1. Commit/Branch와 변경 경로 감지
2. 의존성·정적 분석·Schema/단위 테스트
3. 통합 Workflow·MCP·장애복구·보안 시험
4. Evaluation Set 및 데이터/정책 호환성 점검
5. Docker Image build, tag, 보안/구성 검증, registry push
6. 환경별 승인과 Secret 주입
7. AWS 배포·Health/Smoke 확인
8. 실패 시 배포 차단·이전 버전 Rollback
9. 배포 결과, 커밋, 이미지, 정책/Schema 버전과 로그 링크 기록

각 단계에서 누가 승인하고 어떤 결과가 배포를 막는지, 실패 통보와 담당자 조치 경로가 무엇인지도 정한다.

## 9. 작업 우선순위 제안

### 1단계: 범위와 계약 확정

- 게임 이벤트 기획·검수·승인의 경계와 실제 게임 쓰기 연동의 위치를 확정한다.
- Agent Role/Task/Handoff/Workflow/Schema의 공통 용어와 책임자를 맞춘다.
- 오류 정책 논의의 참여자와 결정 절차를 정한다.

### 2단계: 신뢰 가능한 핵심 흐름

- 게임 데이터 출처/버전, 규칙 검증, 승인 통제를 포함한 정상·오류 Workflow를 증거와 함께 완성한다.
- Task, Trace, Policy Version을 연결하고 사용자에게 결과·근거·실패 상태를 보여준다.
- 가드·권한·보안 정책 변경 경계를 확정한다.

### 3단계: 운영 가능성

- 시험 기록·Evaluation·복구 지표·운영 로그·알림을 연결한다.
- DB migration/backup, Health, 롤백, Runbook, 환경 분리 절차를 만든다.
- Frontend뿐 아니라 Backend/MCP/DB까지 목표 환경과 CI/CD 적용 범위를 확정한다.

### 4단계: 사용성·확장·시연

- Trace 근거에 연결되는 Workflow/AutoHealing 시각화를 다듬는다.
- 정책 편집 UI는 검증·권한·승인·버전·Rollback 설계가 합의된 뒤 구현한다.
- 병목 측정 후 Redis를 결정하고, 게임 API Sandbox를 거친 실제 쓰기 연동은 별도 승인된 단계로 추진한다.
- 짧은 발표 스토리로 정상·오류·복구·사람 승인 흐름을 재현한다.

## 10. 별도 정책 워크숍에서 다룰 오류·복구 의제

구체 오류 목록을 미리 확정하지 않고, 다음 설계 축에 따라 팀이 합의한다.

- 오류 원인/범주 및 감지 신호
- 사용자 영향도·심각도와 안전성 위험
- 재시도 가능 여부, 횟수/시간/비용 상한
- 재연결·fallback·대체 Agent/Tool/모델·캐시 선택 조건
- 재시도 전에 상태를 되돌리거나 중복 실행을 막는 방법
- 결과를 다시 검증할 주체와 승인/권한 필요 여부
- Safe Stop 상태, 보존할 결과·Trace, 사용자 안내
- 담당자 통지·에스컬레이션과 수동 복구 절차
- 정책 버전, 실행 Trace, 평가 데이터와 합격 기준
- 사용자 변경 가능 범위와 보안/관리자 승인 경계

이 워크숍의 산출물은 오류/복구 Schema, 대응 정책표, 권한/승인표, 평가 시나리오, 버전관리·Rollback 절차가 되어야 한다.
