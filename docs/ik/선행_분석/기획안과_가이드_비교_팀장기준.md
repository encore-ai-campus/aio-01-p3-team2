## 문서 목적과 기준 문서

체크포인트의 제품 기획, 구현 기획, 교과목 가이드를 한 기준으로 혼합하지 않고 각각의 역할에 맞게 비교한다. 이 문서는 팀장으로서 구현 방향을 정하기 위한 요구사항 추출 결과이며, 구현 완료 판정은 코드·설정·재현 가능한 시험 증빙을 따로 확인한다.

기준 코드 커밋은 `4ba7ef27a305656dd38bea99b94a7b3f8b927b3b`, 확인 기준일은 2026-10-09다. 과거 테스트 기록은 당시 기록으로만 취급한다.

### 권장 기준 우선순위

1. 제품 범위·사용자 목표는 전체 기획안을 기준으로 한다.
2. MVP 요구와 기능 동작은 개발 기획안을 기준으로 구체화한다.
3. Frontend와 Backend의 데이터 교환은 API 계약과 공통 Schema를 따른다.
4. 담당자별 개발 가이드는 구현 경계와 실행 절차를 정하는 데 사용한다.
5. 교과목 가이드는 위 결과물이 과제의 협업·AutoHealing·배포·검증 요구를 충족하는지 평가한다.
6. 문서 간 충돌은 팀장 결정사항으로 기록한다. 코드는 현재 동작 증거이지, 제품 요구사항이 자동으로 변경되었다는 뜻이 아니다.

## 1. 제품 기획안 요약

### 해결하려는 문제

가상의 게임사 Okepong Games의 모바일 RPG Opong Heroes를 대상으로, 운영팀이 반복적으로 만드는 라이브 이벤트의 초안을 AI가 생성하고, 대상 유저가 미션을 수행할 수 있는지·콘텐츠 조건이 맞는지·보상 아이템이 존재하는지 여러 역할이 검수한다. 오류가 발견되면 자동 수정·재검증하거나 안전하게 중단한다.

### 사용자와 결과

- 사용자: 게임 운영팀 직원, 이벤트 기획자·운영자.
- 입력: `event_name`, `target_user`, `duration`, `objective`.
- 정상 흐름: 요청 → Planner 초안 → Balance & Rule 검증 → Critic 검토 → PASS 결과 승인 대기 → 운영자의 승인·수정·거절.
- 최종 승인의 의미: 내부 이벤트 기획안 확정이다. 실제 게임 서버에 이벤트나 보상을 등록하는 의미가 아니다.
- MVP의 대상 기간: Mock 성장 데이터 범위에 맞춰 1~7일.

### 제품의 중심 가치

핵심은 단순한 LLM 문안 생성이 아니다. 역할이 분리된 Agent와 결정적 규칙 검증, Supervisor의 오류 유형별 복구, Human Approval을 한 Workflow에서 연결하고, Trace로 그 판단과 복구를 보여주는 것이다.

## 2. 개발 기획안에서 추출한 구현 개념

개발 기획안은 제품 기획을 아래 구현 요소로 구체화한다. 항목 전체가 같은 우선순위는 아니다. MVP 필수, 선택 확장, 미실행 계획을 구분해야 한다.

### 핵심 협업과 계약

- Supervisor Orchestrator와 Event Planner, Balance & Rule, Critic의 역할 분리
- Workflow State와 명확한 상태·오류 Enum
- Handoff Contract: task ID, 발신·수신 Agent, 목적, 입력, 제약, 기대 출력, 시도 횟수, 오류 맥락, 상태 참조
- Agent별 Output Contract와 Validation
- Handoff ACCEPTED일 때만 다음 Agent로 소유권 이전
- Agent Context 허용목록 및 시크릿·불필요한 사용자 식별정보 차단

### 안전한 입력·도구·결과 처리

- Input Schema 및 Input Guard
- Tool Guard 및 MCP 응답 검증
- Response Guard와 제한된 결과 반환
- 승인 주체·상태·`result_version` 검증
- 생성·승인 멱등성, 중복 요청 방지
- Trace에서 판단 주체, reason/error, 데이터 출처·버전, 재시도·복구를 추적

### 규칙 검증과 AutoHealing

- MCP에서 기획에 필요한 대상·기간별 게임 맥락을 Planner보다 먼저 조회
- 선택 ID를 검증 Tool로 재조회하고 Python Rule Engine으로 결정적 판정
- MVP 규칙: 콘텐츠 ID·필요 레벨·대상/일자 예상 레벨·이벤트 기간·Mission/Reward Day·아이템 존재·Brief 대상/기간 유지
- Critic은 목적·기획 품질·수정 오류 해결을 검토하고 PASS/RETRY/FAIL 반환
- 기획 오류 수정은 Planner 재실행 후 전체 재검증
- 기술 오류는 현재 실패한 작업부터 제한 재시도, Tool fallback, 성공 복구 또는 Safe Stop
- 검증되지 않은 일부 결과를 성공으로 확정하지 않는 Fail Fast/Partial Failure 정책
- Human Approval의 APPROVE/REQUEST_REVISION/REJECT와 결과 버전 추적
- Fault Injection은 시험 설정에서만 허용

### 서비스·저장·운영

- FastAPI Backend, Streamlit 운영 UI, MCP Server, PostgreSQL
- Task, Workflow 상태, Trace, 멱등성 데이터 영속 저장 계획
- Health Live/Ready, 환경변수·Secret 분리
- Frontend/Backend/MCP Dockerfile, Compose, 서비스별 CI/CD, AWS EC2 배포
- 장애 시험, 평가 세트, 자동 복구율·평균 복구시간, 파이프라인 실행 결과 기록
- 수동 개입 조건과 실패 안내

### 제품이 명시적으로 제한한 범위

- 게임의 보상 수량·경제 밸런스, 실제 유저 자격·로그 분석, 이벤트 재화·상점 가격 검증은 MVP 범위 밖이다.
- LLM 대체 모델, 캐시 fallback, 외부 알림, Prometheus/Grafana, 복수 인스턴스/Kubernetes는 선택 확장으로 기술되어 있다.
- Demo Login은 실제 사내 인증이 아니다.
- 동기 실행이 MVP 정책으로 제시되어 있으므로, 실시간 진행 표시·작업 재개는 별도 제품 결정이 필요하다.

## 3. 교과목 가이드와의 비교

| 가이드 요구·개념 | 제품·개발 기획안에서의 대응 | 현재 체크포인트 관점의 판단 |
|---|---|---|
| 문제·주요 사용자·정상/실패 시나리오 | Opong 라이브 이벤트 운영자, 생성·검수·승인, 기획/시스템 장애 시나리오 | 문서 대응이 강하다. 실제 사용자 가정과 데모 범위를 분리한다. |
| 에이전트 역할·책임·금지 범위 | Planner, Balance & Rule, Critic, Supervisor, Rule Engine 책임 정의 | 구조는 대응한다. 예시의 Executor·Memory Keeper가 동일 이름의 독립 Agent일 필요는 없다. 해당 책임이 다른 구성요소에서 어떻게 충족되는지 설명하면 된다. |
| Handoff·공유 상태·실패 맥락 | Workflow State, Handoff Schema, Context 제한, Task/Trace | 대응한다. DB 설정에 따른 영속성, 재시작 보존은 별도 실행 증거가 필요하다. |
| Critic 분기·반복 상한·안전 종료 | PASS/RETRY/FAIL, Retry/Revision 상한, Safe Stop | 제품 핵심과 일치한다. 실제 분기별 시험 증거가 필요하다. |
| 장애 감지·재연결·대체 경로 | Agent/Tool/MCP/DB 복구, Primary/Fallback, 수동 개입 경계 | 주요 AutoHealing 경로는 대응한다. 대체 모델·범용 cache, 외부 API circuit breaker 등은 확장으로 남는다. |
| 보안 장애·프롬프트 공격 | Input/Tool/Response Guard, Context allowlist, Secret 제외 원칙 | 설계 대응은 있다. 공격 시나리오의 감지·차단 시험 결과를 가이드 산출물에서 보여줘야 한다. |
| 서비스 배포·컨테이너·자동화 | 개발 기획안에 3 서비스 Docker/Compose/CI/CD/AWS EC2 포함 | 가이드 핵심 및 개발 기획 MVP와의 가장 큰 검증 격차다. 현재 Frontend 배포 기록만으로 전체 서비스 배포 완료라 할 수 없다. |
| 테스트 실패 시 배포 차단·롤백·알림 | 개발 기획안 파이프라인 요구와 가이드 산출물 | 실제 전체 Backend/MCP pipeline 동작과 실패 차단·알림 증빙이 필요하다. |
| 장애 주입과 결과 기록 | Fault Injection, 장애 시나리오·시험 기록 양식 | 기능/기록 일부는 있다. 공통 시험 결과, 복구시간, 수동 개입의 체계적 증빙을 확인해야 한다. |
| 자동 복구율·평균 복구시간 | 기획안과 가이드에 계산 기준 명시 | 개념 정의와 자동 집계 구현은 다르다. 실제 시험 결과를 산출하는 작업이 남아 있다. |
| 필수 산출물 3종 | 개발 기획안 33절이 아키텍처·복구·CI/CD 산출물과 연결 | 체크포인트는 개발 문서가 많지만 실제 배포·시험 결과를 채운 최종 보고서가 완성되었다는 뜻은 아니다. |
| 시연과 실행 정보 | 정상·복구·fallback·Safe Stop·승인 시나리오 계획 | 시연 계획과 시연 환경은 구분한다. 각 시연이 현재 실행 환경에서 재현되는지 확인해야 한다. |

## 4. 가이드 예시와 프로젝트 필수요건 구분

아래 예시는 가이드가 권장 설명 방법으로 제시했으며, 그 자체가 고정 기술 선택은 아니다.

| 가이드 예시 | 프로젝트에 적용하는 판단 |
|---|---|
| Planner / Executor / Memory Keeper라는 역할 명칭 | 명칭을 복제하기보다 Planner·Balance & Rule·Critic·Supervisor와 MCP/Repository가 그 책임을 어떻게 분담하는지 설명한다. |
| Kubernetes Deployment, Ingress, Secret | 실제 개발 기획안은 Docker·Compose·AWS EC2를 선택했다. 따라서 그 계획을 따르는지, 다른 기술로 바꾸는지 팀이 결정하고 실제 배포 증거를 제시한다. |
| 대체 모델·대체 API·캐시 fallback | 장애별로 유효한 대체 경로가 있는 경우만 구현한다. 없는 경로는 재시도 후 Safe Stop과 수동 조치로 명시한다. |
| 특정 횟수·시간·지표 수치 | 가이드 예시 숫자를 그대로 약속하지 않는다. 프로젝트 정책과 측정 결과를 구분한다. |
| 외부 알림 채널 | 선택할 수 있으나, 선택하지 않으면 Trace/운영 로그만으로 과제의 수동 개입 전달 요구를 충족하는지 명시적으로 점검한다. |

팀별 문서는 제품 목표를 새로 정하는 상위 기획서가 아니라 담당 영역의 설계·계약·실행 근거다.

| 담당 영역 | 참고 문서 | 팀장 점검 포인트 |
|---|---|---|
| Frontend | `docs/team/frontend/frontend_plan.md`, `implementation.md` | 사용자 흐름, 결과/승인 UX, Trace 표현, API와 UI의 일치. Trace 재생을 실시간 Workflow로 보이게 만들지 않는다. |
| Backend A | `docs/team/backend-1/백엔드 A 개발 가이드_업데이트.md`, `runbook.md`, 계약 결정·통합시험 문서 | API/Schema/Repository/승인/멱등성/Trace 경계와 실제 DB·MCP 실행 모드, 영속성 증거. |
| Backend B | `docs/team/backend-2/백엔드 B 개발 가이드_업데이트.md`, `handoff.md`, Trace 인수인계 | Agent·Supervisor·Routing·Retry·Rule Engine·MCP·Fault Injection 결과와 A 공통 계약 일치. 날짜가 다른 기록 간 현재값을 구분한다. |
| MCP | `docs/team/mcp/planning_context.md` | Tool 이름·응답 계약·데이터 버전·JSON/DB 출처·실패와 fallback 경계. |
| 통합 담당 | README, API 계약, 실행·배포·시험 문서 | 전체 시스템 모드, 종단 간 실행, 테스트 차단 배포, 실행 결과·산출물의 실제 증빙. |

상세 계획이 상위 기획안과 다르면 구현을 바로 바꾸기 전에 차이를 이슈/결정 기록으로 올린다. 특히 다음 차이는 결정이 필요하다.

- 개발 기획안은 Supervisor를 Python 규칙으로 서술한 부분이 있지만 현재 체크포인트에는 Supervisor LLM 기반의 정상 경로 검토가 들어간 기록이 있다. 어떤 행동이 정책적으로 결정적이고 어떤 판단이 LLM 보조인지 정리해야 한다.
- 과거 Backend B 가이드에는 MCP Tool 3개만 기재되거나 기획 전 조회가 계획으로 남은 절이 있지만, 최신 코드·후속 기록에는 `get_event_planning_context`가 반영되어 있다. 상태 설명은 최신 구현과 기록에 맞춰 갱신해야 한다.
- 제품 기획은 Opong Heroes를 중심으로 설명하지만 체크포인트에는 Clash 공개 표본을 이용하는 별도 흐름이 있다. 이것이 승인된 제품 확장인지, 별도 실험/데모인지 범위를 결정하고 문서에 표시해야 한다.
- 개발 기획안의 전체 서비스 배포 요구와 현재 Frontend 중심 배포 증거 사이에 차이가 있다. 완료로 보고하기 전에 Backend/MCP/DB까지 포함한 실제 배포 범위를 확인해야 한다.

## 6. 팀장 기준의 구현 현황 판단

상태는 문서 문구만으로 확정하지 않는다. 아래는 지금까지 체크포인트 코드와 날짜가 확인된 기록을 대조한 팀장용 초기 판정이며, 전체 재시험 결과는 아니다.

| 핵심 영역 | 초기 판정 | 팀장 확인 증거 |
|---|---|---|
| 제품 문제와 사용자 흐름 | 기획 완료, 구현 핵심 흐름 존재 | 전체 기획안, UI 사용자 테스트, 생성/승인 종단 간 실행 |
| Agent 협업·Handoff·계약 | 구현 기반 존재, 문서 정합성 확인 필요 | Workflow 코드, Schema, PASS/RETRY/FAIL 및 실패 케이스 Trace |
| 게임 데이터 조회·규칙 검증 | MCP/Rule Engine 구현, 데이터 소스별 검증 필요 | JSON 및 격리 DB 경로, 출처·버전, 레벨/기간/아이템 사례 |
| AutoHealing·Safe Stop | 여러 경로 구현, 지표 보고 미완료 | Fault Injection 결과표, 복구/최종 실패 및 수동 개입 기록 |
| 승인·수정·거절 안전성 | API/서비스 코드 구현 | 승인 권한, stale version, 멱등성, 수정 후 전체 재검증 시험 |
| 영속 상태·Trace | DB 및 in-memory 경로 모두 코드 존재 | 설정별 DB 실제 연결, 재시작 후 Task/Trace 보존 시험 |
| 사용자 인증 | Demo 수준 | 운영 제품에 필요 여부 결정, 실인증 제외라면 범위·노출 제한 명시 |
| 실시간 Workflow 진행 | 미구현, 완료 Trace 재생 | 동기 실행 설명이 UI와 일치하는지 확인; 실시간 필요 여부 결정 |
| 전체 배포·CI/CD | 부분 구현 상태 | Backend/MCP pipeline, 실패 차단, rollback, health, 알림 실증 |
| 가이드 필수 산출물 | 문서 기반은 있으나 결과 기록 완성 여부 확인 필요 | 설계서, 실제 장애 복구 보고서, 실제 pipeline 결과 보고서 각각 검토 |

## 7. 팀장이 순서대로 내릴 결정

1. **제품 경계 승인:** 내부 기획안 작성·승인까지를 제품 목표로 고정할지 확인한다. 실제 게임 배포를 하려면 별도 범위 변경으로 취급한다.
2. **현재 기능 범위 승인:** Opong MVP와 Clash 표본 경로의 관계를 결정한다.
3. **개발 계획 정합성 승인:** 동기 Workflow, Supervisor 판단 방식, 저장소 모드, 데이터 출처의 기준을 코드 및 계획과 맞춘다.
4. **과제 필수 산출물 책임 배정:** 설계서, 배포·복구 보고서, pipeline 결과 보고서 각각 작성자와 증빙 책임자를 정한다.
5. **현황 점검:** 각 개념을 `구현 확인 / 문서만 / 환경 의존 / 미구현 / 범위 제외`로 분류하고, 각 판정에 코드 경로·설정·시험 기록을 붙인다.
6. **갭 우선순위 결정:** 가이드와 개발 기획의 큰 격차인 전체 배포·파이프라인 및 복구 지표 증빙을 목표 일정에 맞춰 우선순위화한다.
7. **구현 티켓 확정:** 담당자, 브랜치, 변경 범위, 완료 조건, 시험 증거, 관련 문서 갱신을 지정한다.

## 8. 결론

팀이 구현 방향을 정할 때 제품의 상위 기준은 **“게임 이벤트 초안을 여러 Agent가 만들고 검수하며, 복구 가능한 오류는 고치고 검증할 수 없는 결과는 안전하게 멈춘 뒤, 사람이 승인하는 내부 운영 도구”**다. 교과목 가이드는 그 협업 구조를 배포·장애 시험으로 입증하고 세 가지 결과 보고서로 제출하도록 요구한다.

따라서 다음 구현 사이클은 기능 추가부터 시작하기보다, 상위 제품 범위와 계획 간 충돌을 결정하고, 가이드의 필수 항목마다 코드·실행·시험 증거를 붙여 현재 상태표를 완성하는 것이 우선이다. 그 점검 결과에서 미충족된 가이드 요구와 제품 MVP 요구를 분리해 담당자별 작업으로 전환한다.
