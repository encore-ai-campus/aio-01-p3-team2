# 체크포인트 구현 현황과 개발 방향

> **사후 상태 참고 (2026-10-13):** 아래 평가는 2026-10-09 기준 커밋과 당시 계획을 정리한 분석 이력이다. `feature/checkpoint`는 당시 기준을 식별하는 브랜치명이며 현재 작업·통합 기준이 아니다. 이후 `ikonly` CI/CD, AWS 역할별 배포 구성과 검증 자료가 추가됐고, 비어 있던 루트 문서도 현행 안내로 채웠다. 특히 Compose·CI/CD 표는 기록 시점의 평가다. 표의 당시 평가를 현재 완료 상태로 사용하지 말고 [현재 구현 상태](../현재_구현상태.md)와 최신 날짜별 검증 증거를 기준으로 판단한다.

## 문서 목적

이 문서는 체크포인트의 현재 코드를 제품 기획안과 프로젝트 진행 가이드의 기준에 대조해, 팀이 다음 구현 순서와 담당 범위를 정하는 기준으로 사용한다. 계획에 적힌 내용을 완료된 기능으로 간주하지 않고, 실행 모드와 데이터 출처에 따라 확인 범위를 구분한다.

## 요약

체크포인트에는 이벤트 초안 생성, MCP 게임 데이터 조회, 결정적 규칙 검증, Critic 검토, 수정·재검증, 장애 복구와 Safe Stop, 운영자 승인 대기까지의 핵심 흐름이 구현되어 있다. 제품 목적은 실제 게임에 이벤트를 배포하는 것이 아니라 운영자가 검토·승인할 수 있는 기획안을 만드는 것이다.

운영 제품으로 확장하기 전 해결할 주요 격차는 문서의 오래된 상태 기록, 환경별 영속 저장 설정, 실제 인증 부재, Workflow의 동기 실행과 Trace 재생 UI, 운영 지표 집계, 전체 서비스 배포 자동화다. Clash 공개 표본 Tool과 데모 게임은 각각 데이터 조회와 시연 경로이며 실제 게임 계정에 이벤트·보상을 발급하지 않는다.

## 1. 기획 목표와 현재 구현

상태 표기: ✅ 구현, 🟡 부분 구현·환경 의존, ❌ 미구현 또는 별도 확장 범위.

| 기획 목표 | 상태 | 체크포인트 구현 및 범위 |
|---|---|---|
| 운영자가 이벤트명·대상·기간·목적을 입력 | ✅ | 네 항목을 Event Brief로 받아 Workflow를 시작한다. MVP 기간은 1~7일로 제한한다. |
| 이벤트 초안 작성 | ✅ | Event Planner가 구조화된 계획을 생성한다. 설정에 따라 Mock LLM 또는 실제 LLM 전송을 선택한다. |
| 기획 전 게임 맥락 조회 | ✅ | `get_event_planning_context`를 Planner보다 먼저 호출하고, 검증된 레벨·콘텐츠·아이템 정보만 Context로 전달한다. |
| 선택 콘텐츠·아이템의 기획 후 검증 | ✅ | MCP Tool 결과를 검증한 뒤 Python Rule Engine으로 판정한다. 대상·기간 유지, 콘텐츠 접근 레벨, Mission/Reward 날짜 범위, 아이템 ID 등이 범위다. |
| 기획 품질 검토 | ✅ | Critic이 목적과 결과를 평가한다. 결정적 규칙 위반을 LLM 판정으로 통과시킬 수 없다. |
| 기획 오류 자동 수정 | ✅ | 수정 가능한 오류는 Planner 재호출 후 전체 규칙 검증과 Critic 검토를 다시 수행한다. 횟수 초과나 복구 실패는 Safe Stop한다. |
| 단계 전환·장애 복구 감독 | ✅ | Supervisor와 Workflow Engine이 routing, retry, fallback, revision, Safe Stop 경로를 다룬다. |
| 운영자 승인·수정 요청·거절 | ✅ | 승인 대기 결과에 대해 APPROVE, REQUEST_REVISION, REJECT를 처리한다. 허용 Demo actor, 결과 버전, 멱등성 정책을 확인한다. |
| Trace 및 복구 내역 확인 | 🟡 | Trace와 AutoHealing 정보를 Task에 저장하고 UI에서 표시한다. 실행 중 실시간 이벤트가 아니라 완료된 결과를 조회·재생한다. |
| Test Mode 장애 주입 | ✅ | 설정이 허용할 때 Agent, Tool, MCP, DB, Validation 오류 등을 시험 요청으로 주입한다. 운영 기능과 시험 기능은 설정으로 구분한다. |
| 영속 Task·Trace 저장 | 🟡 | PostgreSQL Repository와 인메모리 Repository가 모두 있다. `DATABASE_URL` 설정에 따라 저장 방식이 달라진다. 공용 PostgreSQL 적용 상태와는 별개다. |
| 게임 규칙 Primary/Fallback | ✅ | 게임 규칙 조회는 검증 오류·Tool 오류에서 fallback snapshot을 쓸 수 있다. MCP 연결·Timeout은 같은 서버의 데이터 fallback으로 해결하지 않고 재시도 후 종료한다. 아이템 Tool fallback은 없다. |
| 외부 게임 공개 표본 활용 | 🟡 | `get_clash_event_sample`이 Clash 공개 데이터를 조회하는 별도 경로다. API 키와 외부 접근 조건에 의존한다. 실제 Clash 계정의 이벤트 등록·보상 지급 기능은 없다. |
| 시연용 게임 화면 | 🟡 | 승인·검증된 결과를 데모 전투 화면에 표시한다. 전투·골드 등은 시각적 시연 상태이며 게임 서버에 저장되거나 보상으로 지급되지 않는다. |
| 실사용자 인증과 권한관리 | ❌ | Demo ID 허용 목록 확인은 실인증이 아니다. SSO/JWT/사내 사용자 디렉터리는 구현 범위 밖이다. |
| 비동기 작업·실시간 진행률 | ❌ | Workflow는 동기 API 요청으로 실행한다. Queue/Worker, 실행 중 상태 스트림, SSE/WebSocket은 없다. |
| 복구율·평균 복구시간 자동 집계 | ❌ | 기획 문서에 지표 정의는 있으나, 실제 시험 결과를 수집해 자동 집계하는 기능은 확인되지 않는다. |
| 전체 Backend·MCP·DB 배포 파이프라인 (2026-10-09 점검 당시) | 🟡 | 당시 Frontend AWS 배포 workflow만 확인했고, 전체 서비스 CI/CD와 Compose는 구현 확인이 필요하다고 기록했다. 현재 파이프라인의 상태·검증 결과는 [현재 구현 상태](../현재_구현상태.md)와 최신 검증 자료를 따른다. |
| 실제 게임 서비스에 이벤트 배포 | ❌ | 현 제품 범위 밖이다. 초안 검수·운영자 승인 대기까지가 목표다. |

### 데이터·LLM 실행 모드 구분

“실제 연결”은 한 가지 상태가 아니다. Mock LLM, 실제 LLM, MCP HTTP, JSON 게임 데이터, PostgreSQL 저장소, 공용 DB를 각각 구분해 보고해야 한다.

`docs/team/backend-2/handoff.md`에는 Mock LLM + 실제 MCP HTTP + 격리 PostgreSQL 경로와 실제 OpenAI + 실제 MCP HTTP + 격리 PostgreSQL 경로의 검증 기록이 있다. 또한 실제 LLM 선택 시험 기록도 있다. 이 결과는 공용 DB 적용 또는 LLM 품질의 반복 평가를 증명하지 않는다. 현재 사용자 테스트 환경의 설정은 별도 실행 설정과 대조해야 한다.

## 3. 중요한 UI 동작: Workflow 진행 기록

현재 Frontend의 Workflow 상자는 생성 요청이 끝난 뒤 Task와 전체 Trace를 받아 단계 배열을 만들고, 그 단계 수를 기준으로 순차 재생한다. 따라서 `현재/전체`는 Workflow가 실행 전에 모든 분기를 예측한 값이 아니라 완료 기록의 재생 위치다. 화면에도 완료 Trace 재생이며 실시간 진행이 아니라는 설명이 있다.

단기적으로는 화면 문구를 사용자가 쉽게 이해하도록 유지하고, 단계 수를 사전 확정된 계획처럼 오해하지 않는지 사용자 테스트에서 확인한다. 실제 진행 상태가 제품 요구사항이면 Backend의 비동기 실행·상태 조회·SSE/WebSocket 계약과 Frontend 표시를 함께 설계해야 한다.

## 4. 유지보수와 품질 개선

### 문서 기준 통일

- README의 “예정 구성”과 구현 완료 상태를 맞춘다.
- 과거 브랜치·통합 시점의 인수인계는 날짜와 역사 기록임을 표시하고, 현재 상태 요약은 문서당 한 곳만 기준으로 삼는다.
- “실제 LLM”, “실제 MCP”, “실제 PostgreSQL”, “공용 DB”를 독립된 검증 항목으로 표기한다.
- `docs/deployment.md`, `docs/fault_scenarios.md`, `docs/test_scenarios.md` 및 Compose 파일이 비어 있으므로, 실제 배포·시험이 이뤄지면 검증 사실로 채운다.

### 저장소와 데이터 관리

- 로컬 개발, 사용자 테스트, 공용/운영 환경의 `DATABASE_URL` 및 MCP 데이터 출처를 명확히 구분한다.
- 공용 DB를 사용하기로 결정하면 스키마 변경 이력, 초기 데이터 적용 주체, 백업·복구, 테스트 DB 격리 원칙을 문서화한다.
- 정상 Workflow 상태와 Trace가 어떤 저장소에서 재시작 후 유지되는지 반복 확인한다.

### 시험과 관측

- 정상·기획 수정·Primary fallback·Agent 재시도·MCP timeout·DB 오류·승인 멱등성 시나리오의 기대 상태와 실제 결과를 같은 양식에 기록한다.
- 시험 ID, 실행 모드, 데이터 출처/버전, 실패 유형, 복구 조치, 최종 상태, 소요 시간을 저장해 자동 복구율·평균 복구시간 산출의 근거를 만든다.
- Tool 로그 API와 Trace가 중복·불일치하지 않도록 운영에서 사용할 정본을 정한다.
- LLM 품질 평가는 성공 응답 하나와 구분하고, 고정 평가 세트를 반복 실행해 목적·대상·기간 유지와 규칙 오류 검출을 측정한다.

### 보안과 운영

- 외부 사용 전 Demo ID를 실제 인증·권한 정책으로 대체하거나, 내부 네트워크 제한과 승인자 검증을 명시적으로 설계한다.
- 장애 주입 기능이 테스트 환경에서만 활성화되는지 배포 설정으로 확인한다.
- API Key, 전체 Prompt, 개인정보가 Trace와 로그에 남지 않는지 시험한다.

## 5. 확장성 평가

현재 구조는 Agent, Workflow, API/Repository, MCP Tool, Rule Engine이 분리되어 있어 새 기능을 추가할 기본 경계가 있다. 다만 다음 확장은 여러 구성요소의 계약 변경을 동반한다.

| 확장 방향 | 필요한 변경 |
|---|---|
| 새 게임 데이터 추가 | 게임별 데이터 계약·MCP Tool·규칙·버전 정책·평가 데이터 추가. 현재 Opong 데이터 가정에 묶인 검증을 분리해야 한다. |
| 새 Agent 또는 단계 추가 | Workflow 상태 전이, Handoff, Context 허용 목록, 결과 Schema, Trace UI, 장애·계약 시험을 함께 변경한다. |
| 실제 게임 운영 API 연결 | 게임별 인증, 권한, 발급·취소 계약, 요청 멱등성, 동기화 및 감사 로그를 새로 설계한다. 공개 API 표본·데모 게임은 이를 대체하지 않는다. |
| 사용자·요청량 확대 | 동기 장시간 요청을 비동기 작업으로 전환하고 Queue/Worker, 작업 재개·취소, 영속 저장, 관측을 추가한다. |
| 여러 운영 조직·권한 지원 | 실제 인증, 역할별 접근 정책, Task 소유권과 감사 기록을 추가한다. |

## 6. 팀별 제안 작업과 완료 기준

| 담당 | 제안 작업 | 완료 기준 |
|---|---|---|
| 팀장·통합 담당 | 체크포인트를 기준으로 상태 요약과 문서 링크를 정리하고, 과거 진행 기록과 현재 검증 결과를 구분한다. 작업 단위와 통합 순서를 관리한다. | 팀원이 한 문서로 현재 구현, 실행 모드, 남은 의존성, 검증 방법을 파악한다. |
| Frontend | Workflow 상자의 Trace 재생 성격을 명확히 안내하고 사용자 테스트에서 이해 여부를 확인한다. 실시간 표시 필요성을 요구사항으로 결정한다. | 현재 화면 설명이 동작과 일치한다. 실시간 표시를 선택하면 Backend API 계약·비동기 실행 계획이 함께 확정된다. |
| Backend A | Task API·Repository·환경 설정에서 실제 저장소를 구분하고, PostgreSQL 스키마 변경·초기 적용·재시작 보존 절차를 정리한다. | 인메모리와 PostgreSQL 모드를 설정·문서·검증으로 구분한다. 공용 DB 적용은 담당자 합의와 격리된 검증 후에만 진행한다. |
| Backend B | Workflow 상태 전이와 복구 경로를 핵심 시나리오에 연결하고, LLM 품질 및 자동 복구 지표의 반복 측정 방식을 마련한다. | 각 시나리오의 기대 상태·Trace·실패 조건이 있고 반복 결과를 비교할 수 있다. |
| MCP | 기획 전/후 조회 계약, 데이터 출처·버전, JSON/PostgreSQL 동작을 유지한다. Clash 공개 표본의 외부 API 조건과 실패 범위를 기록한다. | Backend가 응답을 검증할 수 있고 데이터 출처·버전 불일치 시 혼합된 결과를 승인하지 않는다. |
| Frontend·Backend A/B·MCP 공동 | 공통 시험 기록 형식, Tool 로그와 Trace의 역할, 장애 결과 증빙을 정한다. | 정상·장애·승인 시나리오가 재현 가능하며 가이드의 장애 복구 보고서에 결과를 옮길 수 있다. |

담당자 이름은 현재 팀 문서에서 확인되지 않아 역할 기준으로 작성했다. 실제 담당 배정은 팀의 작업 브랜치 원칙에 따라 정한다.

## 7. 권장 구현 순서

1. **기준 정리:** README 및 팀별 문서의 구현 상태를 이 문서와 맞추고 과거 상태에 날짜를 표시한다.
2. **재현 가능한 환경:** 사용자 테스트 환경에서 Backend 실행 모드, MCP 데이터 출처, DB 저장 모드를 기록하고 재시작 후 상태 보존을 확인한다.
3. **사용자 이해도:** Workflow Trace 재생 표시와 승인·수정·Safe Stop 흐름을 사용자 테스트로 확인한다.
4. **운영 검증:** 장애 시나리오 결과를 공통 형식으로 누적하고 복구 지표의 실제 산출 근거를 만든다.
5. **운영 기반:** 공용 DB 사용 여부를 확정한 뒤 migration·백업·인증·전체 서비스 배포의 우선순위를 결정한다.
6. **확장 선택:** 위 기반이 정리된 뒤 새 게임, 실제 게임 API, 비동기 실행 중 제품 목표에 필요한 항목을 선택한다.

## 8. 방향 결정이 필요한 항목

다음 항목은 구현 전에 제품·팀 합의가 필요하다.

1. 제품을 내부 이벤트 기획·검수·승인 도구로 유지할지, 실제 게임 이벤트 등록까지 확장할지.
2. Workflow UI를 완료 Trace 재생으로 유지할지, 실행 중 실시간 진행률을 제공할지.
3. 사용자 테스트 이후 공용 PostgreSQL을 연결할지, 격리된 사용자 테스트 DB를 유지할지.
4. 실제 LLM을 기본 사용자 경로에 둘지, 비용과 품질 평가를 위해 선택 실행으로 유지할지.
5. 다음 구현 사이클에서 인증, 운영 지표, 전체 서비스 CI/CD, 새 게임 연동 중 무엇을 우선할지.
