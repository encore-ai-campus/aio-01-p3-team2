# 체크포인트 코드 확인 — 기획·가이드 대조

## 목적과 확인 범위

체크포인트 코드를 제품/개발 기획안 및 교과목 진행 가이드와 대조해, 기획에서 변경된 사항과 실제 구현 수준을 팀장 점검용으로 기록한다. 기능이 문서에 계획돼 있는지, 코드에 존재하는지, 실행 시험 증거가 있는지는 별도 판정한다.

- 코드 기준 커밋: `4ba7ef27a305656dd38bea99b94a7b3f8b927b3b`
- 기준일: 2026-10-09
- 이번 확인: 소스·설정·문서·기존 시험 기록의 정적 확인
- 이번에 하지 않은 일: 테스트 실행, 사용자 시나리오 재실행, 외부 API 호출, 공유 DB 변경

기준 문서:

- 제품 방향: [이벤트 기획안](../pre/이벤트_기획안.md)
- 구현 요구: [개발 기획안](../pre/개발_기획안.md)
- 과제 기준: [멀티 에이전트 협업 및 서비스 운영 가이드](../pre/멀티_에이전트_협업_및_서비스_운영_가이드.md)
- 화면 세부와 API 계약은 이 분석 작성 당시 참고했으나, 현재 `ik/` 문서 체계에 보존본이 없어 여기서 탐색하지 않는다.
## 판정 기준

- **구현 확인:** 코드에서 동작 경로를 확인했다. 실행 환경에서 시험 완료를 뜻하지 않는다.
- **기록된 시험:** 날짜가 있는 작업 문서에 시험 결과가 기록되어 있다. 이번 확인에서 다시 실행하지 않았다.
- **부분/환경 의존:** 선택 설정, 외부 자격 증명, 특정 데이터 소스가 필요하거나 기능 경계가 제한된다.
- **미구현 확인:** 관련 API/서비스/파이프라인 등의 구현을 확인하지 못했다.
- **기획만 있음:** 설계·양식은 존재하지만 코드나 실제 결과 증빙은 확인되지 않는다.

## 1. 코드에서 확인한 시스템 경로

체크포인트에 다음 구성요소가 존재한다.

- **Frontend:** Streamlit 로그인 화면, 이벤트 요청, 결과/승인, AutoHealing 요약, Trace 재생, Task 목록·삭제, 운영/디버그 화면.
- **Backend API/저장:** FastAPI 생성·조회·목록·삭제·Trace·승인 API, 입력/승인 Schema 및 Validation, Repository 인터페이스, 인메모리와 PostgreSQL 구현.
- **Workflow:** Event Planner, Balance & Rule, Critic, Supervisor, Workflow Engine, Handoff·Routing·Retry, Python Game Rule Engine.
- **안전 경계:** Input/Tool/Response Guard, `security_policies.yaml` 기반 Agent Context 허용 목록, 승인자·결과 버전·멱등성 검사.
- **MCP:** 기획 전 컨텍스트 조회, 규칙·fallback·아이템 조회, Clash 공개 표본 Tool. MCP는 PostgreSQL 설정 시 DB의 기본 자료를 읽고, 미설정 시 JSON 자료를 사용한다. 규칙 fallback은 별도 JSON Snapshot이다.
- **데모:** 승인 결과의 화면 시연을 위한 demo-game. 실제 게임 계정·인벤토리·미션 달성 저장은 하지 않는다.

기본 실행 설정은 `WORKFLOW_ENGINE=mock`이다. `backend_b_mcp`는 B Workflow와 Mock LLM, 실제 MCP 연결이고 `backend_b_live`는 실제 OpenAI와 MCP 연결을 요구한다. 영속 저장은 `DATABASE_URL` 설정 시 PostgreSQL을 선택하며 비어 있으면 인메모리를 사용한다. 따라서 “실제 연동”은 LLM/MCP/게임 데이터/Workflow DB가 각각 무엇을 쓰는지 함께 표기해야 한다.

대표 코드 위치:

- API·승인·Task 처리: `backend/app/api/event.py`, `backend/app/services/task_service.py`
- Workflow·실행 모드: `backend/app/orchestration/engine.py`, `backend/app/services/workflow_service.py`
- Agent·정책: `backend/app/agents/`, `backend/app/config/agents.yaml`, `backend/app/config/security_policies.yaml`
- Handoff·Validation·Guard·Rule Engine: `backend/app/orchestration/handoff.py`, `backend/app/validation/`, `backend/app/guards/`, `backend/app/rules/game_rule_engine.py`
- MCP·기획 데이터: `backend/app/services/mcp_client.py`, `backend/app/services/planning_context_loader.py`, `mcp_server/tools/`
- Clash 표본 Workflow: `backend/app/services/clash_event.py`, `mcp_server/tools/get_clash_event_sample.py`
- 저장소·Trace·Health: `backend/app/repositories/`, `backend/app/services/db_service.py`, `backend/app/services/trace_service.py`, `backend/app/api/health.py`
- 사용자 화면·Trace 재생: `frontend/pages/`, `frontend/components/workflow_status.py`, `frontend/components/trace_viewer.py`
- 데모 게임: `demo-game/`
- 배포 자동화: `.github/workflows/`, `infra/`

실제 MCP/OpenAI/격리 PostgreSQL 경로와 개별 시험 이력은 `docs/team/backend-2/handoff.md`, Backend A 실행·DB 절차는 `docs/team/backend-1/runbook.md`에 날짜별로 남아 있다. 이 기록은 과거 검증 근거이며 이번 문서 작성 중 재실행한 결과가 아니다.

## 2. 제품 기획 기능별 구현 대조

| 제품 기획 기능 | 코드에서 확인한 상태 | 가이드와의 관계·팀장 판단 |
|---|---|---|
| 운영자 이벤트 요청과 기본 정보 | 네 입력 항목을 받아 Task를 만드는 API/화면이 있다. 1~7일, 사용자 대상 등 Schema 검증이 있다. | 문제·사용자·정상 흐름 정의에 대응한다. Demo 로그인은 실제 인증이 아니며, 기획도 실인증을 제외한다. |
| 이벤트 초안 생성 | Event Planner 및 LLM 전송 계층이 있고 Mock/Live 경로를 선택한다. | Planner 역할의 구현이다. Mock 응답과 실제 LLM 응답은 평가·시연에서 구분해야 한다. |
| 기획 전 데이터 조회 | `PlanningContextLoader`가 MCP Tool을 부르고 데이터를 검증해 Planner에 제한 전달한다. | Handoff/공유 상태 및 도구 실행 개념에 대응한다. 초기 3개 Tool 계획보다 `get_event_planning_context`가 추가된 구현 변화다. |
| 규칙·아이템 검증 | Balance & Rule이 MCP 데이터를 얻고 Python Rule Engine이 대상 레벨·콘텐츠·기간·아이템 ID 등 결정적 판정을 한다. | Executor와 검증 책임을 결합한 도메인 구조다. 경제 밸런스, 보상 수량 적절성, 실제 유저 로그/자격 판정은 하지 않는다. |
| Critic 품질 판정 | Critic이 Planner 목표와 검증 결과를 보고 PASS/RETRY/FAIL 계약으로 응답한다. | 가이드의 독립 검토 역할을 충족한다. 기술 장애를 Critic의 품질 오류로 취급하지 않는 경계를 유지한다. |
| Supervisor 정상 경로와 복구 판단 | 코드상 Supervisor가 LLM 서비스에 정상 전환·복구 경로 심사를 요청한다. 허용 경로·상한은 결정적 routing 정책이 제한하고, 일부 기획 수정 경로는 정책으로 직접 처리한다. 판단 실패는 Safe Stop한다. | 개발 기획안의 “Supervisor는 별도 LLM 호출 없이 Python 규칙”과 현재 코드가 다르다. LLM이 심사하는 범위와 결정적 정책의 최종 권한을 팀이 갱신·승인해야 한다. |
| 기획 오류 AutoHealing | 오류에 따른 Planner 수정, 다시 조회·검증·Critic 진행, 수정 한도와 Safe Stop 코드 경로가 있다. | 가이드의 재시도/검증/안전 종료 개념에 대응한다. 실제 수정 성공률은 고정 Evaluation Set의 반복 결과로 입증해야 한다. |
| 기술 장애 AutoHealing | Agent·Tool·MCP·DB·Validation 등 fault type과 Retry/Fallback/Safe Stop 경로가 있다. 규칙 Primary Tool 오류는 snapshot fallback 경로를 가진다. | 장애 유형별 복구 개념에 대응한다. MCP 연결 자체가 끊겼을 때 같은 MCP의 fallback을 쓸 수 없는 한계, 외부 LLM 대체 모델·범용 cache 부재를 보고서에 밝혀야 한다. |
| 운영자 승인·수정·거절 | 승인 API가 actor 허용 목록, WAITING_APPROVAL/PENDING 상태, `result_version`, 멱등성을 확인한다. 수정은 재검증 흐름으로 이어진다. | 사람의 최종 통제·감사 개념에 대응한다. 승인자 목록은 Demo 설정이며 실사용 권한 시스템은 아니다. |
| Task·Trace 기록과 조회 | 생성·저장 Task, Trace 저장·조회, 최근 Task 목록·삭제 API가 있다. UI가 결과와 상세 기록을 제공한다. | 공유 메모리/운영 로그 개념에 대응한다. DB URL 없이는 메모리 저장이므로 재시작 보존을 보장하지 않는다. `test_runs` 저장 모델은 코드에서 확인되지 않았다. |
| Tool Log | API와 Repository 메서드/테이블은 존재하지만 코드 검색에서는 `append_tool_log`를 실제 호출하는 실행 경로가 확인되지 않았다. | 가이드의 도구 실행 기록은 주로 Trace로 확인할 수 있다. 별도 Tool Log API가 운영에 필요한지, Trace를 정본으로 할지 명확히 해야 한다. |
| Workflow 진행 UI | 생성 응답 후 전체 Trace를 받아 실행 기록을 재생한다. 화면에 완료 Trace이며 실시간이 아니라고 안내한다. | 개발 기획은 동기 Workflow를 MVP로 정하므로 현재 동작은 그 계획과 부합한다. 가이드의 실행 흐름 가시성은 충족하지만 실시간 진행률은 제공하지 않는다. |
| Clash 공개 표본 이벤트 | 별도 MCP API 조회·표본 검증·기획/수정·AutoHealing 경로, Trace, 결과 표시가 추가되어 있다. 대상은 all_user이며 승인 미션·보상은 데모 게임용이다. | Opong 중심 제품 기획보다 범위가 넓어진 별도 게임 소스다. 제품 확장인지 실험/시연 경로인지 공식 범위 결정을 남겨야 한다. 실제 Clash 계정 연동은 아니다. |
| demo-game | 승인·검증된 결과를 읽어 전투를 시각적으로 시연한다. 게임 상태와 실제 보상 지급은 저장하지 않는다. | 시연 보조 기능이며 실제 게임 통합 증거로 세면 안 된다. |

| FastAPI + Streamlit + MCP + PostgreSQL | 4개 구성요소의 코드가 있다. PostgreSQL은 선택 설정이고 기본은 in-memory다. | 구현 기반 있음, 배포 환경별 구성·영속성 증빙 필요 |

## 4. 교과목 가이드 필수 개념별 판정

| 가이드 핵심 개념 | 계획 반영 | 코드 확인 | 가이드 충족 판정과 필요한 증빙 |
|---|---|---|---|
| 문제·사용자·정상/실패 시나리오 | 상세히 정의 | 생성·검수·승인 및 오류 흐름 구현 | **설계 충족에 가까움.** 실제 UI의 사용자 흐름을 시연해 확인 |
| 역할 분리와 책임 경계 | Agent별 역할·제한 정의 | Planner/Balance&Rule/Critic/Supervisor 구현 | **구현 기반 있음.** Supervisor LLM 변경을 설계에 반영하고 책임 중복/공백 재검토 |
| Handoff와 공유 상태·메모리 | Task/상태/Context/Trace 계약 | state·handoff·Repository 경로 | **부분 충족.** 실제 DB 모드와 재시작 후 기록 보존 증거 필요 |
| 최소 협업·PASS/RETRY/FAIL | 정상 경로와 Contract 명시 | Engine과 validator 코드 존재 | **구현 기반 있음.** 각 경로의 최근 시험 증거 연결 필요 |
| 장애 유형·감지·복구·종료 | 오류별 policy와 test case 작성 | Fault injection, retry/fallback/safe stop 구현 | **부분 충족.** 장애별 입력·기대·실제·소요시간·수동개입 증거를 한 표로 제출해야 함 |
| 보안/Prompt Injection | blocked phrase, guard와 보안 정책 계획 | Input/Tool/Response Guard 및 allowlist | **부분 충족.** Prompt Injection 차단과 Secret 비노출을 시험으로 증명해야 함 |
| 서비스 배포·컨테이너·상태 확인 | Docker/Compose/AWS/Health 계획 | Dockerfile, Frontend AWS workflow, Health API | **미충족/부분.** Compose가 빈 파일이고 Backend/MCP 배포 pipeline이 없어 전체 배포를 증명하지 못함 |
| 테스트 실패 배포 차단·롤백·알림 | 파이프라인 계획과 rollback 절차 | Frontend workflow만 확인 | **미충족/부분.** Backend/MCP 테스트 차단, 서비스 롤백, 알림 실행을 보여줄 증빙 없음 |
| 장애 시험 결과·복구율·복구시간 | 시험 사례/수식/양식 계획 | Test/fault 코드 존재 | **결과 증빙 미완료.** 계산 가능한 실제 기록과 실패 개선 이력 필요 |
| 필수 산출물 3종 | 기획안에 각 산출물 연결 | 팀별 문서·부분 실행 기록 존재 | **완성 판정 불가.** 설계서 외에 실제 배포·복구 보고서와 Pipeline 결과 보고서를 채워야 함 |

## 5. 가이드 예시와 제품 요구 구분

- `Executor`와 `Memory Keeper`는 가이드 예시 역할명이다. 해당 이름의 별도 Agent를 추가하지 않아도 책임이 다른 구성요소에 명시적으로 배치되면 된다.
- Kubernetes, Ingress, 대체 모델, 대체 API, cache fallback은 가이드의 예시/선택 전략이다. 이 프로젝트 개발 기획은 Docker·Compose·AWS EC2를 MVP로 구체화했으므로 그 계획을 채택한다면 실제로 완성해야 한다.
- 알림은 가이드에 반복적으로 등장한다. 프로젝트 개발 기획은 외부 알림을 확장으로 두고 MVP에서 Trace/Backend log로 확인하도록 했다. 이는 명시적인 범위 차이이므로 팀장 승인 기록이 필요하다.
- 자동 복구 성공은 안전 종료와 다르다. 사람이 서버를 재시작해야 하는 MCP 전체 중단 사례는 자동 복구율과 분리해 서비스 복구/수동 개입으로 보고해야 한다.
- 실제 OpenAI·MCP·PostgreSQL 연결 성공 1회는 통합 경로가 연결 가능하다는 증거이지, 공유 DB 적용·장기 안정성·반복 LLM 품질의 증거가 아니다.

## 6. 계획에서 달라진 점과 팀장 결정사항

### 확인된 구현 변화

1. **기획 전 조회 Tool 추가:** 초기 게임 규칙/아이템 중심 Tool에 `get_event_planning_context`가 추가되어 Planner 이전에 대상별 맥락을 가져온다.
2. **Supervisor 판단 변경:** 개발 기획은 Python 규칙 중심으로 적혀 있으나, 현재 코드는 LLM이 정상 경로와 일부 복구 경로를 심사한다. 결정적 정책이 허용 경로와 상한을 제한하고 LLM 판단 실패 시 Safe Stop한다.
3. **Clash 공개 표본 경로 추가:** 원래 Opong Heroes 기획 외에 Clash 공개 표본으로 데모 이벤트를 생성하는 별도 Workflow가 추가됐다. 데이터는 승인 수정에도 동일한 Task snapshot을 재사용하며 실제 Clash 계정에 배포하지 않는다.
4. **Task 관리 UI/API 추가:** 최근 Task 목록·삭제 등 초기 Frontend 계획/계약보다 확장된 코드가 있다.
5. **배포 계획과 코드 간 차이:** Dockerfile들은 있으나 Compose 파일은 비어 있고, GitHub Actions는 현재 Frontend AWS 경로만 확인된다.

### 팀장 결정이 필요한 질문

- Clash 공개 표본 Workflow를 제품 공식 범위에 포함할지, 별도 데모/확장으로 격리할지?
- Supervisor의 LLM 심사를 유지할지? 유지한다면 Python 정책이 최종 권한을 갖는 경계와 LLM 실패 처리 원칙을 개발 기획안에 어떻게 반영할지?
- Backend/MCP 포함 전체 EC2/Compose/CI/CD까지 이번 과제 완료 범위로 둘지, 구현한 Frontend 배포 범위와 한계를 보고할지?
- 담당자 알림을 MVP 로그·Trace로 한정할지, 실제 이메일/Webhook 에스컬레이션을 추가할지?
- 가이드 산출에 필요한 실측 시험 결과를 어떤 사람이 어떤 양식으로 수집하고 복구율/MTTR을 누가 계산할지?
- 기획안의 `test_runs` 영속 테이블을 구현할지, 시험 산출물을 별도 파일/보고서로 보관할지?

## 7. 권장 작업 순서

1. **요구사항 기준 확정:** 제품 경계(Opong/Clash, 실제 게임 배포 여부), Supervisor 판단 경계, 알림 수준을 팀장 결정사항으로 남긴다.
2. **현재 상태표 확정:** 각 기능에 요구 문서, 코드 위치, 환경 조건, 시험 증빙을 연결하고 `계획/구현/시험완료`를 분리한다.
3. **가이드 산출물 채우기:** 정상·장애·수동복구 시나리오의 기대/실제 결과와 복구 시간을 수집하고 세 보고서의 담당자를 정한다.
4. **배포 기반 작업 결정:** 전체 Compose와 Backend/MCP CI/CD를 과제 범위로 할지 결정한 뒤, 포함한다면 실행 파일·차단 정책·롤백·Health 증빙을 구현한다.
5. **저장·운영 결정:** 사용자 테스트/운영의 DB 모드를 명시하고 migration·백업·상태 보존 및 test_runs 기록 방법을 확정한다.
6. **사용자 경험 확인:** Workflow 상자는 현재 완료 Trace 재생임을 사용자에게 이해시키고, 동기 실행의 대기 경험이 허용되는지 테스트한다. 실시간이 필요하면 별도 비동기 기능으로 계획한다.
7. **작업 브랜치·완료 조건 배정:** 팀원별로 한 작업 단위, 소유 파일, 통과 조건, 증빙, 관련 문서 갱신을 명시한다.

## 결론

체크포인트는 **이벤트 기획·검수·자동 수정·승인 대기와 장애 안전 종료라는 제품 핵심 흐름의 코드 기반을 갖췄다.** 기획 단계보다 더해진 기능(기획 전 MCP 조회, Clash 표본 Workflow, Task 관리)과 설계에서 바뀐 부분(Supervisor LLM 심사)이 있다. 반면 가이드와 개발 기획의 운영 측면인 전체 서비스 Compose/CI/CD, 배포 실패 차단·롤백·알림, 실측 복구 지표와 제출 보고서는 코드 구조만으로 완료라 할 수 없다.

팀장은 이 차이를 “기능이 있다/없다”만으로 판단하지 말고, **제품 범위 승인 → 구현 상태 → 시험 증거 → 산출물 반영** 순으로 점검한다.
