# 가상 게임 구현 계획서

## 문서 상태와 목적

- 상태: 구현 착수 전 계획
- 목적: 설계된 가상 게임을 기존 이벤트 기획·승인 시스템에 연결하고 로컬에서 시연 가능한 순서로 구현한다.
- 범위: 가상 게임 Runtime, DB 저장, 승인 이벤트 적용, UI, 통합 검증.
- 기준: [최상위 시스템 설계서](최상위_시스템_설계서.md), [가상 게임 도메인 상세 설계서](가상게임_도메인_상세설계서.md), [게임 세부 설계 라우터](게임설계/README.md).
- 구현 주체: 팀장(사용자) 단독 구현을 기준으로 작업을 쪼갠다.
- 실행 환경: 로컬 전용. 실제 상용 게임 계정·외부 게임 연동은 범위에서 제외한다.

## 1. 구현 기준선과 저장소 상태

계획 작성 시 확인한 저장소 상태는 `feature/checkpoint` 브랜치이며, 정확한 이름 `checkpoint` 브랜치는 아직 없다. 사용자가 지정한 브랜치 이름을 적용하며, 구현 시작 시 현재 체크아웃을 기준으로 `checkpoint`를 만든다. 현재 미추적 상태인 `docs/ik/` 문서들은 보존하고, 브랜치 생성이나 정리 과정에서 삭제·초기화하지 않는다.

현재 게임 데모(`demo-game`)는 승인된 Task를 `GET /api/tasks/{task_id}`에서 조회하고 화면에 표시한다. 전투·골드·Day 진행은 서버 권위 상태가 아니며, 게임 진행·미션 달성·보상 내역이 DB에 저장되지 않는다. 구현은 이 경계를 명시적으로 바꾼다.

## 2. 목표 사용자 흐름

1. 기존 기획 시스템에서 이벤트를 생성하고 규칙 검증·AI 검수·운영자 승인을 완료한다.
2. 사용자가 가상 게임에서 승인된 이벤트 Task를 선택해 적용한다.
3. Runtime이 승인 상태, 결과 버전, 게임 데이터 버전을 확인하고 특별 던전과 미션을 등록한다.
4. 고정된 가상 유저 한 명으로 스테이지·성장·특별 던전을 플레이한다.
5. 게임 행동은 서버에서 규칙 판정되고 DB에 기록된다. 유효한 행동 기록으로 미션 진행도가 갱신된다.
6. 미션 완료 보상은 가상 인벤토리에 반영되고 보상 기록과 함께 저장된다.
7. 화면 새로고침 후에도 적용 이벤트, 게임 진행, 미션, 인벤토리, 보상 내역이 복원된다.

발표용 핵심 장면은 승인 전 잠긴 특별 던전 → 승인 이벤트 적용 후 개방 → 보스전 행동 → 미션 완료 → 보상 인벤토리 반영이다. 각 장면은 실제 API 응답 및 DB 상태에 근거해야 한다.

## 3. 권장 구현 기술

| 영역 | 선택 | 이유 |
|---|---|---|
| 게임 장면 | Phaser 3 기반 2D Canvas/WebGL 게임 화면 + HTML/CSS HUD·운영 정보 UI | 장면, 스프라이트 애니메이션, 트윈, 입력 처리를 게임 화면에 집중하고 기획안/미션 정보는 접근성 있는 DOM UI로 유지 |
| 프론트엔드 실행 | 최소 Vite 개발/빌드 설정 + 바닐라 JavaScript(React 미사용) | Phaser를 로컬 의존성으로 고정하고 빌드 산출물을 로컬 서버에서 제공해 런타임 외부 CDN 의존을 피함 |
| Runtime/API | 기존 FastAPI 앱에 버전이 명시된 `/api/game/...` 라우트 추가 | 현재 승인 Task API 및 오류 응답 구조 재사용, Python 규칙 엔진과 직접 연결 |
| DB | 기존 PostgreSQL 및 SQLAlchemy 저장소 패턴 확장 | 게임 상태와 기존 이벤트 시스템을 같은 로컬 DB에서 운영 |
| 스키마/초기 데이터 | 버전이 붙은 JSON 카탈로그 + 번호가 지정된 SQL 변경 스크립트 | 규칙 데이터와 런타임 테이블의 변경 이력을 단순하게 관리 |
| 실행 | 로컬 Backend 및 게임 UI 프로세스 + PostgreSQL | 현재 `infra/compose.yml`은 빈 파일이다. 로컬 DB 실행용 Compose 구성을 새로 채우고 Backend·MCP·Vite/게임 UI는 로컬 프로세스로 실행 |

React 같은 SPA UI 프레임워크, Redis, 외부 게임 연동, 실시간 멀티플레이, 오프라인 보상은 MVP에 넣지 않는다. Phaser는 게임 장면/연출 전용으로 제한하고 규칙·전투 판정·저장은 계속 FastAPI Runtime과 PostgreSQL이 담당한다. 기존 `demo-game`의 이미지 자산은 재사용 가능 여부와 크기/라이선스를 확인한 뒤 Phaser 장면으로 옮긴다.

### Phaser 선택 이유와 범위

바닐라 JavaScript만으로도 Canvas를 직접 그리거나 DOM/CSS 애니메이션을 조합해 현재 수준의 간단한 전투 시연은 만들 수 있다. 다만 게임 루프, 장면 생명주기, 스프라이트/애니메이션, 타임라인, 입력, 충돌/카메라 연출을 직접 관리해야 해 화면이 커질수록 구현 부담과 시각 일관성 위험이 커진다. Phaser의 Scene 구조와 입력·Tween·애니메이션 기능은 이런 게임 장면 기능을 제공한다([공식 Scene 문서](https://docs.phaser.io/phaser/concepts/scenes), [Tween 문서](https://docs.phaser.io/phaser/concepts/tweens), [Animation 문서](https://docs.phaser.io/phaser/concepts/animations)).

따라서 권장안은 **게임 장면만 Phaser 3로 만들고, 이벤트 이름/기간/미션/보상/상태와 운영 정보는 HTML/CSS로 구성**하는 것이다. MVP에서 물리 시뮬레이션이나 게임 내 규칙을 Phaser에 구현하지 않는다. Phaser 버전과 Node/Vite 실행법은 구현 착수 시 잠그고 `package-lock.json`을 커밋한다. Edge에서 로컬 빌드 결과를 로드하고, 네트워크 연결을 끊어도 게임 라이브러리/CDN을 가져오지 않고 실행되어야 한다.

## 4. 단계별 구현 계획

| 단계 | 작업 | 산출물·완료 조건 | 선행 |
|---|---|---|---|
| 0. 기준선 고정 | 현재 체크아웃 기준 `checkpoint` 브랜치 생성, 미추적 `docs/ik/` 보존, 작업 트리 확인. 구현 기준 설계에서 미결인 고정 유저/초기 데이터/DB 초기화·리셋 방식을 계획의 가정으로 기록 | 브랜치가 현재 체크아웃 커밋에서 시작하고 기존 변경·문서가 보존됨 | 없음 |
| 1. 저장 기반과 카탈로그 | 물리 DB 모델·키·인덱스·트랜잭션을 확정하고, 버전 카탈로그·단일 가상 유저 fixture·Runtime 테이블과 SQL 마이그레이션/seed/reset 절차 구현 | 신규 로컬 DB에서 반복 실행 가능한 초기화. 카탈로그/규칙 버전 조회. reset이 지정한 데모 Runtime 데이터만 초기화 | 0 |
| 2. 이벤트 적용 수직 흐름 | 승인 Task 원본 조회 및 승인/검증/결과 digest 확인, 버전 검증, 이벤트 설정 스냅샷·Runtime 이벤트·영수증 저장 | 승인 완료 이벤트만 적용 가능. 미승인/거절/검증 실패/버전 불일치 거부. 동일 Task·결과 버전 재요청은 기존 영수증 반환 | 1 |
| 3. Runtime 규칙/API | 상태·카탈로그 조회, 스테이지/일반 던전/특별 던전 행동, 결정적 전투 판정, 성장·미션 집계 구현. 서버에서 행동을 재검증하고 요청 ID로 멱등 처리. 미션 완료 시 보상 자동 지급 | 정상·실패 도전·사전조건 거절·중복·동시 상태 충돌이 구분됨. 미션 완료·지급 원장·잔액·명령 결과가 한 transaction으로 확정 | 2 |
| 4. 게임 UI | Phaser 3 장면(로비/스테이지/일반 던전/특별 던전/전투 결과)과 HTML/CSS HUD·이벤트 패널 구현. API 상태를 장면에 바인딩 | 이벤트 미적용/적용, 전투 전/진행/성공/실패, 미션 진행/완료의 장면 차이가 보이고 실제 API 성공 뒤에만 성공·보상 연출 표시 | 1, 3의 API 계약 |
| 5. 통합 시연 흐름 | 고정 승인 Task를 준비하고 잠금→적용→플레이→미션 자동 완료·보상 지급 흐름을 연결. 운영 확인에 필요한 Task/이벤트/행동/보상 식별자를 추적 | 새로고침·재조회에도 상태 유지. 반복 실행 가능한 로컬 시나리오와 초기화 절차가 문서화됨 | 1–4 |
| 6. 수용 검증 및 정리 | 계약 단위, PostgreSQL 통합, 브라우저 흐름, 재시작 지속성, 멱등성, 실패·복구 경로를 검증하고 문서·실행 안내 갱신 | 아래 완료 기준 전부 충족, 알려진 제한과 실행법이 `docs/ik/`에 반영됨 | 5 |

저장 기반을 먼저 만들고, 그 위에 이벤트 적용과 행동 처리 수직 흐름을 쌓는다. 화면 디자인은 UI 단계에서 처음 시작하지 않는다. 기준선 단계에서 핵심 시연 장면의 와이어프레임과 시각 기준을 정하고 API 응답을 확정할 때 화면 상태도 함께 연결한다.

## 5. 구체성 점검과 작업별 결정

앞선 계획은 남은 세부 결정을 구현 시작의 선행조건처럼 취급했다. 이 항목들은 대체로 최초 완료 기준을 바꾸지 않는 작업 수준 선택이며, 별도의 전체 설계 완료를 기다릴 필요는 없다. 구현은 WP-00부터 시작할 수 있다. 각 선택은 영향을 받는 작업 패키지에서 확정하고 관련 설계 문서에 기록한다. 사용자 완료 기준과 직접 연결되는 불변 조건은 승인된 결과만 적용, Runtime 판정의 서버 권위, DB의 원자적·멱등 상태 변경, 재시작 후 저장 복원이다. 이 조건의 논리 의미는 이미 세부 설계에 있으며, 남은 일은 물리 구현 매핑이다.

| 결정 항목 | 기본 방향·결정 시점 | 완료 기준 영향 |
|---|---|---|
| 물리 DB 모델 | 테이블/키/index/transaction을 WP-02에서 논리 모델에 따라 구현하고 migration으로 고정 | PostgreSQL 저장·원자성을 만족하면 구체 테이블 모양은 사용자 완료 기준을 바꾸지 않음 |
| API와 단일 유저 접근 | `/api/game/*`·서버 측 고정 데모 유저를 기본으로 하고 local-only access를 WP-03에서 확정 | 한 유저로 흐름 완주가 MVP 기준. `user_id`를 클라이언트가 지정하지 않는 조건은 유지 |
| 승인 Task source | 기존 `get_task()`로 최신 Task를 읽고 `result_version`·승인·검증 상태를 확인, 적용 시 digest와 불변 snapshot을 저장 | 승인/검증 실패 차단과 재적용 멱등성은 완료 기준에 직접 영향. source adapter 상세는 WP-03에서 닫음 |
| fixture/규칙 수치 | 버전 JSON에 모으고 WP-01에서 시연 경로가 재현되게 선택·조정 | 수치는 테스트 fixture이며 제품 성공 기준은 아님. 가상 데이터와 버전을 표시 |
| DB·Runtime reset | WP-02에서 로컬 PostgreSQL, seed/reset 절차 확정. reset은 Runtime 자료만 지우고 Workflow Task/catalog/schema는 보존 | 로컬 반복 시연에 필요하지만 전체 구현 시작의 선행조건은 아님 |
| Phaser 리소스 | 현재 PNG를 우선 쓰고 Scene/Tween 연출로 시작, 부족한 프레임만 추가 제작 | 게임다운 화면은 완료 기준에 직접 영향. 특정 sprite sheet 확보는 구현 시작을 막지 않음 |

구현 전체를 막는 별도 착수 게이트는 없다. 각 작업 패키지는 상태 변경을 구현하기 전에 해당 도메인의 사전조건·실패 의미·원자성·중복 처리를 코드와 검증으로 닫고 다음 패키지로 진행한다. MVP는 단일 가상 유저로 제한하며 Runtime API의 actor/access 범위는 local-only임을 실행 구성에서 분명히 한다.

## 6. 구현 대상 파일과 책임

아래 경로를 구현 계획의 기준 경로로 고정한다. 기존 파일은 필요한 부분만 수정하고, 신규 파일은 책임을 섞지 않는다. `pre/`와 게임 기획 Workflow/MCP 코드는 게임 Runtime 구현을 위해 수정하지 않는다.

### Backend

| 파일 | 상태 | 책임 |
|---|---|---|
| `backend/app/api/game.py` | 신규 | `/api/game/*` 상태·카탈로그·이벤트 적용·행동·미션·인벤토리 API 라우트와 Pydantic 입출력 연결 |
| `backend/app/main.py` | 수정 | 새 game router를 `/api` prefix로 등록. 기존 이벤트·health 라우트 동작 유지 |
| `backend/app/game/__init__.py` | 신규 | 게임 도메인 패키지 표시 |
| `backend/app/game/schemas.py` | 신규 | API 입력/응답 및 카탈로그·이벤트 설정의 typed schema, 버전·참조 검증 |
| `backend/app/game/catalog.py` | 신규 | 고정된 게임 카탈로그 fixture 읽기, 버전 선택·참조 검증, 불변 catalog snapshot 제공 |
| `backend/app/game/rules.py` | 신규 | 레벨/해금/시도권/결정적 클리어 판정, 성장·성공 행동 생성, 미션 집계 계산. DB/API에 의존하지 않는 순수 도메인 함수 |
| `backend/app/game/service.py` | 신규 | 상태 조회, 승인 이벤트 적용, 게임 명령 처리, 미션/보상 지급의 유스케이스 및 트랜잭션 경계 |
| `backend/app/repositories/game_runtime.py` | 신규 | SQLAlchemy 연결에서 Runtime 이벤트/유저/attempt/action/progress/inventory/reward/idempotency 저장·조회 |
| `backend/app/game/`의 테스트 도메인별 파일 | 신규 | `backend/tests/test_game_rules.py`, `test_game_service.py`, `test_game_api.py`, `test_game_postgres.py`로 구분 |
| `backend/sql/002_game_runtime.sql` | 신규 | Runtime 영속 테이블·FK·unique/index를 생성하는 한 번만 적용 가능한 변경 SQL. 기존 `001_game_data_catalog.sql`은 수정하지 않음 |
| `backend/data/virtual_game_v1.json` | 신규 | 버전 고정된 콘텐츠·아이템·성장/세그먼트·특별 던전·이벤트 fixture. 기존 MCP 공유 카탈로그와 분리 |
| `backend/scripts/seed_game_runtime.py` | 신규 | 지정 catalog 버전과 단일 가상 유저를 idempotent하게 초기화 |
| `backend/scripts/reset_game_runtime.py` | 신규 | 로컬 데모 Runtime의 유저 진행/이벤트 데이터를 초기화. workflow task, 공용 game catalog, 스키마는 삭제하지 않음 |
| `backend/app/game/event_source.py` | 신규 | 기존 `get_task()` 조회를 호출해 승인 Task를 가져오고, workflow/approval/validation/result version 조건과 digest를 검사해 Runtime용 불변 source snapshot을 생성. 해당 service가 필요한 증거를 제공하지 못할 때만 `task_service.py`를 최소 수정 |
| `infra/compose.yml` | 현재 0 byte; 채움 | 로컬 PostgreSQL 한 서비스, named volume, readiness healthcheck, 비밀이 아닌 개발 기본값. Backend/MCP/UI를 자동 구동하는 전체 Compose는 MVP에서 구성하지 않음 |

`002` SQL은 현재 번호가 `001_game_data_catalog.sql`인 것을 전제로 한다. Runtime 테이블은 기존 workflow 테이블과 이름/소유권을 분리한다. ORM `create_all()`에 Runtime schema 생성 책임을 숨기지 않고, SQL 변경 스크립트를 로컬 init 과정에서 명시적으로 적용한다.

## 7. API 작업 묶음

구체적인 경로와 필드는 [게임 Runtime API 설계](게임설계/04_게임Runtime_API.md)를 기준으로 확정한다. 구현 작업은 다음 계약 단위로 나눈다.

1. 고정 가상 유저와 현재 Runtime 상태 조회
2. 승인 Task 적용 및 적용 영수증 조회
3. 게임 행동 제출과 확정된 행동 결과 조회
4. 이벤트별 미션 진행도 조회
5. 가상 인벤토리·미션 완료 시 자동 지급된 보상 이력 조회
6. 운영용 Runtime 기록 조회와 로컬 fixture 초기화

모든 상태 변경은 서버 판정이 권위자다. 성공이 불확실한 클라이언트 요청은 같은 요청 식별자로 재시도하고, DB 확정 전 성공 연출이나 보상 수령 표시를 하지 않는다.

## 8. 데이터·규칙 구현 원칙

- 정적 게임 카탈로그와 유저별 런타임 상태를 분리한다.
- 승인 이벤트에는 `task_id`, `result_version`, 게임 규칙/카탈로그 버전을 고정한다.
- 런타임은 적용 시 고정된 버전으로 판정하며, 활성 이벤트 진행 중 카탈로그를 조용히 교체하지 않는다.
- 행동은 시도와 확정 결과를 구분하고, 미션은 화면 클릭 수가 아니라 확정된 결과 사실을 집계한다.
- 미션 완료에 따른 자동 보상 지급·인벤토리 반영의 중복 방지 키와 트랜잭션 경계를 구현한다.
- 로컬 데모 fixture와 초기화는 개발 전용으로 제한하고, 실제 운영 계정·실제 경제와 혼동되지 않게 UI에 가상 데이터임을 표시한다.
- 세부 전투 수치와 보상 영향 계산은 [게임 규칙](게임설계/01_게임규칙_플레이루프.md), [데이터 스키마](게임설계/02_게임데이터_스키마.md), [검증·밸런스](게임설계/07_게임검증_밸런스.md)에 추적한다.

## 9. 검증 계획과 완료 기준

구현 중 각 단계에서 관련 테스트를 작성·실행하고, 마지막에 로컬 PostgreSQL과 실제 브라우저를 사용한 종단 간 흐름을 확인한다.

### 최초 완료 기준 추적표

아래 항목은 사용자가 처음 정한 완료 기준을 구현 수용 기준으로 옮긴 것이다. 전부 충족해야 게임 구현 완료로 판정한다.

| 최초 완료 기준 | 완료로 인정하는 관찰 결과 | 확인 방법 |
|---|---|---|
| 가상 게임이 문제없이 동작 | 로컬 Edge에서 로비→스테이지/성장→특별 던전→전투 결과가 이어지고, 각 화면 새로고침·백엔드 재시작 뒤 Runtime 상태와 모순되지 않음. 승인 전 특별 던전은 잠기고 승인 이벤트 적용 뒤에만 열림 | 정해진 fixture로 전 흐름 3회 연속 완료, 개발자 콘솔에 미처리 예외 없음 |
| 이벤트 기획안을 받을 수 있는 연결 | 기존 기획안의 승인 Task를 게임에서 가져오고, 이벤트 이름·기간·대상·미션·보상·결과 버전을 읽어 Runtime 이벤트에 적용. 미승인/검증 실패/버전 충돌은 적용 불가 | 승인/미승인/검증 실패 각각 적용 요청, DB와 UI 상태 대조 |
| 백엔드 API와 DB의 게임 데이터 연결 | 유저 행동은 API에서 판정되고 카탈로그 버전/행동/미션/보상 기록이 PostgreSQL에 저장됨. 재조회 후 같은 결과 복원 | API 응답과 DB 레코드 ID·버전 대조, 백엔드 재시작 후 조회 |
| 게임 규칙·스키마 관리 | 이벤트·게임 데이터·규칙 버전을 분리해 표기하고, 버전 참조/ID/범위/허용 action 조합을 검증. 지원하지 않는 버전과 잘못된 참조는 오류 코드와 경로를 남기고 차단 | 대표 valid/invalid fixture, 버전 불일치·없는 ID 검증 |
| 설계·구현 기준이 화면에 명확히 표현 | 화면에서 이벤트 적용 상태와 출처 Task/result version, 현재 유저 레벨·입장 조건, 현재 미션/목표/진행값, 보상 및 지급 여부, 게임 data/rules 버전을 확인할 수 있음. 성공 연출은 서버 확정 뒤만 보임 | 화면 점검표로 각 상태의 표시 여부와 API/DB 값 비교 |
| 사람이 봤을 때 게임처럼 보임 | 16:9 게임 장면에 배경·캐릭터/몬스터 스프라이트·게임 HUD가 있고, 이동/공격/피격/보스 처치/던전 개방에 각각 시각 피드백이 있음. 이벤트 정보 패널은 게임 장면과 구별되면서도 동일 화면 맥락을 유지 | Edge 1280×800과 1600×900에서 잘림 없이 확인, 5개 장면 연출 체크, 처음 보는 관찰자에게 목표/다음 행동을 설명할 수 있는지 사용자 시연 |

가상 게임 기능 완료는 기존 이벤트 기획 시스템의 동작을 대체하거나 재구현한다는 뜻이 아니다. 기존 생성·검증·승인 결과를 소비하는 접점이 동작해야 하며, 멀티 에이전트 Workflow·MCP·오류 복구 정책·CI/CD의 기존 구현은 게임 MVP의 범위 변경 없이는 수정하지 않는다.

- **게임 동작:** 스테이지·성장·특별 던전의 행동이 서버 규칙으로 판정되고, 성공·실패·진행 제한이 일관된다.
- **기획안 연결:** 승인되고 검증을 통과한 이벤트만 적용되며, 미션·보상·기간·결과 버전이 화면과 Runtime에 반영된다.
- **백엔드·DB:** 상태 변경은 PostgreSQL에 저장되고 서버 재시작/브라우저 새로고침 후 복원된다. 완료된 보상과 인벤토리는 원자적으로 일치한다.
- **스키마·규칙 관리:** 카탈로그/규칙 버전이 적용 이벤트와 연결되고, 잘못되거나 호환되지 않는 버전은 명시적으로 거부된다.
- **화면 표현:** Phaser 장면 연출과 HUD가 게임 공간·행동을 보여 주며, 잠금/개방/진행/완료가 실제 상태와 일치한다.
- **안전한 재시도:** 같은 적용·행동·보상 요청을 반복해도 이벤트, 진행도, 재화가 중복 생성되지 않는다.
- **로컬 재현성:** 저장소에서 안내된 순서로 서비스를 시작하고 fixture를 이용해 동일 시나리오를 반복할 수 있다.

검증 묶음은 규칙 단위 테스트, API/저장소 테스트, PostgreSQL 통합 테스트, 브라우저 종단 간 수동 시연으로 구성한다. 구현 작업 때 기존 테스트 체계를 확인해 추가 위치와 실행 명령을 정하며, 계획 수립 단계에서는 테스트를 실행하지 않는다.

최소 필수 시나리오 매트릭스는 다음과 같다.

| 사례 | 입력/상황 | 기대하는 관찰 결과 |
|---|---|---|
| 적용 거절 | 승인 전, 검증 실패, 결과 버전 불일치 | 이벤트·venue·참여 상태가 생성되지 않고 구분 가능한 거절 코드가 반환됨 |
| 적용 멱등성 | 같은 `task_id/result_version/digest` 2회 | 같은 `runtime_event_id`/영수증, 이벤트 레코드는 1개 |
| 충돌 | 같은 source version에 다른 digest | 충돌 응답, 최초 적용 설정은 변경되지 않음 |
| 입장 거절 | 이벤트 비활성/유저 자격 없음/잠금 층 | 시도권·Attempt·Action·미션·보상 상태가 바뀌지 않음 |
| 게임상 도전 실패 | 입장 가능하지만 `level < clear_level` | 실패 Attempt와 규칙상 시도권 차감만 확정, 성장/미션/보상은 불변 |
| 게임 행동 성공 | `level >= clear_level`인 스테이지 또는 특별 던전 | 성공 Attempt/Action, 상태 변화, 해당하는 미션 진척이 연결됨 |
| 중복 행동 | 완료된 동일 `request_id` 재전송 | 최초 결과 반환, 차감·성장·미션·보상 추가 반영 없음 |
| 미션 보상 지급 | 미션 완료를 발생시킨 동일 게임 명령 재전송 또는 같은 ActionRecord 재집계 | RewardRecord 1건, 잔액 증가 1회, 둘의 합계 일치 |
| 저장 복원 | 서버 재시작 후 같은 유저/이벤트 조회 | 적용 버전, 진행도, 인벤토리, 보상 원장이 DB 값과 일치 |
| 종료 경계 | 이벤트 `end_at` 이후 새 행동 요청 | 새 행동 거절, 이전 영수증·진행·보상 조회는 가능 |

종단 시연은 최소한 `고정 fixture 준비 → 승인 이벤트 적용 → 특별 던전 개방 → 레벨 조건을 충족하는 행동 → 미션 완료 → 보상 인벤토리 확인 → 앱/브라우저 재시작 후 재조회`를 한 번의 기록된 절차로 수행한다. 실패 사례도 별도 시나리오로 재현해 잘못된 성공 애니메이션/보상 표시가 없음을 확인한다.

## 10. 작업 패키지별 결정과 기본값

다음 결정은 구현 전체의 선결 조건이 아니다. 각 항목은 표시한 패키지에서 기본 방향을 확정하고 관련 설계를 갱신한다. 수치와 실행값은 코드 여러 곳에 두지 않고 fixture/config 한 곳에서 관리한다.

1. WP-01: 단일 데모 유저의 시작 레벨/경험치, 성장 임계값, 콘텐츠 `entry_level`/`clear_level`, 시도 한도 및 특별 던전 층 fixture.
2. WP-02: PostgreSQL 테이블·키·인덱스, migration/seed/reset 명령 및 reset 삭제 범위.
3. WP-03: 최신 승인 Task의 version·validation evidence를 읽는 source adapter, digest 저장 방식, local-only actor/access 오류 응답.
4. WP-04: 미션 완료 시 자동 보상 지급과 inventory/RewardRecord의 transaction 및 동시 요청 처리.
5. WP-06: 현재 에셋의 장면/애니메이션 연결표. 먼저 현재 PNG와 Tween으로 구현하고, 실제 시각 완료 기준을 충족하지 못하는 경우만 에셋을 추가한다.

기존 세부 설계서의 논리 계약은 그대로 따른다. 구현 중 계약 변경이 필요한 경우에만 해당 설계서와 이 계획을 함께 갱신한다. 이 목록의 미결 수치·구현 상세만으로 WP-00 또는 다른 독립 작업을 보류하지 않는다.

## 11. 브랜치와 변경 관리

- 구현 시작 시 현재 체크아웃을 기준으로 정확히 `checkpoint` 브랜치를 만든다. 현재 이름은 `feature/checkpoint`이며, 계획 작성 시점에는 `checkpoint`가 없다.
- 현재 작업 트리에는 `docs/ik/` 미추적 문서가 있으므로 브랜치 생성 전후에 보존 여부를 확인하고, 사용자 요청 없이 초기화·삭제·덮어쓰지 않는다.
- 관련 작업 단위로 커밋하고 매 단계 전후 상태와 diff를 검토한다. main은 팀장인 사용자가 통합할 때만 변경한다.
- 구현 중 바뀐 API·DB·실행법은 `docs/ik/`의 관련 설계/구현 문서에도 반영한다. `pre/` 사본은 보존한다.
