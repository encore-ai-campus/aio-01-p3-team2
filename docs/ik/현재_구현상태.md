### 2026-10-10 로컬 구현 및 확인

- 이번 구현 진행에서 canonical Brief 경로에 read-only Planner/Critic Agent 계약, 결정적 Supervisor 전이 검사, 명시적 Handoff, Critic REVIEW의 runtime 차단을 추가했다. 기본 모드는 deterministic adapter이며 `CANONICAL_PLANNING_MODE=live`에서만 OpenAI를 선택한다. Brief와 게임의 권위값은 Agent 출력으로 바뀌지 않는다.
- LLM live 실행은 provider가 반환한 input/output token usage를 누적하고 환경에서 공급한 가격표 버전·USD 단가·workflow token/cost 한도를 적용한다. 누락 설정이나 계측값은 예산 초과로 안전 종료하고 추정치로 통과시키지 않는다. OpenAI 요청에는 output token 상한을 전달한다. 비용 상한은 응답을 받은 뒤 측정되므로 이미 발생한 단일 provider 호출 비용까지 소급 취소할 수는 없다. `llm_usage`는 canonical 성공/안전 종료 Workflow record와 Backend B Trace에 저장된다.
- Canonical Planner/Critic의 `llm_timeout`은 pinned recovery policy와 Supervisor Router를 거쳐 총 4회 이내 재시도하고 exponential jitter 대기한다. Backend B의 허용된 transient retry도 공통 250ms 시작·4초 상한 exponential jitter helper를 사용한다. `llm_execution_error`, budget 초과는 안전 종료 경로다. 실패 실행은 plan 없는 `SAFE_STOP` Workflow record/Trace와 가용한 계측값을 저장하고 운영 기록에서 읽을 수 있도록 구현했다. Backend B도 성공 사용량과 예산·LLM 실패 계측값을 Task Trace에 저장하고 실패 결과를 반환하도록 연결했다. 해당 통합 테스트 실행, live provider 사용량을 포함한 실제 예산 초과 경로와 policy pin 확인은 남아 있어 WP-03/05 완료로 판정하지 않는다.
- 테스트 환경 전환 중 Windows Python 3.12의 SQLAlchemy 바이너리 로딩이 collection을 차단했고, Python 3.11 컨테이너 첫 실행에서 16개 회귀가 드러났다. 원인은 canonical Critic 반환 괄호, live mode test의 환경변수 누수, deadline 사용량 snapshot 누락, telemetry trace 기대값, fake provider 응답 계측값이었다. 테스트 격리와 코드/fixture를 수정했다. SQLAlchemy의 순수 Python fallback도 테스트해 컴파일 바이너리가 필수는 아님을 확인했다.
- `backend/tests/integration/test_llm_record_storage.py`는 PostgreSQL에서 raw prompt/response 암호문 저장, 승인된 운영자 복호화, 요청 헤더 actor spoofing 무시, 만료 삭제와 access audit, 미승인 actor 거부를 확인한다.

- 구현 범위는 CI/CD 직전까지다. `frontend-web/`은 Vite/vanilla JS 운영 콘솔이며, Google Fonts 외부 요청을 제거해 로컬 실행을 단순화했다. `EVENTQUEST_API_TARGET`으로 개발 proxy backend 주소를 지정할 수 있다.

PostgreSQL integration test가 정상 replay와 altered payload conflict를 확인했고, 전체 suite는 다시 **202 passed/11 skipped**다.
- 격리 DB의 정책 API lifecycle(GET/draft/validate/preview/activate/rollback) 통과. Edge에서 기획안 제출→승인→Runtime 등록을 확인하고, MCP timeout 1회 복구·mission unreachable revision·retry limit safe stop을 각 3회 실행해 결과와 오류 코드 sequence가 일치하는 것을 확인했다. fault trace는 활성 복구 정책 버전을 표시했고 Runtime 이벤트 등록 API는 fault 경로에서 호출되지 않았다.
- `infra/e2e-local.ps1`을 추가해 전용 테스트 PostgreSQL만 사용하도록 검사한 뒤 임시 API 컨테이너와 Vite/Playwright Chromium 브라우저를 연결한다. 브라우저 정상 흐름에서 Brief→승인→Runtime 등록 후 3회 스테이지 행동을 실행해 미션 완료, GOLD 보상 기록과 잔액 반영을 확인하고 새로고침·API 재시작 뒤 같은 미션·보상 기록이 복원되는지 검증한다. 미지원 보상 승인 차단 및 prompt injection 422 차단도 통과했다. 세 fault 시나리오를 각 3회 반복해 결과/Trace sequence 일치와 Runtime 상태 불변을 확인했다. 이 스크립트는 Playwright Chromium 설치가 필요하며 포트 8004/5177을 사용한다. 8004 공개는 loopback에 한정되고, Docker bridge 주소 제한 때문에 격리 테스트 API에서만 `GAME_RUNTIME_ALLOW_REMOTE=true`를 사용한다.
- 전체 T5 반복 검증은 `pwsh -NoProfile -File infra/verify-local.ps1`로 실행한다. 이 명령은 Backend PostgreSQL suite, Schema/compile/Ruff, frontend production build, Playwright E2E 및 API 재시작 복원을 한 번에 실행한다. 2026-10-10 동일한 고정 환경에서 3회 연속 통과했고, 첫 회는 `-RestartPostgres`로 전용 테스트 DB 재기동도 포함했다. 매회 Backend 202 passed/11 외부 smoke skipped, 브라우저 핵심 E2E 4 passed/1 restart 전용 skip, API restart 후 복원 1 passed를 확인했다. 별도 `infra/e2e-local.ps1`에서도 MCP timeout 1회 복구·mission revision·retry limit safe-stop 세 시나리오를 각각 3회 반복해 동일 결과를 확인했다.
- 위 Chromium E2E는 실제 UI→API→Workflow→PostgreSQL 경로 일부를 자동 확인한 증거다. 운영 UI의 모든 화면에 대해 Edge viewport별 UX-01~07 체크리스트 검토나 최신 canonical Agent/원문 접근 API Edge 수용을 대신하지 않는다. E2E-01~18/G1~G9 전체 evidence matrix도 아직 완성되지 않았다. 외부 LLM provider와 실제 MCP HTTP server smoke는 credential/endpoint 부재로 skip됐다. 최종 Edge UX 수용 및 전체 요구조건 증거가 남아 WP-08을 완료로 판정하지 않으며, CI/CD도 시작하지 않았다.

## 구현 요약

기존 기획 Workflow와 분리된 PostgreSQL 게임 Runtime을 추가했다. 이벤트 생성·검수·운영 승인·Task 저장은 기존 Backend API를 사용하고, 승인 결과를 게임 API가 다시 읽어 불변 이벤트 설정으로 등록한다. 게임 클라이언트는 레벨·성공 여부·보상량을 결정하지 않는다. FastAPI가 행동을 판정하고 PostgreSQL 트랜잭션으로 시도/행동, 성장, 미션, 인벤토리, 보상 원장, 멱등 응답을 저장한다.

## WP-08 구현 변경 및 확인 상태

WP-08a–c 코드와 SQL 003 migration을 적용했다. 2026-10-10 Edge 사용자 시나리오에서 스테이지 자동 진행·정지, 성장 차감, 이벤트 던전 보스, 일반 던전, 운영 기록을 확인했다. 패배 후 farm 복귀와 전투 경계값, 재시도·멱등성 등은 별도 검증이 남아 있어 WP-08 전체 완료로 판정하지 않는다.

WP-09 구현 변경은 코드에 반영했다. SQL 004와 게임 API 조회, 상점·보관함 화면은 확인했다. 이번 피드백으로 고친 무한 push의 실제 전투 연속 진행과 스킨 구매/장착 후 재접속 복원은 추가 확인이 필요하다. WP-10의 이벤트 반복 운영 정책과 보상 영향 평가는 별도 후속 범위다. 상세 범위는 [가상 게임 구현 계획](가상게임_구현계획서.md)과 각 게임 설계서를 참조한다.

2026-10-10 던전 1:N 구현: 새 규칙/카탈로그 `opong-rules-1.3.0` / `opong-data-1.3.0`을 추가했다. 스테이지와 이벤트 특별 던전의 단일 적 규칙은 유지하고, 폐광은 적 3명 파티·5층 보스+호위 2명 구성, 결정적 선공/회전 반격, Attempt encounter snapshot과 적별 로그를 사용한다. 신규 snapshot을 로컬 PostgreSQL에 idempotent seed로 추가했고 기존 데모 유저 진행 데이터는 초기화하지 않았다. 10,000-step 성장 시뮬레이션에서 stage/dungeon 각 6,855승, 폐광 보스 1,371승, 적 처치 20,565, 정체 0을 확인했다. Vite build와 변경 Python 파일 Ruff 검사는 통과했다. 기존 API `8001`은 1.2.0으로 유지하고 새 1.3.0 API `8002`와 Edge 테스트 UI `5174`를 별도 실행했다. Edge에서 UI 상태/버전(`opong-data-1.3.0`)과 일반 던전 메뉴를 확인했다. API를 통해 39층 일반 파티와 40층 광맥룡+호위 2명을 각각 승리 처리했고, 같은 요청 ID 재전송이 같은 Attempt를 반환하며 중복 진행을 만들지 않는 것을 확인했다. 기존 진행도는 리셋하지 않았고 테스트 결과로 데모 유저가 Lv.37, 최고 40층, 다음 도전 41층이 됐다. 화면에서 실제 공격 애니메이션을 재생하는 Edge 사용자 확인은 아직 남아 있다.

2026-10-10 추가 화면 보완: 스테이지의 5개 visual_slot을 슬라임·고블린·박쥐·수호자·정령의 개별 이미지로 연결했다. 전투 캐릭터 크기를 줄이고 양측의 이름, 공격력·방어력·현재/최대 HP 및 영웅 레벨을 HUD에 표시하며, 전투 로그 재생 중 숫자와 체력바를 함께 갱신한다. Edge에서 실제 화면 확인은 아직 하지 않았다.

2026-10-10 Edge 재현 후 보완: 단일 적 전투에서 공격 피해 숫자는 나오지만 단일 적의 HP 바/숫자는 갱신되지 않던 분기를 수정했다. 단일 적은 합산 파티 HP가 아니라 단일 적 HP 상태를 갱신하도록 정리했다. 폐광 자동 도전은 push일 때 최고 층+1, farm일 때 최고 층을 요청하도록 수정해 최고 층과 현재 층 값이 어긋나도 다음 층 ID가 잘못 선택되지 않게 했다. Edge에서 스테이지 전투 중 영웅 HP 감소는 관찰했고, 몬스터 HP 불일치는 재현했다. 수정 후 확인은 production build까지 완료했으며, DB 상태는 Level 49·최고 스테이지 73·현재 74구역·폐광 최고 69층으로 확인했다. 재현을 위해 시작한 자동 사냥이 정지 전에 7개 구역을 연속 클리어해 영속 진행도가 추가 변경됐다. DB는 초기화하거나 수동 롤백하지 않았다. 수정 후 실제 전투 재생 및 폐광 도전 POST는 아직 검증하지 않았다.

2026-10-10 성장 화면 정리: 로비의 공격력/최대 HP 강화 버튼을 독립된 `성장` 탭으로 이동했다. 성장 화면에 레벨, 공격력, 최대 HP, GOLD/월광 파편 잔액, 강화 rank와 다음 강화 후 예상 스탯 및 비용을 표시한다. 강화는 기존 성장 API를 그대로 호출하며 보유 재화가 부족하거나 한도에 도달하면 버튼을 비활성화한다. Production build와 Edge에서 성장 탭 및 현재 스탯 표시를 확인했다. 강화 API 호출은 기존 DB를 바꾸지 않도록 이번 확인에서는 실행하지 않았다.

2026-10-10 이름/아키타입 정합성 보완: 15구역 이후 동적 스테이지의 3번 슬롯이 `버섯 정령`/slime으로 반환되던 규칙을 `수정 박쥐`/bat으로 맞췄다. 무한 폐광의 3·4·5번 슬롯 이름과 아키타입도 화면 외형 순서와 일치시켰다. UI도 서버의 몬스터 이름 대신 `visual_slot` 기준 이름을 표시해, 실행 중인 API가 재시작되기 전에도 장면에서 박쥐/수정 박쥐로 일치한다. 이 보완은 표시 메타데이터만 수정하며 기존 플레이 데이터는 변경하지 않았다.

2026-10-10 스킨 해제 UX 보완: 보관함에서 현재 장착 중인 스킨 카드에 `장착 해제` 버튼을 표시하고, null 스킨 ID를 기존 API에 보내 기본 영웅 외형으로 되돌린다. 기존 API 계약과 서버 저장 규칙이 이미 해제를 지원했으며 UI 버튼만 빠져 있었다. 실제 API 호출은 실행하지 않았다.

## 로컬 실행 방법

PowerShell에서 저장소 루트(`C:\phase3\proj\team2`) 기준이다. `POSTGRES_PORT` 환경 변수는 기존 로컬 PostgreSQL과 충돌하지 않도록 필요 시 조정한다.

```powershell
$env:POSTGRES_PORT = "5433"
docker compose -f infra/compose.yml up -d postgres

$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
backend\.venv\Scripts\python.exe -m backend.scripts.seed_game_runtime

# Backend 터미널
$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
$env:WORKFLOW_ENGINE = "backend_b_mock"
$env:APPROVED_ACTOR_IDS = "liveops01"
backend\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8001

# 게임 UI를 위한 별도 터미널
$env:BACKEND_BASE_URL = "http://127.0.0.1:8001"
Set-Location demo-game
pnpm install
pnpm dev
```

브라우저에서 `http://127.0.0.1:5173`을 연다. 새 승인 Task는 기존 이벤트 기획 API/운영 UI에서 생성하고 승인한 다음 Task ID를 게임 화면에 입력한다. `backend_b_mock`은 Workflow 에이전트와 데이터 응답을 Mock으로 실행하지만 Task·승인·Trace·게임 Runtime 데이터는 같은 PostgreSQL에 실제 저장한다. 외부 LLM/MCP를 호출하지 않는 로컬 통합 프로필이다. `WORKFLOW_ENGINE=mock` 모드는 `game_data_version`이 없는 결과를 만들기 때문에 게임 적용 source로 사용할 수 없다.

게임 데이터만 초기화하고 Workflow/승인 Task/카탈로그를 보존할 때:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
backend\.venv\Scripts\python.exe -m backend.scripts.reset_game_runtime
backend\.venv\Scripts\python.exe -m backend.scripts.seed_game_runtime
```

## 현재 검증 결과

- WP-09 구현 변경 후: Python 구문 컴파일, Ruff check/format, Vite production build 통과. 2026-10-10 SQL 004 migration을 로컬 PostgreSQL에 적용하고 새 Backend를 재시작했다. state/inventory/shop GET API에서 opong-data-1.2.0, 기존 잔액/원장, 상품 3개를 확인했고 Edge 새 탭에서 게임 화면과 기존 이벤트 상태가 표시됐다. 게임 행동의 Edge 종단 수용과 DB 잔액/원장 전체 대사는 아직 미실행이며 테스트 스위트도 실행하지 않았다. 1,000/10,000-step 밸런스 시뮬레이션은 실행했다.

- 로비에서 무기를 1회 강화해 공격력 25→29, GOLD 20 차감을 확인했다. 일반 던전과 현재 이벤트 던전 보스도 서버 성공 응답을 받았다. 보상 증가와 강화 비용의 잔액 표시, 운영 기록의 Source Task/digest, Attempt/Action 기록을 확인했다. 마지막 상태는 Lv.8, 최고/현재 15구역, farm 모드, 공격력 29, GOLD 360이다.
