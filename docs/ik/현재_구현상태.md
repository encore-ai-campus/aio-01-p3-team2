## 2026-10-11 격리 오류 정책 시험실

28개 canonical 오류 코드와 28개 시나리오를 별도 시험 DB/API/MCP와 case별 프로세스로 실행하도록 구현했다. 일반 Workflow에는 fault 입력 필드를 추가하지 않았다. 고정된 주 흐름·검증/평가·Supervisor 그래프에서 업무 단계→세부 위치→원인→패턴/정책 순으로 선택하며 주입과 실제 검출, 정책 action, 시도/수정/대체 조회, 최종 상태, Runtime 항목별 불변과 정책 복원을 독립적으로 비교한다. 승인 후 Runtime 그래프는 표시되지만 해당 쓰기 장애 runner는 아직 연결하지 않았다. 외부 LLM 실호출과 DB 서버 강제 중단도 이 시험실의 검증 완료 범위가 아니다.

DB 상태 저장 오류는 저장 결과·소유권·버전 확인 후 pinned 정책에 따라 실패 작업만 재시도하도록 보완했다. MCP 게임 규칙 조회 오류는 ERR-DEP-MCP-003으로 분리했으며 과거 정책의 003→002 상속 근거를 기록한다. 실행 방법과 최신 검증 결과는 [시험실 구현·검증 16](기획안설계/16_오류시험실_구현과_검증.md)을 따른다. 아래는 기존 시스템 검증 기록이다.

복구 상태 저장, 승인·Runtime transaction, canonical 실행 예약·종료, 공통 로컬 보안, 정책 hash 고정, 비동기 진행 UI를 구현했다. 최종 실제 PostgreSQL backend 검증은 257 passed / 11 skipped, Edge 전체 검증은 28 passed / 3 skipped다. backend 프로세스 재시작 후 상태·이벤트 복원도 별도로 1 passed였다. 제외된 외부 provider smoke의 성공을 주장하지 않는다. 기존 동기 Task/오류 시연 경로에도 실행 owner·deadline 저장과 만료 정리를 보충했다. 별도 프로세스 강제 종료 뒤 Supervisor SAFE_STOP·FAILED 조회 및 늦은 결과 차단이 영향 검증에서 통과했다.

실제 코드·명령·검증 범위·환경 적용 안내는 [수정 계획 14 §7](기획안설계/14_Workflow_검사결과_설계보완_수정계획.md#7-2026-10-11-구현검증-기록)을 따른다. 아래 완료/테스트 문장은 과거 실행 기록이다.

### 2026-10-10 로컬 구현 및 확인

- 이번 구현 진행에서 canonical Brief 경로에 read-only Planner/Critic Agent 계약, 결정적 Supervisor 전이 검사, 명시적 Handoff, Critic REVIEW의 runtime 차단을 추가했다. 기본 모드는 deterministic adapter이며 `CANONICAL_PLANNING_MODE=live`에서만 OpenAI를 선택한다. Brief와 게임의 권위값은 Agent 출력으로 바뀌지 않는다.

OpenAI 요청에는 output token 상한을 전달한다. 비용 상한은 응답을 받은 뒤 측정되므로 이미 발생한 단일 provider 호출 비용까지 소급 취소할 수는 없다. `llm_usage`는 canonical 성공/안전 종료 Workflow record와 Backend B Trace에 저장된다.

Backend B의 허용된 transient retry도 공통 250ms 시작·4초 상한 exponential jitter helper를 사용한다. `llm_execution_error`, budget 초과는 안전 종료 경로다. 실패 실행은 plan 없는 `SAFE_STOP` Workflow record/Trace와 가용한 계측값을 저장하고 운영 기록에서 읽을 수 있도록 구현했다. Backend B도 성공 사용량과 예산·LLM 실패 계측값을 Task Trace에 저장하고 실패 결과를 반환하도록 연결했다. 해당 통합 테스트 실행, live provider 사용량을 포함한 실제 예산 초과 경로와 policy pin 확인은 남아 있어 WP-03/05 완료로 판정하지 않는다.

## 로컬 실행 방법

PowerShell에서 저장소 루트(`C:\phase3\proj\team2`) 기준이다. `POSTGRES_PORT` 환경 변수는 기존 로컬 PostgreSQL과 충돌하지 않도록 필요 시 조정한다.

```powershell
$env:POSTGRES_PORT = "5433"
docker compose -f infra/compose.yml up -d postgres

$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
backend\.venv\Scripts\python.exe -m backend.scripts.seed_game_runtime

# Backend 터미널
$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
$env:WORKFLOW_ENGINE = "backend_b_mock"
$env:APPROVED_ACTOR_IDS = "liveops01"
backend\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8001

# 게임 UI를 위한 별도 터미널
$env:BACKEND_BASE_URL = "http://127.0.0.1:8001"
Set-Location demo-game
pnpm install
pnpm dev
```

브라우저에서 `http://127.0.0.1:5173`을 연다. 새 승인 Task는 기존 이벤트 기획 API/운영 UI에서 생성하고 승인한 다음 Task ID를 게임 화면에 입력한다. `backend_b_mock`은 Workflow 에이전트와 데이터 응답을 Mock으로 실행하지만 Task·승인·Trace·게임 Runtime 데이터는 같은 PostgreSQL에 실제 저장한다. 외부 LLM/MCP를 호출하지 않는 로컬 통합 프로필이다. `WORKFLOW_ENGINE=mock` 모드는 `game_data_version`이 없는 결과를 만들기 때문에 게임 적용 source로 사용할 수 없다.

게임 데이터만 초기화하고 Workflow/승인 Task/카탈로그를 보존할 때:

```powershell
$env:DATABASE_URL = "postgresql+psycopg://eventquest:eventquest-local-only@127.0.0.1:5433/eventquest"
backend\.venv\Scripts\python.exe -m backend.scripts.reset_game_runtime
backend\.venv\Scripts\python.exe -m backend.scripts.seed_game_runtime
```

# 2026-10-11 이벤트 던전 층별 기획·보상 연결

기획 입력에서 이벤트 던전만 장소로 제공하고, 서버 카탈로그의 층 이름과 보상 아이템을 선택해 층별 첫 클리어 Brief를 생성한다. 각 선택 층마다 target 1인 `special_dungeon_floor_clear` mission을 만들고 reward를 정확한 action/mission에 연결한다. UI는 콘텐츠 ID를 사용자에게 입력시키지 않는다. Plan 결과에는 층별 보상 요약을 표시한다.

승인 Plan의 Runtime 변환은 mission source ID와 층 ID/이름을 보존한다. 모든 신규 층 mission은 `active_during_event`이고 이벤트 날짜 구분 없이 이벤트 전체 기간에 유효하다. 이벤트가 active일 때 해당 층에서 성공한 첫 클리어가 mission을 완료하고 연결 reward를 지급한다. 완료 이후 같은 층을 다시 클리어해도 재지급하지 않는다. 이벤트 시작 전 기록은 이 이벤트의 progress로 쓰이지 않으며, 이벤트 기간 밖 행동은 active Runtime 이벤트가 없어 보상 조건이 되지 않는다.

운영 모드는 finite 1–7일 또는 ongoing이다. ongoing은 `end_at=null`로 저장되며 시작 후 만료되지 않는다. UI의 ongoing 평가 기간은 기획의 평가 범위이고 Runtime 종료일이 아니다. 추가된 migration은 종료 시각 열을 nullable로 바꾼다. 기존 1.3.0 카탈로그 파일은 보존하고 현재 신규 카탈로그는 `event_schema_version=1.1.0`, `opong-rules-1.4.0`, `opong-data-1.4.0`으로 버전 관리한다.

핵심 코드: [기획 입력 UI](../../frontend-web/src/main.js), [Plan→Runtime 어댑터](../../backend/app/game/event_source.py), [게임 Runtime](../../backend/app/game/service.py), [기간 규칙](../../backend/app/game/rules.py), [데모 게임 화면](../../demo-game/src/main.js), [추가 migration](../../backend/sql/013_ongoing_event_and_first_clear_missions.sql). 구현 의사결정과 기준은 [이벤트 던전 변경 기록](기획안설계/11_이벤트던전_층별_미션보상_변경작업.md) 참조.
