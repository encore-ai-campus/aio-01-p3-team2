# 개발 기획안

# 0. 문서 목적

이 문서는 **게임 라이브 이벤트 기획·검수 AutoHealing 시스템**의 실제 구현을 위한 개발 기획서입니다.

상위 기획안이 "무엇을 만들 것인가"를 설명한다면, 이 문서는 **Agent를 어떻게 나누고, 어떤 데이터 구조와 검증 규칙으로 연결하며, 장애를 어떻게 감지·복구하고, 어떻게 테스트·배포할 것인가**를 정의합니다.

<aside>
📌

**문서 작성 원칙**

- 실제 구현할 최소 범위를 우선 정의합니다.
- Validation과 Guard는 Prompt 문구가 아니라 Backend 코드에서도 강제합니다.
- 대체 모델, 캐시 폴백, 외부 알림 등은 구현 완료 전까지 선택 확장 기능으로 구분합니다.
- 최종 보고서에는 실제 구현·시험·측정된 결과만 확정값으로 기록합니다.
</aside>

# 1. 개발 목표와 구현 범위

## 1-1. 개발 목표

사용자가 게임 이벤트 생성을 요청하면 여러 Agent가 역할을 나누어 이벤트를 생성·검증하고, 오류 또는 일시적 시스템 장애가 발생했을 때 Supervisor Orchestrator가 상태와 오류 유형을 기준으로 **재호출·재시도·재연결 또는 안전 종료**를 수행하도록 구현합니다.

### 핵심 구현 목표

1. Agent 역할 분리
2. 명확한 Handoff Contract
3. Output / Tool Result Validation
4. Input / Tool / Response Guard
5. Supervisor Routing 및 Retry 정책
6. security_policies.yaml 기반 Context 접근 제한
7. Trace 기반 실행 이력 관리
8. 장애 주입 및 AutoHealing 검증
9. Docker / GitHub Actions 기반 배포 자동화
10. AWS EC2 배포

- 로그인 정보는 Workflow State나 Agent Context에 전달하지 않음

### Normal Mode

실제 게임회사 직원이 이벤트 초안을 만들고 내부 검수하는 흐름입니다.

```
직원 ID 로그인
↓
Pydantic Input Schema
↓
Input Guard
↓
Event Planner
↓
EventPlanResult Validation
↓
Balance & Rule
↓
게임 규칙 / 아이템 / 이벤트 데이터 검증
↓
RuleValidationResult
- game_data_version
- data_source
↓
Critic
↓
critic_status = PASS
workflow_status = WAITING_APPROVAL
approval_status = PENDING
current_result = 현재 검토 결과
↓
Backend Approval Validation
↓
운영 담당자
├ APPROVE
│  → final_result = current_result
│  → approval_status = APPROVED
│  → workflow_status = COMPLETED
│  → END
├ REQUEST_REVISION
│  → approval_status = REVISION_REQUESTED
│  → workflow_status = RUNNING
│  → critic_status = null
│  → approval_comment 저장
│  → Trace action = human_revision
│  → Planner 재실행
│  → 수정된 event_plan 전체 재검증
│  → Critic PASS 시 새 current_result 저장 + result_version + 1
│  → approval_status = PENDING
│  → workflow_status = WAITING_APPROVAL
└ REJECT
   → approval_status = REJECTED
   → workflow_status = CANCELLED
   → END
```

### 이벤트 오류 AutoHealing

```
Planner가 Day 7 레이드 미션 생성
↓
Balance & Rule
Lv.15 신규 유저 / Lv.30 레이드 조건 비교
↓
mission_unreachable
↓
Critic RETRY
↓
Supervisor
Planner 재호출
↓
던전 미션으로 수정
↓
재검증
↓
PASS
↓
Human Approval
```

### 시스템 장애 AutoHealing

```
MCP Tool 호출
↓
Timeout
↓
mcp_timeout 기록
↓
workflow_status = RETRYING
↓
Supervisor retry_count 증가
↓
Tool 재호출
├ 성공 → workflow_status = RUNNING → Workflow 계속
└ 계속 실패 → max_retries → Safe Stop → FAILED
```

FAILED 상태에서는 자동 처리를 중단하고 Streamlit에 실패 원인과 Trace를 표시합니다.

### Test Mode

개발·QA·발표에서만 사용하는 장애 주입 모드입니다.

```
Streamlit Test Mode
↓
POST /api/test/events/generate
↓
Backend
ENABLE_FAULT_INJECTION == true ?
├ NO → DENY
└ YES → fault_type 검증
         ↓
         의도적 장애 발생
         ↓
         오류 감지
         ↓
         Retry / Tool Fallback / 재연결
         ↓
         복구 성공 또는 Safe Stop
         ↓
         Trace 기록
```

Normal Mode는 `POST /api/events/generate`를 사용하고 Fault Injection 코드를 실행하지 않습니다.

# 2. 아키텍처 선택

## 2-1. 구조

**Supervisor 기반 중앙 조정형 Multi-Agent Architecture**

이번 프로젝트에서는 **3개의 LLM Agent + 1개의 코드 기반 Supervisor Orchestrator** 구조로 구현합니다.

```
LLM Agent
- Event Planner
- Balance & Rule
- Critic

Code-based Orchestrator
- Supervisor
```

Supervisor가 매번 LLM으로 다음 경로를 판단하게 하지 않고, Backend의 `routing.py`와 `retry.py` 규칙으로 Routing과 Retry를 처리합니다.

### 선정 이유

- 이벤트 생성, 게임 규칙 검증, 최종 판정을 분리할 수 있습니다.
- Supervisor가 Handoff와 Retry를 한 곳에서 관리할 수 있습니다.
- 오류 종류에 따라 필요한 Agent만 다시 호출하기 쉽습니다.
- Routing 결과가 예측 가능해 초보자 프로젝트에서 디버깅하기 쉽습니다.
- Validation / Guard 결과를 기준으로 다음 실행 경로를 제한하기 쉽습니다.
- Trace를 하나의 Workflow 기준으로 관리하기 쉽습니다.

### 고려사항

Supervisor 장애가 전체 Workflow에 영향을 줄 수 있으므로 다음을 적용합니다.

- Backend 예외 처리
- Health Check
- Retry 상한
- Trace 저장
- 실패 시 안전 종료

# 3. 전체 시스템 구조

학원에서 배운 개념을 유지하되 구현 난이도를 낮추기 위해 **Guard는 Input / Tool / Response 3개만 독립 기능으로 구현**합니다.

Routing과 Retry는 Supervisor가 담당하고, Agent별 Context 제한은 `security_policies.yaml`의 `context_access`를 적용하는 방식으로 처리합니다.

```
게임회사 직원
↓
Streamlit 직원 ID 로그인
↓
Opong Heroes 운영 화면
↓
Normal Mode 또는 Test Mode 선택
├ Normal → POST /api/events/generate
└ Test → POST /api/test/events/generate
          → ENABLE_FAULT_INJECTION 확인
↓
Pydantic Input Schema Validation
↓
FastAPI Backend
- task_id 생성
- Workflow State 초기화
↓
Input Guard
- 차단 시에도 task_id 기준 Trace 기록
↓
Supervisor Orchestrator
- 현재 상태 확인
- Python Routing
- revision_count / retry_count 관리
↓
Event Planner
↓
EventPlanResult Validation
↓
Handoff Validation
↓
Balance & Rule
↓
Tool 필요?
├ NO → Python Rule Engine
└ YES
   ↓
   Tool Guard
   ↓
   get_game_rules
   ├ 정상 → Tool Result Validation
   ├ mcp_tool_error → get_game_rules_fallback → Tool Result Validation
   └ mcp_timeout / MCP 연결 실패
      → workflow_status = RETRYING
      → retry_count + 1
      → 동일 Tool Retry / max_retries 초과 시 Safe Stop
   ↓
   필요 시 get_item_info
   ↓
   Python Rule Engine
↓
RuleValidationResult
- game_data_version
- data_source
↓
RuleValidationResult Validation
↓
기술·실행 오류 발생?
├ YES
│  → Critic으로 전달하지 않음
│  → Supervisor가 error_type 기준으로 Retry / Tool Fallback / Safe Stop 처리
│  → 복구 성공 시 실패한 단계부터 다시 실행
└ NO
   ↓
   Handoff Validation
   ↓
   Critic
   ↓
   CriticResult Validation
   ↓
   Supervisor
├ RETRY
│  → Critic이 이벤트 품질·기획 오류를 반환
│  ├ mission_unreachable
│  │  → revision_count + 1
│  │  → Planner 수정
│  ├ item_not_found
│  │  → revision_count + 1
│  │  → Planner 수정
│  └ event_brief_mismatch
│     → revision_count + 1
│     → Planner 수정
├ FAIL
│  → Safe Stop
│  → workflow_status = FAILED
└ PASS
   ↓
   current_result 저장
   workflow_status = WAITING_APPROVAL
   approval_status = PENDING
   ↓
   Backend Approval Validation
   ↓
   Human Approval
   ├ APPROVE
   │  → final_result = current_result
   │  → COMPLETED
   ├ REQUEST_REVISION
   │  → approval_status = REVISION_REQUESTED
   │  → workflow_status = RUNNING
   │  → critic_status = null
   │  → human_revision Trace
   │  → Planner 재실행
   │  → 수정된 event_plan 전체 재검증
   │  → Critic PASS 시 새 current_result 저장 + result_version + 1
   │  → PENDING / WAITING_APPROVAL 복귀
   └ REJECT → CANCELLED
↓
Response Guard
↓
사용자 응답

Workflow State / Trace / Idempotency / Test Result
↓
PostgreSQL
```

### 실행 원칙

- **Demo Login**: 직원 ID만 사용하는 시연용 로그인으로 화면 진입 여부만 관리합니다.
- **Normal Mode**: 실제 이벤트 기획·검수 흐름이며 의도적 장애 주입을 사용하지 않습니다.
- **Test Mode**: `ENABLE_FAULT_INJECTION=true`인 개발·QA·발표 환경에서만 활성화합니다.
- **Human Approval**: Critic PASS 이후에도 바로 확정하지 않고 Backend 검증 후 담당자 승인을 기다립니다.
- **Input Schema**: 숫자 범위·허용 값·필수 값을 Pydantic으로 결정적으로 검사합니다.
- **Input / Tool / Response Guard**: 정책 위반 입력·행동·응답을 제한합니다.
- **Validation**: Agent / Handoff / Tool / 승인 요청의 형식과 값을 검사합니다.
- **Routing / Retry**: Supervisor의 Python 규칙으로 처리합니다.
- **Context 제한**: `security_policies.yaml`의 허용 목록만 적용합니다.
- **Partial Failure**: 핵심 Agent는 Required로 보고, 정책 위반은 Fail Fast, 일시 장애만 Retry합니다.
- **Safe Stop**: 더 이상 복구할 수 없을 때 마지막 정상 상태와 Trace를 보존하고 검증되지 않은 결과를 확정하지 않은 채 FAILED로 안전 종료합니다.
- **로그인 정보**: Workflow State와 Agent Context에 포함하지 않습니다.

## 4-1. tiny_heroes.json 이벤트 대상별 Mock 성장 기준 데이터

`target_user = new_user / returning_user / all_user`를 실제 검증에 사용할 수 있도록 `tiny_heroes.json`과 `tiny_heroes_fallback.json`에 동일한 `user_segments` 구조를 둡니다. 콘텐츠 규칙은 EventPlanResult와 MCP Tool 입력이 동일한 키를 사용하도록 `content_id` 기준으로 통일하며, MVP 기준 ID는 `HUNT_001 / DUNGEON_001 / RAID_001`로 사용합니다.

실서비스라면 `expected_levels`는 과거 실제 사용자 플레이 로그를 Segment별로 집계해 산출합니다. Opong Heroes는 가상 서비스이므로 MVP에서는 **과거 사용자 플레이 데이터를 집계했다고 가정한 Mock 기준값**을 사용하며, 별도의 대규모 사용자 DB나 예측 ML 모델은 구현하지 않습니다.

```json
{
  "game_data_version": "tinyheroes-1.0.0",
  "user_segments": {
    "new_user": {
      "validation_policy": "expected_level",
      "expected_levels": {
        "1": 3,
        "3": 8,
        "5": 12,
        "7": 15
      },
      "expected_levels_basis": {
        "type": "mock_historical_aggregate",
        "metric": "median_level",
        "description": "과거 신규 사용자 플레이 데이터를 집계했다고 가정한 MVP 기준값"
      }
    },
    "returning_user": {
      "validation_policy": "expected_level",
      "expected_levels": {
        "1": 25,
        "3": 28,
        "5": 32,
        "7": 35
      },
      "expected_levels_basis": {
        "type": "mock_historical_aggregate",
        "metric": "median_level",
        "description": "과거 복귀 사용자 플레이 데이터를 집계했다고 가정한 MVP 기준값"
      }
    },
    "all_user": {
      "validation_policy": "content_access_only",
      "common_access_max_required_level": 1
    }
  }
}
```

### Mock 기준값 생성 원칙

```
실서비스
과거 실제 사용자 플레이 로그
→ user_segment / play_day / level 집계
→ Segment별 대표 성장 수준 산출
→ expected_levels 생성

MVP
과거 사용자 플레이 집계 결과를 Mock으로 정의
→ tiny_heroes.json에 저장
→ Python Rule Engine에서 결정적 기준으로 사용
```

예시로 가정하는 원천 데이터 필드는 `user_id / user_segment / play_day / level / play_time / content_clear` 정도이며, MVP에서는 개인별 원천 데이터를 대량 저장하지 않고 **집계 결과인 expected_levels만 실제 검증 데이터로 사용**합니다.

대상별 의미:

- `new_user`: 신규 유저 Mock 예상 성장 레벨을 기준으로 미션 달성 가능 여부 검증
- `returning_user`: 기존·복귀 유저 Mock 예상 성장 레벨을 기준으로 미션 달성 가능 여부 검증
- `all_user`: 특정 예상 레벨을 사용하지 않고 전체 유저가 공통으로 접근 가능한 콘텐츠인지 검증

`expected_levels`는 LLM이 생성하거나 추측하지 않고 `tiny_heroes.json`에서 조회한 값을 Python Rule Engine이 사용합니다. `tiny_heroes_fallback.json`도 동일한 `user_segments` Schema와 Mock 기준 근거를 유지하며 마지막으로 검증된 Snapshot 데이터로 사용합니다.

# 5. Agent 설정 YAML

Agent의 역할, 출력 Contract, 사용할 모델, 허용 Tool을 YAML로 분리합니다.

```yaml
workers:
  supervisor:
    name: Supervisor Orchestrator
    type: orchestrator
    goal: Workflow 상태와 오류 유형을 확인하고 다음 실행 경로를 결정한다.
    provider: rule_based
    output_contract: RoutingResult
    allowed_tools: []

  event_planner_agent:
    name: 이벤트 기획 Agent
    goal: 사용자 요청에 맞는 게임 이벤트 초안을 만들고 수정한다.
    instructions: >
      전달받은 이벤트 대상, 기간, 목적을 임의로 변경하지 마세요.
      최종 PASS 또는 FAIL을 직접 판정하지 마세요.
    provider: openai
    output_contract: EventPlanResult
    allowed_tools: []

  balance_rule_agent:
    name: 밸런스·규칙 검증 Agent
    goal: 이벤트가 게임 규칙과 데이터에 맞는지 검증하고 판정 근거를 설명한다.
    instructions: >
      Tool에서 조회한 게임 데이터와 Backend Python Rule Engine의 판정 결과를 근거로 설명하세요.
      레벨 비교, 아이템 존재 여부, 이벤트 기간 범위의 최종 사실 판정을 임의로 뒤집지 마세요.
      이벤트 내용을 직접 수정하지 마세요.
    provider: openai
    output_contract: RuleValidationResult
    allowed_tools:
      - get_game_rules
      - get_game_rules_fallback
      - get_item_info

  critic_agent:
    name: 최종 검수 Agent
    goal: 이벤트와 규칙 검증 결과를 확인해 PASS, RETRY, FAIL을 판정한다.
    instructions: >
      새 이벤트 초안을 직접 작성하지 마세요.
      PASS, RETRY, FAIL 중 하나만 반환하세요.
      RETRY인 경우 reason과 error_type을 반환하세요.
      다음에 실행할 Agent는 직접 지정하지 마세요.
      필수 필드와 출력 형식 검증은 Backend Validation이 담당하므로 품질 판단에 집중하세요.
    provider: openai
    output_contract: CriticResult
    allowed_tools: []
```

### YAML의 역할

| 항목 | 용도 |
| --- | --- |
| goal | Agent 책임 범위 정의 |
| instructions | Prompt 기반 역할 제한 |
| provider | 실행 방식 설정. LLM Agent는 openai, Supervisor는 rule_based |
| output_contract | Validation Schema 지정 |
| allowed_tools | Tool Guard 허용 목록 |

YAML만으로 Guard가 완성되는 것은 아니며, Backend에서 실제 허용 여부를 검사합니다.

## 5-1. security_policies.yaml

`agents.yaml`이 Agent의 역할과 Tool 권한을 정의한다면, `security_policies.yaml`은 **입력·응답·민감정보·Context 접근 정책**을 정의합니다.

```yaml
    - api_key

    - access_token

context_access:
```

### security_policies.yaml 역할

| 항목 | 역할 |
| --- | --- |
| input.max_length | 과도하게 긴 사용자 입력 제한 |
| input.blocked_phrases | Prompt Injection 패턴 차단 |

# 6. Output Contract

## 6-1. EventPlanResult

이벤트 미션과 보상을 안정적으로 검증할 수 있도록 단순 list가 아니라 내부 필드까지 고정합니다.

| 필드 | 형식 | 설명 |
| --- | --- | --- |
| target_user | string | 이벤트 대상 |
| duration | integer | 이벤트 기간 |
| missions | list[Mission] | 날짜별 미션 |
| rewards | list[Reward] | 미션·최종 보상 |

### Mission

```
day
content_id
mission_type
target_count
```

### Reward

```
day
item_id
quantity
```

MVP에서는 보상을 Opong Heroes 테스트 데이터에 존재하는 `ITEM_001~003` 기반 아이템으로 구성하고, **`item_id`가 실제 데이터에 존재하는지만 검증**합니다. 보상 수량의 적절성·경제 밸런스·Event Coin 같은 별도 이벤트 재화·상점 가격 검증은 MVP 이후 확장 범위로 둡니다.

예:

```json
{
  "target_user": "new_user",
  "duration": 7,
  "missions": [
    {
      "day": 7,
      "content_id": "DUNGEON_001",
      "mission_type": "CLEAR",
      "target_count": 3
    }
  ],
  "rewards": [
    {
      "day": 7,
      "item_id": "ITEM_003",
      "quantity": 1
    }
  ]
}
```

## 6-2. RuleValidationResult

| 필드 | 설명 |
| --- | --- |
| is_valid | 게임 규칙 기준 통과 여부 |
| error_type | 오류 종류 |
| reason | 오류 설명 |
| evidence | 검증에 사용한 게임 데이터 근거 |
| game_data_version | 실제 검증에 사용한 Opong Heroes 게임 데이터 버전 |
| data_source | primary / fallback_snapshot 등 실제 검증 데이터 출처 |

`game_data_version`과 `data_source`는 Event Planner가 추측해서 만들지 않고, Balance & Rule이 Primary 또는 Fallback Tool을 실제 조회한 뒤 RuleValidationResult에 기록합니다.

### RuleValidationResult 조건

```
is_valid = true
→ error_type = null
→ reason / evidence는 검증 근거로 유지

is_valid = false
→ error_type 필수
→ reason 필수
→ evidence 필수
```

Pydantic에서는 `error_type`을 nullable로 두되, `is_valid` 값에 따라 모델 검증에서 위 조건을 강제합니다.

## 6-3. CriticResult

```
status: PASS | RETRY | FAIL
error_type: string | null
reason: string
```

조건:

```
PASS
→ error_type = null
→ reason 필수

RETRY
→ error_type 필수
→ reason 필수

FAIL
→ error_type은 null 허용
→ reason 필수
```

Critic은 **이벤트 품질·기획 오류만** PASS / RETRY / FAIL로 판정합니다. Agent 실행 실패, Validation 오류, MCP/DB/LLM 장애는 Critic으로 보내지 않고 Supervisor가 직접 복구합니다.

Critic의 MVP 품질 체크 기준은 다음으로 제한합니다.

- 원래 `user_request`의 `target_user`가 유지되었는가?
- 원래 `user_request`의 `duration`이 유지되었는가?
- 원래 `user_request`의 `objective`와 이벤트 구성 방향이 일치하는가?
- RuleValidationResult에서 발견된 문제가 해결되었는가?
- 이전 RETRY 사유가 수정되었는가?

대상·기간·목적 불일치처럼 Event Brief와 결과가 어긋난 경우에는 `event_brief_mismatch`를 반환합니다.

Critic은 다음 Agent를 직접 지정하지 않습니다. Supervisor가 `error_type`, 현재 State, revision_count를 기준으로 기획 수정 경로를 결정합니다.

## 6-4. RoutingResult

```
next_agent: event_planner_agent | balance_rule_agent | critic_agent | null
action: RUN_AGENT | RETRY | TOOL_FALLBACK | WAIT_APPROVAL | SAFE_STOP | COMPLETE | CANCEL
reason: string
retry_count: int
```

`WAIT_APPROVAL / SAFE_STOP / COMPLETE / CANCEL`처럼 다음 Agent가 없는 상태에서는 `next_agent = null`을 사용합니다.

RoutingResult는 LLM이 자유롭게 생성하는 값이 아니라 **Backend의 `routing.py` / `retry.py` 규칙이 생성하는 결과**이며 Pydantic Schema로 검증합니다.

### 구현 원칙

LLM Agent 결과는 Pydantic Schema를 사용해 Output Contract와 맞는지 Backend에서 검증합니다.

```python
result = EventPlanResult.model_validate(raw_result)
```

Supervisor의 RoutingResult도 코드에서 생성한 뒤 Schema 검증을 적용할 수 있습니다.

```

error_reason

approval_comment

retry_count
max_retries

trace

final_result
```

### 상태 값

```
critic_status
→ PASS / RETRY / FAIL

workflow_status
→ RUNNING / RETRYING / WAITING_APPROVAL / COMPLETED / FAILED / CANCELLED

approval_status
→ PENDING / APPROVED / REVISION_REQUESTED / REJECTED
```

### 상태 관리 원칙

Workflow를 처음 생성할 때는 다음 초기값을 사용합니다.

```
workflow_status = RUNNING
critic_status = null
approval_status = null
result_version = 0
current_result = null
final_result = null
revision_count = 0
retry_count = 0
```

첫 Critic PASS 결과가 승인 후보로 저장되면 `current_result`가 생성되고 `result_version = 1`이 됩니다.

- 모든 요청에 고유 `task_id`를 생성합니다.
- Agent 실행 전후에 `current_agent`와 결과를 갱신합니다.
- AutoHealing이 기획 오류를 감지해 Event Planner를 자동 수정한 횟수는 `revision_count`로 관리합니다.
- `retry_count`는 Workflow 전체 누적값이 아니라 **현재 기술 장애에 대한 연속 재시도 횟수**로 사용합니다. 같은 장애가 복구되면 `retry_count = 0`으로 초기화합니다.
- Workflow 전체 Retry 통계는 Trace의 `RETRY` action 기록을 집계해 계산합니다.
- 담당자의 REQUEST_REVISION은 Human Revision이므로 `revision_count`에 포함하지 않습니다.
- RETRY 시 이전 실패 원인을 삭제하지 않습니다.
- Critic PASS 이후에는 `critic_status = PASS`, `workflow_status = WAITING_APPROVAL`, `approval_status = PENDING`으로 전환하고 현재 검토 대상은 `current_result`에 둡니다.
- 담당자 승인 시 `final_result = current_result`로 확정하고 `workflow_status = COMPLETED`, `approval_status = APPROVED`로 변경한 뒤 END 처리합니다.
- 담당자 REJECT 시 `workflow_status = CANCELLED`, `approval_status = REJECTED`로 변경해 사용자 취소 종료와 시스템 실패를 구분합니다.
- 수정 요청 시 `approval_status = REVISION_REQUESTED`, `workflow_status = RUNNING`, `critic_status = null`로 변경하고 `approval_comment`를 저장해 Event Planner 재실행 시 참고합니다. 이전 PASS 상태를 새 수정안에 재사용하지 않습니다.
- Human 수정 요청은 `revision_count`를 증가시키지 않고 Trace의 `human_revision`으로 구분합니다.
- 새 `current_result`는 **Critic PASS로 승인 후보가 확정된 시점에만** 저장하며, 그때 `result_version`을 1 증가시킵니다.
- 기술 장애 Retry가 시작되면 `workflow_status = RETRYING`, `retry_count`를 1씩 증가시킵니다. 재실행·재연결 성공 시 `workflow_status = RUNNING`, `retry_count = 0`으로 복귀합니다.
- Primary → Fallback Tool 전환은 Retry가 아니므로 `workflow_status = RUNNING`을 유지합니다.
- 승인 시 사용자가 확인한 `result_version`과 서버의 현재 버전이 일치해야 합니다.
- 다른 `task_id`의 State를 혼합하지 않습니다.
- Secret은 State에 넣지 않습니다.

# 8. Handoff Contract

이번 프로젝트에서는 Handoff를 단순 결과 전달이 아니라 **책임 소유권 이전**까지 포함해 구현합니다.

Handoff 데이터는 다음 구조를 기본으로 합니다.

```json
{
  "task_id": "TASK-001",
  "from_agent": "event_planner_agent",
  "to_agent": "balance_rule_agent",
  "owner_agent": "balance_rule_agent",
  "handoff_status": "ACCEPTED",
  "objective": "신규 유저 7일 이벤트의 게임 규칙 검증",
  "inputs": {
    "target_user": "new_user",
    "duration": 7,
    "missions": [],
    "rewards": []
  },
  "constraints": [
    "게임 데이터에 존재하는 콘텐츠만 검증 근거로 사용"
  ],
  "expected_output": "RuleValidationResult",
  "attempt": 1,
  "revision_count": 0,
  "retry_count": 0,
  "error_context": null,
  "state_ref": "TASK-001"
}
```

`handoff_status`:

```
REQUESTED
ACCEPTED
REJECTED
```

다음 Agent가 필수 입력을 정상 수신하고 계약을 만족할 때만 `ACCEPTED` 처리하고 `owner_agent`를 변경합니다. `REJECTED`이면 책임은 이전되지 않고 Supervisor가 이전 책임자 또는 복구 경로를 선택합니다.

### RETRY Handoff 추가 필드

```
error_type
error_reason
previous_validation
revision_count
retry_count
수정해야 할 내용
```

### Human Approval 운영자 피드백 / 수정 요청 Handoff

담당자가 `REQUEST_REVISION`을 선택하면 `approval_comment`를 **운영자 피드백**으로 사용하고 현재 `event_plan`과 함께 Event Planner에 전달합니다.

```
운영자 피드백
"Day 1~3 미션을 전투보다 성장 중심으로 바꿔주세요"
↓
approval_comment Validation + Input Guard
↓
현재 event_plan + approval_comment
↓
Event Planner 수정
↓
EventPlanResult Validation
↓
Balance & Rule
↓
RuleValidationResult Validation
↓
Critic
↓
새 승인 후보 저장
```

이 흐름은 시스템 장애 Retry나 AI AutoHealing과 구분해 Trace에 `human_revision`으로 기록하며 `revision_count`를 증가시키지 않습니다.

### Handoff Validation

다음 중 하나라도 실패하면 다음 Agent로 전달하지 않습니다.

- task_id 없음
- from_agent / to_agent 없음
- 허용되지 않은 Agent 이동
- expected_output 없음
- 필요한 inputs 누락
- RETRY인데 error_context 없음
- task_id 불일치

# 9. Routing 규칙

## 9-1. 정상 경로

```
START
→ Event Planner
→ Balance & Rule
→ Critic
→ PASS
→ critic_status = PASS
→ workflow_status = WAITING_APPROVAL
→ approval_status = PENDING
→ Backend Approval Validation
→ 담당자 선택
   ├ APPROVE
   │  → approval_status = APPROVED
   │  → workflow_status = COMPLETED
   │  → END
   ├ REQUEST_REVISION
   │  → approval_status = REVISION_REQUESTED
   │  → workflow_status = RUNNING
   │  → critic_status = null
   │  → Trace action = human_revision
   │  → Event Planner 재실행
   │  → 수정된 event_plan 전체 재검증
   │  → Critic PASS 시 새 current_result 저장 + result_version + 1
   │  → PENDING / WAITING_APPROVAL 복귀
   └ REJECT
      → approval_status = REJECTED
      → workflow_status = CANCELLED
      → END
```

Critic PASS는 Workflow 종료가 아니라 **승인 대기 상태로 전환되는 조건**입니다.

## 9-2. 기획 수정 경로

```
mission_unreachable
→ revision_count + 1
→ Event Planner

item_not_found
→ revision_count + 1
→ Event Planner

event_brief_mismatch
→ revision_count + 1
→ Event Planner

revision_count >= max_revisions
→ Safe Stop
→ workflow_status = FAILED
```

보상량·이벤트 재화·상점 가격 검증은 MVP 이후 확장 범위로 두며, 관련 Error Type은 현재 구현 범위에서 제외합니다.

## 9-3. 기술·실행 장애 경로

```
validation_error
→ workflow_status = RETRYING
→ retry_count + 1
→ 결과를 만든 Agent 재실행
→ 성공 시 workflow_status = RUNNING / retry_count = 0

agent_failure
→ workflow_status = RETRYING
→ retry_count + 1
→ 동일 Agent Retry
→ 성공 시 workflow_status = RUNNING / retry_count = 0

mcp_tool_error
→ failed_tool 확인
├ get_game_rules
│  → get_game_rules_fallback 호출
│  → 성공 시 Validation 후 retry_count 증가 없이 Workflow 계속
│  → Fallback도 실패하면 Safe Stop
├ get_item_info
│  → workflow_status = RETRYING
│  → retry_count + 1
│  → get_item_info 동일 Tool Retry
│  → 성공 시 workflow_status = RUNNING / retry_count = 0
└ get_game_rules_fallback
   → 대체 Tool 없음
   → Safe Stop

mcp_timeout
→ workflow_status = RETRYING
→ retry_count + 1
→ 동일 Tool Retry
→ 성공 시 workflow_status = RUNNING / retry_count = 0

db_connection_error
→ workflow_status = RETRYING
→ retry_count + 1
→ DB 재연결 후 Retry
→ 성공 시 workflow_status = RUNNING / retry_count = 0

llm_timeout
→ workflow_status = RETRYING
→ retry_count + 1
→ LLM 재호출
→ 성공 시 workflow_status = RUNNING / retry_count = 0

retry_count >= max_retries
→ Safe Stop
→ workflow_status = FAILED
```

`retry_count`는 현재 기술 장애의 연속 재시도 횟수입니다. 기술 Retry가 성공하면 `retry_count = 0`으로 초기화하며, Workflow 전체 Retry 통계는 Trace의 `RETRY` action을 집계합니다.

## 9-4. Guard / 승인 정책 차단 경로

Guard 또는 승인 정책 차단은 일반적인 AutoHealing Retry 대상으로 처리하지 않습니다.

```
input_guard_error
→ 즉시 차단
→ Trace 기록

tool_guard_error
→ Tool 실행 차단
→ 안전한 경로가 없으면 FAILED

approval policy DENY
→ 승인 상태 변경 없음
→ reason_code 기록
→ 최신 화면/정상 요청 필요

response_guard_error
→ 원문 응답 차단
→ 안전한 응답 반환
```

Prompt Injection이나 Secret 요청은 별도 복잡한 Error Type을 늘리지 않고 `error_reason` 또는 `reason_code`에 기록합니다.

# 10. Validation 설계

Validation은 **사용자 입력, 승인 요청, Agent 결과, Tool 결과가 다음 단계에서 사용할 수 있는 정상적인 형태와 값인지 확인하는 기능**입니다.

## 10-0. Input Schema Validation

금지 문구 검사만으로는 입력 검증이 충분하지 않으므로 Pydantic으로 결정적 조건을 먼저 확인합니다.

이벤트 생성 입력 예:

```
event_name: 필수
target_user: new_user / returning_user / all_user 중 하나
duration: 1~7
objective: 빈 문자열 불가
```

승인 입력 예:

```
action: APPROVE / REQUEST_REVISION / REJECT
actor_id: 필수
result_version: 1 이상의 정수
comment: 최대 길이 제한

승인 계열 멱등성 Key는 클라이언트 입력을 신뢰하지 않고 Backend가
task_id + result_version + action 기준으로 생성
```

`approval_comment`도 LLM에 전달되기 전에 Schema 검증과 Input Guard를 모두 통과해야 합니다.

## 10-1. Output Validation

모든 Agent의 결과는 다음 단계로 전달되기 전에 해당 Output Contract로 검증합니다.

EventPlanResult는 특히 다음 필드를 확인합니다.

- Mission의 `day`, `content_id`, `mission_type`, `target_count`
- Reward의 `day`, `item_id`, `quantity`

RuleValidationResult는 실제 게임 데이터 조회 이후 다음 필드를 확인합니다.

- `game_data_version`
- `data_source`
- `is_valid`
- `error_type`
- `reason`
- `evidence`

```
Event Planner
→ EventPlanResult Validation

Balance & Rule
→ RuleValidationResult Validation

Critic
→ CriticResult Validation

Supervisor
→ RoutingResult Validation
```

검증 항목:

- Pydantic Schema 검증
- 필수 필드 확인
- 필드 타입 확인
- 허용 값 확인

예:

```
duration > 0
missions가 비어 있지 않음
status ∈ {PASS, RETRY, FAIL}
```

## 10-2. Handoff Validation

- task_id 일치
- from_agent / to_agent 존재
- owner_agent 존재
- handoff_status가 REQUESTED / ACCEPTED / REJECTED 중 하나
- expected_output 존재
- 다음 Agent 입력값 존재
- RETRY 시 error_context 존재
- ACCEPTED일 때만 owner_agent를 다음 Agent로 변경

## 10-3. Tool Result Validation

MCP Tool 결과도 외부에서 들어오는 **신뢰하지 않는 데이터**로 보고 Agent가 바로 사용하지 않고 Schema를 검사합니다.

```
get_game_rules
→ content_id, content_name, required_level, game_data_version 확인

get_game_rules_fallback
→ content_id, content_name, required_level, game_data_version, source 확인

get_item_info
→ item_id, item_name, exists 확인
```

Primary Tool 결과가 비어 있거나 형식이 맞지 않으면 그대로 Agent에게 전달하지 않고 `mcp_tool_error`로 기록한 뒤 Fallback Tool 사용 가능 여부를 확인합니다.

Fallback Tool 결과도 동일하게 Validation하며, 정상일 때만 Python Rule Engine에 전달합니다.

## 10-4. Approval Validation

승인 API는 Streamlit의 session_state를 신뢰 근거로 사용하지 않습니다.

Backend에서 다음을 결정적으로 확인합니다.

```
workflow_status == WAITING_APPROVAL
approval_status == PENDING
actor_id가 서버 설정의 승인 가능 담당자 목록에 포함
request.result_version == current.result_version
```

결과 버전이 다르면:

```
policy_decision = DENY
reason_code = STALE_RESULT_VERSION
```

으로 Trace에 기록하고 승인을 거부합니다.

## 10-5. Validation 실패 처리

Validation 실패는 발생 위치에 따라 처리 방식을 분리합니다.

```
Validation 실패
├ EventCreateRequest / Input Schema
│  → Fail Fast
│  → Agent 실행 전 차단
│
├ Agent Output / Handoff
│  → validation_error
│  → workflow_status = RETRYING
│  → retry_count + 1
│  → 결과를 만든 Agent 재호출
│
├ MCP Tool Result
│  → mcp_tool_error
│  → failed_tool 확인
│  ├ get_game_rules → get_game_rules_fallback
│  ├ get_item_info → 동일 Tool Retry
│  └ get_game_rules_fallback → Safe Stop
│
└ Approval Validation
   → policy_decision = DENY
   → 상태 변경 없음
   → reason_code 기록
```

모든 실패는 Trace에 기록하며, 실패한 결과를 다음 단계로 그대로 전달하지 않습니다.

Prompt에 "형식을 지켜주세요"라고 적는 것만으로는 Validation 구현으로 보지 않습니다.

**Backend에서 Schema와 값을 검사하고, 실패 결과를 다음 단계로 전달하지 않아야 합니다.**

# 11. Guard 설계

이번 프로젝트에서는 구현 난이도를 낮추기 위해 **3개의 Guard만 독립 기능으로 구현**합니다.

```
1. Input Guard
2. Tool Guard
3. Response Guard
```

Routing, Retry, Context 제한, Secret 처리는 별도 Guard 파일로 만들지 않고 기존 구조에 포함합니다.

## 11-1. Input Guard

사용자 입력이 Supervisor로 전달되기 전에 간단하게 검사합니다.

검사 항목:

- `input.max_length`
- `input.blocked_phrases`

```
사용자 입력
↓
Input Guard
├ PASS → Supervisor
└ BLOCK
   ↓
   input_guard_error
   ↓
   Trace 저장
   ↓
   안전 종료
```

Prompt Injection 패턴도 `blocked_phrases`에 포함하여 동일한 Input Guard에서 검사합니다.

## 11-2. Tool Guard

Agent가 Tool을 호출하기 전에 `agents.yaml > allowed_tools`를 확인합니다.

```python
if tool_name not in worker.allowed_tools:
    raise PermissionError("허용되지 않은 Tool 호출")
```

### 예

- Balance & Rule → 게임 조회 Tool 사용 가능
- Event Planner → Tool 사용 불가
- Critic → Tool 사용 불가

## 11-3. Response Guard

최종 응답을 사용자에게 반환하기 직전에 `security_policies.yaml`의 응답 정책을 검사합니다.

검사 항목:

- `response.blocked_phrases`
- `response.sensitive_keys`

```
최종 응답
↓
Response Guard
├ PASS → 사용자에게 반환
└ BLOCK
   ↓
   response_guard_error
   ↓
   민감정보 제거 또는 안전한 오류 응답
   ↓
   Trace 저장
```

## 11-4. Supervisor에 포함되는 제어

Routing과 Retry는 별도 Guard로 구현하지 않습니다.

Supervisor는 기획 수정과 기술 장애를 구분합니다.

```
현재 Workflow State 확인
↓
기획 오류?
├ YES → revision_count / max_revisions 확인
└ NO → 기술 장애이면 retry_count / max_retries 확인
↓
routing.py 규칙으로 다음 실행 대상 결정
↓
상한 초과 시 FAILED
```

예:

```python
if is_revision_error and state.revision_count >= state.max_revisions:
    state.workflow_status = "FAILED"

if is_system_error and state.retry_count >= state.max_retries:
    state.workflow_status = "FAILED"
```

## 11-5. Agent Context 제한

Context 제한은 별도 `context_guard.py`를 만들지 않습니다.

Agent 실행 직전에 `security_policies.yaml > context_access`를 읽어 허용된 값만 전달합니다.

```python
allowed_keys = security_policy["context_access"][agent_name]

agent_context = {key: state[key] for key in allowed_keys if key in state}
```

즉 Agent마다 전체 Workflow State를 전달하지 않고 필요한 정보만 전달합니다.

## 11-6. Agent 역할 제한

Agent의 역할 제한은 `agents.yaml > instructions`와 Output Contract로 관리합니다.

| Agent | 주요 역할 | 하지 않는 일 |
| --- | --- | --- |
| Event Planner | 이벤트 생성·수정 | PASS / FAIL 최종 판정 |
| Balance & Rule | 게임 규칙 검증 | 이벤트 직접 수정 |
| Critic | PASS / RETRY / FAIL 판정 | 새 이벤트 작성 |
| Supervisor | Routing / Retry / 종료 | 세부 이벤트 직접 작성 |

### 실제 구현 기준

<aside>
✅

**Guard 구현 최소 범위**

Input Guard, Tool Guard, Response Guard 3개를 코드로 구현합니다. Routing과 Retry는 Supervisor에 포함하고, Context 제한은 security_policies.yaml을 읽어 필요한 값만 전달하는 방식으로 단순화합니다.

</aside>

# 12. Guard / Validation 실행 순서와 AutoHealing 연결

```
사용자 입력
↓
Pydantic Input Schema Validation
↓
Backend
- task_id 생성
- Workflow State 초기화
↓
Input Guard
- 차단 시에도 task_id 기준 Trace 기록
↓
Supervisor
- Routing
- revision_count / retry_count 관리
↓
Agent별 Context 제한
↓
Event Planner
↓
EventPlanResult Validation
↓
Handoff Validation
↓
Balance & Rule
├ Tool 불필요 → 결과 생성
└ Tool 필요
   ↓
   Tool Guard
   ↓
   Tool 1 get_game_rules
   ├ 정상 → Tool Result Validation
   ├ Tool Exception / 잘못된 결과
   │  → mcp_tool_error
   │  → Tool 2 get_game_rules_fallback
   │  → Tool Result Validation
   └ mcp_timeout / MCP 연결 실패
      → workflow_status = RETRYING
      → retry_count + 1
      → 동일 Tool Retry
      → 성공 시 workflow_status = RUNNING
      → max_retries 초과 시 Safe Stop / FAILED
   ↓
   필요 시 Tool 3 get_item_info
   ↓
   Python Rule Engine
↓
RuleValidationResult Validation
↓
기술·실행 오류 발생?
├ YES
│  → Critic으로 전달하지 않음
│  → Supervisor가 error_type 기준으로 Retry / Tool Fallback / Safe Stop 처리
│  → 복구 성공 시 실패한 단계부터 다시 실행
└ NO
   ↓
   Handoff Validation
   ↓
   Critic
   ↓
   CriticResult Validation
   ↓
   Supervisor
├ RETRY
│  → Critic이 이벤트 품질·기획 오류를 반환
│  ├ mission_unreachable
│  │  → revision_count + 1
│  │  → Planner 수정
│  ├ item_not_found
│  │  → revision_count + 1
│  │  → Planner 수정
│  └ event_brief_mismatch
│     → revision_count + 1
│     → Planner 수정
├ FAIL
│  → Safe Stop
│  → 마지막 정상 상태 / Trace 보존
│  → workflow_status = FAILED
└ PASS
   ↓
   workflow_status = WAITING_APPROVAL
   approval_status = PENDING
   ↓
   Backend Approval Validation
   - 상태
   - actor_id
   - result_version
   - 멱등성
   ↓
   Human Approval
   ├ APPROVE
   │  → final_result = current_result
   │  → COMPLETED
   ├ REQUEST_REVISION
   │  → approval_status = REVISION_REQUESTED
   │  → workflow_status = RUNNING
   │  → critic_status = null
   │  → approval_comment 저장
   │  → Trace action = human_revision
   │  → Planner 재실행
   │  → 수정된 event_plan 전체 재검증
   │  → Critic PASS 시 새 current_result 저장 + result_version + 1
   │  → PENDING / WAITING_APPROVAL 복귀
   └ REJECT → CANCELLED
↓
Response Guard
↓
사용자 응답
```

### 실패 발생 시

```
기획 오류
→ revision_count 증가
→ Planner 수정
→ Python Rule Engine 재검증

Validation 실패
→ retry_count 증가
→ Supervisor
→ 복구 가능하면 결과를 만든 Agent 재호출

MCP Tool 단위 실패
→ mcp_tool_error
→ failed_tool 확인
├ get_game_rules → get_game_rules_fallback → Fallback 결과 Validation
├ get_item_info → retry_count 증가 → 동일 Tool Retry
└ get_game_rules_fallback → Safe Stop

MCP Server / DB / LLM 일시 장애
→ workflow_status = RETRYING
→ retry_count 증가
→ Supervisor Retry / 재연결
→ 성공 시 workflow_status = RUNNING

Tool Guard 위반
→ Tool 실행 차단
→ Trace 기록

Input Guard 위반
→ Agent 실행 전 차단
→ Trace 기록
→ FAIL

Response Guard 위반
→ 원문 응답 차단
→ 안전한 응답 반환
```

### 핵심 원칙

- **Guard는 3개만 독립 구현**
- **Routing / Retry는 Supervisor 책임**
- **Context 제한은 security_policies.yaml 정책 적용**
- **Validation은 실행 결과 검증**
- **복구 가능한 오류만 Retry**
- **보안 위반은 반복 실행하지 않고 차단**

# 13. Error Type 표준

Error Type도 구현 난이도를 낮추기 위해 실제 처리에 필요한 항목만 사용합니다.

| Error Type | 종류 | 기본 처리 |
| --- | --- | --- |
| mission_unreachable | 기획 오류 | Event Planner RETRY |
| item_not_found | 기획 오류 | Event Planner RETRY |
| event_brief_mismatch | 기획 오류 | Event Brief의 대상·기간·목적을 기준으로 Event Planner RETRY |
| validation_error | Agent Output / Handoff Validation | workflow_status = RETRYING → retry_count 증가 → 결과 생성 Agent 재호출 |
| input_guard_error | Input Guard | 입력 차단 / FAIL |
| tool_guard_error | Tool Guard | Tool 실행 차단 |
| response_guard_error | Response Guard | 원문 응답 차단 / 안전 응답 |
| agent_failure | Agent 실행 장애 | 동일 Agent Retry |
| mcp_tool_error | MCP Tool 실행 / 결과 오류 | failed_tool 기준 처리: get_game_rules → Fallback Tool, get_item_info → 동일 Tool Retry, get_game_rules_fallback → Safe Stop |
| mcp_timeout | MCP Server / 통신 장애 | Tool Retry 또는 서비스 상태 확인 |
| db_connection_error | 시스템 장애 | 재연결 후 Retry |
| llm_timeout | 외부 API 장애 | LLM 재호출 |

Prompt Injection, Secret 요청 등 세부 원인은 별도 Error Type을 늘리지 않고 `error_reason`에 기록합니다.

# 14. Retry / Partial Failure / Safe Stop 정책

## 기본값

```
max_revisions = 2
max_retries = 3
```

## 기획 오류 수정

```
mission_unreachable / item_not_found / event_brief_mismatch
↓
revision_count < max_revisions ?
├ YES → revision_count + 1 → Planner 수정 → 재검증
└ NO → Safe Stop → FAILED
```

## 기술·실행 장애 Retry

```
Agent / MCP Server / DB / LLM / Output Validation 일시 장애
↓
retry_count < max_retries ?
├ YES → retry_count + 1 → 재호출 / 재연결 → Validation
└ NO → Safe Stop → FAILED
```

### MVP Recovery Contract / 복구 성공 판정

이번 MVP는 Queue / Worker 없이 동기식으로 실행하므로 복구 범위를 다음처럼 제한합니다.

#### 복구 기준점 원칙

- **복구 기준점은 마지막으로 Validation을 통과해 정상으로 확정된 입력·결과**입니다.
- Validation을 통과하지 않은 부분 결과는 폐기하며 다음 Retry에서 재사용하지 않습니다.
- 기술 오류는 마지막 정상 검증 결과를 유지하고 **실패한 Agent / Tool / DB 작업부터 다시 실행**합니다.
- 기획 오류(`mission_unreachable`, `item_not_found`, `event_brief_mismatch`)는 기술 Retry와 다르게 **원래 Event Brief를 기준점으로 Planner부터 수정**합니다.

#### 오류별 복구 기준점

| 오류 | 복구 기준점 | 재사용 / 폐기 | 다시 실행 |
| --- | --- | --- | --- |
| agent_failure | 해당 Agent에 전달된 마지막 검증 입력 | 이전 단계 PASS 결과 재사용 | 실패 Agent |
| validation_error | 결과 생성 Agent 실행 직전 상태 | Validation 실패 Output 폐기 | 결과 생성 Agent |
| mcp_timeout | Validation을 통과한 event_plan | event_plan 재사용 | 동일 MCP Tool |
| get_game_rules 오류 | Validation을 통과한 event_plan | event_plan 재사용 | get_game_rules_fallback |
| get_item_info 오류 | Validation을 통과한 event_plan | event_plan 재사용 | get_item_info |
| db_connection_error | DB 작업 직전의 검증된 Workflow State | 검증된 State 재사용 | 실패한 DB 작업 |
| mission_unreachable | 원래 Event Brief | 오류 event_plan은 수정 참고용만 사용 | Planner → 전체 재검증 |
| item_not_found | 원래 Event Brief | 오류 event_plan은 수정 참고용만 사용 | Planner → 전체 재검증 |
| event_brief_mismatch | 원래 Event Brief | 불일치한 event_plan은 수정 참고용만 사용 | Planner → 전체 재검증 |
| Retry / Revision 한도 초과 | 마지막 정상 검증 상태 | Trace와 상태만 보존 | 재개하지 않음 → FAILED |

#### 재검증 범위

- 기술 오류는 실패했던 Agent / Tool / DB 작업의 재실행이 성공하고 해당 Output 또는 Tool Result Validation을 통과한 뒤 다음 정상 단계로 이동하면 복구 성공으로 봅니다.
- 기획 오류(`mission_unreachable`, `item_not_found`, `event_brief_mismatch`)는 `Event Brief → Planner 수정 → EventPlanResult Validation → Balance & Rule → RuleValidationResult Validation → Critic` 순서로 전체 재검증합니다.
- MCP Server 중단 등 Retry 안에서 복구되지 않는 장애는 Safe Stop → `FAILED`로 종료합니다. 서비스 복구 후에는 기존 `task_id`를 재개하지 않고 **새 요청·새 `task_id`로 Workflow를 다시 시작**합니다.

### Partial Failure 정책

```
Required
- Event Planner
- Balance & Rule
- Critic
→ 최종적으로 복구되지 않으면 Workflow 완료 불가

Tool Fallback
- failed_tool = get_game_rules
→ mcp_tool_error
→ get_game_rules_fallback 호출
→ 성공 시 retry_count 증가 없이 Workflow 계속
→ Trace action = TOOL_FALLBACK

Tool Retry
- failed_tool = get_item_info
→ retry_count + 1
→ get_item_info 재호출
→ max_retries 초과 시 Safe Stop

Fail Fast
- Input Schema 위반
- Input / Tool Guard 정책 위반
- 승인 권한 / result_version 검증 실패
→ 동일 요청 자동 Retry 없음

Retry
- Agent 일시 실패
- LLM / MCP Timeout
- DB 일시 연결 실패
- 복구 가능한 Output Validation 실패

Best Effort
→ 사용하지 않음
→ 일부 Agent 결과만으로 이벤트를 최종 확정하지 않음

Safe Stop
- Fallback Tool도 실패하거나 Retry / Revision 한도를 초과한 경우 사용
- 마지막 정상 State / Trace 보존
- 검증되지 않은 결과는 final_result로 확정하지 않음
- workflow_status = FAILED
- 운영자 수동 확인
```

### 카운터 구분

- `attempt`: Agent 실행 횟수
- `revision_count`: AutoHealing이 기획 오류를 감지해 Event Planner를 자동 수정한 횟수
- Human `REQUEST_REVISION`은 `revision_count`에 포함하지 않고 `human_revision` Trace와 `result_version`으로 관리
- `retry_count`: 같은 Agent / Tool / 연결을 다시 시도한 기술·실행 장애 재시도 횟수
- Primary → Fallback Tool 전환은 Retry와 구분하며 `retry_count`를 증가시키지 않음

```json
  "content_name": "레이드",

```

## Tool 2. get_game_rules_fallback — Fallback Tool

Primary Tool이 Tool 단위 오류로 실행되지 않거나 Tool Result Validation에 실패한 경우 호출합니다.

Fallback Tool은 `tiny_heroes_fallback.json`의 **마지막 검증된 게임 규칙 Snapshot**을 조회합니다.

```json
  "source": "fallback_snapshot"
}
```

### Primary → Fallback 정책

```
get_game_rules
↓
Tool Exception 또는 Tool Result Validation FAIL
↓
mcp_tool_error
↓
get_game_rules_fallback
├ PASS → Tool Result Validation → Python Rule Engine → Workflow 계속
└ FAIL → Safe Stop → workflow_status = FAILED
```

Tool 1과 Tool 2는 같은 MCP Server 안에 있으므로 **MCP Server 자체가 중단되면 둘 다 사용할 수 없습니다.** 이 경우 동기 요청 안에서 `mcp_timeout` Retry를 수행하고, `max_retries`까지 복구되지 않으면 Safe Stop → `FAILED`로 종료합니다. 운영자가 MCP Server를 복구한 뒤에는 TC-08 기준으로 **새 요청·새 task_id**를 생성해 다시 실행합니다.

```json
}
```

출력:

```json

  "item_id": "ITEM_003",
```

```
get_item_info
↓
Tool Exception 또는 Tool Result Validation FAIL
↓
mcp_tool_error

↓
retry_count + 1
↓
get_item_info 동일 Tool Retry
├ 성공 → Tool Result Validation → Python Rule Engine
└ max_retries 초과 → Safe Stop → FAILED
```

get_item_info와 같은 목적의 Fallback Tool은 MVP에서 별도로 만들지 않습니다.

이벤트 기간과 Mission Day 범위는 별도 MCP Tool로 처리하지 않고 EventPlanResult와 Backend Python Rule Engine이 직접 검증합니다.

## 15-1. Python Rule Engine

레벨 비교, 아이템 존재 여부, 이벤트 기간 범위처럼 정답이 명확한 사실 판정은 LLM의 최종 판단에 맡기지 않습니다.

```
Primary 또는 Fallback Tool
↓
Tool Result Validation
↓
Backend Python Rule Engine
├ user_level >= required_level ?
├ item_id exists ?
└ 1 <= mission.day <= duration ?
↓
결정적 is_valid / error_type 생성
↓
Balance & Rule Agent
판정 근거 설명 및 문제 분류
```

예:

```python
if expected_level < required_level:
    is_valid = False
    error_type = "mission_unreachable"
```

LLM이 잘못된 `is_valid` 값을 생성하더라도 Python Rule Engine의 결정적 판정과 충돌하면 통과시키지 않습니다.

검증에 사용한 `game_data_version`과 Primary / Fallback 사용 여부를 Trace에 함께 남깁니다.

### target_user별 Rule Engine 분기

Python Rule Engine은 `target_user`에 따라 레벨 검증 기준을 다르게 적용합니다.

```
target_user = new_user
→ user_segments.new_user.expected_levels 사용

target_user = returning_user
→ user_segments.returning_user.expected_levels 사용

target_user = all_user
→ expected_levels 사용 안 함
→ common_access_max_required_level 기준으로 전체 유저 공통 접근 가능 여부 검증
```

`new_user`와 `returning_user`의 예상 레벨 데이터는 Day 1 / 3 / 5 / 7을 기준점으로 사용합니다. MVP 이벤트 기간은 1~7일로 제한하며, 기준점 사이 날짜는 해당 날짜보다 작거나 같은 가장 최근 기준점의 예상 레벨을 사용합니다.

예:

```
returning_user / Day 5
예상 레벨 = 32
레이드 필요 레벨 = 30
→ 달성 가능

new_user / Day 5
예상 레벨 = 12
레이드 필요 레벨 = 30
→ mission_unreachable

all_user / 레이드
required_level = 30
common_access_max_required_level = 1
→ 전체 유저 공통 콘텐츠가 아님
→ mission_unreachable
```

이 분기는 LLM Prompt가 아니라 `backend/app/rules/game_rule_engine.py`의 Python 규칙으로 결정적으로 구현합니다.

### MVP Rule Engine 검증 범위와 제외 범위

**검증함**

- `content_id` 기준 콘텐츠 존재·필요 레벨
- 대상별 예상 레벨과 콘텐츠 필요 레벨 비교
- `1 <= mission.day <= duration`
- 보상 `item_id` 존재 여부

**MVP에서 검증하지 않음**

- `target_count`가 실제 플레이 난이도에 적절한지 여부
- 일일 플레이 횟수·시도 한도
- `mission_type`별 실제 게임 로그·완료 조건
- `new_user` / `returning_user` 자격을 실제 회원 데이터로 판정하는 기능

`target_user`는 실제 유저 데이터를 자동 분석해 정하는 값이 아니라 **운영 담당자가 이벤트 기획 시 선택하는 입력값**으로 취급합니다.

# 17. Backend API

시연용 로그인은 Streamlit Frontend에서만 처리합니다. Backend에는 별도의 로그인 API나 사용자 인증 DB를 만들지 않습니다.

## POST /api/events/generate

Opong Heroes 이벤트 생성 Workflow 실행

입력:

```json
{
  "event_name": "신규 유저 7일 성장 이벤트",
  "target_user": "new_user",
  "duration": 7,
  "objective": "초기 적응 지원",
  "idempotency_key": "evt-20261006-001"
}
```

### EventCreateRequest Validation

```
event_name: 필수
target_user: new_user / returning_user / all_user
duration: 1~7
objective: 빈 문자열 불가
idempotency_key: 필수
```

### MVP Event Brief

별도의 복잡한 Event Brief 객체를 추가하지 않고, 사용자 입력 4개 필드를 MVP의 Event Brief로 사용합니다.

```
event_name
target_user
duration
objective
```

`idempotency_key`는 중복 실행 방지를 위한 전송·처리 필드이며 Event Brief에는 포함하지 않습니다. Event Planner는 `target_user`와 `duration`을 임의로 변경하지 않고, `objective`의 방향을 유지해 이벤트를 생성합니다.

같은 `idempotency_key`의 이벤트 생성 요청이 반복되면 새로운 Workflow를 만들지 않고 기존 task_id와 결과를 반환합니다.

Normal Mode의 일반 이벤트 API에는 `test_mode`와 `fault_type`을 노출하지 않습니다.

Backend는 입력값을 받아 Workflow State에 필드를 계속 추가하지 않고, Event Planner가 사용할 하나의 `user_request`로 정리합니다.

### Test Mode 접근 원칙

- Fault Injection은 서버 환경 설정 `ENABLE_FAULT_INJECTION=true`인 개발·QA·발표 환경에서만 허용합니다.
- 운영 환경에서는 `ENABLE_FAULT_INJECTION=false`로 비활성화합니다.
- Test Mode 선택은 Streamlit 내부 화면에서만 노출하고 Backend는 서버 설정을 다시 확인합니다.
- Backend가 Docker 내부 Network에 있으므로 외부 사용자가 장애 주입 API를 직접 호출하는 구조로 만들지 않습니다.
- Fault Injection 설정은 Agent Context에 전달하지 않습니다.

예:

```
Opong Heroes 신규 유저를 대상으로 7일 동안 진행하며
초기 적응을 돕는 성장 이벤트를 만들어줘.
이벤트명: 신규 유저 7일 성장 이벤트
```

```
API 입력
↓
Backend에서 user_request 생성
↓
Workflow State.user_request 저장
↓
Event Planner 전달
```

출력:

```
task_id
workflow_status
approval_status
result_version
current_result
final_result
revision_count
retry_count
```

승인 전에는 `current_result`에 검토 중 결과가 들어가며 `final_result`는 비어 있습니다. APPROVE가 완료되면 `final_result = current_result`로 확정합니다.

### MVP API 실행 방식

이번 MVP는 Queue / Worker를 사용하지 않고 **동기식 Workflow 실행**으로 구현합니다.

```
POST /api/events/generate
↓
Event Planner
↓
Balance & Rule
↓
Critic
↓
WAITING_APPROVAL 또는 FAILED 도달
↓
API Response
```

`POST /api/test/events/generate`도 동일하게 동기 실행합니다. Fault Injection 복구까지 수행한 뒤 `WAITING_APPROVAL` 또는 `FAILED` 상태를 반환합니다.

`REQUEST_REVISION` 역시 승인 API 요청 안에서 Planner → Balance & Rule → Critic 재검증을 수행한 뒤, 새 `WAITING_APPROVAL` 또는 `FAILED` 상태를 반환합니다.

`GET /api/tasks/{task_id}`는 화면 새로고침, 상태 재조회, 컨테이너 재시작 후 보존 상태 확인 용도로 사용합니다. 실행 중 Workflow의 백그라운드 Queue 재개는 MVP 범위에 포함하지 않습니다.

## POST /api/tasks/{task_id}/approval

Human Approval 처리

입력:

```json
{
  "action": "APPROVE",
  "actor_id": "liveops01",
  "result_version": 3,
  "comment": ""
}
```

승인 계열 멱등성 Key는 클라이언트에서 받지 않고 Backend가 `task_id + result_version + action`으로 생성합니다.

허용 action:

- APPROVE
- REQUEST_REVISION
- REJECT

### Backend 승인 검증

```
1. workflow_status == WAITING_APPROVAL
2. approval_status == PENDING
3. actor_id가 서버 설정의 승인 가능 Demo 담당자 목록에 포함
4. request.result_version == workflow_runs.result_version
5. Backend가 생성한 server_idempotency_key 중복 여부 확인
```

모두 통과해야 실제 상태 변경을 수행합니다.

처리:

- APPROVE → final_result = current_result → approval_status = APPROVED → workflow_status = COMPLETED
- REQUEST_REVISION → approval_status = REVISION_REQUESTED → workflow_status = RUNNING → critic_status = null → approval_comment 저장 → Trace action = human_revision → Event Planner 재실행 → 수정된 event_plan 전체 재검증 → Critic PASS 시 새 current_result 저장 + result_version 증가 → PENDING / WAITING_APPROVAL로 복귀
- REJECT → approval_status = REJECTED → workflow_status = CANCELLED → 작업 종료

결과 버전이 다르면:

```
DENY
reason_code = STALE_RESULT_VERSION
```

같은 `task_id + result_version + action` 조합이 다시 들어오면 Backend가 동일한 server_idempotency_key를 생성하고, 새로운 쓰기를 만들지 않고 기존 처리 결과를 반환합니다.

### Fault Injection 구현 원칙

Test Mode에서만 Backend의 장애 주입 로직을 사용합니다.

Streamlit에서 Test Mode를 선택하더라도 Backend가 `ENABLE_FAULT_INJECTION` 서버 설정을 다시 검사합니다. 운영 환경에서는 이 값이 비활성화되어 장애 주입이 실행되지 않습니다.

```
mission_unreachable_once
→ 첫 Planner 결과에만 달성 불가능 미션을 강제로 포함
→ Planner 재실행부터는 다시 주입하지 않음

agent_failure_once
→ 첫 Agent 실행에서만 Exception 발생

primary_tool_error_once
→ get_game_rules에서만 의도적 Exception 또는 잘못된 결과 발생
→ get_game_rules_fallback 호출 확인

mcp_timeout_once
→ 첫 MCP 호출에서만 Timeout 발생

db_connection_error_once
→ 첫 DB 접근에서만 ConnectionError 발생

validation_error_once
→ 첫 Agent 결과에서 필수 필드를 의도적으로 누락

retry_limit_exceeded
→ 지정 단계가 계속 실패하도록 설정
```

`mission_unreachable_once`는 첫 Planner 결과에만 기획 오류를 주입하고 자동 수정 재실행에서는 다시 주입하지 않습니다. `agent_failure_once`, `mcp_timeout_once`, `db_connection_error_once`, `validation_error_once`는 첫 실패 후 다음 Retry에서 정상화합니다. `primary_tool_error_once`는 Primary Tool만 1회 실패시키고 `get_game_rules_fallback`으로 전환해 Fallback 복구를 확인합니다.

# 20. 개발 전 평가 기준 및 테스트

구현 후 결과에 맞춰 평가 기준을 바꾸지 않고, **개발 전에 Expected Result를 먼저 확정한 뒤 구현 결과인 Actual Result와 비교**합니다.

## 20-0. 평가 영역 4가지

| 평가 영역 | 평가 방법 | Expected Result |
| --- | --- | --- |
| 요청 조건 준수 | Planner 결과와 MVP Event Brief 비교 | `target_user`, `duration` 유지 + `objective` 방향 유지 |
| 게임 규칙 검증 | Mock 성장 기준·콘텐츠 필요 레벨·item_id를 고정 Rule Test로 비교 | 예: 신규 Day 7 Lv15 + Raid Lv30 → `mission_unreachable`, 없는 item_id → `item_not_found` |
| AutoHealing | Fault Injection 및 Trace의 실제 복구 경로 확인 | Error Type별 정의된 복구 기준점과 Planner 수정 / Agent Retry / Tool Retry / Fallback 경로가 일치 |
| 안전 종료 | 복구 불가능 장애와 Retry 한도 초과 주입 | `workflow_status = FAILED`, `final_result` 미확정, 마지막 정상 State / Trace 보존 |

### 개발·평가 순서

```
1. Mock 과거 사용자 성장 기준 정의
↓
2. 게임 규칙 데이터 정의
↓
3. Evaluation Set의 Expected Result 확정
↓
4. Agent / Workflow 개발
↓
5. Evaluation Set 실행
↓
6. Actual Result 수집
↓
7. Expected vs Actual 비교
```

### 기존 테스트와 평가 영역 연결

- EV-01~EV-02 → 요청 조건 준수
- EV-03~EV-05 + SEG-01~SEG-03 → 게임 규칙 검증
- TC-02~TC-06 + TC-10 → AutoHealing
- TC-07 / TC-08 / Primary+Fallback 모두 실패 → 안전 종료

이후의 장애·Approval·Guard 테스트는 위 평가 기준을 실제로 검증하기 위한 테스트 케이스입니다.

## 20-1. 핵심 장애 복구 테스트

| ID | 시험 | 검증 대상 | 기대 결과 |
| --- | --- | --- | --- |
| TC-01 | 정상 이벤트 | Agent Workflow 정상 종료 조건 | Critic PASS → workflow_status = WAITING_APPROVAL / approval_status = PENDING |
| TC-02 | 달성 불가능 미션 | 기획 오류 AutoHealing | mission_unreachable → revision_count 증가 → Planner 수정 → Python Rule 재검증 → PASS |
| TC-03 | Agent 응답 실패 | Agent 장애 복구 | agent_failure 감지 → 동일 Agent Retry → 성공 시 Workflow 계속 |
| TC-04 | LLM 또는 MCP Timeout | API / Tool 장애 복구 | Timeout 감지 → 재호출 → 성공 시 Workflow 계속 |
| TC-05 | DB 일시 연결 실패 | DB 장애 복구 | 재연결 → 성공 시 Workflow 계속 |
| TC-06 | Output Validation 실패 | Validation | 잘못된 Result 차단 → 생성 Agent 재호출 |
| TC-07 | 기술 장애 Retry 한도 초과 | Supervisor Retry | max_retries 이후 추가 실행 없이 Safe Stop → workflow_status = FAILED |
| TC-08 | 실제 MCP Server 중단 | 동기식 Workflow의 Safe Stop + 운영 복구 | MCP 컨테이너 중단 → 연결 실패 → max_retries 초과 → FAILED → 운영자 MCP 재시작 → /health/ready 확인 → 새 요청·새 task_id → 정상 Workflow 실행 |
| TC-09 | 재시작 후 상태 보존 | PostgreSQL 지속성 | WAITING_APPROVAL 및 Trace 저장 → 컨테이너 재시작 → 동일 task_id 상태·이력 유지 |
| TC-10 | Primary Tool 실패 → Fallback Tool | Tool Fallback AutoHealing | get_game_rules 실패 → mcp_tool_error → get_game_rules_fallback → Tool Result Validation PASS → Python Rule Engine → Workflow 계속 |

### target_user 검증 단위 테스트

### Fault Injection 핵심 원칙

- 정상 코드에서 우연히 에러가 나기를 기다리지 않고 **Test Mode에서 의도적으로 장애를 주입**합니다.
- Test Mode는 `ENABLE_FAULT_INJECTION=true` 환경에서만 허용합니다.
- `mission_unreachable_once`는 첫 Planner 결과에만 달성 불가능 미션을 주입하고, Planner 재실행에서는 다시 주입하지 않습니다.
- `agent_failure_once`, `mcp_timeout_once`, `db_connection_error_once`, `validation_error_once`는 첫 실패 후 다음 Retry에서 정상화합니다.
- `primary_tool_error_once`는 Primary Tool만 1회 실패시키고 Retry하지 않고 Fallback Tool로 전환합니다.
- `retry_limit_exceeded`는 계속 실패하게 만들어 max_retries 이후 Safe Stop → FAILED가 되는지 확인합니다.
- 장애 주입 시작 → 감지 → Retry / Tool Fallback → 복구 또는 Safe Stop 전 과정을 Trace에 기록합니다.
- `primary_tool_error_once`는 Primary Tool만 실패시키고 MCP Server 자체는 정상 상태로 유지해 Fallback Tool 전환을 검증합니다.
- Test Mode가 꺼져 있을 때는 장애 주입 코드가 실행되지 않아야 합니다.
- 별도로 TC-08에서는 Fault Injection이 아니라 **MCP 컨테이너를 실제 중단**해 동기식 Workflow가 Retry 한도 후 안전하게 `FAILED`로 종료되는지 검증합니다.
- 이후 운영자·발표자가 MCP Server를 재시작하고 `/health/ready`를 확인한 뒤 **새 요청·새 task_id**로 정상 실행되는지 확인합니다.
- TC-08은 사람의 재시작이 필요한 시나리오이므로 자동복구 성공률 계산에는 포함하지 않고 수동 개입 서비스 복구 지표로 별도 기록합니다.

### 선택 확장 테스트

- LLM API 429 / 5xx
- Tool Result Validation 실패
- 존재하지 않는 아이템 오류

# 34. 시안 연동을 위한 Backend API 파일 구현 책임
이 절은 현재 저장소의 빈 API 파일과 문서상 API 계약의 관계를 명확히 합니다. 구현 예정 사항이며 코드가 이미 완성되었다는 뜻은 아닙니다.
## 34-1. `backend/app/api/event.py`
- `POST /api/events/generate`, `POST /api/test/events/generate`, `GET /api/tasks/{task_id}`, `POST /api/tasks/{task_id}/approval`, `GET /api/tasks/{task_id}/trace`를 노출합니다.
- Request/Response는 Frontend_Backend_API_Contract의 현행 MVP 계약을 따릅니다. 생성 및 수정 요청은 동기 Workflow가 `WAITING_APPROVAL` 또는 `FAILED`에 도달한 뒤 Task Response를 반환합니다.
- 입력 검증, Test Mode 접근 제한, idempotency, 저장·재조회, 결과 버전 및 승인 상태 검증, Trace 조회를 기존 Schema·Service·Orchestration 책임과 연결합니다. Route 안에 임의의 예시 결과를 고정 반환하지 않습니다.
- `workflow_status=FAILED`는 정상 생성된 Task의 실패 상태로 반환하여 Frontend가 Safe Stop과 Trace를 볼 수 있게 합니다. HTTP 오류와 구분합니다.
## 34-2. `backend/app/api/health.py`
- `GET /health/live`는 FastAPI 프로세스 생존을 확인합니다.
- `GET /health/ready`는 기존 17절의 PostgreSQL 및 MCP 준비 상태를 확인하고, 의존성 장애 시 HTTP 503을 반환합니다.
- Ready 응답을 개별 MCP 연결 상태나 게임 데이터 건수로 사용하지 않습니다. 이 수치는 API 계약서 40절에서 별도 확장 후보로 관리합니다.
## 34-3. 연결 및 완료 확인
- `backend/app/main.py`에 두 Router를 등록하고, API 스키마·오류 응답·환경변수·Trace 저장 방식은 기존 계약과 일치시킵니다.
- Backend 완료 기준은 정상·Test·FAILED 생성, Task 재조회, Trace, 승인 세 동작, stale `result_version` 409, Live/Ready 성공·장애 응답의 계약 시험 통과입니다.
- 첨부 시안의 추가 입력, 실제 최근 Task, 게임 데이터 건수, 항목별 검증 결과, 정확한 실행 시간은 현행 MVP 외의 확장 후보입니다. 확정된 계약과 구현 없이 완료 기능으로 표시하지 않습니다.
