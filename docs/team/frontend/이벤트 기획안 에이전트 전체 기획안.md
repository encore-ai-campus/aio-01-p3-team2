# 게임 라이브 이벤트 기획·검수 AutoHealing 시스템

## 1. 프로젝트 개요

### 프로젝트명

**게임 라이브 이벤트 기획·검수 AutoHealing 시스템**

### 프로젝트 한 줄 설명

가상의 게임사 **Okepong Games**가 서비스하는 모바일 판타지 RPG **Opong Heroes**의 라이브 이벤트를 AI가 기획하고, 여러 Agent가 **미션 수행 가능성·보상 아이템 유효성·게임 규칙**을 검수한 뒤 문제가 발견되면 자동 수정·재검증하는 내부 운영용 Multi-Agent AutoHealing 시스템입니다.

### 프로젝트 배경

**Okepong Games**는 모바일 RPG **Opong Heroes**를 서비스하고 있으며, 라이브서비스 운영팀은 신규 유저 성장 이벤트, 출석 이벤트, 미션 이벤트 등을 반복적으로 기획합니다.

이 프로젝트는 실제 게임 서버에 이벤트를 배포하는 도구가 아니라, **게임회사 직원이 이벤트 초안을 만들고 내부 검수하기 전에 사용하는 AI 기획·검수 도구**를 가정합니다.

### 프로젝트 목적

게임에서 진행하는 출석 이벤트, 성장 이벤트, 미션 이벤트 등을 기획할 때는 이벤트 기간, 미션, 보상, 게임 규칙을 함께 확인해야 합니다.

예를 들어 신규 유저를 대상으로 한 7일 이벤트인데 마지막 날 미션이 `레벨 30 레이드 참여`라면 신규 유저가 해당 미션을 수행하기 어려울 수 있습니다.

이 프로젝트에서는 이러한 문제를 사람이 일일이 찾는 것이 아니라 여러 Agent가 역할을 나누어 이벤트를 기획하고 검수합니다. 문제가 발견되면 오류 유형에 따라 관련 Agent를 다시 호출하고, 정해진 재시도 범위 안에서 수정·재검증합니다.

또한 이벤트 내용 오류뿐 아니라 Agent 응답 실패, MCP Tool Timeout, 일시적인 DB 연결 오류와 같은 시스템 장애를 감지하고 재시도·재연결하는 흐름도 함께 구현합니다.

#### “게임 이벤트를 기획하고 검수해서 운영 담당자가 승인할 수 있는 상태까지 만드는 시스템”

```jsx
우리가 Okepong Games라는 가상 게임회사에서 일함
↓
Opong Heroes라는 게임이 이미 존재함
↓
게임 규칙도 이미 존재함
- 던전 Lv10
- 레이드 Lv30
- 아이템 ITEM_001~003
- 신규 유저 예상 성장 레벨
↓
운영 담당자가 요청
"신규 유저 7일 성장 이벤트 만들어줘"
↓
AI Multi-Agent가 이벤트 기획 + 검수
↓
사람이 최종 승인
```

# 2. 서비스 시나리오

## 2-1. 실제 업무 상황

### 주요 사용자

- Okepong Games 운영팀 직원
- 게임 이벤트 기획자
- 게임 운영자

Okepong Games는 모바일 RPG **Opong Heroes**를 서비스하고 있습니다.

운영팀은 신규 유저 유입이나 업데이트 일정에 맞춰 출석 이벤트, 성장 이벤트, 미션 이벤트 등을 반복적으로 준비합니다. 이벤트를 만들 때는 재미있는 미션을 구성하는 것뿐 아니라 **실제 유저가 수행 가능한지, 콘텐츠 해금 레벨과 맞는지, 존재하는 아이템을 보상으로 사용하는지** 확인해야 합니다.

예시 담당자:

```
이름: 김하늘
소속: 운영팀
역할: 이벤트 기획자
Demo ID: liveops01
```

로그인은 프로젝트 시연을 위한 가상 계정이며 실제 사내 인증 시스템은 구현하지 않습니다.

### 업무 요청 예시

신규 유저 유입 캠페인을 앞두고 운영 담당자가 다음 주부터 사용할 7일 성장 이벤트 초안이 필요하다고 가정합니다.

> 신규 유저가 Opong Heroes의 초반 콘텐츠를 자연스럽게 경험할 수 있도록 7일 성장 이벤트를 만들어줘.

## 2-2. 정상 업무 시나리오

```
운영 담당자 로그인
↓
Opong Heroes Live Ops 화면 진입
↓
이벤트명 / 대상 / 기간 / 목적 입력
(MVP Event Brief)
↓
Event Planner
이벤트 초안 생성
↓
Balance & Rule
게임 데이터 기준 검증
↓
Critic
최종 품질 검수
↓
PASS
↓
Human Approval 대기
↓
운영 담당자 결과 확인
↓
[승인]
↓

```

여기서 **승인**은 실제 게임 서버 반영이 아니라 내부 기획안 확정을 의미합니다.

MVP에서는 사용자가 입력하는 `event_name / target_user / duration / objective` 4개 필드를 **Event Brief 역할**로 사용합니다. 별도의 복잡한 Brief 객체는 추가하지 않으며, Event Planner는 입력된 대상·기간·목적을 임의로 변경하지 않습니다. Mock 성장 기준이 Day 1~7까지 정의되어 있으므로 **MVP 이벤트 기간은 1~7일로 제한**합니다.

## 2-3. 이벤트 기획 오류 시나리오

AI가 항상 완벽한 이벤트를 만든다고 가정하지 않습니다.

예를 들어 Event Planner가 다음과 같이 생성할 수 있습니다.

```
Day 7
레이드 보스 1회 처치
보상: 한정 코스튬
```

하지만 Opong Heroes의 신규 유저 Day 7 예상 레벨은 15이고 레이드 입장 조건은 레벨 30입니다.

```
Event Planner
Day 7 레이드 미션 생성
↓
Balance & Rule
게임 규칙 조회
↓
신규 유저 예상 Lv.15
레이드 필요 Lv.30
↓
mission_unreachable 감지
↓
Critic
RETRY
↓
Supervisor
Event Planner 재호출
↓
Event Planner
Day 7 미션을 던전 3회 완료로 수정
↓
Balance & Rule 재검증
↓
Critic PASS
↓
운영 담당자 승인 대기
```

즉, 잘못된 이벤트를 단순히 실패 처리하는 것이 아니라 **문제를 발견하고 수정 가능한 Agent를 다시 호출해 자동 복구**합니다.

## 2-4. 시스템 장애 시나리오

이벤트 내용이 정상이어도 Agent, Tool, DB와 같은 실행 과정에서 장애가 발생할 수 있습니다.

### Tool 단위 장애

Primary Tool만 실패하고 MCP Server는 살아 있는 경우에는 다른 Tool로 우회합니다.

```
Balance & Rule
↓
Tool 1 get_game_rules 호출
↓
Tool Exception / 잘못된 결과
↓
mcp_tool_error
↓
Tool 2 get_game_rules_fallback
↓
마지막 검증된 게임 규칙 Snapshot 조회
↓
Tool Result Validation PASS
↓
Workflow 계속
```

### MCP 통신 장애

MCP 응답이 Timeout 나는 경우에는 Supervisor가 기술 Retry를 처리합니다.

```
Balance & Rule
↓
MCP Tool 호출
↓
MCP Timeout
↓
mcp_timeout 기록
↓
Supervisor
retry_count = 1
↓
MCP Tool 재호출
├ 정상 응답 → Workflow 계속
└ 계속 실패
   ↓
   최대 Retry까지 반복
   ↓
   Safe Stop
   ↓
   workflow_status = FAILED
   ↓
   운영 담당자에게 실패 원인과 Trace 표시
```

AutoHealing의 목표는 무조건 성공시키는 것이 아니라 **복구 가능한 오류는 Retry 또는 Fallback으로 복구하고, 복구할 수 없는 오류는 안전하게 중단해 사람이 확인할 수 있도록 하는 것**입니다.

### MVP Recovery Contract

- **복구 기준점은 마지막으로 Validation을 통과해 정상으로 확정된 입력·결과**로 정의합니다.
- Validation을 통과하지 않은 부분 결과는 복구 시 재사용하지 않습니다.
- 기술 오류는 **현재 동기식 API 요청 안에서만** 정해진 Retry를 수행하며, 마지막 정상 검증 결과는 유지하고 **실패한 Agent / Tool / DB 작업부터 다시 실행**합니다.
- 실패 단계 재실행 또는 재연결이 성공하고, 해당 결과 Validation을 통과한 뒤 다음 정상 단계로 이동해야 복구 성공으로 봅니다.
- 기획 오류(`mission_unreachable`, `item_not_found`, `event_brief_mismatch`)는 **원래 Event Brief를 기준점으로 Event Planner가 수정**하고, `EventPlanResult Validation → Balance & Rule → RuleValidationResult Validation → Critic`까지 전체 재검증합니다.
- MCP Server 중단처럼 Retry 안에서 복구되지 않는 장애는 `FAILED`로 종료합니다. 운영자가 서비스를 복구한 뒤에는 **기존 task를 이어서 실행하지 않고 새 요청·새 task_id로 Workflow를 다시 시작**합니다.

## 2-5. 운영자 피드백 및 수정 요청 시나리오

Critic이 PASS를 반환해도 운영 담당자가 최종 결과를 그대로 사용할 필요는 없습니다. **AutoHealing이 시스템·기획 오류를 자동 수정하는 것과 별개로, 운영 담당자는 운영 방향에 대한 피드백을 직접 입력할 수 있습니다.**

```
Critic PASS
↓
approval_status = PENDING
workflow_status = WAITING_APPROVAL
current_result 표시
↓
운영 담당자 검토
├ [승인]
│  → COMPLETED
└ [운영자 피드백 / 수정 요청]
   "Day 1~3 미션을 전투보다 성장 중심으로 바꿔주세요"
   ↓
   approval_status = REVISION_REQUESTED
   workflow_status = RUNNING
   ↓
   approval_comment 저장
   Trace action = human_revision
   ↓
   Event Planner 재실행
   ↓
   EventPlanResult Validation
   ↓
   Balance & Rule 재검증
   ↓
   RuleValidationResult Validation
   ↓
   Critic 재검수
   ↓
   PASS
   ↓
   새 current_result 저장
   result_version + 1
   approval_status = PENDING
   workflow_status = WAITING_APPROVAL
   ↓
   다시 승인 대기
```

운영자 피드백은 AI가 오류를 발견해 자동 수정하는 AutoHealing과 구분합니다. 따라서 `revision_count`를 증가시키지 않고 `human_revision` Trace로 기록하며, 수정된 결과도 반드시 동일한 전체 검증 절차를 다시 거칩니다.

## 2-6. Test Mode 시나리오

실제 운영 화면에서는 일부러 장애를 만들지 않습니다.

하지만 개발·QA·발표 시에는 AutoHealing이 실제로 동작하는지 증명하기 위해 **Test Mode에서 장애를 의도적으로 주입**합니다.

```
Test Mode ON
↓
장애 유형 선택
├ 달성 불가능 미션
├ Agent 1회 실패
├ Primary Tool 1회 실패
├ MCP 1회 Timeout
├ DB 1회 연결 실패
├ Validation 1회 실패
└ Retry 한도 초과
↓
장애 발생
↓
감지
↓
Retry / Tool Fallback / 재연결
↓
복구 성공 또는 Safe Stop
↓
Trace에서 전체 과정 확인
```

따라서 이 프로젝트의 핵심 서비스 흐름은 다음과 같습니다.

**이벤트 생성 → 오류·장애 감지 → 자동복구 → 재검증 → 사람 승인 또는 Safe Stop(FAILED)**

# 3. 멀티에이전트 구성

이번 프로젝트에서는 총 **4개의 Agent 역할**을 사용합니다.

```
1. Supervisor Orchestrator
2. Event Planner Agent
3. Balance & Rule Agent
4. Critic Agent
```

## 3-1. Supervisor Orchestrator

### 한마디로

**전체 Workflow와 실행 경로를 관리하는 중앙 조정자**

이번 프로젝트에서는 Supervisor를 별도의 LLM 판단 Agent로 복잡하게 만들지 않고, **Backend의 Python 규칙 기반 Orchestrator**로 구현합니다.

### 하는 일

- 사용자의 요청을 받음
- 현재 Workflow State 확인
- `routing.py` 규칙에 따라 다음 Agent 결정
- Agent 결과를 다음 Agent에게 Handoff
- 오류 유형에 따라 재실행 경로 결정
- `retry.py`에서 Retry 횟수 관리
- Critic의 판정을 기준으로 Workflow 계속·종료 결정
- 시스템 장애 발생 시 복구 정책 실행
- 전체 Trace 기록

### 하지 않는 일

- 이벤트의 세부 미션과 보상을 직접 기획하지 않음
- 게임 규칙을 직접 검수하지 않음
- Critic 대신 품질 판정을 만들지 않음
- LLM에게 자유롭게 다음 Agent를 선택하게 하지 않음

<aside>
💡

**책임 구분**

Critic Agent는 결과를 검수해 `PASS / RETRY / FAIL` 판정을 반환합니다.

Supervisor Orchestrator는 그 판정과 `error_type`, Retry 횟수를 Python Routing 규칙에 적용해 실제 다음 실행 경로를 결정합니다.

</aside>

## 3-2. Event Planner Agent

### 한마디로

**게임 이벤트를 실제로 기획하고 수정하는 담당자**

### 하는 일

- 사용자가 입력한 이벤트 목적을 반영
- 입력된 이벤트 대상(`target_user`) 유지
- 입력된 이벤트 기간(`duration`) 유지
- 날짜별 미션 생성
- 미션별 보상 생성
- 최종 보상 구성
- RETRY 요청이 오면 오류 원인을 반영해 문제가 된 부분 수정

MVP에서는 `ITEM_001~003`처럼 게임 데이터에 존재하는 아이템 보상을 사용합니다. 이벤트 재화 설계·검증은 MVP 이후 확장 범위로 둡니다.

### 예시

| 날짜 | 미션 | 보상 |
| --- | --- | --- |
| Day 1 | 로그인 | 회복 포션 1개 (ITEM_001) |
| Day 2 | 몬스터 10마리 처치 | 회복 포션 2개 (ITEM_001) |
| Day 3 | 던전 3회 완료 | 성장 상자 1개 (ITEM_002) |
| Day 7 | 레이드 보스 1회 처치 | 한정 코스튬 1개 (ITEM_003) |

이 단계에서는 이벤트 초안을 만드는 것이 핵심이며, 실제 게임 규칙상 가능한지는 다음 검증 단계에서 확인합니다.

## 3-3. Balance & Rule Agent

### 한마디로

**게임 데이터와 규칙을 기준으로 사실 검증을 수행하는 담당자**

### MVP 검증 범위

- `content_id` 기준 콘텐츠 존재·입장 레벨 확인
- 대상별 예상 레벨 기준 콘텐츠 접근 가능 여부
- 이벤트 기간과 Mission Day 범위(`1\~duration`) 정합성
- 보상 `item_id` 존재 여부

### MVP에서 검증하지 않는 항목

- `target_count` 난이도 적절성·일일 플레이 한도
- `mission_type`별 실제 게임 행동 로그·완료 조건
- 신규/복귀 유저의 실제 자격 판정(운영 담당자가 `target_user`를 선택)
- 보상 수량·경제 밸런스·이벤트 재화·상점 가격

### 역할 경계

Balance & Rule Agent는 **게임 데이터 기준의 사실 검증**에 집중합니다. 전체 결과의 최종 승인 여부는 Critic Agent가 판단합니다.

MVP에서는 현재 준비된 테스트 데이터로 확인 가능한 **레벨·기간·아이템·Mission Day 범위 정합성**을 우선 검증하고, 보상 밸런스·이벤트 재화 검증은 관련 데이터가 추가된 이후 확장합니다.

### RuleValidationResult 원칙

```
is_valid = true
→ error_type = null

is_valid = false
→ error_type 필수
→ reason / evidence 필수
```

### 예시

| 콘텐츠 | 입장 조건 |
| --- | --- |
| 일반 사냥 | 레벨 1 |
| 던전 | 레벨 10 |
| 레이드 | 레벨 30 |

신규 유저의 Day 7 예상 레벨이 15인데 Day 7 미션이 레이드 보스 처치라면 다음과 같이 오류를 반환합니다.

```
error_type: mission_unreachable

reason:
신규 유저 예상 레벨 15
레이드 필요 레벨 30
→ 이벤트 기간 안에 수행하기 어려움
```

## 3-4. Critic Agent

### 한마디로

**전체 결과의 품질을 최종 검수하고 판정을 반환하는 담당자**

### 확인 내용

- 원래 Event Brief의 `target_user`와 `duration`이 그대로 유지되었는가?
- 원래 Event Brief의 `objective`와 이벤트 구성 방향이 일치하는가?
- Balance & Rule Agent가 발견한 문제가 해결되었는가?
- 이전 RETRY 사유가 실제로 수정되었는가?
- Agent 결과 간 모순이 없는가?

Critic은 원래 요청과 비교할 수 있도록 `user_request`와 현재 `event_plan`, `validation_result`를 함께 전달받습니다. 대상·기간·목적 불일치를 발견해 수정 가능한 경우 `event_brief_mismatch`로 RETRY를 반환합니다.

필수 필드 누락, 타입, 출력 형식은 Critic이 아니라 **Backend의 Output Validation**에서 확인합니다.

### 판정

```
PASS
→ 검수 통과

RETRY
→ 수정하면 해결 가능한 문제

FAIL
→ 현재 결과를 자동 수정 대상으로 보기 어렵거나 품질 기준을 충족하지 못한 상태
```

Critic Agent는 이벤트를 직접 수정하거나 다음 Agent를 지정하지 않고 **판정, 오류 유형, 근거만 반환**합니다.

재시도 횟수와 실제 다음 실행 경로는 Supervisor Orchestrator가 결정합니다.

### Critic 결과 Contract 원칙

```
PASS
→ error_type = null
→ reason 필수

RETRY
→ error_type 필수
→ reason 필수

FAIL
→ error_type은 null 허용
→ reason 필수
```

기술·실행 장애는 Critic의 RETRY 판정 대상이 아닙니다. Agent 실행 실패, Validation 오류, MCP/DB/LLM 장애는 Critic으로 보내지 않고 Supervisor가 직접 복구합니다.

# 4. 전체 Workflow

```

- Tool Result Validation

- 실제 검증에 사용한 game_data_version / data_source 기록

↓

│     → END
│
```

# 6. Agent 협업 설계

## 6-1. Workflow State

각 Agent가 작업할 때마다 전체 정보를 새로 만들지 않고, 하나의 공통 상태인 `Workflow State`를 기준으로 작업 상황을 관리합니다.

Supervisor Orchestrator는 Workflow State를 확인해 현재 단계, 오류, 재시도 횟수, 이전 결과를 파악하고 다음 Agent를 결정합니다.

| 항목 | 설명 |
| --- | --- |
| task_id | 전체 작업을 구분하는 고유 ID |
| user_request | 사용자 요청 |
| event_plan | Event Planner의 이벤트 결과 |
| validation_result | Balance & Rule 검증 결과 |
| error_type | 발생한 오류 종류 |
| error_reason | 오류 원인 |
| failed_tool | MCP Tool 오류가 발생한 경우 실패한 Tool 이름. get_game_rules / get_game_rules_fallback / get_item_info |
| critic_status | PASS / RETRY / FAIL |
| workflow_status | RUNNING / RETRYING / WAITING_APPROVAL / COMPLETED / FAILED / CANCELLED |
| attempt | 현재 Agent의 전체 실행 횟수 |
| revision_count | AutoHealing이 기획 오류를 감지해 Event Planner를 자동 수정한 횟수. Human 수정 요청은 포함하지 않음 |
| max_revisions | 허용 가능한 최대 기획 수정 횟수 |
| retry_count | 현재 기술 장애에 대한 연속 재시도 횟수. 복구 성공 시 0으로 초기화 |
| max_retries | 허용 가능한 최대 기술 재시도 횟수 |
| current_agent | 현재 실행 중인 Agent |
| trace | Agent 실행 및 오류 이력 |
| approval_status | PENDING / APPROVED / REVISION_REQUESTED / REJECTED |
| approval_comment | 담당자의 승인 또는 수정 요청 의견 |
| result_version | 현재 이벤트 결과 버전. 새 current_result가 생성될 때 증가하며 승인 시 화면 버전과 서버 버전을 비교 |
| current_result | 현재 검토 중인 이벤트 결과. Critic PASS 후 Human Approval 대상으로 표시 |
| final_result | APPROVE 이후 current_result를 복사해 저장하는 최종 확정 결과 |

### 상태 관리 원칙

Workflow를 처음 생성할 때는 다음 초기값을 사용합니다.

```
workflow_status = RUNNING
critic_status = null
approval_status = null
result_version = 0
current_result = null
final_result = null
revision_count = 0
retry_count = 0
```

첫 Critic PASS 결과가 승인 후보로 저장되면 `current_result`가 생성되고 `result_version = 1`이 됩니다.

- 모든 작업에 `task_id`를 부여합니다.
- Agent 실행 시 결과와 현재 상태를 업데이트합니다.
- AutoHealing이 기획 오류를 감지해 자동 수정한 횟수는 `revision_count`, Agent·MCP·DB 등 기술 장애 재시도는 `retry_count`로 분리해 기록합니다.
- 담당자의 REQUEST_REVISION은 Human Revision이므로 `revision_count`에는 포함하지 않습니다.
- RETRY 시 이전 실패 원인과 수정 지시를 다음 Agent에 함께 전달합니다.
- Critic PASS 시 `critic_status = PASS`, `approval_status = PENDING`, `workflow_status = WAITING_APPROVAL`로 전환하며 `current_result`는 승인 대기 상태이고 아직 END가 아닙니다.
- 담당자가 승인하면 `final_result = current_result`로 확정하고 `approval_status = APPROVED`, `workflow_status = COMPLETED`로 변경한 뒤 END 처리합니다.
- 담당자가 REJECT를 선택하면 `approval_status = REJECTED`, `workflow_status = CANCELLED`로 변경해 사용자 취소 종료와 시스템 실패를 구분합니다.
- 승인 요청은 Backend가 `WAITING_APPROVAL` 상태인지, 승인 가능한 담당자인지, 사용자가 확인한 `result_version`이 현재 결과와 같은지 다시 검증합니다.
- 수정 후 결과 버전이 바뀌었는데 이전 화면에서 승인한 경우에는 승인하지 않고 최신 결과를 다시 확인하도록 합니다.
- 담당자가 REQUEST_REVISION을 선택하면 `approval_status = REVISION_REQUESTED`, `workflow_status = RUNNING`, `critic_status = null`로 바꾸고 `approval_comment`를 Event Planner에 전달합니다. 이전 PASS 상태를 새 수정안에 재사용하지 않습니다.
- Human 수정 요청은 `revision_count`를 증가시키지 않고 Trace의 `human_revision`으로 구분합니다. 수정안이 전체 재검증을 거쳐 Critic PASS가 되었을 때 새 `current_result`를 저장하고 `result_version`만 증가합니다.
- `retry_count`는 Workflow 전체 누적값이 아니라 **현재 기술 장애에 대한 연속 재시도 횟수**입니다. Retry가 시작되면 `workflow_status = RETRYING`, `retry_count`를 1씩 증가시키고, 재실행·재연결에 성공하면 `workflow_status = RUNNING`, `retry_count = 0`으로 초기화합니다.
- Workflow 전체 Retry 통계는 State의 누적값이 아니라 Trace의 `RETRY` action 기록을 집계합니다.
- Tool Fallback은 Retry가 아니므로 `workflow_status = RUNNING`을 유지하고 `retry_count`도 증가시키지 않습니다.
- API Key, 비밀번호와 같은 민감정보는 Workflow State와 Trace에 기록하지 않습니다.

## 6-2. Handoff

이번 프로젝트의 Handoff는 단순 결과 전달뿐 아니라 **현재 작업의 책임 소유권을 다음 Agent에게 넘기는 과정**으로 정의합니다.

### 주요 전달 정보

```
task_id
from_agent / to_agent
owner_agent
handoff_status
objective
inputs
expected_output
revision_count
retry_count
error_context
```

`handoff_status`는 `REQUESTED / ACCEPTED / REJECTED`를 사용합니다. 다음 Agent가 필요한 입력을 정상적으로 받았을 때만 `ACCEPTED`로 처리하고 `owner_agent`를 변경합니다. Handoff가 거절되면 책임 소유권은 이전되지 않으며 Supervisor가 이전 책임자 또는 안전한 복구 경로를 선택합니다.

오류가 발생한 경우에는 `error_type`, `error_reason`, 이전 검증 결과를 함께 전달해 같은 오류가 반복되지 않도록 합니다.

Critic PASS 이후 담당자가 `수정 요청`을 선택한 경우에는 `approval_comment`와 현재 이벤트 결과를 Event Planner에 전달해 사람의 피드백을 반영한 뒤 다시 검증합니다.

📌

상세 Handoff JSON Schema와 필드 검증 규칙은 하위 **개발 기획안**에서 정의합니다.

</aside>

## 6-3. Routing

Routing은 Supervisor Orchestrator가 현재 상태와 오류 종류를 보고 다음 실행 대상을 정하는 과정입니다.

```
처음 요청
→ Event Planner

이벤트 사실 검증
→ Balance & Rule

전체 최종 검수
→ Critic

mission_unreachable
→ revision_count + 1
→ Event Planner 재호출

item_not_found
→ revision_count + 1
→ Event Planner 재호출

event_brief_mismatch
→ revision_count + 1
→ Event Planner 재호출

validation_error
→ workflow_status = RETRYING
→ retry_count + 1
→ 오류를 만든 Agent 재호출
→ 성공 시 workflow_status = RUNNING

agent_failure
→ workflow_status = RETRYING
→ retry_count + 1
→ 동일 Agent 재시도
→ 성공 시 workflow_status = RUNNING

mcp_tool_error
→ failed_tool 확인
├ get_game_rules → get_game_rules_fallback → 성공 시 retry_count 증가 없이 계속
├ get_item_info → retry_count + 1 → get_item_info 동일 Tool 재시도
└ get_game_rules_fallback → Safe Stop

mcp_timeout
→ workflow_status = RETRYING
→ retry_count + 1
→ MCP Tool 재시도
→ 성공 시 workflow_status = RUNNING

db_connection_error
→ workflow_status = RETRYING
→ retry_count + 1
→ DB 재연결 후 재시도
→ 성공 시 workflow_status = RUNNING

기획 오류에서 revision_count >= max_revisions
→ Safe Stop → FAILED

기술 장애에서 retry_count >= max_retries
→ Safe Stop → FAILED
```

기술 Retry가 성공하면 `retry_count = 0`으로 초기화합니다. 전체 Retry 횟수 통계는 Trace의 `RETRY` action을 집계합니다.

## 6-4. Validation

Validation은 **사용자 입력, Agent 결과, Tool 결과가 다음 단계에서 사용할 수 있는 정상적인 형태와 값인지 확인하는 과정**입니다.

Input Guard의 금지 문구 검사는 보조 수단이며, 숫자 범위·허용 값·필수 값처럼 정답이 명확한 조건은 Backend의 Python / Pydantic Schema로 결정적으로 검증합니다.

이번 프로젝트에서는 다음 4가지를 중심으로 검증합니다.

1. **Input Schema Validation**
    - duration 허용 범위
    - target_user 허용 값
    - objective 필수 여부
    - 승인 요청의 action / result_version 형식
    - approval_comment 길이와 형식
2. **Output Validation**
    - Agent별 Output Contract
    - 필수 필드와 허용 값 확인
3. **Handoff Validation**
    - task_id, 전달 대상, 필요한 입력값 확인
4. **Tool Result Validation**
    - MCP Tool 응답의 필수 데이터와 형식 확인
    - MCP 결과도 외부에서 들어오는 신뢰하지 않는 데이터로 취급

```
Validation 실패
├ 사용자 Input Schema
│  → Fail Fast
│  → Agent 실행 전 차단
│
├ Agent Output / Handoff
│  → validation_error
│  → retry_count + 1
│  → 결과를 만든 Agent 재호출
│
├ MCP Tool Result
│  → mcp_tool_error
│  → failed_tool 기준 Fallback 또는 동일 Tool Retry
│
└ Approval Validation
   → policy DENY
   → 상태 변경 없음
```

Validation 실패 결과는 다음 단계로 그대로 전달하지 않습니다.

`approval_comment`도 LLM에 전달되기 전에 길이·형식을 검증하고 Input Guard를 거칩니다.

<aside>
📌

Pydantic Schema, 상세 필드, 코드 구현 방식은 하위 **개발 기획안**에서 정의합니다.

</aside>

## 6-5. Guard

Guard는 **허용되지 않은 입력·Tool 호출·응답을 실행 전후에 제한하는 규칙**입니다.

학원에서 배운 구조를 유지하면서 구현 난이도를 낮추기 위해 독립 Guard는 3개만 사용합니다.

```
1. Input Guard
   - 입력 길이 제한
   - blocked_phrases 검사

2. Tool Guard
   - Agent별 allowed_tools 확인

3. Response Guard
   - 금지 응답 문구 확인
   - 민감정보 노출 확인
```

Routing과 Retry는 별도 Guard로 만들지 않고 **Supervisor Orchestrator가 관리**합니다.

Agent별 Context 접근 범위는 `security_policies.yaml`의 `context_access` 정책을 사용해 필요한 정보만 전달합니다.

### 보안 정책 파일

```
security_policies.yaml
├ input
├ response
└ context_access
```

<aside>
✅

상위 기획안에서는 Guard의 목적과 범위만 설명하고, security_policies.yaml 예시와 실제 코드 구조는 하위 [**개발 기획안**](https://app.notion.com/p/3f181f168976803581dbf5ff867e2125?pvs=21)에서 관리합니다.

## 6-6. Trace

Trace에는 어떤 Agent가 언제 실행되었고 어떤 결과·Validation 오류·Guard 차단을 발생시켰는지 기록합니다.

```
TASK-001

1. Supervisor
→ Event Planner 선택

2. Event Planner
→ 이벤트 생성 완료

3. Validation
→ EventPlanResult PASS

4. Balance & Rule
→ mission_unreachable 발견

5. Critic
→ RETRY

6. Supervisor
→ revision_count = 1
→ Event Planner 재호출

7. Event Planner
→ 미션 수정

8. Validation
→ EventPlanResult PASS

9. Balance & Rule
→ 검증 통과

10. Critic
→ PASS

11. Supervisor
→ workflow_status = WAITING_APPROVAL
→ approval_status = PENDING

12. 담당자
→ APPROVE

13. Supervisor
→ workflow_status = COMPLETED
→ 최종 결과 확정
```

Guard 차단이 발생한 경우도 동일한 Trace에 기록합니다.

예:

```
Guard
→ critic_agent가 허용되지 않은 Tool 호출 시도
→ tool_guard_error
→ 실행 차단
```

이 기록은 Agent 실행 흐름, Validation 결과, Guard 차단 내역, 장애 복구 결과와 복구 시간을 확인하는 증빙으로 사용합니다.

### 보안·승인·Tool Fallback Trace

승인·정책 판단 또는 Tool Fallback이 발생한 경우에는 다음 항목도 Trace에 남깁니다.

```
actor_id
policy_decision
reason_code
result_version
tool_name
failed_tool
fallback_tool
data_source
game_data_version
```

승인 예:

```
action = APPROVE
actor_id = liveops01
policy_decision = DENY
reason_code = STALE_RESULT_VERSION
result_version = 2
```

Tool Fallback 예:

```
action = TOOL_FALLBACK
failed_tool = get_game_rules
fallback_tool = get_game_rules_fallback
data_source = fallback_snapshot
game_data_version = tinyheroes-1.0.0
status = SUCCESS
```

비밀번호, API Key, 전체 Prompt 원문과 같은 민감정보는 Trace에 기록하지 않습니다.

# 7. AutoHealing 설계

이번 프로젝트의 AutoHealing은 **이벤트 내용 오류**와 **시스템 실행 장애** 두 종류로 구분합니다.

## 7-1. 이벤트 기획 오류 AutoHealing

### 주요 오류

- 신규 유저가 달성하기 어려운 미션
- 이벤트 종료 이후에 열리는 미션
- 게임에 존재하지 않는 아이템

### 추가 확장 가능 오류

- 보상량 불균형
- 이벤트 재화와 상점 가격 불균형

### 대표 예시

```
Event Planner
Day 7 레이드 보스 처치 생성
↓
Balance & Rule
신규 유저 예상 레벨 15
레이드 필요 레벨 30
→ mission_unreachable
↓
Critic
RETRY
↓
Supervisor
Event Planner 재호출
↓
Event Planner
던전 3회 완료로 수정
↓
Balance & Rule 재검증
↓
Critic PASS
```

## 7-2. 시스템 장애 AutoHealing

| 장애 유형 | 감지 | 최소 구현 복구 | 추가 확장 | 최종 처리 |
| --- | --- | --- | --- | --- |
| Agent 응답 실패 | Exception / 응답 없음 | 동일 Agent 재시도 | 프롬프트 단순화 | 재시도 한도 초과 시 FAIL |
| LLM Timeout | 지정 시간 초과 | LLM 재호출 | 대체 모델 호출 | 재시도 한도 초과 시 FAIL |
| MCP Primary Tool 실행 실패 | Tool Exception / 잘못된 응답 | Fallback Tool 호출 | 마지막 검증된 게임 규칙 Snapshot 사용 | Fallback도 실패하면 FAIL |
| MCP Tool Timeout | Tool 응답 시간 초과 | Supervisor Retry | 서버 상태 확인 후 재호출 | 재시도 한도 초과 시 FAIL |
| DB 일시 연결 실패 | ConnectionError | DB 재연결 후 재시도 | 임시 상태 보존 | FAIL 및 오류 기록 |
| Validation 실패 | 필수 필드 누락 | 생성 Agent 재호출 | 오류 내용을 포함한 수정 프롬프트 | FAIL |

<aside>
⚠️

**구현 범위 원칙**

기본 구현 범위는 Agent 실패, LLM/MCP Timeout, DB 일시 오류, Validation 실패에 대한 Retry·재연결·재호출입니다. LLM API 429/5xx, 대체 모델, 캐시 폴백 등은 실제 구현이 완료된 경우에만 확장 기능으로 기록합니다.

</aside>

## 7-3. 수정·Retry 및 종료 정책

이벤트 내용 수정과 기술 장애 Retry를 같은 횟수로 계산하지 않습니다.

기본값:

```
max_revisions = 2
max_retries = 3
```

### 이벤트 내용 오류

```
mission_unreachable / item_not_found / event_brief_mismatch
↓
revision_count < max_revisions ?
├ YES → revision_count + 1 → Event Planner 수정 → 재검증
└ NO → Safe Stop → workflow_status = FAILED
```

### Tool 오류 처리

```
mcp_tool_error
↓
failed_tool 확인

├ failed_tool = get_game_rules
│  → get_game_rules_fallback 호출
│  → 성공 시 Tool Result Validation
│  → retry_count 증가 없이 Workflow 계속
│  → Fallback도 실패하면 Safe Stop → FAILED
│
├ failed_tool = get_item_info
│  → retry_count + 1
│  → get_item_info 동일 Tool Retry
│  → max_retries 초과 시 Safe Stop → FAILED
│
└ failed_tool = get_game_rules_fallback
   → 대체 Tool 없음
   → Safe Stop → FAILED
```

Primary → Fallback 전환은 같은 Tool을 다시 시도하는 Retry가 아니므로 `retry_count`를 증가시키지 않습니다.

### 기술·실행 장애

```
Agent / MCP Server / DB / LLM / Output Validation 일시 장애
↓
retry_count < max_retries ?
├ YES → retry_count + 1 → 재호출 / 재연결 → 결과 Validation
└ NO → Safe Stop → FAILED
```

복구 성공은 단순히 재호출이 끝난 상태가 아니라 **재호출 또는 Fallback 성공 + 해당 결과 Validation 통과 + Workflow가 다음 단계로 정상 진행된 경우**로 정의합니다.

`attempt`는 Agent 실행 횟수, `revision_count`는 기획 수정 횟수, `retry_count`는 같은 Agent·Tool·연결을 다시 시도한 기술 장애 재시도 횟수로 구분합니다.

## 7-4. Human Approval

AutoHealing이 성공해 Critic이 PASS를 반환하더라도 바로 최종 확정하지 않습니다.

```
Critic PASS
↓
current_result 저장
approval_status = PENDING
workflow_status = WAITING_APPROVAL
↓
담당자 결과 확인
├ APPROVE
│  → final_result = current_result
│  → approval_status = APPROVED
│  → workflow_status = COMPLETED
│
├ REQUEST_REVISION
│  → approval_status = REVISION_REQUESTED
│  → workflow_status = RUNNING
│  → critic_status = null
│  → approval_comment 저장
│  → Trace action = human_revision
│  → Event Planner 재실행
│  → 수정된 event_plan 전체 재검증
│  → Critic PASS 시 새 current_result 저장 + result_version + 1
│  → PENDING / WAITING_APPROVAL 복귀
│
└ REJECT
   → approval_status = REJECTED
   → workflow_status = CANCELLED
```

Human 수정 요청은 `revision_count`를 증가시키지 않습니다. 자동복구는 시스템이 수행하되 **최종 사용 여부는 사람이 결정하는 Human-in-the-Loop 구조**로 설계합니다.

## 7-5. Fault Injection Mode

이 프로젝트는 정상 실행만 보여주는 것이 아니라 **일부러 장애를 발생시켜 AutoHealing 동작을 확인하는 것**이 핵심입니다.

개발·시연 모드에서는 다음 오류를 선택적으로 주입할 수 있게 합니다.

```
mission_unreachable_once
agent_failure_once
primary_tool_error_once
mcp_timeout_once
db_connection_error_once
validation_error_once
retry_limit_exceeded
```

`*_once` 장애는 최초 한 번만 발생시킵니다.

- `mission_unreachable_once`는 첫 Planner 결과에만 달성 불가능 미션을 강제로 넣고, Planner가 재실행될 때는 다시 주입하지 않아 자동 수정이 가능하게 합니다.
- `agent_failure_once`, `mcp_timeout_once`, `db_connection_error_once`, `validation_error_once`는 다음 Retry에서 정상화됩니다.
- `primary_tool_error_once`는 Primary Tool만 1회 실패시키고, Retry하지 않고 `get_game_rules_fallback`으로 전환해 Tool Fallback을 검증합니다.

`retry_limit_exceeded`는 계속 실패하도록 만들어 최대 Retry 이후 Safe Stop으로 종료되는 흐름을 검증합니다.

## 7-6. 실제 MCP 서비스 장애 시나리오

Fault Injection만으로 끝내지 않고 실제 MCP Server 중단도 1회 검증합니다.

이번 MVP는 Queue / Worker나 실행 중 task 재개 기능을 만들지 않습니다. 따라서 MCP Server가 Retry 안에서 복구되지 않으면 해당 Workflow를 안전하게 종료합니다.

```
이벤트 검증 실행
↓
Balance & Rule이 MCP Tool 호출
↓
MCP Server 컨테이너 중단
↓
연결 실패 감지
↓
동기 요청 안에서 retry_count 증가
↓
max_retries 초과
↓
Safe Stop / workflow_status = FAILED
↓
운영자 / 발표자가 MCP Server 재시작
↓
/health/ready 정상 확인
↓
새 이벤트 생성 요청
↓
새 task_id로 정상 Workflow 실행
```

이 시나리오는 **같은 Workflow를 이어서 재개하는 방식이 아니라, 장애 시 안전 종료한 뒤 서비스 복구 후 새 Workflow로 다시 실행하는 운영 복구 방식**이며 자동복구율 계산에서는 별도 관리합니다.

## 7-7. Partial Failure / Safe Stop 정책

학원에서 배운 Partial Failure 정책을 다음처럼 적용합니다.

```
Required
- Event Planner
- Balance & Rule
- Critic
→ 핵심 Agent이므로 최종적으로 복구되지 않으면 Workflow 완료 불가

Fail Fast
- Input Schema 위반
- Input / Tool Guard 정책 위반
- 승인 권한·result_version 검증 실패
→ 동일 요청을 자동 Retry하지 않고 즉시 차단

Tool Fallback
- get_game_rules가 Tool Exception 또는 잘못된 Tool Result로 `mcp_tool_error`가 발생한 경우
→ get_game_rules_fallback 호출
→ 성공 시 Validation 후 Workflow 계속
→ retry_count 증가 없음
- mcp_timeout / MCP 연결 실패는 Fallback이 아니라 동기 요청 안에서 Retry하고, 한도 초과 시 FAILED로 종료

Retry
- get_item_info 실패
- Agent 일시 실패
- LLM / MCP Timeout
- DB 일시 연결 실패
- 복구 가능한 Output Validation 실패

Safe Stop
- Fallback Tool도 실패
- max_retries / max_revisions 초과
→ 마지막 정상 상태와 Trace 보존
→ 검증되지 않은 결과는 final_result로 확정하지 않음
→ workflow_status = FAILED
→ 운영자 수동 확인
```

이번 MVP에서는 일부 Agent 실패 결과만으로 이벤트를 확정하는 **Best Effort 방식은 사용하지 않습니다.**

# 8. MCP / Tool 구성

MCP Server는 구현 부담을 줄이기 위해 **1개, Tool 3개**로 구성합니다.

### MCP Server

```
game_mcp_server
```

### Tool 1. get_game_rules — Primary Tool

현재 Opong Heroes 게임 규칙을 `content_id` 기준으로 조회하는 기본 Tool입니다.

```
content_id = RAID_001 조회
→ 콘텐츠명: 레이드
→ 필요 레벨: 30
```

Event Planner의 `content_id`를 그대로 Tool 입력에 사용하며 별도의 `content_name` 변환 규칙은 두지 않습니다.

### Tool 2. get_game_rules_fallback — Fallback Tool

Tool 1이 Tool 단위 오류로 실행되지 않거나 결과 Validation에 실패한 경우 사용하는 대체 Tool입니다.

```
get_game_rules
↓
Tool Exception 또는 Tool Result Validation 실패
↓
mcp_tool_error
↓
get_game_rules_fallback
↓
마지막 검증된 게임 규칙 Snapshot 조회
```

Fallback Tool은 Primary Tool과 같은 목적의 데이터를 다른 조회 경로로 제공합니다. **MCP Server 자체가 중단된 경우에는 같은 서버의 Tool 1·2를 모두 사용할 수 없으므로 동기 요청 안에서 Retry하고, 한도 초과 시 FAILED로 종료합니다. MCP 복구 후에는 새 요청·새 task_id로 다시 실행합니다.**

### Tool 3. get_item_info

아이템 ID가 실제 게임 데이터에 존재하는지 조회합니다.

```
ITEM_003 조회
→ 한정 코스튬
```

이벤트 기간과 미션 날짜 범위는 별도 MCP Tool로 판단하지 않고 EventPlanResult와 Backend Python Rule Engine에서 결정적으로 검증합니다.

### Tool 오류 / Fallback 정책

```
Balance & Rule
↓
Tool Guard
↓
Tool 실행
↓
mcp_tool_error 발생?
├ NO → Tool Result Validation
└ YES
   ↓
   failed_tool 확인
   ├ get_game_rules
   │  → Tool 2 get_game_rules_fallback
   │  ├ 정상 → Tool Result Validation → Python Rule Engine
   │  └ 실패 → Safe Stop → FAILED
   │
   └ get_item_info
      → retry_count + 1
      → get_item_info Retry
      └ max_retries 초과 → Safe Stop → FAILED
```

### 게임 규칙 최종 판정 원칙

MCP Tool은 게임 데이터를 조회하고, **레벨 비교·아이템 존재 여부·이벤트 기간 범위처럼 정답이 명확한 사실 판정은 Backend Python 규칙으로 최종 결정**합니다.

```
Primary 또는 Fallback MCP Tool
↓
게임 데이터 조회
↓
Tool Result Validation
↓
Python Rule Engine
├ 예상 레벨 >= 콘텐츠 입장 레벨
├ item_id 존재 여부
└ 1 <= mission day <= 이벤트 기간
↓
결정적 판정
↓
Balance & Rule Agent가 결과 설명
```

LLM의 판단이 Python 규칙 결과와 충돌하면 Python 판정을 우선합니다.

Event Planner가 만드는 `EventPlanResult`에는 게임 데이터 조회 이전 단계이므로 다음 정보만 포함합니다.

```
Mission: day / content_id / mission_type / target_count
Reward: day / item_id / quantity
```

`game_data_version`과 `data_source`는 Balance & Rule이 실제 Primary 또는 Fallback Tool을 조회한 뒤 `RuleValidationResult`와 Trace에 기록합니다. 즉, 어떤 데이터 기준으로 검증했는지는 **검증 단계에서 확정**합니다.

# 10. Backend

Backend는 FastAPI를 사용하며 다음 기능을 담당합니다.

- 사용자 요청 수신
- Pydantic Input Schema Validation
- Input Guard 적용
- 승인 요청의 상태·담당자·result_version 검증
- 이벤트 생성 / 승인 / 수정 요청 멱등성 처리
- Fault Injection 서버 권한 확인
- Agent 실행
- Workflow State 관리
- Supervisor의 Python 규칙 기반 Routing / Retry 관리
- Handoff
- Output / Handoff / Tool Result Validation
- Agent별 `context_access` 적용
- Tool Guard 적용
- MCP Tool 호출
- Response Guard 적용
- 게임 데이터 조회
- DB 연결 및 재연결
- Trace 저장
- 승인 전 `current_result`와 승인 후 `final_result`를 구분해 반환
- Health Check

Guard와 Context 접근 정책은 `agents.yaml`, `security_policies.yaml` 설정을 기준으로 적용합니다.

## 10-1. 승인 안전성

Streamlit 로그인 상태만으로 Backend 승인 권한이 생긴 것으로 보지 않습니다.

승인 요청 시 Backend는 다음을 확인합니다.

```
workflow_status == WAITING_APPROVAL ?
approval_status == PENDING ?
actor_id가 승인 가능한 담당자인가 ?
요청 result_version == 현재 result_version ?
```

모두 통과해야 APPROVE / REQUEST_REVISION을 처리합니다.

이벤트가 수정되어 서버의 결과 버전이 증가했는데 사용자가 이전 화면의 결과를 보고 승인하면 `STALE_RESULT_VERSION`으로 거부합니다.

MVP에서는 실제 사내 SSO/JWT를 구현하지 않고, **외부 비공개 Backend + 서버 설정에 등록된 Demo 승인 담당자 검증**으로 범위를 제한합니다.

## 10-2. 멱등성

같은 요청이 반복되어도 실제 쓰기는 한 번만 수행하도록 합니다.

적용 대상:

- 이벤트 생성
- APPROVE
- REQUEST_REVISION

기준은 다음처럼 통일합니다.

```
이벤트 생성
→ Frontend가 idempotency_key 생성
→ Backend가 DB UNIQUE 기준으로 중복 확인

승인 / 수정 요청
→ Backend가 task_id + result_version + action으로
  server_idempotency_key 생성
→ DB UNIQUE 기준으로 중복 확인
```

같은 Key가 다시 들어오면 새로운 Workflow·최종 확정·수정 요청을 만들지 않고 기존 처리 결과를 반환합니다. 클라이언트가 임의의 승인용 Key를 만들어 중복 기준을 바꾸지 못하도록 승인 계열 Key는 Backend가 생성합니다.

## 10-3. Test Mode 내부 API 경로

Normal Mode와 Test Mode의 Backend 진입 경로를 분리합니다.

```
Normal Mode
Streamlit
→ POST /api/events/generate

Test Mode
Streamlit
→ POST /api/test/events/generate
→ Backend가 ENABLE_FAULT_INJECTION == true 확인
→ 허용된 fault_type만 적용
```

`/api/test/events/generate`는 Docker 내부 Network에서 Streamlit만 호출하는 개발·QA·발표용 내부 경로이며 외부에 직접 공개하지 않습니다. 운영 환경에서는 `ENABLE_FAULT_INJECTION=false`이므로 실행되지 않습니다.

## 10-4. API 실행 방식

이번 MVP는 Queue / Worker를 사용하지 않고 **동기식 Workflow 실행**으로 구현합니다.

```
POST /api/events/generate
↓
Event Planner
↓
Balance & Rule
↓
Critic
↓
WAITING_APPROVAL 또는 FAILED 도달
↓
API Response
```

`REQUEST_REVISION`도 같은 요청 안에서 Planner → Balance & Rule → Critic 재검증까지 실행한 뒤 새 `WAITING_APPROVAL` 또는 `FAILED` 상태를 반환합니다.

`GET /api/tasks/{task_id}`는 화면 재조회, 새로고침, 재시작 후 상태 확인 용도로 사용합니다. 실행 중 작업의 백그라운드 Queue 재개는 MVP 범위에 포함하지 않습니다.

## 10-5. 입력 신뢰 경계

다음 데이터는 모두 검증 전에는 신뢰하지 않습니다.

- 사용자 이벤트 입력
- approval_comment
- MCP Tool 결과
- Test Mode 요청

Pydantic Schema와 Guard를 함께 사용하고, LLM에 전달하기 전에 필요한 형식·범위·길이를 확인합니다.

# 11. 배포 구조

```

Streamlit Frontend만 외부 접근

↓
Docker Compose 내부 Network
```

## 11-2. Health Check

Health Check는 생존 여부와 요청 처리 준비 상태를 구분합니다.

```

→ FastAPI 프로세스가 살아 있는지 확인

GET /health/ready
→ PostgreSQL과 MCP Server가 실제 요청 처리 가능한지 확인
```

이번 MVP에는 Queue / Worker를 추가하지 않으므로 Ready Check 대상은 **DB와 MCP**로 한정합니다.

```
frontend/** 변경
↓
.github/workflows/frontend-ci-cd.yml
↓
Frontend Build / Smoke Check
↓
frontend/Dockerfile
↓
Frontend Image Build & Push
↓
EC2에서 Frontend Service 갱신

backend/** 변경
↓
.github/workflows/backend-ci-cd.yml
↓
Backend Pytest / Workflow / Validation / Guard Test

backend/Dockerfile
```

```
해당 Service Test FAIL
↓
해당 CI/CD Pipeline 중단
↓
해당 Docker Image Push / AWS Deploy 실행 안 함
↓

```

```
↓
SSH → AWS EC2
↓

↓

전체 서비스 상태 확인
↓
GET /health/live
↓
GET /health/ready
├ PASS → 배포 성공
└ FAIL
   ↓
   해당 서비스의 이전 정상 이미지 태그로 수동 Rollback
   ↓

```

# 13. 장애 주입 테스트

정상 동작뿐 아니라 의도적으로 오류를 발생시켜 AutoHealing이 실제로 동작하는지 확인합니다.

## 핵심 시나리오

| 구분 | 대표 시험 | 기대 결과 |
| --- | --- | --- |
| 정상 | 정상 이벤트 생성 | Critic PASS → workflow_status = WAITING_APPROVAL / approval_status = PENDING |
| 기획 오류 | 달성 불가능 미션 | 오류 감지 → Planner 수정 → 재검증 → PASS |
| Agent 실패 | Agent 응답 없음 / Exception | 동일 Agent Retry → 한도 초과 시 FAIL |
| Primary Tool 실패 | get_game_rules Exception / 잘못된 응답 | mcp_tool_error 감지 → get_game_rules_fallback 호출 → Validation PASS 시 Workflow 계속 |
| Primary + Fallback 모두 실패 | get_game_rules와 get_game_rules_fallback 모두 실패 | 검증되지 않은 데이터 사용 금지 → Safe Stop → workflow_status = FAILED → Trace 보존 |
| API / Tool Timeout | LLM 또는 MCP Timeout | Timeout 감지 → Retry → 성공 시 Workflow 계속 |
| 실제 MCP 중단 | MCP Server 컨테이너 중단 | 연결 실패 → 정해진 Retry 실패 → Safe Stop / FAILED → 운영자 MCP 재시작 → /health/ready 확인 → 새 요청·새 task_id로 정상 Workflow 재실행 |
| DB 오류 | 일시적 ConnectionError | 재연결 → 성공 시 Workflow 계속 |
| Validation | 필수 Output 누락 | 다음 단계 전달 차단 → 생성 Agent 재호출 |
| 오래된 승인 | 이전 result_version 화면에서 APPROVE | Backend가 버전 불일치를 감지해 승인 거부 |
| 중복 요청 | 동일 승인 또는 수정 요청 반복 전송 | 멱등성 키 확인 → 새 쓰기 없이 기존 결과 반환 |

### 이벤트 기획 품질 Evaluation Set

장애 복구 테스트와 별도로, AI가 요청 조건을 지키는지 확인하는 최소 품질 테스트 5건을 둡니다.

| ID | 입력 / 조건 | 기대 결과 |
| --- | --- | --- |
| EV-01 | 신규 유저 / 7일 / 초기 적응 | new_user·7일 유지, 목적 방향과 일치 |
| EV-02 | 복귀 유저 / 5일 | returning_user·5일 유지 |
| EV-03 | 신규 유저 Day 7 레이드 | mission_unreachable 감지 |
| EV-04 | 존재하지 않는 보상 아이템 | item_not_found 감지 |
| EV-05 | 전체 유저 대상 | all_user 접근 정책 적용 |

Guard의 세부 테스트(Input / Tool / Response Guard)와 실제 TC 번호는 하위 **개발 기획안**에서 관리합니다.

### 장애를 일부러 만드는 방식

```
달성 불가능 미션
→ fault_type = mission_unreachable_once
→ 첫 Planner 결과에만 Day 7 레이드 미션을 강제로 넣음
→ Planner 재실행부터는 다시 주입하지 않음

Agent 실패
→ 첫 실행에서 의도적으로 Exception 발생

Primary Tool 오류
→ get_game_rules 호출에서 의도적으로 Exception 또는 잘못된 결과 발생
→ get_game_rules_fallback으로 전환

MCP Timeout
→ 첫 Tool 호출에서 Timeout 발생

DB 오류
→ 첫 DB 접근에서 ConnectionError 발생

Validation 오류
→ 첫 Agent 결과에서 필수 필드를 의도적으로 누락

Retry 한도 초과
→ 지정 Agent가 계속 실패하도록 설정
```

이 기능은 **Test Mode에서만 사용**하고 정상 운영 흐름에서는 비활성화합니다.

### DB 장애 주입 원칙

완전히 중단된 DB가 스스로 복구되는 상황이 아니라, **첫 번째 접근에서 일시적인 ConnectionError를 발생시키고 다음 재연결에서 정상화되는 상황**을 시험합니다.

### 상태 보존 재시작 시험

PostgreSQL은 Docker named volume을 사용합니다. 최소 1회 다음 상태 보존 시험을 수행합니다.

```
Critic PASS
↓
workflow_status = WAITING_APPROVAL
↓
상태 / Trace DB 저장
↓
서비스 컨테이너 재시작
↓
동일 task_id 조회
↓
WAITING_APPROVAL 및 기존 Trace 유지 확인
```

승인 대기 상태와 실패 이력이 재시작 후에도 사라지지 않는지 확인합니다.

# 15. 평가 지표

## 15-1. 개발 전 평가 기준

구현 후 결과를 보고 평가 기준을 정하는 것이 아니라, **개발 전에 Expected Result를 먼저 정의하고 동일한 Evaluation Set으로 Actual Result를 비교**합니다.

| 평가 영역 | 평가 내용 | MVP 성공 기준 |
| --- | --- | --- |
| 요청 조건 준수 | 사용자가 입력한 대상·기간·목적을 유지하는가 | `target_user`, `duration` 유지 + `objective` 방향 유지 |
| 게임 규칙 검증 | 수행 불가능 미션·없는 아이템을 정확히 탐지하는가 | 사전에 정한 Rule Test의 Expected Result와 실제 결과 일치 |
| AutoHealing | 오류 종류에 맞는 위치에서 올바르게 복구하는가 | Planner 수정 / Agent Retry / Tool Retry / Fallback이 정의된 경로대로 실행 |
| 안전 종료 | 복구 불가능한 오류가 잘못된 결과로 통과되지 않는가 | Retry 한도 초과 시 `FAILED`, `final_result` 미확정 |

```
개발 전 Expected Result 정의
↓
구현
↓
Evaluation Set 실행
↓
Actual Result 수집
↓
Expected vs Actual 비교
```

# 18. 프로젝트 핵심 요약

이번 프로젝트의 핵심은 게임을 개발하는 것이 아닙니다.

**게임 이벤트를 만드는 과정에서 여러 Agent가 역할을 나누어 협업하고, 검증 오류나 실행 장애가 발생했을 때 Supervisor가 오류 유형과 상태를 기준으로 적절한 복구 경로를 선택해 다시 정상 흐름으로 복귀시키는 것**이 핵심입니다.

### 한 문장 요약

> **AI가 게임 이벤트를 기획하고 전문 Agent들이 검수하며, 오류나 일시적 장애가 발생하면 Supervisor가 Retry·재호출·재연결을 수행해 자동 복구하는 멀티에이전트 AutoHealing 시스템입니다.**
> 

### 과제 산출물과 연결

- **멀티 에이전트 아키텍처 설계서**: 1~7장 중심
- **배포 및 장애 복구 보고서**: 7장, 11장, 13~15장 중심
- **파이프라인 구현 결과 보고서**: 12장 중심
